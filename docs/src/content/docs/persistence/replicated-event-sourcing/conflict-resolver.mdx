---
title: Conflict resolver
description: The strategy that reconciles two concurrent events into one — pairwise, commutative, deterministic. The most app-specific piece of replicated event sourcing. Ships with last-writer-wins and a custom-merge wrapper.
---

When two replicas of the same entity write events concurrently
(detected via
[vector clocks](/persistence/replicated-event-sourcing/vector-clocks/)),
the framework needs to know **what the concurrent events mean
together**.  By default it applies all of them; a **conflict
resolver** — a strategy you supply by overriding `resolver()` on
the actor — picks one or merges them instead.

```ts
import { ReplicatedEventSourcedActor, LastWriterWinsResolver } from 'actor-ts/persistence';
import type { ConflictResolver } from 'actor-ts/persistence';

class Counter extends ReplicatedEventSourcedActor<Command, Event, State> {
  // The default is null — no resolver; override to reconcile concurrent events:
  protected override resolver(): ConflictResolver<Event> {
    return new LastWriterWinsResolver<Event>();
  }
  // ...
}
```

## The default: no resolver

`resolver()` returns `null` unless you override it, and then
nothing is reconciled: every event, concurrent or not, goes through
`onEvent` in the canonical order — `(timestamp, replica,
seqAtReplica)`, the same list on every replica.  For an event that
*replaces* a value that already behaves like last-writer-wins (the
concurrent event stamped later is applied last); for an event that
*adds*, both sides apply.  Override `resolver()` when neither is what
your domain means.

## Which events reach the resolver

The canonical order still decides where every event sits.  The
resolver decides what a run of concurrent events in that order
means.  Walking the history in canonical order, an event joins the
current **conflict group** when it is concurrent with every event
already in it, and opens a new group otherwise.  A group of one is
folded as it is; a larger group is reduced pairwise through
`resolve`, left to right in canonical order, and the one event that
comes out is folded through `onEvent`.  An event that *happens
after* another is never handed to the resolver with it.

The groups depend on the set of events alone, so two replicas that
hold the same events fold the same state, whatever order the events
arrived in.

## The interface

The resolver reconciles a **concurrent pair** — it returns one
event (a winner, or a synthesised merge of the two):

```ts
interface ConflictResolver<E> {
  resolve(a: ConflictCandidate<E>, b: ConflictCandidate<E>): E;
}

type ConflictCandidate<E> = {
  event:     E;             // the user-domain event payload
  timestamp: number;        // wall-clock at the originating replica
  replica:   ReplicaId;     // originating replica id
  vc:        VectorClock;   // vector clock at persist time
};
```

Note the **single type parameter** (the event, *not* the state).
When a group holds more than two events, the framework folds them
pairwise through `resolve`, so the whole group reduces to one event
— which is then applied through your normal `onEvent`.  A returned
input carries its own `timestamp`, `replica` and `vc` into the next
step; a synthesised event carries the later candidate's `timestamp`
and `replica` and the merge of both clocks.

## Two hard contracts

`resolve` must be:

- **Deterministic** — the same `(a, b)` pair yields the same
  result on every replica; no `Date.now()`, no `Math.random()`,
  no external reads.
- **Commutative** — `resolve(a, b)` must equal `resolve(b, a)`.
  Events arrive in different orders on different replicas, so a
  non-commutative resolver makes replicas diverge.

Decide the winner from the candidates' own data (`timestamp`,
`replica`, payload) — never from arrival order or "prefer `a`."

## Built-in resolvers

### `LastWriterWinsResolver`

```ts
protected override resolver(): ConflictResolver<Event> {
  return new LastWriterWinsResolver<Event>();
}
```

Higher `timestamp` wins; on a tie the higher (lexicographic)
`replica` id wins, and a tie on both — one replica stamping two
events in one millisecond — goes to the event whose typed canonical
key (`canonicalOrderKey` from `actor-ts/util`, the same order
`LWWRegister` uses) ranks higher, so the winner never depends on argument order and
every replica converges.  Simple and often
"good enough."  Caveat: relies on roughly comparable wall clocks
across replicas — the same trade-off as `LWWRegister`.  Unlike the
default, it **drops** the losing event of a concurrent pair, so use
it for state that is replaced, not accumulated.

### `CustomMergeResolver`

Wrap a commutative merge of the two event payloads — use it when
you have domain knowledge LWW doesn't capture (e.g. two
concurrent deposits simply add):

```ts
import { CustomMergeResolver } from 'actor-ts/persistence';

protected override resolver(): ConflictResolver<Event> {
  return new CustomMergeResolver<Event>((a, b) => ({
    kind:   'deposited',
    amount: a.amount + b.amount,   // additive merge
  }));
}
```

`CustomMergeResolver` sorts the two candidates by replica id
before calling your merge, so it receives a deterministic
argument order even if your function isn't perfectly symmetric —
but the contract still says **be commutative**.

## Custom strategies

For anything else, implement `ConflictResolver<Event>` directly.
`resolve` returns a single event; the actor applies it via
`onEvent`.

### Pick a winner (max / min)

```ts
class HighestWins implements ConflictResolver<Event> {
  resolve(a: ConflictCandidate<Event>, b: ConflictCandidate<Event>): Event {
    if (a.event.value !== b.event.value) {
      return a.event.value > b.event.value ? a.event : b.event;
    }
    return a.replica > b.replica ? a.event : b.event;   // deterministic tie-break
  }
}
```

Right for values that must not regress: stock levels, high
scores.  Break exact ties on `replica` so the result is the same
on every replica.

### Deterministic order by (timestamp, replica)

```ts
class OrderedWins implements ConflictResolver<Event> {
  resolve(a: ConflictCandidate<Event>, b: ConflictCandidate<Event>): Event {
    if (a.timestamp !== b.timestamp) return a.timestamp > b.timestamp ? a.event : b.event;
    return a.replica > b.replica ? a.event : b.event;
  }
}
```

This is the order `LastWriterWinsResolver` uses — shown as the
template for your own tie-breaking.  It is commutative only while
two candidates never share both `timestamp` and `replica`; the
built-in breaks that last tie on the payload as well.

## When a merge is the wrong abstraction

Sometimes concurrent events **shouldn't merge** — they conflict
semantically (e.g. "close account" concurrent with "deposit").
For those, prefer **single-writer with a lease** — see
[Single-writer lease](/persistence/replicated-event-sourcing/single-writer-lease/) —
which forces sequential writes so no conflicts arise.

Use replicated ES when concurrent events **merge naturally**; use
the lease when they shouldn't happen at all.

## Performance

`resolve` runs only on **concurrent-write detection** — bounded
by the rate of cross-replica events, typically rare.  Even a
heavier merge is cheap next to the journal I/O.

import { Aside } from '@astrojs/starlight/components';

<Aside type="caution" title="Resolvers must be commutative">
  ```ts
  resolve(a, b) { return a.event; }   // ✗ "prefer whichever arrived as a"
  ```
  `a` and `b` arrive in different orders on different replicas.
  Decide from the candidates' own data so `resolve(a, b) === resolve(b, a)`.
</Aside>

<Aside type="caution" title="Non-deterministic resolvers don't converge">
  ```ts
  resolve(a, b) { return Math.random() < 0.5 ? a.event : b.event; }   // ✗
  ```
  Every replica picks differently; the cluster never agrees.
  Always pure + deterministic.
</Aside>

<Aside type="caution" title="Return an event, not a state">
  ```ts
  resolve(a, b) { return { value: 42 }; }   // ✗ must be an Event
  ```
  `resolve` returns one of the two events (or a synthesised event
  of the same type).  The actor folds it into state through your
  existing `onEvent`.
</Aside>
