title: Cached snapshot store
description: A decorator that wraps any `SnapshotStore` with a TTL-based read-through cache backed by any `Cache` (in-memory, Redis, or Memcached). Useful when the underlying store is slow (network-mounted, encrypted) and snapshot loads happen frequently (high actor churn).
---

`CachedSnapshotStore` is a **decorator** — wrap any
`SnapshotStore` to add a TTL-based read-through cache for
`loadLatest`, backed by any `Cache` (in-memory, Redis, or
Memcached).

```ts
import {
  ActorSystem,
  ActorSystemOptions,
} from 'actor-ts';
import {
  CachedSnapshotStore,
  CachedSnapshotStoreOptions,
  ObjectStorageSnapshotStore,
  ObjectStorageSnapshotStoreOptions,
} from 'actor-ts/persistence';

const objectStorageSnapshotStoreOptions = ObjectStorageSnapshotStoreOptions.create().withBackend(backend);
const underlying = new ObjectStorageSnapshotStore(
  objectStorageSnapshotStoreOptions, // S3 / filesystem backend
);

const cachedSnapshotStoreOptions = CachedSnapshotStoreOptions.create()
  .withCache(cache)          // backing cache (typically Redis)
  .withTtlMs(60_000);
const cached = new CachedSnapshotStore(
  underlying,
  cachedSnapshotStoreOptions,        // optional TTL
);

const actorSystemOptions = ActorSystemOptions.create().withPersistence({
  journal:       myJournal,
  snapshotStore: cached,
});
const system = ActorSystem.create('app', actorSystemOptions);
```

## When you need it

Three patterns:

1. **Slow underlying store** — object storage with multi-hop
   network latency, encrypted state with expensive decryption.
   For the encrypted case read
   [Security — the cache holds plaintext](#security--the-cache-holds-plaintext)
   first: it is the strongest reason to reach for the cache and the
   one that needs a decision.
2. **Frequent actor churn** — sharded entities passivating /
   re-spawning constantly, each load re-reading the same
   snapshot.
3. **Recovery storms** — full-cluster restart, every actor loads
   its snapshot at once.  Cache reduces redundant loads when
   the same snapshot is queried during the storm.

For local SQLite-backed snapshots (sub-millisecond reads), the
cache adds overhead with no benefit.  **Use it only when the
underlying store has measurable read latency.**

## Configuration

```ts
type CachedSnapshotStoreOptionsType = {
  cache:                 Cache;    // backing cache (required)
  ttlMs?:                number;   // cache TTL in ms, default 5 minutes
  keyPrefix?:            string;   // key prefix, default 'snap:'
  allowPlaintextCache?:  boolean;  // cache encrypted state anyway, default false
};
```

| Field | What |
| --- | --- |
| `cache` | Backing cache (**required**) — typically Redis in production.  Any `Cache`: in-memory, Redis, or Memcached. |
| `ttlMs` | Cache TTL in milliseconds.  Default: 5 minutes. |
| `keyPrefix` | Key prefix (default `'snap:'`) — prevents collisions in shared caches. |
| `allowPlaintextCache` | Acknowledge that the cache may hold the plaintext of state the wrapped store encrypts at rest, and cache it anyway.  Default `false` — see below. |

The underlying store is the constructor's **first argument** —
`new CachedSnapshotStore(underlying, options)` — not an option.

## Security — the cache holds plaintext

What gets cached is whatever `loadLatest` returns, and that is the
**decoded** domain state: decompressed, and for the object-storage
stores decrypted.  Compose this decorator with
[client-side snapshot encryption](/persistence/object-storage/encryption/)
and the deployment holds two copies of the state — one encrypted in
the bucket, one in plaintext in a cache you own, share with other
subsystems, and often run unauthenticated on a "private" network.
Reading the second copy needs neither the bucket nor the master key,
and a Redis RDB dump keeps it readable afterwards.

Nothing at rest in the bucket is weakened by this; the second copy
is the whole exposure.  That makes it a composition hazard rather
than a flaw in either piece — and the composition is one this page
recommends, which is why it is spelled out here.

So a `loadLatest` that carries `encryption` with a mode other than
`'none'` is **served straight from the wrapped store, uncached**,
and the decorator warns once:

```text
persistence: CachedSnapshotStore caches decoded snapshot state, and this
loadLatest on 'ObjectStorageSnapshotStore' asked for encryption — …
```

`withAllowPlaintextCache(true)` is your acknowledgement that the
cache is as protected as the bucket, and restores the caching:

```ts
const cachedSnapshotStoreOptions = CachedSnapshotStoreOptions.create()
  .withCache(cache)
  .withTtlMs(60_000)
  .withAllowPlaintextCache(true);
```

Reasonable answers to the question it asks:

- **In-process `InMemoryCache`** — the plaintext never leaves the
  node that already decrypted it.  Set the flag.
- **Redis or Memcached inside the same trust boundary**, with
  authentication, encryption in transit and no persistence to
  disk — set the flag, and record the reasoning where your other
  key-management decisions live.
- **A shared cache that also backs HTTP middleware**, or one whose
  operators are not the operators of the bucket — do not set the
  flag.  Give the encrypted store its own cache, or accept the
  cold-start cost.

The check sees the **per-call** `PersistenceOptions` your actor's
`encryption()` hook produces, which is what reaches every read.  It
cannot see a store configured with encryption at construction and
never told about it per call: `SnapshotStore` has no member that
reports that, and `persistenceOptionSupport` answers a different
question ("could this store encrypt?", not "is it going to?").  If
your encryption lives entirely in the store's own configuration,
this decorator has nothing to warn about and the decision is yours
alone.

## Cache semantics

- **`loadLatest(persistenceId)`** — read-through with TTL.  Check cache; on
  hit, return.  On miss, load from underlying, cache the result with `ttlMs`,
  return.
- **`save(persistenceId, seq, state)`** — write-through-with-invalidate:
  delegate to the underlying store, then **delete** the cache entry.  It
  deliberately does *not* write the new snapshot back — in a cluster two
  nodes may race on save, and a local write would leave a stale entry.  The
  next read repopulates.
- **`loadBefore(persistenceId, seq)`** — **not cached** (too many possible
  `seq` values, and it's used rarely — only during recovery).
- **`delete(persistenceId, toSeq)`** — delegate to the underlying store, then
  invalidate the cache entry.

After a `save`, the cache entry is invalidated, so the next
`loadLatest` re-fetches from the underlying store and returns the
just-saved snapshot.  TTL is the safety net: even if a node crashes
between the underlying write and the cache invalidation, the stale
entry expires within `ttlMs`.

## Performance

For a slow underlying store (say, 50 ms per load), the cache
turns subsequent loads of the same snapshot into sub-microsecond
operations.  A typical sharded-entity workload sees 80-95 % hit
rate after warm-up.

The cache can be **shared across nodes** — back it with Redis or
Memcached and every node reads from the same cache, so a snapshot
loaded on one node is a hit on all the others.  Back it with an
in-memory cache instead and each node keeps its own copy; misses
on a fresh node pay the full underlying-load cost.

## Pitfalls

import { Aside } from '@astrojs/starlight/components';

<Aside type="caution" title="External modifications">
  ```ts
  // Underlying store modified outside the cache (manual
  // SQL update, batch backfill) → cache returns stale data
  ```
  The cache assumes **it's the only writer**.  If something
  else writes to the underlying store, set a TTL or invalidate
  manually.
</Aside>
