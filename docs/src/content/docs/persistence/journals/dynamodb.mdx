---
title: DynamoDB
description: Event journal, snapshot store and durable-state store backed by Amazon DynamoDB. Conditional writes give it the strongest optimistic concurrency of any backend — a multi-event append is atomic, so a losing writer can never leave a partial one behind.
---

The DynamoDB backend provides all three persistence components against Amazon
DynamoDB, via [`@aws-sdk/client-dynamodb`](https://www.npmjs.com/package/@aws-sdk/client-dynamodb):

- **`DynamoDbJournal`** — the event journal for `PersistentActor`s.
- **`DynamoDbSnapshotStore`** — snapshots to bound recovery.
- **`DynamoDbDurableStateStore`** — key-value durable state for
  `DurableStateActor`s.

It has the **strongest optimistic concurrency** of any backend the framework
ships — see [Concurrency model](#concurrency-model) — and it is fully serverless:
no instance to run, on-demand capacity by default.

## Install

`@aws-sdk/client-dynamodb` is an optional peer dependency:

```bash
bun add @aws-sdk/client-dynamodb
```

It is the same SDK family already used for the S3 object-storage backend, so if
you use that, the runtime story is one you already have. The framework
lazy-imports it only when a DynamoDB store is first used.

## Setup

Register the journal + snapshot store against the `PersistenceExtension` and
receive a ready-to-use durable-state store. Set the connection once on the
composite and all three components inherit it:

```ts
import {
  ActorSystem,
  ActorSystemOptions,
} from 'actor-ts';
import {
  DynamoDbDurableStateStoreOptions,
  DynamoDbJournalOptions,
  DynamoDbSnapshotStoreOptions,
  PersistenceExtensionId,
  RegisterDynamoDbPluginsOptions,
  registerDynamoDbPlugins,
} from 'actor-ts/persistence';

const systemOptions = ActorSystemOptions.create()
  // Select the DynamoDB plugins as the active journal + snapshot store.
  .withConfig({
    'actor-ts': {
      persistence: {
        journal: { plugin: 'actor-ts.persistence.journal.dynamodb' },
        'snapshot-store': { plugin: 'actor-ts.persistence.snapshot-store.dynamodb' },
      },
    },
  });
const system = ActorSystem.create('my-app', systemOptions);

const ext = system.extension(PersistenceExtensionId);
const dynamoDbSnapshotStoreOptions = DynamoDbSnapshotStoreOptions.create()
  .withKeepN(3);
const registerOptions = RegisterDynamoDbPluginsOptions.create()
  .withRegion('eu-central-1')
  .withJournal(DynamoDbJournalOptions.create() /* .withEventsTable(...) */)
  .withSnapshotStore(dynamoDbSnapshotStoreOptions)
  .withDurableStateStore(DynamoDbDurableStateStoreOptions.create() /* .withTable(...) */);
const { durableStateStore } = registerDynamoDbPlugins(ext, registerOptions);
```

Credentials come from the standard AWS provider chain (environment, shared
config, IAM role), so nothing about them is actor-ts-specific. Pass
`withClientConfig({ credentials })` to override.

### Local development

`dynamodb-local` needs an endpoint override, and the SDK will not sign a request
without credentials even though the emulator ignores them:

```ts
const dynamoDbJournalOptions = DynamoDbJournalOptions.create()
  .withRegion('eu-central-1')
  .withEndpoint('http://localhost:8000')
  .withClientConfig({ credentials: { accessKeyId: 'local', secretAccessKey: 'local' } });
```

## Configure it from HOCON

The plugin id **is** the config section, so the block named after the id is the
block that plugin reads (#872).  The whole reachability half — region, endpoint
and the table names — can come from `application.conf`, which means
`registerDynamoDbPlugins(ext)` needs no options at all:

```ts
import { PersistenceExtensionId, registerDynamoDbPlugins } from 'actor-ts/persistence';

const persistence = system.extension(PersistenceExtensionId);
registerDynamoDbPlugins(persistence);
```

```hocon
actor-ts.persistence {
  journal        { plugin = "actor-ts.persistence.journal.dynamodb" }
  snapshot-store { plugin = "actor-ts.persistence.snapshot-store.dynamodb" }
  durable-state  { plugin = "actor-ts.persistence.durable-state.dynamodb" }

  journal.dynamodb        { region = "eu-central-1", events-table = "actor_ts_events" }
  snapshot-store.dynamodb { region = "eu-central-1", keep-n = 5 }
  durable-state.dynamodb  { region = "eu-central-1", table = "actor_ts_durable_state" }
}
```

`endpoint` is the leaf you set for `dynamodb-local` or LocalStack; left empty it
means the real service.  **Credentials have no leaf at all** — omitted, the SDK's
own default chain supplies them (`AWS_ACCESS_KEY_ID` / `AWS_SECRET_ACCESS_KEY`,
an instance profile, or IAM Roles for Service Accounts), which is the same
treatment the object-storage plugin's S3 backend gets.  Neither does
`clientConfig` — the SDK's whole option surface, which stays code-only — nor a
pre-built `operations` façade or a `serializer`, which are live objects.

What you do tune on the client has **typed leaves** (#1490), each a comment in
the reference configuration so that leaving it out keeps the SDK's own
resolution — `AWS_MAX_ATTEMPTS` or `AWS_RETRY_MODE`, then the shared config
file, then the SDK's default — rather than overruling it:

```hocon
actor-ts.persistence.journal.dynamodb {
  region             = "eu-central-1"
  max-attempts       = 5          # attempts per request, the first included (SDK default 3)
  retry-mode         = adaptive   # standard (the SDK default) or adaptive
  request-timeout    = 10s        # one attempt's limit, after which it fails (default: none)
  connection-timeout = 2s         # opening the connection (default: none)
}
```

Each reaches the SDK only when set.  `retry-mode` takes `standard` or
`adaptive` — the SDK's own words, kebab-case already — and anything else is
refused at startup with the key and the two values, because the SDK would read
any other word as `standard` and say nothing.  The two timeouts become the
request handler's `requestTimeout` and `connectionTimeout`, and
`request-timeout` sets `throwOnRequestTimeout` beside it: without that, the
handler only logs a warning when a request outlives its timeout, so the leaf
would time nothing out.  It bounds one attempt, and the retry strategy may try
again, so one call can take up to `max-attempts` of them plus the backoff in
between.  A handler built from these leaves replaces the SDK's default one, so a
connection timeout that `AWS_DEFAULTS_MODE` would supply no longer applies; set
`connection-timeout` beside `request-timeout` if you rely on one.

The store checks them when it is built: an attempt count or timeout that is not
a positive whole number, or a timeout longer than a timer can hold, is refused
with an `OptionsError`.  So is a leaf beside what it replaces in `clientConfig`
— `maxAttempts` or `retryMode`, a `retryStrategy` that makes both moot, or a
`requestHandler` — naming both, rather than one of them quietly winning.

Table **provisioning** — how a table the store creates on first use is created
— has leaves too (#1490), under all three blocks: `billing-mode`
(`"pay-per-request"`), `table-ready-timeout` (`30s`) and `auto-create-tables`
(`on`).  The billing mode's values are kebab-case, like every HOCON value, and
the reader maps them to AWS's spelling: `pay-per-request` is `PAY_PER_REQUEST`
and `provisioned` is `PROVISIONED`.  `PAY_PER_REQUEST` written in a config file
is refused at startup with the key and the two values it takes.

The capacity pair ships as a **comment**, because published it would be refused
for every store under the default `pay-per-request` — AWS ignores capacity
there, and the validator says so rather than letting a typo pass unseen.
**A `provisioned` table with no pair is created at 5 read and 5 write capacity
units** (`DEFAULT_DYNAMODB_PROVISIONED_CAPACITY_UNITS`), from a config file as
from code, so name the pair when you provision on purpose:

```hocon
actor-ts.persistence.journal.dynamodb {
  billing-mode = provisioned
  provisioned-throughput { read-capacity-units = 25, write-capacity-units = 10 }
}
```

Set one half without the other and the store refuses to start, naming the
missing half — a default does not quietly complete the pair.

**`durable-state.plugin` now selects this backend's durable-state store.**  It
used to be built eagerly and handed back from `registerDynamoDbPlugins`, so it
could only be wired by threading that instance through application code.  The
returned handle still works and still yields the same instance — it is simply
built on first use rather than at registration.

## When to use it

- **You are on AWS and want no database to operate.** No instance, no
  connection pool, no patching.
- **You want the strongest append guarantee available.** The transactional
  append is atomic, which not even the relational backends manage for a
  multi-event batch under contention.
- **Your write pattern is spiky.** On-demand billing needs no capacity planning.

## Configuration

```ts
type DynamoDbConnection = {
  region?:              string;                    // eu-central-1, …
  endpoint?:            string;                    // http(s) URL — dynamodb-local, LocalStack
  clientConfig?:        Record<string, unknown>;   // { credentials, … } — the code-only long tail
  operations?:          DynamoDbOperations;        // pre-built / shared façade
  maxAttempts?:         number;                    // attempts per request, SDK default 3  (max-attempts)
  retryMode?:           'standard' | 'adaptive';   // SDK default 'standard'               (retry-mode)
  requestTimeoutMs?:    number;                    // requestTimeout, fails the attempt    (request-timeout)
  connectionTimeoutMs?: number;                    // connectionTimeout                    (connection-timeout)
};

type DynamoDbTableProvisioning = {
  autoCreateTables?:      boolean;   // default true
  billingMode?:           'PAY_PER_REQUEST' | 'PROVISIONED';   // default on-demand
  provisionedThroughput?: { readCapacityUnits: number; writeCapacityUnits: number };
  tableReadyTimeoutMs?:   number;    // default 30_000
};

interface DynamoDbJournalOptions extends DynamoDbConnection, DynamoDbTableProvisioning {
  eventsTable?: string;   // default 'actor_ts_events'
}
interface DynamoDbSnapshotStoreOptions extends DynamoDbConnection, DynamoDbTableProvisioning {
  snapshotsTable?: string;   // default 'actor_ts_snapshots'
  keepN?:          number;   // keep newest N per pid; default 3, <=0 keeps all
}
interface DynamoDbDurableStateStoreOptions extends DynamoDbConnection, DynamoDbTableProvisioning {
  table?: string;   // default 'actor_ts_durable_state'
}
```

Options are validated when the store is constructed. Two rules earn their
keep: a table name is checked against DynamoDB's own charset and length, and
capacity units are rejected unless `billingMode` is `PROVISIONED` — AWS silently
ignores them otherwise, which makes the mistake invisible.  The opposite gap is
allowed and silent: `PROVISIONED` with no `provisionedThroughput` creates every
table at 5 read and 5 write capacity units.

## Tables

| Table | Partition key | Sort key | Holds |
| --- | --- | --- | --- |
| `actor_ts_events` | `pid` | `seq` (N) | one item per event; `seq = 0` is the compaction mark |
| `actor_ts_snapshots` | `pid` | `seq` (N) | one item per snapshot |
| `actor_ts_durable_state` | `pid` | — | one item per persistence id |

With `autoCreateTables` (the default) each store creates its table on first use
and **waits for it to become `ACTIVE`** — `CreateTable` returns while the table
is still `CREATING`, and every operation against it fails until it flips. The
wait happens inside the lazy init, so the first caller blocks and everyone behind
it gets a table that works.

## Concurrency model

- **Journal append is one atomic transaction.** Every event goes into a single
  `TransactWriteItems`, each `Put` carrying
  `ConditionExpression: attribute_not_exists(pid)` — "only if this `(pid, seq)`
  item does not exist". A racing writer therefore cannot win a partial append:
  the transaction is all-or-nothing, and its cancellation becomes
  `JournalConcurrencyError`. The head read that precedes it is only an
  optimization *for the write's safety*, turning the common stale append into one
  cheap query instead of a rejected transaction — but the **value** it returns is
  load-bearing, which is why it is a strong read (next bullet).
- **Every read that recovery or a sequence-number decision depends on is a strong
  read.** DynamoDB serves eventually-consistent reads unless a request says
  `ConsistentRead: true`, and the journal sets it on the head read, on the replay
  query and on the doomed-key query behind `delete`; the snapshot store sets it on
  `loadLatest` and `loadBefore`. A stale read here is not "slightly old data": a
  head from a lagging replica makes an intact stream look *rewound*, and a stale
  replay page truncates history in a way nothing downstream can detect — the
  replay integrity checks catch a hole, a wrong order and an out-of-window event,
  but nothing states where the stream should end.
- **Durable-state CAS is a native conditional write** —
  `PutItem … attribute_not_exists(pid)` to create, `UpdateItem … revision = :expected`
  to update — needing neither a transaction nor a read-back.
- **The compaction mark only rises.** It is updated with
  `attribute_not_exists(deletedTo) OR deletedTo < :value`, which is `GREATEST`
  expressed as a condition; a lower value is rejected, and that rejection is the
  expected outcome rather than an error.

<Aside type="note" title="Why this is the strongest of the backends">
  The relational backends and MongoDB both read the head and then write, relying
  on a primary key to reject a racing writer — which works, but a mid-batch
  failure can still leave part of an append behind (MongoDB documents exactly
  that caveat). DynamoDB's transactional put removes the possibility: the
  batch either lands whole or not at all.
</Aside>

## Pitfalls

<Aside type="caution" title="Strong reads cost double, and not only on recovery">
  A `ConsistentRead` consumes twice the read capacity of an eventually-consistent
  one, and this is **not** a per-recovery cost: `read` and `highestSeq` are also
  what the query layer's catch-up path, `currentEventsByTag`, remember-entities and
  projection tooling call, so those pay it too. It is the right default — a
  projection that silently misses the newest events is its own defect, and a stale
  head is reported to you as a second writer rather than as lag — but budget for
  it. If you need the cheaper posture, `persistenceIds` is already the one read
  left eventually consistent (an id surfacing one poll later costs nothing), and
  snapshot pruning likewise, because a stale read there can only under-delete.
  There is no per-store consistency option; Cassandra's `withConsistency` has no
  DynamoDB equivalent yet.
</Aside>

<Aside type="caution" title="An append is capped at 100 events">
  DynamoDB allows at most 100 items in one `TransactWriteItems`. An append of
  more than that is **refused** with a clear error rather than split into
  chunks — chunking would break the atomicity the concurrency model rests on.
  Persist in smaller batches; a single-event append is the common case anyway.
</Aside>

<Aside type="caution" title="persistenceIds is a full table scan">
  DynamoDB can only enumerate partition keys by scanning, so this call reads the
  whole events table and costs accordingly. The framework never uses it on a
  hot path — it is for projection tooling — but do not call it per request.
</Aside>

<Aside type="caution" title="No indexed tag query yet">
  `currentEventsByTag` falls back to the journal-walking scan, exactly as it does
  on Postgres and MariaDB. An indexed path needs a second table keyed by tag (or
  a slice-based model), which is design work of its own rather than a
  configuration flag. If you rely on heavy tag queries, prefer MongoDB, SQLite /
  libSQL or Cassandra.
</Aside>

<Aside type="caution" title="Reads page, and the 400 KB item limit is real">
  A `Query` returns at most 1 MB, so recovery pages through `LastEvaluatedKey` —
  handled for you. What is not handled: a single event whose JSON exceeds
  DynamoDB's 400 KB per-item limit is rejected by the service. Keep events
  small, which event sourcing wants anyway.
</Aside>

<Aside type="caution" title="Per-actor encryption and integrity do not protect events">
  Per-call `PersistenceOptions` apply only to the object-storage stores, as with
  every SQL backend, Cassandra and MongoDB.  The DynamoDB snapshot and
  durable-state stores declare that they honour none of the three hooks, so
  an `encryption()` or `integrity()` override against either of them
  **refuses the actor at start**, and `compression()` warns once
  ([#960](https://github.com/pathosDev/actor-ts/issues/960)).

  The journal is never asked.  `encryption()` and `integrity()` on a
  `PersistentActor` protect its snapshots only: every journal stores
  events as plaintext JSON, nothing detects an event edited in place, and
  database-side controls — transparent data encryption, an encrypted
  volume, access control — are the only protection for events today.  An
  actor that pairs this journal with the object-storage snapshot store
  starts cleanly and writes its events here in plaintext.
</Aside>
