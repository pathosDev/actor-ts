title: Microsoft SQL Server
description: Event journal, snapshot store, and durable-state store backed by Microsoft SQL Server via the `mssql` (tedious) driver — the enterprise relational backend. Pure-JavaScript driver, so it runs on Bun, Node and Deno alike.
---

The SQL Server backend provides all three persistence components against a
single SQL Server database, via the
[`mssql`](https://www.npmjs.com/package/mssql) driver (tedious under the
hood):

- **`MsSqlJournal`** — the event journal for `PersistentActor`s.
- **`MsSqlSnapshotStore`** — snapshots to bound recovery.
- **`MsSqlDurableStateStore`** — key-value durable state for
  `DurableStateActor`s.

Like Postgres, it is **shared across cluster nodes** — any node can read or
write any persistenceId — and `mssql`/tedious is **pure JavaScript**, so it
needs no native build step and runs on all three supported runtimes.

## Install

`mssql` is an optional peer dependency — install it alongside actor-ts:

```bash
bun add mssql
```

The framework lazy-imports it only when a SQL Server store is first used, so
it stays out of your bundle until you opt in.

## Setup

Register the journal + snapshot store against the `PersistenceExtension` and
receive a ready-to-use durable-state store.  Pass a shared `pool` so all
three components reuse one connection pool:

```ts
import sql from 'mssql';
import {
  ActorSystem,
  ActorSystemOptions,
} from 'actor-ts';
import {
  MsSqlDurableStateStoreOptions,
  MsSqlJournalOptions,
  MsSqlSnapshotStoreOptions,
  PersistenceExtensionId,
  RegisterMsSqlPluginsOptions,
  registerMsSqlPlugins,
} from 'actor-ts/persistence';

const systemOptions = ActorSystemOptions.create()
  // Select the SQL Server plugins as the active journal + snapshot store.
  .withConfig({
    'actor-ts': {
      persistence: {
        journal: { plugin: 'actor-ts.persistence.journal.mssql' },
        'snapshot-store': { plugin: 'actor-ts.persistence.snapshot-store.mssql' },
      },
    },
  });
const system = ActorSystem.create('my-app', systemOptions);

const ext = system.extension(PersistenceExtensionId);
const pool = await new sql.ConnectionPool({
  server: 'db.example.com',
  port: 1433,
  user: 'actor_ts',
  password: process.env.MSSQL_PASSWORD,
  database: 'app',
  options: { encrypt: true },
}).connect();

const msSqlSnapshotStoreOptions = MsSqlSnapshotStoreOptions.create()
  .withKeepN(3);
const registerOptions = RegisterMsSqlPluginsOptions.create()
  // One pool shared by journal + snapshot + durable-state (recommended).
  .withPool(pool)
  .withJournal(MsSqlJournalOptions.create() /* .withEventsTable(...).withTagsTable(...) */)
  .withSnapshotStore(msSqlSnapshotStoreOptions)
  .withDurableStateStore(MsSqlDurableStateStoreOptions.create() /* .withTable(...) */);
const { durableStateStore } = registerMsSqlPlugins(ext, registerOptions);
```

`registerMsSqlPlugins` registers the journal + snapshot store via the
extension (selected by the config plugin IDs above) and **returns** the
durable-state store.  `PersistenceExtension` has no durable-state registry —
hand `durableStateStore` to your `DurableStateActor` settings directly (same
pattern as the Postgres and object-storage plugins).

A shared pool is **caller-owned**: no store ends it, so close it yourself at
shutdown.  Without one, each component lazily builds its own from its
`poolConfig` / `url` and closes it on `close()`:

```ts
const poolConfig = {
  server: 'db.example.com', database: 'app',
  user: 'actor_ts', password: process.env.MSSQL_PASSWORD,
  options: { encrypt: true },
};
const msSqlJournalOptions = MsSqlJournalOptions.create()
  .withPoolConfig(poolConfig);
```

## When to use it

- **SQL Server is your system of record.** The enterprise default in a lot of
  stacks, and Akka.NET's primary backend — this is the closest analogue.
- **Cluster-shared persistence.** Sharded entities that move between nodes, or
  cross-node projections, need a journal every node can read.
- **You want a relational backend without a native driver.** tedious is pure
  JavaScript, unlike `better-sqlite3`.

For single-node development, [`SqliteJournal`](/persistence/journals/sqlite/)
is simpler (one file, no server).

## Configuration

```ts
type MsSqlConnection = {
  url?:        string;                    // Server=…;Database=… or mssql://user:pass@host:1433/db
  poolConfig?: Record<string, unknown>;   // mssql config object; takes precedence over url
  pool?:       MsSqlPoolLike;             // pre-built / shared pool
};

interface MsSqlJournalOptions extends MsSqlConnection {
  eventsTable?:      string;   // default 'events'
  tagsTable?:        string;   // default '<eventsTable>_tags'
  autoCreateTables?: boolean;  // default true
}
interface MsSqlSnapshotStoreOptions extends MsSqlConnection {
  snapshotsTable?:   string;   // default 'snapshots'
  keepN?:            number;   // keep newest N per pid; default 3, <=0 keeps all
  autoCreateTables?: boolean;
}
interface MsSqlDurableStateStoreOptions extends MsSqlConnection {
  table?:            string;   // default 'durable_state'
  autoCreateTables?: boolean;
}
```

Options are validated when the store is constructed.  Table names come from
config (not user input) and are checked against a safe-identifier pattern;
everything else — persistenceIds, tags, payloads — is passed as a **named bind
parameter** (`@p1`, `@p2`, …), never string-concatenated.

## Schema

With `autoCreateTables` (the default), the backend runs guarded `CREATE TABLE`
statements on first use.  T-SQL has no `CREATE TABLE IF NOT EXISTS`, so each is
wrapped in an `IF OBJECT_ID(…) IS NULL` check:

```sql
CREATE TABLE events (
  persistence_id NVARCHAR(255) COLLATE Latin1_General_100_BIN2 NOT NULL,
  sequence_nr    BIGINT NOT NULL,
  payload        NVARCHAR(MAX) NOT NULL,   -- JSON
  tags           NVARCHAR(MAX) NULL,       -- CSV (also mirrored into events_tags)
  timestamp      BIGINT NOT NULL,
  CONSTRAINT PK_events PRIMARY KEY (persistence_id, sequence_nr)
);
CREATE TABLE events_tags (                 -- indexed tag lookups for projections
  persistence_id NVARCHAR(255) COLLATE Latin1_General_100_BIN2 NOT NULL,
  sequence_nr    BIGINT NOT NULL,
  tag            NVARCHAR(255) COLLATE Latin1_General_100_BIN2 NOT NULL,
  timestamp      BIGINT NOT NULL,
  CONSTRAINT PK_events_tags PRIMARY KEY NONCLUSTERED
    (tag, timestamp, persistence_id, sequence_nr)
);
CREATE TABLE events_meta (                 -- compaction high-water mark
  persistence_id NVARCHAR(255) COLLATE Latin1_General_100_BIN2 NOT NULL,
  deleted_to     BIGINT NOT NULL,
  CONSTRAINT PK_events_meta PRIMARY KEY (persistence_id)
);
CREATE TABLE snapshots (
  persistence_id NVARCHAR(255) COLLATE Latin1_General_100_BIN2 NOT NULL,
  sequence_nr    BIGINT NOT NULL,
  payload        NVARCHAR(MAX) NOT NULL,
  timestamp      BIGINT NOT NULL,
  CONSTRAINT PK_snapshots PRIMARY KEY (persistence_id, sequence_nr)
);
CREATE TABLE durable_state (
  persistence_id NVARCHAR(255) COLLATE Latin1_General_100_BIN2 NOT NULL,
  revision       BIGINT NOT NULL,
  payload        NVARCHAR(MAX) NOT NULL,
  timestamp      BIGINT NOT NULL,
  CONSTRAINT PK_durable_state PRIMARY KEY (persistence_id)
);
```

The tags table's primary key is **nonclustered** on purpose.  `NVARCHAR(n)`
counts 2n bytes toward an index key, so `(tag, timestamp, persistence_id,
sequence_nr)` needs 1036 bytes — past SQL Server's 900-byte clustered limit,
but inside the 1700-byte nonclustered one.  That is why **SQL Server 2016 or
later** is required.  The collation is metadata, not width, so it costs
nothing against that budget.

Pre-provision these (granting only `INSERT/SELECT/UPDATE/DELETE`) and set
`autoCreateTables: false` if the database role cannot run DDL.

### Why `persistence_id` and `tag` are collated

Every `persistence_id` and `tag` column carries an explicit `COLLATE
Latin1_General_100_BIN2`.  Without it the column inherits the database
default — `SQL_Latin1_General_CP1_CI_AS` on a stock instance, which is
**case-insensitive**.

A `persistence_id` is not merely a value: it is the *name of an event
stream* and half of the `events` primary key.  Under a folding collation
`Alice` and `alice` are therefore **one** stream here and **two** on
Postgres, SQLite, MongoDB and DynamoDB.  An actor started as `Alice`
recovers `alice`'s events, folds them into its own state and appends into
`alice`'s stream — a cross-entity read whose only symptom is a run of
`JournalConcurrencyError`s that reads like a storage fault.  The same
column keys durable-state load, revision CAS and delete, so there a
collision overwrites and deletes another entity's state.

Validating the id cannot fix this: `Alice` and `alice` are both perfectly
legal ids.  What differs is the *comparison*, which is a property of the
column.

`BIN2` compares by Unicode code point, the way every other backend already
does.  The `Latin1_General` half of the name only selects a code page for
non-Unicode types; on `NVARCHAR` it is inert, so this is a full-Unicode
ordinal comparison and not a Western-European restriction.  Version `100`
has shipped since SQL Server 2008, well below the 2016 floor the tags
table's nonclustered key already imposes.

### Migrating an existing schema

The DDL is guarded with `IF OBJECT_ID(…) IS NULL` and `autoCreateTables`
defaults to `true`, so **an existing database does not pick this up**: the
framework never revisits a table it finds.  New deployments get the
collation silently, old ones keep the instance default, and nothing at
startup says so.

SQL Server refuses to re-collate a column that an index or constraint
depends on (error 5074), so each table is drop, alter, recreate.  Run it
once per database, with no node writing:

```sql
ALTER TABLE events DROP CONSTRAINT PK_events;
DROP INDEX idx_events_pid ON events;
ALTER TABLE events ALTER COLUMN persistence_id
  NVARCHAR(255) COLLATE Latin1_General_100_BIN2 NOT NULL;
ALTER TABLE events ADD CONSTRAINT PK_events
  PRIMARY KEY (persistence_id, sequence_nr);
CREATE INDEX idx_events_pid ON events (persistence_id);

ALTER TABLE events_tags DROP CONSTRAINT PK_events_tags;
DROP INDEX idx_events_tags_pid_seq ON events_tags;
ALTER TABLE events_tags ALTER COLUMN persistence_id
  NVARCHAR(255) COLLATE Latin1_General_100_BIN2 NOT NULL;
ALTER TABLE events_tags ALTER COLUMN tag
  NVARCHAR(255) COLLATE Latin1_General_100_BIN2 NOT NULL;
ALTER TABLE events_tags ADD CONSTRAINT PK_events_tags
  PRIMARY KEY NONCLUSTERED (tag, timestamp, persistence_id, sequence_nr);
CREATE INDEX idx_events_tags_pid_seq ON events_tags (persistence_id, sequence_nr);

ALTER TABLE events_meta DROP CONSTRAINT PK_events_meta;
ALTER TABLE events_meta ALTER COLUMN persistence_id
  NVARCHAR(255) COLLATE Latin1_General_100_BIN2 NOT NULL;
ALTER TABLE events_meta ADD CONSTRAINT PK_events_meta PRIMARY KEY (persistence_id);

ALTER TABLE snapshots DROP CONSTRAINT PK_snapshots;
ALTER TABLE snapshots ALTER COLUMN persistence_id
  NVARCHAR(255) COLLATE Latin1_General_100_BIN2 NOT NULL;
ALTER TABLE snapshots ADD CONSTRAINT PK_snapshots
  PRIMARY KEY (persistence_id, sequence_nr);

ALTER TABLE durable_state DROP CONSTRAINT PK_durable_state;
ALTER TABLE durable_state ALTER COLUMN persistence_id
  NVARCHAR(255) COLLATE Latin1_General_100_BIN2 NOT NULL;
ALTER TABLE durable_state ADD CONSTRAINT PK_durable_state PRIMARY KEY (persistence_id);
```

`ALTER COLUMN` replaces the **whole** definition, so `NOT NULL` has to be
repeated — omit it and the column silently becomes nullable.  Substitute
your own table names if you overrode `eventsTable`, `tagsTable`,
`snapshotsTable` or `table`.

Check for damage **before** migrating, while the folding collation is still
what `GROUP BY` uses:

```sql
SELECT MIN(persistence_id) AS sample,
       COUNT(DISTINCT persistence_id COLLATE Latin1_General_100_BIN2) AS spellings
  FROM events
 GROUP BY persistence_id
HAVING COUNT(DISTINCT persistence_id COLLATE Latin1_General_100_BIN2) > 1;
```

Any row means two ids have already been sharing a stream.  The migration
splits them apart again, and each half is then missing the other's events —
so those actors fail recovery loudly with `JournalIntegrityError` (a hole
in the sequence) instead of quietly serving a merged history.  That is the
better failure, but it is still a failure: decide what those streams ought
to be *before* you migrate, not after.

## Concurrency model

- **Journal append** reads the current head and inserts inside one
  transaction; the caller's `expectedSeq` is checked against that head.  A
  racing writer that slips through trips the primary key, and SQL Server error
  **2627** (or 2601 for a unique index) is translated to
  `JournalConcurrencyError` as a backstop.
- **Durable-state CAS** uses the `revision` column: a create
  (`expectedRevision === 0`) is a plain `INSERT`, so a collision arrives as
  error 2627; an update is `UPDATE … WHERE revision = expected`, where zero
  affected rows means the stored revision diverged.  Either way the current
  revision is read back for the `DurableStateConcurrencyError`.
- **Upserts use `MERGE … WITH (HOLDLOCK)`.** Without the hint, two concurrent
  merges can both take the `NOT MATCHED` branch and one fails on the primary
  key.

## Pitfalls

import { Aside } from '@astrojs/starlight/components';

<Aside type="caution" title="SQL Server 2016 or later">
  The tags table's four-column key exceeds the 900-byte clustered index limit
  and relies on the 1700-byte **nonclustered** limit, which SQL Server 2016
  introduced.  On an older instance the `CREATE TABLE` fails.
</Aside>

<Aside type="caution" title="persistenceIds and tags are capped at 255 characters">
  `NVARCHAR(255)` is what keeps those index keys inside the limit above.  A
  longer persistenceId or tag is rejected by the server rather than silently
  truncated.
</Aside>

<Aside type="caution" title="An existing database keeps the old collation">
  The guarded `CREATE TABLE` never revisits a table that already exists, so
  a database created before the `COLLATE Latin1_General_100_BIN2` pin keeps
  the instance's case-insensitive default — and nothing at startup says so.
  Two ids differing only in case then share one event stream (and one
  durable-state row) on this backend, and stay distinct on every other one.
  Run the [migration](#migrating-an-existing-schema); check for
  already-merged streams first.
</Aside>

<Aside type="caution" title="TLS is on by default in the driver">
  `mssql` defaults to `encrypt: true`.  Against a server with a self-signed
  certificate you must either install the certificate or set
  `options: { trustServerCertificate: true }` — the latter disables chain
  verification, so keep it to development.
</Aside>

<Aside type="caution" title="No in-process event bus">
  SQL Server is a cross-process backend (like Postgres and Cassandra), so it
  does NOT publish an in-process journal event bus.  `PersistenceQuery` live
  subscribers fall back to polling.
</Aside>

<Aside type="caution" title="Compression / encryption options are ignored">
  Per-call `PersistenceOptions` (compression, encryption) apply only to the
  object-storage stores.  The SQL backends store JSON as text — the options are
  silently ignored here, same as SQLite, Postgres, MariaDB and Cassandra.
</Aside>
