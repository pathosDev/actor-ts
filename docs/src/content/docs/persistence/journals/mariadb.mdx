The MariaDB backend is the sibling of the
[Postgres backend](/persistence/journals/postgres/) for teams on
MariaDB or MySQL.  It provides the same three components —
**`MariaDbJournal`**, **`MariaDbSnapshotStore`**, and
**`MariaDbDurableStateStore`** — against a single database, via the
official [`mariadb`](https://github.com/mariadb-corporation/mariadb-connector-nodejs)
connector (which speaks both MariaDB and MySQL).

It's a **separate implementation** from Postgres (not a shared dialect
layer), so the SQL is idiomatic MariaDB, but the public contract and
behaviour are identical.

## Install

`mariadb` is an optional peer dependency:

```bash
bun add mariadb
```

Lazy-imported on first use, like every other adapter.

## Setup

```ts
import {
  ActorSystem,
  ActorSystemOptions,
} from 'actor-ts';
import {
  PersistenceExtensionId,
  MariaDbJournalOptions,
  MariaDbSnapshotStoreOptions,
  MariaDbDurableStateStoreOptions,
  RegisterMariaDbPluginsOptions,
  registerMariaDbPlugins,
} from 'actor-ts/persistence';

const actorSystemOptions = ActorSystemOptions.create().withConfig({
    'actor-ts': {
      persistence: {
        journal: { plugin: 'actor-ts.persistence.journal.mariadb' },
        'snapshot-store': { plugin: 'actor-ts.persistence.snapshot-store.mariadb' },
      },
    },
  });
const system = ActorSystem.create('my-app', actorSystemOptions);

const ext = system.extension(PersistenceExtensionId);
const mariaDbJournalOptions = MariaDbJournalOptions.create().withPoolConfig(connection);
const mariaDbSnapshotStoreOptions = MariaDbSnapshotStoreOptions.create()
  .withPoolConfig(connection)
  .withKeepN(3);
const mariaDbDurableStateStoreOptions = MariaDbDurableStateStoreOptions.create().withPoolConfig(connection);
const registerMariaDbPluginsOptions = RegisterMariaDbPluginsOptions.create()
  .withJournal(mariaDbJournalOptions)
  .withSnapshotStore(mariaDbSnapshotStoreOptions)
  .withDurableStateStore(mariaDbDurableStateStoreOptions);
const { durableStateStore } = registerMariaDbPlugins(ext, registerMariaDbPluginsOptions);

// connection = { host, port: 3306, user, password, database } — or pass a
// shared `pool` (from mariadb.createPool) at the top level via
// `.withPool(pool)` to reuse one pool across all three, or a connection
// URL via `.withUrl(...)`.
```

As with Postgres, the journal + snapshot store are selected by the config
plugin IDs, and the **durable-state store is returned** for you to pass
into your `DurableStateActor` settings.

## Configuration

```ts
type MariaDbConnection = {
  url?:        string;                    // mariadb://user:pass@host:3306/db
  poolConfig?: Record<string, unknown>;   // { host, port, user, password, database, … }
  pool?:       MariaDbPoolLike;           // pre-built / shared pool
};
interface MariaDbJournalOptions extends MariaDbConnection {
  eventsTable?: string; tagsTable?: string; autoCreateTables?: boolean;
}
interface MariaDbSnapshotStoreOptions extends MariaDbConnection {
  snapshotsTable?: string; keepN?: number; autoCreateTables?: boolean;
}
interface MariaDbDurableStateStoreOptions extends MariaDbConnection {
  table?: string; autoCreateTables?: boolean;
}
```

Discrete `poolConfig` (host/user/password/database) is the most portable
way to connect; `url` and a pre-built `pool` are also accepted.

## Schema

Same shape as [Postgres](/persistence/journals/postgres/#schema), with
MariaDB types — `VARCHAR(255)` ids, `BIGINT` sequence/revision/timestamp,
`LONGTEXT` payloads — and indexes declared **inline** in `CREATE TABLE`
(portable across MariaDB/MySQL versions, unlike `CREATE INDEX IF NOT
EXISTS`):

```sql
CREATE TABLE events (
  persistence_id VARCHAR(255) COLLATE utf8mb4_bin NOT NULL,
  sequence_nr    BIGINT NOT NULL,
  payload        LONGTEXT NOT NULL,
  tags           TEXT,
  timestamp      BIGINT NOT NULL,
  PRIMARY KEY (persistence_id, sequence_nr),
  INDEX idx_events_pid (persistence_id)
);
-- events_tags, snapshots, durable_state: as Postgres, with the types above
```

### Why `persistence_id` and `tag` are collated

Every `persistence_id` and `tag` column carries an explicit `COLLATE
utf8mb4_bin`.  Without it the column inherits the server default —
`utf8mb4_general_ci` on a stock MariaDB, `utf8mb4_0900_ai_ci` on MySQL 8 —
and both of those **fold case and accents**.

A `persistence_id` is not merely a value: it is the *name of an event
stream* and half of the `events` primary key.  Under a folding collation
`Alice` and `alice` are therefore **one** stream here and **two** on
Postgres, SQLite, MongoDB and DynamoDB.  An actor started as `Alice`
recovers `alice`'s events, folds them into its own state and appends into
`alice`'s stream — a cross-entity read whose only symptom is a run of
`JournalConcurrencyError`s that reads like a storage fault.  The same
column keys durable-state load, revision CAS and delete, so there a
collision overwrites and deletes another entity's state.

Validating the id cannot fix this: `Alice` and `alice` are both perfectly
legal ids.  What differs is the *comparison*, which is a property of the
column.

`utf8mb4_bin` compares code point by code point, the way every other
backend already does.  It is also the portable spelling —
`utf8mb4_0900_bin` is MySQL 8 only and MariaDB has never had it.  Naming a
collation with no `CHARACTER SET` fixes the charset to `utf8mb4` as well,
rather than leaving it on whatever the database defaults to.

One divergence survives on purpose: `utf8mb4_bin` is **PAD SPACE**, so
`'alice '` still equals `'alice'` here where Postgres keeps them apart.
The NO PAD binary collations are vendor-split (`utf8mb4_nopad_bin` on
MariaDB, `utf8mb4_0900_bin` on MySQL), so there is nothing portable to
pin — avoid trailing whitespace in ids you generate.

### Migrating an existing schema

The DDL is `CREATE TABLE IF NOT EXISTS` and `autoCreateTables` defaults to
`true`, so **an existing database does not pick this up**: the framework
never revisits a table it finds.  New deployments get the collation
silently, old ones keep the server default, and nothing warns either way.
Run this once per database, with no node writing:

```sql
ALTER TABLE events        MODIFY persistence_id VARCHAR(255) COLLATE utf8mb4_bin NOT NULL;
ALTER TABLE events_tags   MODIFY persistence_id VARCHAR(255) COLLATE utf8mb4_bin NOT NULL,
                          MODIFY tag            VARCHAR(255) COLLATE utf8mb4_bin NOT NULL;
ALTER TABLE events_meta   MODIFY persistence_id VARCHAR(255) COLLATE utf8mb4_bin NOT NULL;
ALTER TABLE snapshots     MODIFY persistence_id VARCHAR(255) COLLATE utf8mb4_bin NOT NULL;
ALTER TABLE durable_state MODIFY persistence_id VARCHAR(255) COLLATE utf8mb4_bin NOT NULL;
```

`MODIFY` replaces the **whole** column definition, so `NOT NULL` has to be
repeated — omit it and the column silently becomes nullable.  Changing the
collation of an indexed column is not an in-place alteration, so InnoDB
rebuilds each table: budget a lock for the duration and disk for a second
copy.

Check for damage **before** migrating, while the folding collation is still
what `GROUP BY` uses:

```sql
SELECT persistence_id,
       COUNT(DISTINCT persistence_id COLLATE utf8mb4_bin) AS spellings
  FROM events
 GROUP BY persistence_id
HAVING spellings > 1;
```

Any row means two ids have already been sharing a stream.  The `ALTER`
splits them apart again, and each half is then missing the other's events —
so those actors fail recovery loudly with `JournalIntegrityError` (a hole
in the sequence) instead of quietly serving a merged history.  That is the
better failure, but it is still a failure: decide what those streams ought
to be *before* you migrate, not after.

## Tag queries

`MariaDbQuery` reads the `events_tags` index exactly as `PostgresQuery`
does — same statements, same three plans, only the placeholders differ.
See [Tag queries on the Postgres page](/persistence/journals/postgres/#tag-queries)
for the shapes.

```ts
import { MariaDbJournal, MariaDbJournalOptions, MariaDbQuery } from 'actor-ts/persistence';

const journalOptions = MariaDbJournalOptions.create().withUrl(process.env.MARIADB_URL!);
const eventsJournal = new MariaDbJournal(journalOptions);
const query = new MariaDbQuery(eventsJournal);
```

## Dialect differences vs. Postgres

The behaviour is identical; the SQL differs:

| Operation | Postgres | MariaDB |
| --- | --- | --- |
| Placeholders | `$1, $2` | `?` |
| Tag dedup insert | `ON CONFLICT DO NOTHING` | `INSERT IGNORE` |
| Snapshot upsert | `ON CONFLICT … DO UPDATE` | `ON DUPLICATE KEY UPDATE` |
| `keepN` prune | `NOT IN (SELECT … LIMIT)` | derived-table-wrapped subquery¹ |
| Durable create conflict | `ON CONFLICT DO NOTHING` → rowCount | plain `INSERT`, catch `ER_DUP_ENTRY` (1062) |
| Concurrency backstop | SQLSTATE `23505` | `ER_DUP_ENTRY` / 1062 |
| Contention backstop | SQLSTATE `40001` / `40P01` | `ER_CHECKREAD` (1020), 1213, 1205² |
| Id / tag comparison | `TEXT` — byte-exact already | `VARCHAR(255) COLLATE utf8mb4_bin`³ |

¹ MySQL/MariaDB reject `LIMIT` inside a bare `IN (SELECT …)` against the
table being deleted, so the prune wraps the subquery in a derived table.

² A losing writer does not always reach the primary key.  Under real
contention InnoDB aborts it first — *"Record has changed since last read"*
(errno 1020) — so the duplicate-key backstop alone would have handed the
caller an opaque `JournalError` and no way to tell a retryable race from a
storage failure.  Those aborts are classified too, but they are only
reported as `JournalConcurrencyError` when a re-read shows the head actually
moved; otherwise the error stands, because a lock-wait timeout against an
unrelated long transaction is a real failure and retrying it would spin.
The same applies to durable-state CAS.

³ Postgres compares `TEXT` byte-exactly, so it needs nothing; MariaDB
would otherwise inherit a case-folding server default and merge two
entities into one stream.  See
[Why `persistence_id` and `tag` are collated](#why-persistence_id-and-tag-are-collated).

`BIGINT` may surface from the connector as a JS `bigint`; the backend
coerces sequence/revision/timestamp to `number` at the mapping boundary.

## Pitfalls

import { Aside } from '@astrojs/starlight/components';

<Aside type="caution" title="No in-process event bus">
  Cross-process backend — no in-process journal event bus; `PersistenceQuery`
  live subscribers poll.  Same as Postgres and Cassandra.
</Aside>

<Aside type="caution" title="Compression / encryption options are ignored">
  The SQL backends store JSON as `LONGTEXT`; per-call `PersistenceOptions`
  (compression/encryption) apply only to the object-storage stores.
</Aside>

<Aside type="caution" title="utf8mb4 + key length">
  Pinning `utf8mb4_bin` also pins the charset, so both `VARCHAR(255)`
  columns of the `events_tags` primary key count 1020 index bytes — 2056
  for the four-column key.  That is comfortable under InnoDB's 3072-byte
  limit on the `DYNAMIC` row format (the default since MariaDB 10.2 and
  MySQL 5.7), and over the 767-byte limit of the legacy `COMPACT` format.
  Widening the columns in a custom schema eats that headroom fast.
</Aside>

<Aside type="caution" title="An existing database keeps the old collation">
  `CREATE TABLE IF NOT EXISTS` never revisits a table that already exists,
  so a database created before the `COLLATE utf8mb4_bin` pin keeps the
  server's case-insensitive default — and nothing at startup says so.  Two
  ids differing only in case then share one event stream on this backend
  and stay distinct on every other one.  Run the
  [`ALTER TABLE` migration](#migrating-an-existing-schema); check for
  already-merged streams first.
</Aside>
