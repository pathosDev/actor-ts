---
title: Request timeout
description: requestTimeout() races a handler against a deadline and returns 503 when it wins. Bounds client-observed latency; the handler is not cancelled.
---

`requestTimeout(deadlineMs)` races the handler against a deadline and returns
`503` if the deadline wins.

```ts
import { requestTimeout, withMiddleware } from 'actor-ts/http';

const routes = withMiddleware(requestTimeout(5000), appRoutes);
```

Pass options for a custom response:

```ts
import { completeJson, requestTimeout, Status, TimeoutOptions, withMiddleware } from 'actor-ts/http';

const timeoutOptions = TimeoutOptions.create()
  .withDeadlineMs(5000)
  .withOnTimeout((request) => completeJson(Status.ServiceUnavailable, { error: 'slow', path: request.path }));

const routes = withMiddleware(requestTimeout(timeoutOptions), appRoutes);
```

## Configuration

| Builder method | Field | Default | Config |
| --- | --- | --- | --- |
| `withDeadlineMs(deadlineMs)` | `deadlineMs` | `30000` | `deadline` |
| `withOnTimeout(onTimeout)` | `onTimeout` | `503 { error: 'request timed out' }` | **code-only** — a function |

The deadline is also settable from `actor-ts.http.request-timeout`. What
`requestTimeout(...)` names in code wins, then the block, then the built-in
30 s — so `requestTimeout()` with no argument takes its deadline from the
configuration file:

```hocon
actor-ts.http.request-timeout {
  deadline = 10s
}
```

The merged deadline is validated once, when `bind()` compiles the route tree:
one that is not positive, or longer than a timer can hold (2147483647 ms,
about 24.9 days), fails `bind()` with an `OptionsError` instead of answering
every request `503` at once.

It is a different key from `actor-ts.http.server.request-timeout`, which
bounds how long a peer takes to *send* a request and never a response. This
one starts once the request has arrived and bounds the handler. See
[Configuration → `actor-ts.http`](/reference/configuration/).

On the [Hono backend](/http/backends/hono/) under Bun the deadline also sets
the server's idle default. `Bun.serve` closes a connection whose handler has
written nothing for its idle timeout, which would cut a slow handler before its
`503` is sent, so while `actor-ts.http.server.idle-timeout` is unset the idle
timeout follows the longest deadline on the server — this block's, raised to the
longest `requestTimeout(...)` in the route tree — with room for the `503` to
go first: 36 s for the built-in 30 s. Above about 250 s it cannot: `Bun.serve`
holds at most 255 s, so the idle timeout stays there, a handler silent that
long is still cut without a response, and `bind()` logs a warning naming the
key and the deadline. Set `idle-timeout` yourself, at most `255s` or `0` for
none, if a route needs longer.

The block reaches `requestTimeout()` through a hook that `compile()` resolves,
so hand the middleware to `withMiddleware(...)` as it is. Wrapped in a function
of your own it runs on its code options and the built-in default, and when the
block is configured and nothing in the tree read it, `bind()` logs a warning
naming it.

<Aside type="caution" title="The handler keeps running">
  A timeout does **not** cancel the handler — it keeps running and its late
  result is discarded. This bounds client-observed latency and how long a
  response is held open, nothing more. For true cancellation, thread an
  `AbortSignal` through your own async work.
</Aside>
