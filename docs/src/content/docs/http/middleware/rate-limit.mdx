---
title: Rate limit middleware
description: Per-key fixed-window rate limiting on HTTP routes. Default per-IP; configurable key (per-user, per-tenant). Backed by the Cache abstraction, so single-pod uses memory and multi-pod uses Redis.
---

`rateLimit` is a per-key request limiter.  It returns a
**handler wrapper** — call it with the options, then call the
returned function with the handler you want to protect.
Excess requests get **429** with a `Retry-After` header.

```ts
import { rateLimit } from 'actor-ts/http';
import { InMemoryCache } from 'actor-ts/cache';

const limited = rateLimit({
  cache:    new InMemoryCache(),
  windowMs: 60_000,                       // 1 minute window
  max:      100,                          // 100 reqs per key per minute
  key:      (request) => request.remoteAddress ?? 'unknown',   // socket peer — not a spoofable header
});

const routes = path('api', post(limited(apiHandler)));
```

Each distinct key (here: per client IP taken from the socket peer,
`request.remoteAddress`) gets a 100/minute budget.  Excess requests get 429
with a `Retry-After` header.  **Key on a value the client can't forge** —
never key on a raw `x-forwarded-for` (see the security note below), or an
attacker rotates it per request to bypass the limit.

## Configuration

```ts
type RateLimitOptions = {
  cache:       Cache;
  windowMs:    number;
  max:         number;
  key:         (request: HttpRequest) => string | Promise<string>;
  keyPrefix?:  string;                    // default 'rl:'
  onLimit?:    (context: RateLimitContext) => HttpResponse;
};

type RateLimitContext = {
  key:               string;
  count:             number;
  max:               number;
  windowMs:          number;
  retryAfterSeconds: number;
};
```

| Field | Purpose |
| --- | --- |
| `cache` | Backing store (in-memory or Redis). |
| `windowMs` | Fixed-window size. |
| `max` | Max requests per key per window. |
| `key(request)` | Derive the rate-limit key — typically client IP, user ID, or API key. **Required.** |
| `keyPrefix` | Cache-key namespace.  Default `'rl:'` so multiple limiters in the same Redis don't collide. |
| `onLimit(context)` | Override the 429 response — full control over status / body / headers. |

## Custom keying

```ts
const limited = rateLimit({
  cache,
  windowMs: 60_000,
  max:      100,
  key:      (request) => {
    const userId = extractUserId(request);
    return userId ? `user:${userId}` : `ip:${request.remoteAddress ?? 'unknown'}`;
  },
});
```

Per-user when authenticated; per-IP when not.  Common pattern:

- **Auth'd routes** — per-user limit.
- **Public routes** — per-IP limit.

Combine with the framework's
[Cache](/cache/overview/) abstraction so the limiter
works across pods with Redis backing.

## How counting works

```
Fixed window (default):
  - Window starts when the first request in a key arrives.
  - Increments a counter in the cache.
  - When counter exceeds `max`, subsequent requests in the
    window get 429.
  - TTL on the counter ensures fresh windows start cleanly.
```

The implementation uses the cache's **`incr` with TTL** —
atomic across pods when backed by Redis.

## Response headers

The middleware sets:

```
X-RateLimit-Limit:     100
X-RateLimit-Remaining: 47
Retry-After:           23           ← (on 429 only) seconds until reset
```

Clients use these to back off without retrying randomly.

## Cluster-aware rate limiting

```ts
import { RedisCache, RedisCacheOptions } from 'actor-ts/cache';

const redisCacheOptions = RedisCacheOptions.create().withUrl('redis://...');
rateLimit({
  cache:    new RedisCache(redisCacheOptions),
  windowMs: 60_000,
  max:      100,
  key:      (request) => request.remoteAddress ?? 'unknown',   // socket peer — not a spoofable header
});
```

With Redis-backed cache, **all pods share the counter** — a
client hitting any pod accumulates against the same budget.

With `InMemoryCache`, each pod has its own counter — a client
distributed across 4 pods gets effectively **4× the limit**.
Acceptable for permissive limits; problematic for strict ones.

## When to use it

Three good fits:

1. **Public APIs** — prevent abuse / DoS.
2. **Tier-based limits** — different `key` per tier
   (free / paid / enterprise).
3. **Per-action limits** — login attempts, password resets,
   email-send rates.

## Layered rate limits

```ts
// Different limits per handler:
const apiLimited = rateLimit({
  cache, windowMs: 60_000, max: 1000,
  key: (request) => request.headers['x-user-id'] ?? request.remoteAddress ?? 'anon',
});

const loginLimited = rateLimit({
  cache, windowMs: 60_000, max: 10,
  key: (request) => `login:${request.remoteAddress ?? 'unknown'}`,
});

const routes = concat(
  path('login',  post(loginLimited(loginHandler))),
  path('orders', get(apiLimited(ordersHandler))),
);
```

Stricter limits on sensitive handlers; more permissive on
general traffic.  Compose by wrapping each handler with the
matching limiter.

<Aside type="caution" title="Trusting X-Forwarded-For">
  ```ts
  key: (request) => request.headers['x-forwarded-for'];   // ✗ spoofable
  ```
  Behind a load balancer / proxy, the real IP is in
  `X-Forwarded-For` (or similar) — but not at a position the request can
  be trusted to name: NGINX, AWS ALB and Cloudflare all **append** to the
  header, so whatever the client typed stays at its left.  Key on
  `request.remoteAddress`, or resolve the client address the way
  [`IpAllowlist`](/http/middleware/ip-allowlist/) does — name the proxies
  and read the chain from the socket end inwards.
</Aside>

<Aside type="caution" title="In-memory cache across pods">
  ```ts
  // 4 pods × 100 req limit = effective 400/min for a user
  ```
  Use Redis-backed cache for production multi-pod
  deployments.  In-memory cache only suffices for single-pod
  or "rough" limiting.
</Aside>

<Aside type="caution" title="Don't share the cache with cached() or idempotent()">
  ```ts
  const limiterCache = new InMemoryCache();   // ✓ the limiter's own instance
  ```
  `InMemoryCache` counts the counter as carrying a guarantee — `incr`
  with a `windowMs` created it — and evicts entries that carry none
  first, so a `cached` key flood no longer resets other clients'
  windows.  It does not rank guarantees against each other, though: on
  an instance shared with `idempotent`, a flood of attacker-chosen
  `Idempotency-Key`s is a flood of claims, and once the map holds
  nothing cheaper the counters go too.  The flooder's own counter is
  safe either way: `incr` marks it most-recently-used on every request,
  so it is never the victim.

  Pass a dedicated instance — or `ext.cache('rate-limit')` — and size
  its `maxEntries` above the number of distinct keys you expect inside
  one `windowMs`; a client with an IPv6 `/64` mints them all day, and
  every one is a counter the cache protects.  See
  [what eviction protects and what it does not](/cache/in-memory/#what-eviction-protects-and-what-it-does-not).
</Aside>

<Aside type="caution" title="Fixed-window edge effects">
  ```ts
  // Limit is 100/minute.
  // At t=59s: user hits 100; at t=60s: window resets; at t=61s: user hits 100 more.
  // → 200 requests in 2 seconds
  ```
  Fixed windows have edge effects where bursts cross window
  boundaries.  For strict-burst protection, the framework
  doesn't currently ship a sliding-window or token-bucket
  variant — implement manually if needed.
</Aside>
