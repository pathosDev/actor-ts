---
title: Idempotency-key middleware
description: Deduplicate write requests via an `Idempotency-Key` header — second request with the same key returns the first request's stored response. Standard pattern for payment / order APIs where retries shouldn't double-charge.
---

`idempotent` enforces **at-most-once write processing** via a
client-provided header:

```
POST /api/payments
Idempotency-Key: tx-1684923847-abc

→ 201 Created  (first time — processed + stored)
{ "txId": "tx-42" }

POST /api/payments
Idempotency-Key: tx-1684923847-abc   ← same key

→ 201 Created  (second time — returned from cache, no re-processing)
{ "txId": "tx-42" }
```

The handler runs **only on the first request**.  Subsequent
requests with the same key return the cached response.

```ts
import { idempotent, path, post } from 'actor-ts/http';
import { InMemoryCache } from 'actor-ts/cache';

const dedup = idempotent({
  cache:         new InMemoryCache(),
  ttlMs:         24 * 60 * 60_000,   // 24 hours
  missingHeader: 'reject',           // 400 when the header is absent
});

const routes = path('api',
  path('payments', post(dedup(processPayment))),
);
```

## Why this matters

Network retries are common.  Without idempotency:

```
Client → POST /payments  ($100)
         → network timeout (request actually succeeded server-side)
Client → POST /payments  ($100)   ← retry; charges twice
```

With idempotency-key, the retry sees "key already processed,
here's the original response."  No double charge.

## Configuration

```ts
type IdempotencyOptions = {
  cache:          Cache;
  ttlMs?:         number;                              // default 24h
  lockTtlMs?:     number;                              // default 60s
  onHandlerError?: 'retain' | 'release';               // default 'retain'
  cacheStatuses?:  ReadonlyArray<number>;              // default: all but 5xx, 408, 429
  headerName?:    string;                              // default 'idempotency-key'
  keyPrefix?:     string;                              // default 'idem:'
  maxKeyLength?:   number;                             // default 255
  maxScopeLength?: number;                             // default 255
  missingHeader?:  'reject' | 'pass-through';          // default 'reject'
  identity?:       (req: HttpRequest) => string | Promise<string>;   // per-caller scope; default none
};
```

| Field | Purpose |
| --- | --- |
| `cache` | Backing store.  Redis is required for multi-pod.  **Give it its own instance** — see the caution below. |
| `ttlMs` | How long to remember each finished request's response.  Default 24 hours. |
| `lockTtlMs` | How long the claim on an in-flight key lives.  Default 60 seconds.  Also the longest a handler can run and stay exclusive — see [in-flight handling](#in-flight-handling). |
| `onHandlerError` | What a **thrown** handler leaves behind: `'retain'` (default) records the failure, `'release'` frees the key for a retry.  See [what gets cached](#what-gets-cached). |
| `cacheStatuses` | Statuses whose responses are recorded; any other status frees the key.  Default: every status except 5xx, 408 and 429. |
| `headerName` | Customize the header name (case-insensitive match).  Default `'idempotency-key'`. |
| `keyPrefix` | Cache-key namespace.  Default `'idem:'` so multiple idempotency wrappers in the same Redis don't collide. |
| `maxKeyLength` | Longest accepted header value.  Default 255 (Stripe's cap); a longer key is refused with 400. |
| `maxScopeLength` | Longest accepted `identity` result.  Default 255; a longer scope is refused with 400. |
| `missingHeader` | What to do when the header is absent.  Default `'reject'` (400); set `'pass-through'` to run the handler without dedup when only some clients use idempotency. |
| `identity` | Optional per-caller scope folded into the cache key so a cached, identity-specific response is never replayed to a different caller — derive it from what a middleware **verified**, e.g. `(req) => jwtClaimsOf(req)?.sub ?? 'anonymous'` inside `JwtAuth`, never from a raw header such as `x-account`, which a caller can set to another account's id.  Without it, two callers reusing the same key for the same method + path + query + body share one cached response; safe only for identity-agnostic endpoints (security audit HTTP-4).  **Return an id, not free text** — the result is held to the same two rules as the header value. |

The wrapper also stores a **SHA-256 fingerprint of the request**
— method, path, query string and body — alongside each cached
response.  When a second request arrives with the same key but
any of those four differing, the wrapper rejects with 422 —
preventing a client (malicious or buggy) from reusing a key for
a semantically different request to receive the wrong stored
response.  `POST /refunds?amount=1` and `POST /refunds?amount=9999`
are different requests even when their bodies are identical.

The query is folded in **canonically**: parameter *keys* are
sorted, so a retry that reorders `?a=1&b=2` into `?b=2&a=1`
still replays instead of being rejected — reordering is not a
different request.  The values of a *repeated* key keep their
original order, so `?tag=a&tag=b` stays distinct from
`?tag=b&tag=a`, which matters for any API that reads such a
list positionally.

## The key itself is validated

The header value is attacker-chosen and lands verbatim in a cache key,
so it is checked before it gets there.  A request is refused with
**400** when the key

- is **longer than `maxKeyLength`** (default 255 characters), or
- contains an **ASCII control character or a space** — CR and LF are
  the classic header-injection pair, and space plus the control range
  are command delimiters in Memcached's text protocol, so a key
  carrying one is only safe depending on which `Cache` happens to be
  wired in behind the middleware.

The rejection names the limit and the offending index, never the key
itself — echoing attacker bytes back into a response body is how a
rejection message becomes a payload.

Real clients send a UUID or a short opaque token, so neither rule costs
honest traffic anything.  Raise `maxKeyLength` only for a client fleet
you control that genuinely mints longer keys.

**Both rules apply to the `identity` scope too**, bounded by
`maxScopeLength` (also 255 by default), because the scope is the other
half of the same composed key:

```
idem:<scope>:<Idempotency-Key>
```

That matters most for a scope read from client input, where the client
picks the size.  A two-character `Idempotency-Key` with a 64 KiB
`x-account` header as the scope used to be accepted with 200 and stored a
64 KiB cache key under a middleware whose documented cap is 255.
Deriving the scope from a validated session or token, as the `identity`
row above does, keeps the check inert.

The two caps are separate numbers rather than one cap over the composed
key, so a tenant with a long id cannot spend an honest client's header
budget: 255 + 255 is accepted, and `maxKeyLength` stays exactly Stripe's
published figure.

Note what all of this bounds: how much cache **one** minted key costs,
not how **many** a caller can mint.  The eviction caution below is the
other half.

## What gets cached

```ts
{
  status:  201,
  headers: { 'content-type': 'application/json' },
  body:    '{"txId":"tx-42"}',
}
```

The middleware stores the **complete response**.  Subsequent
requests with the same key get an identical response — same
status, headers, body.

For **error responses**, what counts is whether the handler
**returns** or **throws**.

A *returned* response is recorded when its status is in
`cacheStatuses` — by default every status except **5xx, 408 and
429**.  A 400, 404 or "payment declined" 402 is the answer to that
request and replays on retry exactly like a 2xx, so it is not
re-processed into a different outcome.  The three excluded families
are the ones that mean "not now, try again": a downstream 503 used
to be pinned under the key for the full `ttlMs`, replayed to the
client that was retrying exactly as told.  Now such a response frees
the key and the retry runs the handler.  A handler returning one of
those statuses is asserting the request is safe to retry — return
them only from a point where nothing has been applied.

A handler that *throws* is different, because nothing tells the
middleware how far it got.  A payment handler that captured the
charge and then failed on the receipt e-mail has done the one thing
idempotency exists to do only once.  So by default
(`onHandlerError: 'retain'`) the failure is **recorded**: the
original caller gets the error the framework renders for a throw,
and every retry with that key is answered **500** without the
handler running —

```json
{ "error": "an earlier request with this idempotency-key failed after it may have applied side effects; it is not run again — reconcile, then retry with a new key" }
```

— for the rest of `ttlMs`.  The client checks what happened (the
payment provider, its own order list) and, if the operation is still
wanted, sends it again under a **new** key.  The record keeps its
fingerprint, so a different request under the same key is still a
422.

`onHandlerError: 'release'` frees the key instead, so a retry runs
the handler again.  Use it only for a handler that is
**all-or-nothing** — one database transaction that either commits or
rolls back — where a throw guarantees nothing was applied.

## Per-tenant scoping

For per-tenant key isolation, build a separate `idempotent`
wrapper per tenant (or include the tenant in `keyPrefix`):

```ts
const dedupForTenant = (tenant: string) =>
  idempotent({
    cache,
    ttlMs:     24 * 60 * 60_000,
    keyPrefix: `idem:${tenant}:`,
  });
```

Important when:

- Different tenants might pick the same key by chance.
- You're billing or auditing per-tenant.

If you need a single wrapper that derives the tenant from the
request itself, wrap the handler with a thin adapter that
re-keys the cache before calling `idempotent`'s wrapper.

## Multi-pod with Redis

```ts
import { RedisCache, RedisCacheOptions } from 'actor-ts/cache';

const redisCacheOptions = RedisCacheOptions.create().withUrl('redis://...');
idempotent({
  cache:  new RedisCache(redisCacheOptions),
  ttlMs:  24 * 60 * 60_000,
});
```

With Redis backing, **every pod sees the same idempotency
state** — a retry to pod-2 after the original hit pod-1
returns the cached response.

InMemoryCache → per-pod state → retries hitting different
pods could double-process.  Always Redis for prod.

## Where to use

```
POST /api/payments        ✓ idempotency-key recommended
POST /api/orders          ✓ same
POST /api/emails          ✓ avoid double-sends
PUT  /api/users/:id       ✓ retries safe
GET  /api/users/me        ✗ no need (idempotent already)
DELETE /api/orders/:id    ✓ retries safe
```

Apply to **any mutating endpoint where double-processing is
harmful**.

## Client-side responsibility

```js
const key = `${userId}-${operation}-${Date.now()}-${random}`;

fetch('/api/payments', {
  method: 'POST',
  headers: {
    'idempotency-key': key,
    'content-type':    'application/json',
  },
  body: JSON.stringify({ amount: 100 }),
});

// On retry: REUSE THE SAME KEY
fetch('/api/payments', {
  method: 'POST',
  headers: { 'idempotency-key': key },   // ← same key
  body:    JSON.stringify({ amount: 100 }),
});
```

The **client must generate the key + retry with the same
key**.  If the client generates a fresh key per try, the
middleware sees them as different requests and processes each.

Common bug: generating a key inside the retry loop instead of
once before the first attempt.

## In-flight handling

If two requests with the same key arrive **simultaneously**
(double-click, concurrent retry), the first claims the key and runs
the handler; the second sees the key **in flight** and is rejected
immediately with **`409 Conflict`** (`{ "error": "idempotency-key
in-flight; retry shortly" }`) — it is **not** queued or made to wait.

The client retries after a short backoff; once the first request has
completed and cached its response, the retry replays that stored
response.  Failing fast (rather than holding the second connection
open for the handler's whole runtime) also means there is no
cross-pod lock to coordinate — the claim lives in the same cache as
the cached responses.

The claim has its **own lifetime, `lockTtlMs`** (60 seconds by
default), separate from the 24-hour `ttlMs` of a finished record.
That lifetime is the only thing that frees a key whose worker died
mid-handler — an evicted pod, an OOM kill, a deploy — and with the
record's TTL in that role a crash used to answer every retry 409 for
a day.  Now the claim lapses in a minute, and the retry after it runs
the handler, because nothing recorded that the first attempt
finished.

**Size `lockTtlMs` above your slowest handler**, and treat it as that
handler's timeout: a handler still running when its claim lapses can
be joined by a retry.  That overrun is caught on the way out but not
prevented.  The claim holds a random token rather than a shared
marker, and the late finisher writes or deletes only while its own
token is still there.  So it neither stores its response over the
retry's claim nor deletes it — its response still reaches its own
caller, and the key stays with the retry, whose record is the one
that replays.  Before that check, a late throw deleted the retry's
claim and let a third request run alongside it.

<Aside type="caution" title="Cache loss = double processing">
  ```ts
  // Cache TTL expires; client retries the original request
  ```
  After TTL, the key is forgotten.  A delayed retry now
  processes again.  Pick TTL longer than any reasonable retry
  window (24 hours typical for payments).
</Aside>

<Aside type="caution" title="Never share the cache with rateLimit() or cached()">
  ```ts
  const idempotencyCache = new InMemoryCache();   // ✓ this middleware's own instance
  ```
  Every request can mint a new key here, and `InMemoryCache` is
  LRU-bounded (10 000 entries by default).  Its eviction takes entries
  that carry no guarantee first — a claim and the record that replaces
  it both count as one — so a flood through `cached` no longer reaches
  a stored response.  Two things still do, both silent:

  - Share one **undivided** instance with `rateLimit` and a flood of
    **counters** evicts records anyway.  Both sides carry a guarantee,
    and the guarantee split does not rank guarantees against each other
    — `prefixQuotas` is what does.
  - This middleware's own key space is attacker-controlled, so a flood
    of distinct `Idempotency-Key`s evicts *other* callers' records out
    of the same instance.  `maxKeyLength` and `maxScopeLength` bound how
    big each minted key is, not how many there are — and no quota helps
    here either, because attacker and victim write under the same
    prefix and therefore share whatever is reserved for it.

  A record is also only marked most-recently-used when it is **read**.
  `setIfAbsent` does not count, so a claimed key that nobody has
  retried yet is the first thing dropped once a cap is reached.

  Pass a dedicated instance — or `ext.cache('idempotency')` — and size
  its `max-entries` for the keys you expect within one `ttlMs`, under
  that cache's own name:

  ```hocon
  actor-ts.cache.idempotency.in-memory.max-entries = 200000
  ```

  Where one instance genuinely has to be shared, reserve this
  middleware's `keyPrefix` out of it instead:

  ```hocon
  actor-ts.cache.shared.in-memory {
    max-entries   = 10000
    prefix-quotas { "idem:" = 8000, "rl:" = 2000 }
  }
  ```

  Where the guarantee has to hold under an adversary who chooses the
  keys, back it with Redis instead of an in-process LRU — that is the
  one exposure neither a named instance nor a quota removes.  See
  [what eviction protects and what it does not](/cache/in-memory/#what-eviction-protects-and-what-it-does-not)
  and [dividing one instance by key prefix](/cache/in-memory/#dividing-one-instance-by-key-prefix).
</Aside>

<Aside type="caution" title="In-memory cache + multiple pods">
  ```ts
  // Pod-1 handles first; retry hits pod-2 (different InMemoryCache)
  ```
  Pod-2's cache doesn't see pod-1's key → re-processes.
  Use Redis.
</Aside>

<Aside type="caution" title="Idempotency-key with non-idempotent side effects">
  ```ts
  // Handler creates a Stripe charge.  First time succeeds; cached.
  // But Stripe also has its own idempotency-key concept; you'd want to pass it through.
  ```
  When the handler calls **other** idempotent services
  (Stripe, payment processors), forward the idempotency-key
  to them.  Belt and braces.
</Aside>
