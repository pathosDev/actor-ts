---
title: Response cache middleware
description: Cache handler responses keyed by a user-supplied key(req) function. Useful for read-heavy APIs with stable responses. Required TTL, per-status-code caching, per-process single-flight, pluggable cache backend.
---

`cached` wraps a handler with **response caching** keyed by a
user-supplied `key(req)` function.  A cache hit serves the
stored response without invoking the underlying handler.

```ts
import { cached, path, get } from 'actor-ts/http';
import { InMemoryCache } from 'actor-ts/cache';

const productCache = cached({
  cache: new InMemoryCache(),
  ttlMs: 30_000,
  key:   (req) => `products:${pathParam(req, 'id')}`,
});

const routes = path('api',
  path('products',
    get(productCache(async (req) => /* expensive lookup */)),
  ),
);
```

Cache for 30 seconds per product ID.  First request hits the
handler; subsequent GETs in the next 30 s return the cached
response.

## Configuration

```ts
type ResponseCacheOptions = {
  cache:          Cache;
  ttlMs:          number;
  key:            (req: HttpRequest) => string | Promise<string>;
  keyPrefix?:     string;                            // default 'rsp:'
  cacheStatuses?: ReadonlyArray<number>;             // default [200]
  identity?:      (req: HttpRequest) => string | Promise<string>;
};
```

| Field | Purpose |
| --- | --- |
| `cache` | The [Cache](/cache/overview/) backend.  `InMemoryCache` for single-node; Redis for shared. |
| `ttlMs` | How long each cached response stays valid. |
| `key(req)` | Derive the cache key from the request — typically includes URL params, tenant ID, accept header etc.  **Required.** |
| `keyPrefix` | Cache-key namespace.  Default `'rsp:'` so multiple response-caches in the same Redis don't collide. |
| `cacheStatuses` | Which status codes are cacheable.  Default `[200]` — only 2xx responses get cached. |
| `identity(req)` | Optional per-caller scope folded into the key, so a response is only replayed to the caller it was produced for.  Also the opt-in for caching requests that carry credentials — see [what is never shared](#what-is-never-shared).  **Derive it from a verified identity**, never from a raw header. |

## Cache key composition

The `key(req)` function is the entire cache-key contract — what
you include there determines what's cached separately.  Common
patterns:

```ts
// Per-URL-path key:
key: (req) => req.path,

// Per-tenant:
key: (req) => `${req.headers['x-tenant-id'] ?? 'public'}:${req.path}`,

// Per-locale + content type:
key: (req) => `${req.headers['accept-language']}:${req.headers['accept']}:${req.path}`,

// Query-sensitive — the query is NOT part of req.path:
key: (req) => `${req.path}|page=${req.query.page ?? '1'}`,
```

`req.path` is the **pathname only** — `/api/products`, never
`/api/products?page=2`.  An endpoint whose response varies by a query
parameter has to fold that parameter into the key itself; otherwise
every page shares one entry and page 2 is served page 1.

Build the key to be deterministic across equivalent requests
but unique across responses you want cached separately.

## When to cache

```
GET /api/products       → cache (stable, read-heavy)
POST /api/orders        → passes straight through — only GET is stored
GET /api/users/me       → cache only with identity (per-caller scope)
GET /api/feed?cursor=X  → cache (one entry per cursor)
```

The wrapper is a handler-level decision — you choose which
handlers to wrap.  Mutations should typically use
[`idempotent`](/http/middleware/idempotency-key/) instead.

## What is never shared

A cache hit returns **before the wrapped handler runs**.  Any check
inside the handler — authentication, authorization, a per-caller
lookup — therefore runs for the first caller only.  **Authorization
has to wrap `cached(...)`, never sit inside it:**

```ts no-compile — ext, jwtOptions and loadProfile belong to the surrounding application
import { cached, get, JwtAuth, jwtClaimsOf, path, withMiddleware } from 'actor-ts/http';

const profileCache = cached({
  cache:    ext.cache('response-cache'),
  ttlMs:    30_000,
  key:      () => 'users:me',
  identity: (req) => jwtClaimsOf(req)?.sub ?? 'anonymous',
});

// ✓ JwtAuth verifies the token on every request, hit or miss
const routes = withMiddleware(JwtAuth(jwtOptions),
  path('me', get(profileCache(loadProfile))),
);
// ✗ a check inside loadProfile is skipped by every hit
```

Beyond that, the wrapper refuses on its own every case in which one
caller's response could reach another:

| Rule | Why |
| --- | --- |
| Only `GET` is stored; only `GET` and `HEAD` are answered from the cache. | A replayed `POST` is never right.  `HEAD` reads a `GET` entry but never writes one, because a `HEAD` answer may carry no body. |
| A request carrying `Authorization`, `Proxy-Authorization` or `Cookie` bypasses the cache unless `identity` is set. | Nothing else in the key says whose response it is.  Setting `identity` is the explicit opt-in; for an endpoint that genuinely does not depend on the caller, `identity: () => 'public'` says exactly that. |
| A response carrying `Set-Cookie` is not stored. | There is no correct way to hand one caller's cookie to another. |
| `Cache-Control: no-store`, `no-cache` or `private` on the response suppresses storing. | The handler said the response is not for a shared cache. |
| A response carrying `Vary` is stored with the request's values of the named headers and served only to a request with the same values; `Vary: *` is not stored. | The handler said the response depends on those headers. |
| A streaming body is not stored. | A stream is one-shot. |

The same rules govern stampede protection: a request waiting on
another request's in-flight handler takes that response only when it
could have taken it from the cache, and otherwise runs the handler
itself.  `Cache-Control` on the **request** is deliberately ignored — a
client must not be able to force the handler past the cache.

## Cache invalidation

`cached` **doesn't auto-invalidate** on writes — staleness is
bounded by `ttlMs`.

For **stronger consistency**, two patterns:

### Short TTLs

```ts
cached({ cache, ttlMs: 1_000, key });   // 1 second
```

Sub-second TTLs limit staleness.  Good for "real-time-ish" APIs.

### Manual invalidation

```ts
// After a write that affects products:42, invalidate the cache:
await cache.delete('rsp:products:42');   // 'rsp:' is the default keyPrefix
```

The cache is just a `Cache` — you can `delete` the prefixed key
directly when a write should invalidate it.  With `identity` set, the
key is `<keyPrefix><scope>:<key>`, the scope URI-encoded
(`rsp:alice:users:me`).

## Shared cache across pods

```ts
import { RedisCache, RedisCacheOptions } from 'actor-ts/cache';

const redisCacheOptions = RedisCacheOptions.create().withUrl('redis://...');
const productCache = cached({
  cache: new RedisCache(redisCacheOptions),
  ttlMs: 30_000,
  key:   (req) => `products:${pathParam(req, 'id')}`,
});
```

With a Redis-backed cache, all pods share the same cache —
useful for multi-pod deployments where you want consistent
caching.

For **per-pod caches** (each pod has its own InMemoryCache),
pods may serve different cached responses briefly until TTLs
align.  Often acceptable; depends on consistency requirements.

## Caching different status codes

```ts
cached({
  cache, ttlMs: 30_000, key,
  cacheStatuses: [200, 404],   // cache both hits AND "not found"s
});
```

Cache `404`s when you've got many lookups for IDs that don't
exist — saves repeat DB hits.  Defaults to `[200]` only so a
transient 500 never sticks around for 30 seconds.

import { Aside } from '@astrojs/starlight/components';

<Aside type="caution" title="Scope per-caller responses with identity">
  ```ts
  identity: (req) => jwtClaimsOf(req)?.sub ?? 'anonymous',   // ✓ verified
  identity: (req) => req.headers['x-user-id'] ?? 'anonymous', // ✗ client-chosen
  ```
  A response that depends on who is asking must be scoped with
  `identity`, and the scope must come from what a middleware verified.
  A raw header lets any caller claim someone else's scope and read
  their cached response.  Credentialed requests bypass the cache until
  `identity` is set, but a per-caller response to a request that
  carries no credential header — a custom API-key header, say — is
  only kept apart by `identity`.
</Aside>

<Aside type="note" title="Stampede protection is per-process">
  ```ts
  // TTL expires; 1000 concurrent requests on one pod → the handler runs once
  ```
  On a cache miss the wrapper runs the handler **once per process** and
  the other concurrent requests for the same key await that single
  result (an in-process single-flight map).  It is **not** cluster-wide:
  with N pods the handler can run up to N times concurrently.
  Stale-while-revalidate isn't built in — implement it manually if you
  need it.
</Aside>

<Aside type="caution" title="Size the in-memory cache to your response set">
  ```ts
  new InMemoryCache();                        // LRU-bounded: 10 000 entries
  new InMemoryCache({ maxEntries: 100_000 }); // raise it for a larger response set
  ```
  `InMemoryCache` is LRU-bounded by default (10 000 entries), so a
  response cache can't grow without limit — but a too-small cap evicts
  hot responses early.  Size `maxEntries` to the number of distinct
  cache keys you expect.  See [In-memory cache](/cache/in-memory/).
</Aside>

<Aside type="caution" title="This is the key-minting side — don't share the instance">
  ```ts
  const responseCache = new InMemoryCache();   // ✓ this middleware's own instance
  ```
  `key(request)` almost always derives from something the client
  controls — a path parameter, a tenant header — so a caller who varies
  it mints a new entry per request.  Harmless here: the LRU bound is
  exactly what stops the response cache growing without limit.  Every
  one of those entries is a plain `set`, so `InMemoryCache` treats them
  as the cheap victims and drains them before it touches a rate-limit
  counter or a record that stops a payment being taken twice — which is
  what makes this flood survivable in a shared instance at all.  Do not
  rely on it: the bound is still hard, this middleware's entries are
  the only slack the shared map has, and Memcached and Redis under
  `allkeys-lru` have no such policy.  Hand this middleware a dedicated
  instance — or `ext.cache('response-cache')` — rather than the one
  enforcing a guarantee.  Where one instance has to be shared, give it
  a `prefixQuotas` reservation for this middleware's `keyPrefix`, which
  bounds the flood to that share whatever else the map holds:

  ```hocon
  actor-ts.cache.shared.in-memory {
    max-entries   = 10000
    prefix-quotas { "rsp:" = 7000, "idem:" = 2000, "rl:" = 1000 }
  }
  ```

  See
  [what eviction protects and what it does not](/cache/in-memory/#what-eviction-protects-and-what-it-does-not)
  and [dividing one instance by key prefix](/cache/in-memory/#dividing-one-instance-by-key-prefix).
</Aside>
