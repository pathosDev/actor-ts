`ExpressBackend` lets you run actor-ts routes through
**Express** — the most-widely-used Node HTTP framework.  Right
choice when:

- You already have **Express middleware** invested (custom auth,
  session handling, app-specific instrumentation).
- Team familiarity with Express > framework benefits of Fastify.
- You're **incrementally migrating** an existing Express app to
  actor-ts.

```ts
import { ActorSystem } from 'actor-ts';
import { HttpExtensionId } from 'actor-ts/http';
import { ExpressBackend, ExpressBackendOptions } from 'actor-ts/http';

const http = system.extension(HttpExtensionId);

await http.newServerAt('0.0.0.0', 8080)
  .useBackend(new ExpressBackend())
  .bind(routes);
```


## Configuration

```ts
const expressBackendOptions = ExpressBackendOptions.create().withMaxBodyBytes(4 * 1024 * 1024);
new ExpressBackend(
  expressBackendOptions,
);
```

Express-style settings. `maxBodyBytes` defaults to **1 MiB**, the shared
cap every backend applies — raise it only for an endpoint that genuinely
takes more, as above. The server-wide
`actor-ts.http.server.max-content-length` says the same for every backend and
is the one to reach for: a backend built without `withMaxBodyBytes` takes the
key, and one built with a different number is **refused** at `bind()`, naming
both — one server does not hold two body caps, and picking either would leave
the other silently unenforced. The same number in both places binds.

The backend builds the server it listens on — `node:http`, or `node:https`
under `withTls(...)` (see [TLS](#tls)) — handing the app over exactly as
`app.listen()` would, but with the server options `app.listen()` has no way to
take: `max-header-bytes`, when set, is built into it, and a request whose
header block is larger never reaches a handler. The connection-level bounds under
[`actor-ts.http.server`](/reference/configuration/) are installed on the same
server, so they hold here whether the backend was built by the framework or
handed to `useBackend(...)` — including on a bring-your-own app. Express
touches none of them itself, so what applies without configuration is
`node:http`'s own: a 5 s keep-alive window, a 300 s receive deadline and a
16 KiB header cap.

## Behind a reverse proxy

`req.ip` is the socket peer, which is what lands in
`HttpRequest.remoteAddress`. Express can be told to derive it from
`X-Forwarded-For` instead — but only on a **bring-your-own app**
(`app.set(...)`, passed via `.withApp(app)`), because
`ExpressBackendOptions` has no `trustProxy` field.

Prefer [`IpAllowlist`'s `trustedProxies`](/http/middleware/ip-allowlist/)
over that route. It is the same trust-by-address rule, it does not need a
bring-your-own app, and it reads identically on all three backends —
Hono has no trust-proxy concept at all.

import { Aside } from '@astrojs/starlight/components';

<Aside type="danger" title="app.set('trust proxy', true) is not the safe setting">
  ```ts
  app.set('trust proxy', true);     // ✗ returns the client-controlled entry
  ```
  `true` compiles to a trust-everything function, so `proxy-addr` never
  truncates the address list and `req.ip` becomes the **leftmost**
  `X-Forwarded-For` entry — exactly the value the client sent. Every
  common proxy *appends* to that header rather than replacing it, so there
  is no deployment in which `true` is correct. A numeric hop count is
  better but still address-blind: it believes the header on a request that
  passed no proxy at all. A trusted-subnet list is the only form that
  checks who is actually connecting.
</Aside>

## Security headers

Every response this backend writes carries
`X-Content-Type-Options: nosniff` — its error mapping, the `fallback` 404
and the body-too-large 413 included, none of which a middleware sees.
A response's own header still wins.

Configure it **per server, not per backend** — one surface instead of three:

```ts
await http.newServerAt('0.0.0.0', 8080)
  .useBackend(new ExpressBackend())
  .withSecurityHeaders(false)      // or a SecurityHeadersOptions bundle
  .bind(routes);
```

See [Security best practices](/http/security/).

## Adding Express middleware

```ts
import express from 'express';
import { ExpressBackend } from 'actor-ts/http';

const backend = new ExpressBackend();
await http.newServerAt('0.0.0.0', 8080)
  .useBackend(backend)
  .bind(routes);

// Access the raw Express app:
backend.getApp().use(express.session({ secret: '...' }));
backend.getApp().use(expressRateLimitFromNpm);
backend.getApp().use(customAuth);
```

Express middleware **wraps** the actor-ts routes — request
flows through your middleware first, then to the actor-ts
handler.

This is **the main reason to pick Express** over Fastify: the
middleware ecosystem.  If you don't need it, Fastify is faster.

### WebSocket handshakes go through it too

A `websocket()` route is registered as an ordinary Express `GET`,
and the upgrade is dispatched through the app — so `app.use(...)`
runs for the handshake exactly as it runs for a request:

```ts
const backend = new ExpressBackend();
backend.getApp().use(customAuth);          // gates /ws as well

await http.newServerAt('0.0.0.0', 8080)
  .useBackend(backend)
  .bind(websocket('/ws', chat));
```

A middleware that **answers** the request (`res.status(401).end()`)
cancels the handshake: the socket is closed instead of upgraded and
`onClientConnected` never fires.  A middleware that calls `next()`
lets it through to the framework's own upgrade guard
(`withMiddleware()` / `allowedOrigins`), which still has the last
word — see [WebSockets](/http/websocket/).

Two caveats on this path.  A middleware that neither answers nor
calls `next()` leaves the client waiting, the same way it would
stall an ordinary request.  And a rejection's *body* only reaches
the client on runtimes that let a hijacked upgrade socket be written
to — Bun and Node do, Deno does not, where the client sees the
connection close instead.  Either way the handshake is refused.

## TLS

Set it where every backend takes it, on the server options
(see [TLS and HTTP/2](/http/overview/#tls-and-http2)):

```ts
import { readFileSync } from 'node:fs';
import { ExpressBackend, HttpServerOptions } from 'actor-ts/http';

const serverOptions = HttpServerOptions.create()
  .withTls({ cert: readFileSync('./tls/cert.pem'), key: readFileSync('./tls/key.pem') });

await http.newServerAt('0.0.0.0', 8443)
  .useBackend(new ExpressBackend())
  .withServerOptions(serverOptions)
  .bind(routes);
```

The backend then builds its server with `https.createServer`, handing the app
over the way Express's own HTTPS recipe does, so a bring-your-own app changes
nothing: its middleware sees every request, a `websocket()` route upgrades as
`wss://` through that same middleware, and `max-header-bytes` and the
connection-level bounds hold on the TLS server as they do on a plain one. The
header deadline follows each connection into TLS, so a slow-loris is answered
`408` inside it. Deno is the exception, as it is for plain HTTP: its `node:http`
and `node:https` emit none of the connection events the guards rest on and
ignore the header cap, so there neither the header deadline, `max-connections`
nor `max-header-bytes` holds, and `bind()` warns about a set `header-timeout` or
`max-header-bytes`. `requestClientCert` becomes `node:tls`'s `requestCert` and
`rejectUnauthorized` passes through, as on the Hono backend under Node. The
demand needs a `ca` to verify against: without one `bind()` refuses it, on
every backend, because `node:tls` would otherwise check client certificates
against the runtime's default trust store and admit any certificate a public
CA issued. On Deno a client-certificate demand is **refused** at `bind()`
either way, because Deno's `node:https` accepts the option and enforces
nothing — measured on deno 2.6.8, a client presenting no certificate was
answered.

**HTTP/2 is refused.** `withHttp2()` fails at `bind()` rather than answering
HTTP/1.1 under a setting that says h2. Express reassigns every request and
response onto `node:http`'s own prototypes, and the compatibility objects of
`node:http2` do not survive that: measured with express 5.2.1 behind
`http2.createSecureServer({ allowHTTP1: true })`, an h2 request was negotiated
and never answered on node v26.10.0 and bun 1.4.2, while HTTP/1.1 on the same
port was; deno 2.6.8 does not implement `http2.createSecureServer` at all. For
HTTP/2, use the [Fastify](/http/backends/fastify/#tls) or
[Hono](/http/backends/hono/) backend.

Wrapping a bring-your-own app in `https.createServer(…, app)` yourself, as
earlier versions of this page did, still does not work: the backend listens on
a server of its own, so that wrapper never receives a connection.
`withTls(...)` is the way in.

Behind a reverse proxy, an ingress or a load balancer that terminates TLS for
you, leave `tls` unset and let the backend speak plain HTTP behind it — still
how most production setups run.

## Peer dependency

```bash
npm install express
# or: bun add express
```

For Express 5+ recommendation; older versions may work but
aren't tested.

## Performance

Rough numbers:

- **40K-60K req/sec** for trivial routes (slower than Fastify).
- **P50 latency** similar; throughput differs.

Express's middleware chain has more overhead than Fastify's
hooks.  For high-throughput paths, prefer Fastify; for paths
gated by heavy middleware, the framework choice doesn't matter
much.

## Migrating from existing Express app

If you have an existing Express app and want to add actor-ts:

```ts
import express from 'express';
import { ExpressBackend, ExpressBackendOptions } from 'actor-ts/http';

const app = express();

// Existing routes + middleware stay as-is:
app.use('/legacy', oldLegacyRouter);

// Hand the existing app to the backend; actor-ts registers its
// routes on the same app, alongside your existing ones.
const expressBackendOptions = ExpressBackendOptions.create().withApp(app);
const backend = new ExpressBackend(expressBackendOptions);

await http.newServerAt('0.0.0.0', 8080)
  .useBackend(backend)
  .bind(routes);
```

Pass your existing app to the backend via `.withApp(app)` —
actor-ts registers its routes on the same app, so your existing
routes and middleware keep working without swapping the whole
HTTP stack.

<Aside type="caution" title="Express vs Fastify benchmarks">
  ```ts
  // Choose Express because "it's simpler"
  ```
  Both are simple from an actor-ts perspective.  Fastify is
  faster.  Express has more middleware.  Pick by **what
  middleware you need**, not by perceived simplicity.
</Aside>

<Aside type="caution" title="Async error handling">
  ```ts
  app.use((req, res, next) => {
    asyncWork().then(...);   // ✗ unhandled rejection
  });
  ```
  Express's default error handling is synchronous-friendly.
  For async middleware, use `express-async-errors` or wrap
  manually.  The actor-ts routes themselves handle async
  cleanly; this is about your custom middleware.
</Aside>
