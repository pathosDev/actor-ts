[Hono](https://hono.dev/) is a **runtime-agnostic** HTTP
framework — the same code runs on Bun, Node, Deno, Cloudflare
Workers, AWS Lambda, Vercel, etc.  `HonoBackend` wraps it for
actor-ts.

```ts
import { ActorSystem } from 'actor-ts';
import { HttpExtensionId } from 'actor-ts/http';
import { HonoBackend, HonoBackendOptions } from 'actor-ts/http';

const http = system.extension(HttpExtensionId);

await http.newServerAt('0.0.0.0', 8080)
  .useBackend(new HonoBackend())
  .bind(routes);
```

## When to use Hono

Hono is the right pick when:

- **Edge / serverless** — Cloudflare Workers, Vercel Edge,
  Deno Deploy.  Hono is one of the few HTTP frameworks that
  works in those environments.
- **Cross-runtime portability** — same code on Bun + Node + Edge.
- **Minimal overhead** — Hono is lighter than Fastify, faster
  than Express.

For a typical long-running production server, **Fastify is
usually preferable** — bigger plugin ecosystem, more
production hours.  Hono shines when "runs in many places" is a
hard requirement.

## Cross-runtime + serverless caveat

```ts
// On a long-running VM: this works
await http.newServerAt('0.0.0.0', 8080)
  .useBackend(new HonoBackend())
  .bind(routes);

// On Cloudflare Workers: there's no "newServerAt(host, port)"
//   The runtime invokes a handler per request.
```

`HonoBackend` exposes its underlying `Hono` instance:

```ts
const backend = new HonoBackend();
const honoApp = backend.getApp();   // ← export to the edge runtime
```

In Cloudflare Workers:

```ts
// worker.ts
export default { fetch: honoApp.fetch };
```

The framework's actor-ts side then runs **in-memory inside the
isolate** — short-lived, no clustering, no persistence.  Useful
for stateless request-handling logic that benefits from actor
patterns (state machines, validation pipelines).

For long-running actor systems with cluster + persistence,
**don't run on edge runtimes** — they're isolate-per-request,
not long-lived processes.

## Configuration

```ts
// Hono itself has minimal config; most settings come via routes / middleware.
// The request-body cap defaults to 1 MiB, as on every backend; raise it
// with HonoBackendOptions where an endpoint takes more:
const honoBackendOptions = HonoBackendOptions.create().withMaxBodyBytes(4 * 1024 * 1024);
new HonoBackend(honoBackendOptions);
```

The server-wide `actor-ts.http.server.max-content-length` sets the same cap
without touching the backend, and it holds on **every** runtime this backend
runs on: the body is read by this backend's own code, so Bun and Deno count it
exactly as Node does — a declared length over it is refused before a byte is
read, a chunked body is abandoned once it crosses it. A backend built with a
different `withMaxBodyBytes` is refused at `bind()`, naming both.

:::caution[Most of `actor-ts.http.server` reaches this backend on Node only]
The connection-level bounds — `idle-timeout`, `header-timeout`,
`request-timeout`, `max-connections` — are properties of a `node:http` server,
and Hono owns no server of its own: it delegates to a runner per runtime.
Only `@hono/node-server` hands its `node:http` server back, so on **Deno none
of the four is installed at all**, and on **Bun only `idle-timeout`** is —
through `Bun.serve`'s own `idleTimeout`, below. Nothing is written and nothing
pretends to have been, and `bind()` names each one you set that did not take in
a warning.

`max-header-bytes` is the same split by another route. On Node the runner
builds it into `@hono/node-server`'s server, and a request whose header block
is larger never reaches a handler. `Bun.serve` and `Deno.serve` take no
per-server header cap, so there it is reported not in effect and warned about
too: Bun's cap is the process-wide `--max-http-header-size`, 16 KiB unless the
process was started with another, and `Deno.serve` accepted a 256 KiB header
block (deno 2.6.8).

It is the same shape as the WebSocket transport frame cap on this page: a knob
the runtime does not expose is reported as absent rather than approximated.
Use the Fastify or Express backend where these bounds matter, or set them at
the reverse proxy in front.

On Bun, `idle-timeout` is `Bun.serve`'s own `idleTimeout`, and that is a
**whole-connection** bound rather than a keep-alive window: a connection is
closed once it has been silent that long, and a request whose handler has not
written a byte yet counts as silent. So on Hono under Bun a long poll, an SSE
stream with sparse events or a slow handler has to write within the idle
timeout, or is closed without a response. It counts whole seconds — a value is
rounded up, so it never becomes the `0` that disables it — and Bun checks it on
a 4 s sweep, so a connection can be closed up to one sweep early. Above `255s`
it fails `bind()`, naming the key: `Bun.serve` holds no more. An idle HTTP/2
session is closed by it too.

Unset, it is not Bun's own 10 s, which closed any request silent for about
12 s. The backend derives it from the server's longest request deadline —
`actor-ts.http.request-timeout.deadline`, raised to the longest
`requestTimeout()` in the route tree — so that the `503` is written before the
connection is cut: **36 s for the built-in 30 s deadline**. Past a deadline of
about 250 s the timeout is held at `255s`, which no longer covers it, and
`bind()` says so in a warning. On Deno none of this exists: `Deno.serve` has no
idle knob, and `idle-timeout` is reported not installed there.
:::

## Security headers

Every response this backend writes carries
`X-Content-Type-Options: nosniff` — its error mapping, the `fallback` 404
and the body-too-large 413 included, none of which a middleware sees.
A response's own header still wins.

Configure it **per server, not per backend** — one surface instead of three:

```ts
await http.newServerAt('0.0.0.0', 8080)
  .useBackend(new HonoBackend())
  .withSecurityHeaders(false)      // or a SecurityHeadersOptions bundle
  .bind(routes);
```

See [Security best practices](/http/security/).

## Hono middleware

```ts
import { logger, cors, secureHeaders } from 'hono/middleware';

const backend = new HonoBackend();
await http.newServerAt('0.0.0.0', 8080)
  .useBackend(backend)
  .bind(routes);

backend.getApp().use('*', logger());
backend.getApp().use('/api/*', cors());
backend.getApp().use('*', secureHeaders());
```

Hono's middleware ecosystem is smaller than Express's but
covers the common cases — CORS, security headers, JWT auth,
basic auth, compression.  For JWT verification that behaves the
same on every backend, use the portable
[`JwtAuth`](/http/middleware/jwt/) instead of Hono's own.

## Performance

Rough numbers:

- **100K-150K req/sec** on Bun for trivial routes.
- **Slightly slower than Fastify** on Node.
- **Edge runtime numbers** depend on the platform (Cloudflare
  Workers: ~50K req/sec per worker; throttled by the
  platform).

## Edge runtime caveats

import { Aside } from '@astrojs/starlight/components';

<Aside type="caution" title="Edge runtime + actor-ts cluster">
  ```ts
  // Cloudflare Workers + cluster.join()
  ```
  Edge runtimes don't support outbound TCP connections (or
  only via specific platforms-specific APIs).  Cluster join
  fails.  Don't try to cluster on edge — use actor-ts as a
  library inside the request lifecycle only.
</Aside>

<Aside type="caution" title="In-memory state across requests">
  ```ts
  // Two Cloudflare Worker invocations: different isolates
  // → in-memory actor state doesn't share
  ```
  Edge isolates are **per-request** (or shared briefly for
  warm-up).  Don't expect state to persist between requests.
  For state, use external storage (KV, D1, etc.).
</Aside>

<Aside type="caution" title="Long-running actors in edge isolates">
  ```ts
  // Spawn an actor that should live for hours
  ```
  Edge runtimes time out (Cloudflare: 30 s wall clock).
  Long-running actors don't fit.  Use for short-lived
  per-request actor patterns only.
</Aside>

## TLS and HTTP/2

Set on the server options like every backend
(see [TLS and HTTP/2](/http/overview/#tls-and-http2)); Hono hands the pair
to whichever runtime it is on:

| Runtime | TLS | `http2: true` |
| --- | --- | --- |
| Bun | `Bun.serve({ tls })` | `Bun.serve({ http2: true })` — h2 through ALPN, HTTP/1.1 kept; Bun ≥ 1.4.1, refused on an older one |
| Node | `https.createServer` under `@hono/node-server` | `http2.createSecureServer` with `allowHTTP1` |
| Deno | `Deno.serve({ cert, key })` | negotiated whenever TLS is on; no knob, so the flag records intent |

Client-certificate verification (`requestClientCert`) reaches the Bun and
Node sockets; `Deno.serve` has no client-auth option, so on Deno it is
**refused** at bind rather than accepted and not applied. It needs a `ca` to
verify against: without one, bind refuses it on every runtime, because the
TLS stack would otherwise check client certificates against the runtime's
default trust store and admit any certificate a public CA issued.
