---

actor-ts verwendet **HOCON** zur Konfiguration — eine Obermenge von
JSON, die in JVM-Config-Dateien üblich ist, mit Substitutionen,
Durations und Sizes.  ([`include`-Direktiven werden
abgelehnt](#includes-werden-nicht-unterstützt) — setze die Quellen im
Code zusammen.)  Drei Schichten, von oben nach unten aufgelöst:

1. **Konstruktor-Argumente** an `ActorSystem.create(name, settings)`
   — explizite Code-Overrides.
2. **Nutzer-Config** — `application.conf` im Projekt-Root, oder ein
   expliziter Pfad via `configFile`, oder ein inline `config`-Objekt
   in den Settings.
3. **Reference-Defaults** — im Framework gebündelt als
   `REFERENCE_CONF` (siehe `src/config/reference.ts`).

Alles, was nicht in Schicht 1 oder 2 spezifiziert ist, fällt auf
den Reference-Default zurück.

Diese Seite erklärt, was die einzelnen Keys *tun*.  Die vollständige
Liste — jede Einstellung, die das Framework mitbringt, wörtlich aus der
gebündelten Datei — steht unter
[Die vollständige reference.conf](/de/reference/reference-conf/).

## Eine vollständige `application.conf`

```hocon
actor-ts {
  system { name = "my-app" }
  logger { level = "info" }

  dispatcher {
    default    = "immediate"   # immediate | microtask | throughput
    throughput = 16
  }

  cluster {
    gossip-interval     = 1s
    seed-retry-interval = 3s
    weakly-up-after     = 0s      # 0 = opt-in only
    max-members         = 1000
    max-tombstones      = 10000
    tombstone {
      time-to-live   = 24h
      prune-interval = 5m
      min-retention  = 0s         # 0 = derive from down-after
    }
    failure-detector {
      implementation     = simple   # simple | phi
      heartbeat-interval = 500ms    # shared by both implementations
      unreachable-after  = 2s
      down-after         = 5s
      phi {
        unreachable-threshold      = 8
        down-threshold             = 12
        max-sample-size            = 200
        min-std-deviation          = 100ms
        acceptable-heartbeat-pause = 0s
      }
    }
    pub-sub {
      gossip-interval            = 1s
      max-subscribers-per-topic  = 10000
      max-topics                 = 10000
      max-remote-nodes-per-topic = 1000
      send-to-dead-letters-when-no-subscribers = on
    }
    receptionist {
      gossip-interval         = 1s
      max-subscribers-per-key = 1000
      max-subscriptions-total   = 10000
    }
  }

  distributed-data {
    gossip-interval             = 1s
    max-pending-quorum-requests = 1000    # 0 = kein Cap
    max-quorum-timeout          = 30s     # 0 = keine Obergrenze
    max-gossip-bytes            = 1M      # pro Gossip-Frame; 0 = kein Budget
  }

  remote {
    tcp {
      host = "0.0.0.0"
      port = ${?ACTOR_TS_PORT}   # Env-Var-Substitution; fällt auf Default zurück
    }
    max-frame-bytes = 16M
  }

  persistence {
    journal        { plugin = "actor-ts.persistence.journal.in-memory"        }
    snapshot-store { plugin = "actor-ts.persistence.snapshot-store.in-memory" }
  }

  sharding {
    number-of-shards           = 64
    role                       = ""       # "" = unrestricted; names a role, never grants one
    rebalance-interval         = 2s
    hand-off-timeout           = 10s
    acquire-retry-interval     = 5s       # retry a failed coordinator lease acquire
    remember-entities          = false
    passivation-idle           = 5m       # 0 deaktiviert die Auto-Passivierung
    # shard-passivation-idle              # ungesetzt: folgt passivation-idle
    max-entities               = 0        # 0 = kein Cap pro Node
    buffer-size                = 100000   # regionsweit; 0 = niemals puffern
    register-retry-interval    = 500ms
    shard-region-query-timeout = 5s
    entity-recovery {                     # wie erinnerte Entities zurückkommen
      strategy = all                      # all | constant-rate
      constant-rate.frequency = 100ms
      constant-rate.number-of-entities = 5   # regionsweit, nicht pro Shard
    }
  }
}
```

Platziere das im Projekt-Root.  Das Framework lädt es bei
`ActorSystem.create` automatisch.

## Die Keys, gruppiert nach Modul

### `actor-ts.system`

| Key | Default | Zweck |
| --- | --- | --- |
| `system.name` | `"default"` | Systemname — verwendet in Actor-Pfaden und zur Cluster-Identifikation.  Greift, wenn `ActorSystem.create()` ohne Namen aufgerufen wird; ein explizites `create('billing')` gewinnt. |
| `system.shutdown-drain-timeout` | `2s` | Wie lange `terminate()` den Actors unter `/user` gibt, die eingereihte Arbeit zu beenden, bevor die Stop-Kaskade startet.  Kehrt zurück, sobald der Baum ruhig ist — ein untätiges System zahlt einen Tick.  Halte den Wert unter `coordinated-shutdown.default-phase-timeout`; `0` schaltet den Drain ab. |

### `actor-ts.logger`

| Key | Default | Zweck |
| --- | --- | --- |
| `logger.level` | `"info"` | Einer von `debug` / `info` / `warn` / `error` / `off`. |

### `actor-ts.actor`

| Key | Default | Zweck |
| --- | --- | --- |
| `actor.throughput` | `16` | User-Nachrichten, die **ein** Actor pro Dispatcher-Turn vor dem Yield abarbeitet.  Pro Actor überschreibbar mit `ActorOptions.withThroughput()`. |

### `actor-ts.diagnostics`

| Key | Default | Zweck |
| --- | --- | --- |
| `diagnostics.log-dead-letters` | `10` | Dead Letters, die vollständig geloggt werden, bevor das Logging aussetzt.  `0` schaltet das Dead-Letter-Logging ganz ab.  Erfasst und auf dem Event-Stream publiziert wird jedes Letter ohnehin — das hier steuert nur die Log-Zeile. |
| `diagnostics.log-dead-letters-during-shutdown` | `off` | Den Schwall loggen, den `terminate()` beim Leeren der Mailboxen in die Dead Letters erzeugt.  Aus, weil ein geordnetes Herunterfahren jede eingereihte und gestashte Nachricht so entsorgt; ein einzelnes `ref.stop()` loggt weiterhin, denn das System terminiert nicht. |
| `diagnostics.log-dead-letters-suspend-duration` | `5m` | Wie lange das Logging aussetzt, sobald die Anzahl oben erreicht ist.  `0` setzt nie aus — so schreibt man „jedes Dead Letter loggen“. |
| `diagnostics.log-config-on-start` | `off` | Schreibt die zusammengeführte Konfiguration einmal beim Start ins Log — ein `info`-Eintrag, jeder Key mit der Schicht, die ihn gesetzt hat, nach Pfad sortiert.  Die Antwort auf „warum steht die Einstellung nicht so, wie ich sie geschrieben habe“.  Vor dem Einschalten den Hinweis zur Schwärzung unten lesen. |
| `diagnostics.debug.unhandled` | `off` | Ein `debug`-Eintrag pro Nachricht, die ein Actor entgegengenommen und abgelehnt hat: Empfängerpfad, Nachrichtenklasse, Sender.  Der Zähler (`actor_unhandled_total`) und das Dead Letter entstehen ohnehin. |
| `diagnostics.debug.lifecycle` | `off` | Ein `debug`-Eintrag pro Start, Stopp und Neustart eines Actors.  `ActorStarted` / `ActorStopped` / `ActorRestarted` tragen dieselben Fakten zu einem Subscriber auf dem Event-Stream, der selektiv sein kann — was ein Log-Level nicht kann. |
| `diagnostics.debug.event-stream` | `off` | Ein `debug`-Eintrag pro Subscribe und Unsubscribe auf dem Event-Stream — nie pro Publish, das bei jedem Actor-Start, jedem Stopp und jedem Dead Letter läuft.  Ein Unsubscribe über alle Kanäle, das nichts entfernt hat, wird nicht protokolliert; jeder Actor-Stopp erzeugt eines. |

Der Eintrag nennt den Empfängerpfad, den Sender sofern bekannt und die Klasse
der Nachricht — nie die Payload, aus demselben Datenschutzgrund, aus dem
`dead-letters.store` auf `off` steht.  Jeder Key hier ist auch im Code
setzbar, feldweise, über `ActorSystemOptions.withDiagnostics(…)`.  Siehe
[Dead Letters](/de/operations/dead-letters/) für das ganze Bild.

**Die `debug.*`-Keys brauchen zwei Schalter, nicht einen.**  Der Key
entscheidet, ob ein Eintrag entsteht; `logger.level = debug` entscheidet, ob
er geschrieben wird.  Nur einen von beiden zu setzen sieht exakt so aus wie
ein Schalter, der nicht funktioniert.  `log-config-on-start` gehört
absichtlich nicht zu dieser Familie — es ist ein `info`-Eintrag, denn wer
einen Konfigurations-Dump anfordert, hat um Ausgabe gebeten.

**Was der Dump schwärzt und was nicht.**  Ein Wert wird zurückgehalten, wenn
sein **Key-Name** auf `pass`, `secret`, `token`, `key`, `credential` oder
`auth` passt — `cache.redis.password` und ein `api-key` erscheinen also als
`<redacted>`.  Das ist eine Heuristik über Key-Namen und die schwächere
Hälfte der Zusage: Ein Geheimnis, dessen Key es nicht verrät — ein `dsn`, ein
`connection-string`, eine `uri` mit Passwort darin — kann sie nicht fassen,
denn wenn der zusammengeführte Baum existiert, ist ein
`${?DATABASE_PASSWORD}` längst zu einer gewöhnlichen Zeichenkette aufgelöst,
der man ihre Herkunft nicht mehr ansieht.  Die Liste wird auch nicht weiter
gefasst: `seed` würde `cluster.seed-nodes` schwärzen, und ein Dump, dessen
gewöhnliche Keys `<redacted>` lauten, wird nicht mehr gelesen.  Behandle die
Ausgabe also als vertraulich, lass den Key außerhalb einer Untersuchung auf
`off`, und sieh nach, wie deine eigenen Keys heißen, bevor du einen Dump in
ein Ticket kopierst.  Dieselbe Regel, dieselbe Liste und dieselben Grenzen
gelten für das Konfigurations-Panel der DevTools.

### `actor-ts.mailbox`

| Key | Default | Zweck |
| --- | --- | --- |
| `mailbox.default.capacity` | `0` | Begrenzt jeden Actor unter `/user` auf so viele eingereihte User-Nachrichten, ohne eine Spawn-Stelle anzufassen.  `0` heißt: keine globale Schranke — das ist das ausgelieferte Verhalten.  Das hier ist also kein Nachjustieren, sondern der Schalter, der für alle Anwendungs-Actors auf einmal Nachrichtenverlust einführt. |
| `mailbox.default.overflow` | `"drop-head"` | Systemweite Policy für **jede** begrenzte Mailbox: die globale Schranke oben und jeden Actor, der `withMailboxCapacity()` setzt, ohne eine eigene Policy zu nennen.  `drop-head` / `drop-new` / `reject`. |

Die Schranke erreicht ausschließlich echte Nachfahren von `/user`.  Die
eigenen Actors des Frameworks leben unter `/system` — Shard-Regions, der
Pub-Sub-Mediator, der Reliable-Delivery-Producer, der DevTools-Hub — und ihren
Verkehr abzuwerfen würde Invarianten brechen, nach denen die Anwendung nie
gefragt hat und die sie nicht sieht.  Eine Spawn-Stelle sticht beide Keys:
`ActorOptions.withMailboxCapacity()` überschreibt die Kapazität,
`withMailbox()` ersetzt die Queue vollständig.

Lies [Mailbox-Dimensionierung](/de/operations/tuning/mailbox-sizing/), bevor
du das einschaltest.  Es ist der einzige Key in dieser Datei, der eine
Nachricht in einem Actor verlieren kann, dessen Code nichts über eine Mailbox
sagt — und die Seite nennt die beiden Fälle, `WebsocketServerActor` und seine
Connections, in denen eine pauschale Schranke weiterhin erreichbar ist, weil
User-Code sie spawnt.

### `actor-ts.dispatcher`

| Key | Default | Zweck |
| --- | --- | --- |
| `dispatcher.default` | `"immediate"` | `immediate` (Default) / `microtask` / `throughput`. |
| `dispatcher.throughput` | `16` | Eingereihte Actor-**Turns**, die ein `ThroughputDispatcher` pro Tick abarbeitet, über Actors hinweg — keine Nachrichten und nicht pro Actor.  Siehe `actor.throughput` oben für den Per-Actor-Batch. |

### `actor-ts.dead-letters`

| Key | Default | Zweck |
| --- | --- | --- |
| `dead-letters.store` | `"off"` | Geordnet danach, wie viel aufbewahrt wird: `off` = nur publishen, nichts aufbewahren / `metrics` = zählen, keine Payload aufbewahren / `memory` = ein begrenzter Ring / `persistent` = zusätzlich ins Journal schreiben, sodass die Queue einen Neustart übersteht. |
| `dead-letters.max-entries` | `1000` | Aufbewahrte Letters, bevor das älteste verdrängt wird.  Von `off` und `metrics` ignoriert, die keine aufbewahren. |
| `dead-letters.retention` | `1h` | Letters nach dieser Zeit altern lassen.  `0` schaltet das Altern ab und lässt `max-entries` als einzige Schranke. |
| `dead-letters.max-replays` | `3` | Wie oft ein Letter erneut zugestellt werden darf, bevor es in Quarantäne kommt. |
| `dead-letters.persistence-id` | `""` | Journal-Stream, in den der `persistent`-Store schreibt.  Leer leitet ihn aus dem Systemnamen ab, sodass zwei Systeme mit gemeinsamem Journal getrennte Queues behalten. |

Jeder Key hier ist auch im Code setzbar, feldweise, über
`ActorSystemOptions.withDeadLetters(…)` — was diesen Block überstimmt, wie
explizite Options es immer tun. Siehe [Dead
Letters](/de/operations/dead-letters/) dafür, was die Queue enthält und wie
man daraus erneut zustellt.

### `actor-ts.cluster`

| Key | Default | Zweck |
| --- | --- | --- |
| `cluster.gossip-interval` | `1s` | Wie oft Gossip mit einem zufälligen Peer ausgetauscht wird. |
| `cluster.seed-retry-interval` | `3s` | Wie oft Seed-Verbindungen während des Joins wiederholt werden. |
| `cluster.weakly-up-after` | `0s` | Befördert ein `joining`-Mitglied nach dieser Zeit automatisch zu `weakly-up`.  `0` schaltet das ab — siehe [Weakly-up](/de/cluster/weakly-up/). |
| `cluster.max-members` | `1000` | Obergrenze für lebende Mitgliedseinträge, die Gossip anlegen darf.  `0` schaltet die Grenze ab. |
| `cluster.max-tombstones` | `10000` | Obergrenze für `removed`-Tombstones, die Gossip anlegen darf.  `0` schaltet die Grenze ab. |
| `cluster.tombstone.time-to-live` | `24h` | Wie lange ein `removed`-Tombstone gehalten wird, bevor er gepruned wird. |
| `cluster.tombstone.prune-interval` | `5m` | Wie oft der Prune-Durchlauf läuft. |
| `cluster.tombstone.min-retention` | `0s` | Mindestalter, bevor ein Tombstone gepruned werden darf.  `0` leitet es aus `failure-detector.down-after` ab (6×). |
| `cluster.failure-detector.implementation` | `simple` | Welchen Erkennungsalgorithmus dieser Node fährt — `simple` (Zeitschwellen) oder `phi` (varianzbewusstes φ-Accrual). |
| `cluster.failure-detector.heartbeat-interval` | `500ms` | Wie oft Heartbeats gesendet werden.  Gilt für beide Implementierungen — siehe unten. |
| `cluster.failure-detector.unreachable-after` | `2s` | Verdachtsschwelle für `unreachable`-Status.  Nur `simple`. |
| `cluster.failure-detector.down-after` | `5s` | Verdachtsschwelle für erzwungenes Down.  Wird ab dem letzten Heartbeat gemessen, muss also größer als `unreachable-after` sein.  Nur `simple`. |
| `cluster.failure-detector.phi.unreachable-threshold` | `8` | φ-Wert, ab dem der Peer als `unreachable` gilt.  Ein kontinuierlicher Score, Nachkommastellen sind also erlaubt. |
| `cluster.failure-detector.phi.down-threshold` | `12` | φ-Wert, ab dem der Peer als `down` gilt.  Muss größer als `phi.unreachable-threshold` sein. |
| `cluster.failure-detector.phi.max-sample-size` | `200` | Wie viele jüngste Zwischenankunftszeiten pro Peer behalten werden. |
| `cluster.failure-detector.phi.min-std-deviation` | `100ms` | Untergrenze für die gemessene Standardabweichung, damit ein sehr gleichmäßiger Peer nicht wegen Rauschen auffällt. |
| `cluster.failure-detector.phi.acceptable-heartbeat-pause` | `0s` | Kulanz auf den letzten Heartbeat, bevor φ zu steigen beginnt. |
| `cluster.split-brain-resolver.active-strategy` | `off` | Welche Downing-Strategie eine Partition entscheidet — `off`, `keep-majority`, `keep-oldest`, `keep-referee` oder `static-quorum`. |
| `cluster.split-brain-resolver.keep-majority.role` | `""` | Nur Mitglieder mit dieser Rolle zählen zur Mehrheit.  `""` zählt alle. |
| `cluster.split-brain-resolver.keep-oldest.role` | `""` | Nur Mitglieder mit dieser Rolle kommen als „ältestes“ infrage.  `""` betrachtet alle. |
| `cluster.split-brain-resolver.static-quorum.role` | `""` | Nur Mitglieder mit dieser Rolle zählen zum Quorum.  `""` zählt alle. |
| `cluster.split-brain-resolver.static-quorum.quorum-size` | *(ungesetzt)* | Wie viele erreichbare Mitglieder nötig sind, um weiterzulaufen.  Von `static-quorum` verlangt; in `reference.conf` nur als Kommentar — siehe unten. |
| `cluster.split-brain-resolver.keep-referee.referee-address` | *(ungesetzt)* | Adresse des Referee-Nodes; die Seite mit ihm gewinnt.  Von `keep-referee` verlangt; nur als Kommentar. |
| `cluster.split-brain-resolver.keep-referee.down-all-if-below-quorum` | *(ungesetzt)* | Alle downen, wenn die Referee-Seite kleiner als dieser Wert ist.  Optional; nur als Kommentar. |
| `cluster.configuration-compatibility-check.enforce` | `off` | Was eine Abweichung bewirkt, über das Melden hinaus.  `on` schließt den abweichenden Peer zusätzlich aus den Platzierungskandidaten dieses Nodes aus — siehe unten. |
| `cluster.configuration-compatibility-check.checked-paths` | `["actor-ts.remote.max-frame-bytes"]` | Einstellungen, deren **effektive** Werte dieser Node an seine Peers veröffentlicht und mit deren Werten vergleicht. |

Diese Keys liegen unter dem, was `Cluster.join(system, options)` übergibt —
ein explizites `withGossipIntervalMs(…)` gewinnt also weiterhin.  Der
Failure Detector wird *pro Schwelle* gemergt: setzt du im Code nur
`down-after`, bleiben die beiden anderen aus der Datei erhalten.  Der
`phi`-Block wird genauso feldweise gegen `withPhiAccrual(…)` gemergt.

`heartbeat-interval` steht bewusst außerhalb von `phi` und hat dort keine
Kopie.  Die Kadenz gehört zur Heartbeat-Schleife des Clusters und nicht zu
einem der beiden Algorithmen; ein Wechsel von `implementation` darf also
nicht ändern, wie oft dieser Node mit seinen Peers spricht.  Alles Übrige
unter `failure-detector` gehört genau einer Implementierung und wird von der
anderen ignoriert.

HOCON-Baum und `ClusterOptions`-Felder sind bewusst nicht deckungsgleich:
die drei Tombstone-Stellschrauben stehen unter `tombstone`, weil man sie so
einstellt, während die Felder flach bleiben (`withTombstoneTtlMs(…)`, …).
`remote.tcp.host` → `host` macht dieselbe Übersetzung schon länger.

`min-retention = 0s` heißt *leite die Untergrenze aus dem Failure Detector
ab*, nicht *keine Untergrenze* — also genau das, was ein ungesetztes Feld
bedeutet.  Eine Datei, die den Default ausschreibt, verhält sich damit wie
eine, die ihn wegläßt.

Die beiden `max-*`-Grenzen begrenzen die lokale Mitgliederkarte.
`remote.max-frame-bytes` begrenzt *einen* Gossip-Frame; diese begrenzen,
was eine Folge wohlgeformter Frames ansammeln kann — eine andere Größe,
siehe [Cluster-Sicherheit](/de/operations/security/cluster-security/).

`split-brain-resolver.active-strategy` *benennt* eine Strategie, statt sie
zu beschreiben — deshalb braucht das gebaute Objekt keine eigene
HOCON-Form.  Der konstruierte Provider landet in demselben Slot, den
`withDowning(…)` füllt, und es gilt dieselbe Präzedenz: ein explizites
`withDowning(…)` gewinnt, ein fehlendes fällt auf die Datei durch.  Was
jede Strategie entscheidet, steht unter
[Downing-Strategien](/de/cluster/downing-strategies/).

Drei ihrer Keys stehen in `reference.conf` **nur als Kommentar** und sind
damit abwesend, bis du sie schreibst.  Jeder ist erforderlich oder
begrenzt und hat keinen legalen Default: `quorum-size = 0` und
`referee-address = ""` werden von den Validatoren der Strategien
abgelehnt, ein ausgelieferter Leaf könnte also nur ein Wert sein, der den
Node am Starten hindert.  `static-quorum` ohne `quorum-size` oder
`keep-referee` ohne `referee-address` wird beim Start abgelehnt — mit dem
fehlenden Key in der Meldung.

`lease-majority` ist hier **nicht** wählbar.  Es entscheidet über ein
lebendes `Lease`, dessen `owner` die eigene Adresse dieses Nodes ist, und
kein Key kann eines benennen — `actor-ts.coordination` stellt Leases ein,
wählt aber kein Backend.  Baue es im Code:
`withDowning(new LeaseMajority(…))`.  Wer den Namen trotzdem in diesen Key
schreibt, bekommt eine Ablehnung statt stillen Ignorierens.

`configuration-compatibility-check` vergleicht **effektive** Werte, keine
Config-Werte.  Jeder Node veröffentlicht, was er für jede Einstellung aus
`checked-paths` tatsächlich aufgelöst hat, und vergleicht das mit dem, was
seine Peers veröffentlichen — so werden auch zwei Nodes erwischt, die sich
nur unterscheiden, weil einer `.withMaxFrameBytes(…)` gerufen hat.  Ein
Vergleich des Config-Baums könnte das nicht: eine explizite Option liegt
darüber.  `checked-paths` ist eine Erlaubnisliste dessen, was den Node
*verlässt* — eine Einstellung, die nicht darin steht, wird nie gegossipt;
und nur Namen, die auch jemand veröffentlicht, lassen sich vergleichen.  Das
Framework veröffentlicht drei davon (siehe
[Joining und Seeds](/de/cluster/joining-and-seeds/)).  Abwesenheit auf einer
der beiden Seiten ist Schweigen, damit ein Cluster mit gemischten Versionen
nichts meldet statt alles.

`enforce = on` schließt den abweichenden Peer aus den Platzierungskandidaten
dieses Nodes aus — und sonst nichts.  Es downed oder quarantäniert niemanden:
eine falsch konfigurierte *Mehrheit* würde dann die korrekt konfigurierte
Minderheit verdrängen, und aus einer Warnung würde ein Ausfall.  Die
Kandidatenmenge ist außerdem eine Sicht pro Node, deshalb liest nichts, das
eine Rolle *wählt* (der Host eines Singletons, das Zuhause eines Shards),
daraus — sonst wählten zwei Nodes zwei Gewinner.

`seeds`, `roles` und der Transport haben keine HOCON-Form — die ersten
beiden sind Deployment-Identität, die an die Join-Stelle gehört, und der
Transport ist ein Objekt, das eine Config-Datei nicht ausdrücken kann.

### `actor-ts.cluster.pub-sub`

| Key | Default | Zweck |
| --- | --- | --- |
| `cluster.pub-sub.gossip-interval` | `1s` | Wie oft ein Mediator seine Topic-Menge an einen zufälligen Peer schickt. |
| `cluster.pub-sub.max-subscribers-per-topic` | `10000` | Obergrenze für lokale Subscriber eines Topics.  Ein `Subscribe` darüber wird mit `SubscribeRejected` beantwortet. |
| `cluster.pub-sub.max-topics` | `10000` | Obergrenze für verschiedene Topics eines Mediators — gilt für gegossipte Topic-Ansprüche genauso wie für lokale Subscribes. |
| `cluster.pub-sub.max-remote-nodes-per-topic` | `1000` | Obergrenze für Peers, die Subscriber für ein Topic beanspruchen dürfen. |
| `cluster.pub-sub.send-to-dead-letters-when-no-subscribers` | `on` | Ein Publish, das niemanden erreicht hat, geht an `system.deadLetters`, statt verworfen zu werden. |

Die drei Obergrenzen begrenzen, was ein Mediator überhaupt halten kann,
und der Publish-Fan-out läuft über alle — sie sind also ebenso sehr eine
Latenz- wie eine Speichergrenze.  Die Gossip-Hälfte ist die, die man
kennen sollte: ein Peer, der Topics ankündigt, für die er Subscriber
beansprucht, hat früher auf jedem Empfänger einen Eintrag pro Namen
angelegt — ganz ohne lokales `Subscribe`.  Siehe
[DistributedPubSub](/de/cluster/pubsub/).

### `actor-ts.cluster.receptionist`

| Key | Default | Zweck |
| --- | --- | --- |
| `cluster.receptionist.gossip-interval` | `1s` | Wie oft der Receptionist seine lokalen Registrierungen gossipt. |
| `cluster.receptionist.max-subscribers-per-key` | `1000` | Obergrenze für Subscriber eines Service Keys.  Ein `Subscribe` darüber wird mit `ReceptionistSubscribeRejected` beantwortet. |
| `cluster.receptionist.max-subscriptions-total` | `10000` | Obergrenze für Key/Subscriber-Paare über alle Keys dieses Nodes — ein Subscriber mit drei Keys zählt dreifach. |

Beide Blöcke liegen unter dem, was dem `start(...)` der Extension
übergeben wurde — ein explizites `withMaxTopics(…)` gewinnt also
weiterhin.  Gestoppte Subscriber werden vom Death Watch freigegeben und
zählen gegen keine der Grenzen.

### `actor-ts.distributed-data`

| Key | Default | Zweck |
| --- | --- | --- |
| `distributed-data.gossip-interval` | `1s` | Wie oft eine Replika ihren Key-Satz an einen zufälligen Peer schickt. |
| `distributed-data.max-pending-quorum-requests` | `1000` | Obergrenze für offene Quorum-Requests — `updateAsync` und `getAsync` teilen sich ein Budget.  Ein Request darüber wird direkt abgelehnt.  `0` deaktiviert das Cap. |
| `distributed-data.max-quorum-timeout` | `30s` | Obergrenze für das `timeoutMs` eines Aufrufs; ein größerer Wert wird darauf heruntergeschnitten.  `0` deaktiviert die Obergrenze. |
| `distributed-data.max-gossip-bytes` | `1M` | Byte-Budget für die Payload eines Gossip-Frames.  Ein größerer Store wird pro Tick in Scheiben geschickt und setzt dort fort, wo der letzte Tick aufgehört hat.  `0` entfernt das Budget. |
| `distributed-data.log-data-size-exceeding` | `100K` | Warnt (ratenbegrenzt) über einen Key, dessen eigene Kodierung diese Byte-Zahl überschreitet.  Reine Meldung — der Key wird gegossipt wie zuvor.  `0` warnt nie. |
| `distributed-data.durable-keys` | `[]` | Welche Keys ein konfigurierter `durableStore` persistiert.  **Leer heißt jeder Key.**  Ein Eintrag ist ein exakter Key-Name oder ein Präfix mit einem abschließenden `*`. |

`max-gossip-bytes` wird immer **auf `remote.max-frame-bytes` heruntergeschnitten**:
Wer das Wire-Cap senkt, senkt damit auch das Gossip-Budget, und keine
Einstellung kann Gossip wieder darüber schieben.  Das ist wichtig, weil die
beiden Fehlerbilder nicht vergleichbar sind: Ein Frame über dem Wire-Cap wird
schon an seinem 4-Byte-Längenpräfix abgelehnt, und der empfangende Transport
verwirft die komplette Peer-Verbindung — Heartbeats, Membership-Gossip und
jedes `tell` über Knotengrenzen inklusive — während ein Budget denselben Zustand
lediglich über mehr Ticks verteilt.  Ein einzelner Key, dessen eigene Kodierung
das Budget überschreitet, lässt sich nicht weiter aufteilen: Er wird
übersprungen, mit einer ratenbegrenzten Warnung samt Key-Name und beiden Größen
gemeldet, in `distributed_data_gossip_skipped_keys_total` gezählt — und er
konvergiert **nicht**.

Der Block liegt auf oberster Ebene statt unter `cluster.*` (wo `pub-sub`
und `receptionist` wohnen), weil das Modul dort liegt: `DistributedData`
kommt aus `src/crdt/`, und der Cluster ist ein positionales Argument von
`start(cluster)`, kein Tunable davon.  `durableStore` hat hier keinen Key —
es ist eine `DurableStateStore`-Instanz, die eine Config-Datei nicht
ausdrücken kann.

Beide Caps begrenzen die Menge der offenen Requests selbst.  Jeder offene
Quorum-Request hält ein Promise, einen Timer und ein Ziel-Set am Leben, bis
seine Deadline abläuft — ein ungedeckelter Replikator unter Last sammelt also
alle drei an, ohne dass irgendetwas ihn bremst.  Wer über
`max-pending-quorum-requests` hinaus ablehnt, macht aus dem, was später als
Timeout-Sturm ankäme, sofortige Fehler, die den Knopf beim Namen nennen.
Siehe [Quorum-Reads und -Writes](/de/distributed-data/quorum-reads-writes/).

`log-data-size-exceeding` meldet dieselbe Messung, die auch
`max-gossip-bytes` vornimmt — nur eine Größenordnung früher — und ändert
nichts daran, was verschickt wird.  Ein Key jenseits des gesamten Budgets ist
ohnehin laut; ein Key bei einem großen *Bruchteil* davon gossipt einwandfrei
und verbraucht dabei genau diesen Bruchteil jedes Ticks, in dem er auftaucht —
der Rest des Stores wird also entsprechend langsamer verteilt, ohne dass
irgendetwas sagt, warum.  `100K` ist ungefähr ein Zehntel des ausgelieferten
Budgets — zehn solcher Keys füllen ein ganzes Frame — und bewusst nicht Akkas
`10KiB`, was noch einmal ein Zehntel davon wäre und beim ersten
legitimen `ORSet` eines Deployments anschlagen würde.  Die Zeile hat ihre
eigene Ruhephase, statt sich die der Oversize-Warnung zu teilen: Ein höheres
`max-gossip-bytes` behebt jene und macht diese *relevanter*, keine der beiden
darf die andere unterdrücken.

`durable-keys` schränkt ein, was ein konfigurierter `durableStore` schreibt;
ohne Store ist der Key wirkungslos, und eine nicht-leere Liste ohne Store wird
beim Start als Warnung gemeldet.  **Eine leere Liste heißt jeder Key** — das
Verhalten jedes Releases vor dieser Option — und niemals „nichts
persistieren"; nichts zu persistieren erreicht man, indem man keinen Store
konfiguriert.  Ein Eintrag ist ein exakter Key-Name oder ein Präfix mit einem
abschließenden `*` (`session-*`), und das ist die gesamte Syntax: Ein
reichhaltigeres Muster hieße, aus einer Config-Datei einen Matcher zu bauen,
und `new RegExp(…)` über einen vom Betreiber gelieferten Text ist eine
ReDoS-Angriffsfläche auf genau dem Pfad, der entscheidet, was einen Neustart
überlebt.  Der Datensatz einer Replika wird bei jedem Save vollständig neu
geschrieben — **einen Eintrag zu entfernen löscht die Keys**, die er benannte,
bei der nächsten Mutation aus dem persistierten Datensatz.  Siehe
[Durable Storage](/de/distributed-data/durable-storage/).

`max-quorum-timeout` begrenzt die andere Achse.  Ein offener Request hält
seinen Slot über die gesamte Deadline, ein einzelner Aufrufer mit einem
stundenlangen `timeoutMs` parkt also das Budget für Stunden und sperrt
spätere Aufrufer aus, die dem Cap selbst nie nahe kamen.

### `actor-ts.coordination`

| Key | Default | Zweck |
| --- | --- | --- |
| `coordination.lease.ttl` | *(ungesetzt)* | Lease-TTL für das gesamte Deployment.  Liefert **kein Leaf** aus — ein Wert hier würde `ttlMs` für jeden Lease im Prozess setzen und die Prüfung „`ttlMs` ist Pflicht" unerreichbar machen. |
| `coordination.lease.renewal-interval` | *(ungesetzt)* | Wie oft ein gehaltener Lease erneuert wird.  Liefert **kein Leaf** aus — ungesetzt wählt das berechnete `max(500ms, ttl/3)`, und `0` kann nicht „leite es ab" heißen, weil der Validator es ablehnt. |
| `coordination.lease.kubernetes.namespace` | *(ungesetzt)* | Namespace, in dem das `Lease`-Objekt liegt.  Liefert **kein Leaf** aus — ungesetzt heißt „lies `namespace-path` aus dem ServiceAccount-Mount des Pods", und `""` wird abgelehnt. |
| `coordination.lease.kubernetes.namespace-path` | `"/var/run/secrets/kubernetes.io/serviceaccount/namespace"` | Datei, aus der der Namespace des Pods gelesen wird. |
| `coordination.lease.kubernetes.token-path` | `"/var/run/secrets/kubernetes.io/serviceaccount/token"` | Datei, aus der das Bearer-Token gelesen wird.  Ein **Pfad**, niemals das Token. |
| `coordination.lease.kubernetes.ca-path` | `"/var/run/secrets/kubernetes.io/serviceaccount/ca.crt"` | Datei, aus der das CA-Zertifikat für das TLS-Pinning des API-Servers gelesen wird. |
| `coordination.lease.kubernetes.token-reload-interval` | `1m` | Wie lange ein aus diesem Mount gelesenes Credential wiederverwendet wird, bevor die mtime der Token-Datei erneut geprüft wird.  Ohne Wirkung auf ein explizites `authToken`. |
| `coordination.lease.kubernetes.operation-timeout` | `10s` | Obergrenze für einen einzelnen Request an den API-Server. |
| `coordination.lease.kubernetes.lease-name-max-length` | `253` | Lease-Objektnamen, die länger sind, werden auf einen stabilen Kopf plus einen Hash des vollständigen Namens gekürzt.  `253` ist die DNS-1123-Subdomain-Grenze, die der API-Server durchsetzt. |

Das Framework baut keinen `Lease` für dich — jeder `withLease(…)`-Slot nimmt
eine Instanz entgegen —, dieser Block liegt also **unter** den Optionen, die du
an `new InMemoryLease(…)` / `new KubernetesLease(…)` übergibst, in der üblichen
Reihenfolge: explizite Optionen gewinnen, dann dieser Block, dann die
eingebauten Defaults.  Ein Lease entsteht, bevor es ein `ActorSystem` gibt,
deshalb laden die beiden Konstruktoren die Config-Kette selbst und
berücksichtigen dabei `ACTOR_TS_CONFIG` und `./application.conf`.

Drei Keys liefern **überhaupt kein Leaf** aus und stehen oben nur, damit die
Namen auffindbar sind.  Jeder davon ist ein Feld, das der Code verlangt oder
ableitet, und ein ausgelieferter Wert würde `hasPath` für immer wahr machen —
genau so wird das, wofür er einspringt, unerreichbar.  Setz einen davon in
deiner eigenen `application.conf` und er wird ganz normal gelesen:

```hocon
actor-ts.coordination.lease {
  ttl = 30s
  kubernetes.namespace = "actors"
}
```

:::caution[Die Credential-Keys sind Pfade, keine Werte]
Es gibt bewusst **keinen Key für `authToken`, `caCert` oder `apiServerUrl`**.
Zwei davon sind ein Bearer-Token und ein privater Vertrauensanker, und eine
Config-Datei ist für beides der falsche Ort: `ACTOR_TS_CONFIG` und eine
abgelegte `application.conf` speisen denselben Loader, und die zusammengeführte
Konfiguration ist im Config-Panel der DevTools lesbar.  Die drei Pfad-Keys sind
der vorgesehene Weg, diese Hälfte der Konfiguration aus dem Code zu holen —
Indirektion auf eine Datei, nie das Geheimnis selbst.

Sie beschreiben außerdem ausschließlich die **In-Cluster**-Quelle.  Einen davon
woandershin zu zeigen und gleichzeitig ein explizites `apiServerUrl` zu setzen,
wirft beim Konstruieren `OptionsError` — denn genau diese Paarung hat einmal das
ServiceAccount-Token des Clusters an den Host geschickt, den ein Operator
zufällig genannt hat
([Issue #599](https://github.com/pathosDev/actor-ts/issues/599)).
:::

`acquire-retries` und `acquire-retry-delay` sind hier nicht setzbar.  Die beiden
Backends liefern unterschiedliche eingebaute Defaults — 3 Versuche / 100 ms für
Kubernetes, 1 / 50 ms in-memory —, und ein Leaf könnte beide nicht ausdrücken,
ohne sie stillschweigend zu vereinheitlichen.  Setz sie pro Lease im Code.

### `actor-ts.remote`

| Key | Default | Zweck |
| --- | --- | --- |
| `remote.tcp.host` | `"0.0.0.0"` | Das Interface, auf dem **gebunden** wird.  Ein Wildcard gehört hierher und ist der Default.  Wird verwendet, wenn `ClusterOptions` `host` nicht setzt. |
| `remote.tcp.advertised-host` | *(ungesetzt)* | Die Adresse, die Peers **wählen** — die Identität dieses Nodes.  Ungesetzt folgt sie `remote.tcp.host`, sofern der routebar ist, dann `CLUSTER_HOST` / `POD_IP` / `HOSTNAME`, dann Loopback.  Ein Wildcard wird abgelehnt.  Bewusst nicht in der `reference.conf`, denn genau von einem ausgelieferten Wert müsste sich „ungesetzt" unterscheiden lassen. |
| `remote.tcp.port` | `2552` | Der Port, auf dem **gebunden** wird.  Wird verwendet, wenn `ClusterOptions` `port` nicht setzt. |
| `remote.tcp.advertised-port` | *(ungesetzt)* | Der Port, den Peers **wählen**.  Ungesetzt bedeutet dasselbe wie `remote.tcp.port` — setz ihn nur dort, wo das Deployment den Prozess auf einem anderen veröffentlicht.  Aus demselben Grund wie `advertised-host` nicht in der `reference.conf`. |
| `remote.max-frame-bytes` | `16M` | Wire-Cap pro Frame.  Ein Frame, dessen Längen-Präfix darüber liegt, wird verworfen, bevor irgendeine Payload gepuffert wird. |
| `remote.tls.enabled` | `false` | **Nicht umgesetzt** — `true` bringt eine Startup-Warnung, keine Verschlüsselung.  Siehe unten. |
| `remote.untrusted-mode` | `false` | Ein eingehendes Envelope nur annehmen, wenn `trusted-selection-paths` sein Ziel nennt.  Aus ist jeder `/user`-Aktor namentlich adressierbar — genau das lässt eine `ActorRef` über Knoten hinweg funktionieren.  `/system` wird in beiden Fällen abgelehnt.  Siehe unten. |
| `remote.trusted-selection-paths` | `[]` | Pfade, die ein Peer namentlich adressieren darf, solange `untrusted-mode` an ist.  Leer heißt: nichts über die Framework-Endpunkte hinaus, die dieser Knoten registriert hat. |
| `remote.handshake-timeout` | `5s` | Wie lange eine Verbindung ohne ihre Hälfte des Handshakes bestehen darf, bevor sie abgeräumt wird.  **Ein Wert für beide Richtungen** — siehe unten. |
| `remote.outbound-queue-size` | `1000` | Wie viele Frames für einen Peer gehalten werden, der sie gerade nicht annehmen kann; die ältesten fallen zuerst weg. |
| `remote.max-inbound-connections` | `1024` | Wie viele eingehende Verbindungen dieser Knoten annimmt, bevor er Sockets rundheraus ablehnt — abgelehnt wird die neueste, nicht die älteste verdrängt. |
| `remote.incomplete-frame-idle` | `30s` | Wie lange eine Verbindung ein halb empfangenes Frame halten darf, ohne dass ein weiteres Byte eintrifft.  Eine Stall-Schranke, bei jedem Chunk neu gestellt. |

`host`/`port` sind das **Bind**-Paar, `advertised-host`/`advertised-port` das
**Identitäts**-Paar: das erste sagt, wo der Listener aufmacht, das zweite,
was in jedes Gossip-Frame wandert, damit Peers zurückwählen können.  Sie sind
dieselben Werte, bis ein Deployment einen davon umbiegt — deshalb erledigt
ein routebarer Host plus ein Port weiterhin beide Jobs und nichts, was heute
konfiguriert ist, bewegt sich.

Weil die Bind-Adresse aus der Config lesbar ist, kann ein Deployment sie
komplett aus dem Code herausziehen:

```hocon
actor-ts.remote.tcp {
  host = "0.0.0.0"
  port = ${?ACTOR_TS_PORT}   # Env-Var-Substitution
}
```

Ein veröffentlichter Container-Port ist der Fall, der alle vier braucht.  Der
Prozess lauscht im Container auf `2552`, `docker run -p 3000:2552` legt ihn
draußen auf `3000`, und `3000` ist die Zahl, die in die Seed-Liste jedes
anderen Nodes gehört:

```hocon
actor-ts.remote.tcp {
  host            = "0.0.0.0"    # bind every interface — the container
  port            = 2552         #   does not know its published address
  advertised-host = ${?HOST_IP}  # what peers dial …
  advertised-port = 3000         #   … and on which port
}
```

Unter Kubernetes bewegt sich nur die Host-Hälfte: Pod-zu-Pod-Gossip wählt den
Container-Port direkt, also ist `advertised-host = ${?POD_IP}` allein schon
die ganze Konfiguration.

`remote.max-frame-bytes` gilt für den Transport, den der Cluster sich
selbst baut.  Wenn du einen `TcpTransport` selbst konstruierst und per
`withTransport(…)` übergibst, setz das Cap dort — das Framework re-capped
keinen Transport, den es nicht erzeugt hat.

#### Wen ein Peer namentlich adressieren darf

Ein eingehendes `envelope`-Frame trägt den Zielpfad, den der **Absender**
gewählt hat, und der Knoten löst ihn gegen seinen eigenen Aktor-Baum auf.  Das
ist das eine, was eine Gegenstelle auf der Cluster-Verbindung frei wählt, und
die beiden Keys oben sind der Rahmen darum.

`/system` gehört nicht zu diesem Rahmen.  Die Aktoren des Frameworks — Shard-
Coordinators und -Regions, Singleton-Manager, der PubSub-Mediator, das
DistributedData-Replikat, beide DevTools-Lanes — sind ausschließlich über den
Pro-Pfad-Handler erreichbar, den jeder von ihnen registriert, in beiden Modi.
Diese Tür heftet die Identität der Verbindung an das Frame; die namentliche
Pfadauflösung hat das nie getan, weshalb ein so zugestellter Body überhaupt
keinen Absender hatte.  Das ist eine **Verhaltensänderung**: davor konnte jeder,
der ein `hello` abgeschlossen hatte, sie adressieren
([Issue #964](https://github.com/pathosDev/actor-ts/issues/964)).

`untrusted-mode` engt die andere Hälfte ein.  Aus — der Default — darf ein Peer
jeden `/user`-Aktor benennen, was genau das ist, was eine aus einer Wire-Ref
rekonstruierte `RemoteActorRef` tut und was eine `ActorRef` über Knoten hinweg
überhaupt brauchbar macht.  An gelten nur die Pfade, die du auflistest:

```hocon
actor-ts.remote {
  untrusted-mode          = true
  trusted-selection-paths = ["/user/orders/*", "/user/reporting/intake"]
}
```

Ein Eintrag ist ein **exakter** Pfad, außer er endet auf `/*` — dann ist er
dieser Pfad und alles darunter.  Das Suffix ist segmentverankert:
`/user/orders/*` lässt `/user/orders/7` zu und lehnt `/user/orders-archive` ab.
Sonst ist hier nichts ein Muster, und ein `*` irgendwo anders als als ganzes
letztes Segment wird beim Start abgelehnt statt literal gematcht.  Pfade werden
guardian-verwurzelt geschrieben, so wie der Baum sie rendert; der führende `/`
ist optional.

Schalte den Modus dort an, wo das Cluster-Netz eine Grenze überschreitet, die du
nicht kontrollierst — dieselben Netze, in denen sich auch
`remote.max-frame-bytes` zu senken lohnt.  Der Preis ist, dass jeder namentlich
adressierte Aktor aufgelistet sein muss, auch die, die über eine gewanderte Ref
erreicht werden; fang deshalb damit an, auf einem Knoten mit angeschaltetem
Modus und einer für vollständig gehaltenen Allow-List
`cluster_envelope_refusals_total{reason="not-allow-listed"}` zu beobachten.

Ablehnungen werden gezählt statt einzeln geloggt: ein Envelope ist sein eigenes
Frame, eine Zeile pro Ablehnung ließe einen Peer also das Log dieses Knotens im
Nachrichtentakt schreiben.  Die erste Ablehnung je Grund wird als `WARN`
geloggt, weitere werden zu höchstens einer Zeile pro 30 Sekunden gefaltet, die
den Peer der **Verbindung** nennt und nie den angefragten Pfad.

Dieselbe Regel gilt für `ClusterClientReceptionist`, und das ist die stärker
exponierte der beiden Nahtstellen: ein
[`ClusterClient`](/de/cluster/cluster-client/) ist dem Membership-Ring nie
beigetreten.  Ein abgelehnter Pfad wird mit demselben `path not found`
beantwortet, das der Client für einen nicht existierenden Pfad bekommt — der
Endpunkt taugt also nicht dazu, den Aktor-Baum zu kartieren.

#### Der Assoziations-Lebenszyklus

Die letzten vier Keys begrenzen, was eine Gegenstelle, die eine TCP-Verbindung
zum Cluster-Port aufbauen kann, diesen Knoten halten lassen darf. Alle vier
werden durchgesetzt, seit der Transport gehärtet wurde; neu ist nur, dass sie
einstellbar sind
([Issue #846](https://github.com/pathosDev/actor-ts/issues/846)):

```hocon
actor-ts.remote {
  handshake-timeout       = 5s
  outbound-queue-size     = 1000
  max-inbound-connections = 1024
  incomplete-frame-idle   = 30s
}
```

`handshake-timeout` deckt eine Verbindung ab, die ihre Hälfte des Handshakes nie
spricht — einen Dial, der nie sein `hello-ack` bekommt, und einen
angenommenen Socket, der nie ein `hello` schickt. Es ist bewusst **ein Key für
beide Richtungen**. Die Uhr der wählenden Seite startet vor dem TCP-Connect und
dem TLS-Handshake, die der annehmenden Seite erst nach dem Accept — mit einer
Zahl hat der Peer, der es noch versucht, also immer zuerst aufgegeben, und die
annehmende Seite kann nie die Frist sein, die einen langsamen, aber legitimen
Dial bestraft. Ein getrenntes Dial-/Accept-Paar würde erlauben, die
Accept-Frist unter die Dial-Frist zu setzen und damit einen gesunden Peer
dauerhaft unerreichbar zu machen — ohne dass in irgendeinem Log stünde, warum.

`incomplete-frame-idle` deckt die andere Hälfte ab: eine Verbindung, die
gesprochen hat und dann mitten im Frame verstummt ist. Es ist eine
**Stall**-Schranke, kein Budget für das Frame — sie wird bei jedem Chunk neu
gestellt, ein Peer, der ein großes Frame über eine verstopfte Leitung schiebt,
wird also nie für seine Langsamkeit bestraft, nur fürs Aufhören. Halte sie über
`handshake-timeout`; beide Validatoren lehnen einen Wert darunter oder darauf
ab, denn ein Socket, der überhaupt nichts sendet, erreicht diese Frist nie —
dafür ist der Handshake-Timer da.

`max-inbound-connections` verhindert, dass sich beide Kosten durch Sockets im
Loop vervielfachen lassen, und ist die Hälfte der Schranke für eingehenden
Decode-Speicher, die sich zu senken lohnt: diese Schranke ist dieser Zähler mal
dem, was eine Verbindung puffern darf. Setz ihn nach der echten Peer-Zahl, wo du
sie kennst — eine eingehende Verbindung je Peer im Vollmesh, plus die
[`ClusterClient`](/de/cluster/cluster-client/)s, die sich einwählen — und lass
Luft, denn einen legitimen Peer abzulehnen ist eine Partition. Abgelehnt wird
die neueste Verbindung statt die älteste verdrängt; Verdrängung ließe einen
Angreifer etablierte Peers vom Knoten schieben.

`outbound-queue-size` ist der einzige Key hier, der begrenzt, was dieser Knoten
hält, statt was ein Peer gegen ihn hält: Frames, die für einen Peer geschrieben
wurden, der sie gerade nicht annehmen kann; die ältesten fallen zuerst weg, denn
der neueste Membership- und Heartbeat-Stand ist der, den zu behalten sich lohnt.
Heute ist das der Puffer vor dem Handshake, damit ein `tell`, das mit dem
Handshake um die Wette läuft, gehalten statt verloren wird. Der Key ist nach der
Kategorie benannt, nicht nach diesem einen Puffer: die Backpressure-Queue nach
dem Handshake ([Issue #931](https://github.com/pathosDev/actor-ts/issues/931))
ist dieselbe Größe mit derselben Policy und derselben Warnung und landet unter
diesem Key statt unter einem zweiten.

Keiner der vier hat eine „Aus"-Schreibweise. `0` wird für jeden abgelehnt, weil
es keine Art ist, eine Schranke zu entfernen, sondern jeweils eine eigene Art,
den Knoten kaputtzumachen: kein Handshake-Fenster, kein Platz zum Puffern, keine
eingehende Verbindung angenommen, keine Verbindung, die auf einer
Frame-Grenze enden darf.

Diese Werte erreichen den Transport, den der Cluster sich selbst baut. Ein
`TcpTransport`, den du selbst baust und per `withTransport(…)` übergibst, trägt
seine eigenen — setz sie in dessen `TcpTransportOptions`.

:::caution[`remote.tls.enabled` verschlüsselt nichts]
Der Key wird gelesen, aber nicht umgesetzt.  Ihn auf `true` zu setzen
aktiviert **kein** TLS — der Node loggt beim Start ein `WARN`, das den Key
nennt und sagt, dass die Cluster-Verbindung Klartext ist.  Ein
Security-Setting, das das Framework ignoriert, taucht damit in deinen Logs
auf und nicht nur auf dieser Seite
([Issue #591](https://github.com/pathosDev/actor-ts/issues/591)).  Den
Transport zu verschlüsseln ist separat verfolgt als
[Issue #941](https://github.com/pathosDev/actor-ts/issues/941); bis das
landet, behandle das Cluster-Netz als etwas, das du anderweitig absichern
musst.

Der Wert wird typgeprüft, wie jeder andere Key auf dieser Seite.  `true`, `on`
und `yes` fordern alle TLS an und erzeugen alle die Warnung; `false`, `no` und
`off` lehnen alle ab und bleiben still.  Alles andere — `maybe` oder ein
nacktes `1` — wirft einen `ConfigError` aus `Cluster.join` heraus, und der Node
startet nicht.  Ein Security-Schalter ist der falsche Ort, um zu raten, was
ein Tippfehler gemeint hat: die nachsichtige Lesart wäre „nicht aktiviert",
und damit stünde der Node wieder auf Klartext, während die Config TLS sagt —
genau der Zustand, den diese Warnung ausschließen soll.

Die Warnung gilt für den Transport, den der Cluster sich selbst baut.
Übergibst du per `ClusterOptions.withTransport(…)` einen eigenen, bleibt der
Node zu diesem Key still: was dieser Transport mit TLS macht, entscheidest
du, und das Framework kann von außen nicht erkennen, ob er verschlüsselt ist.
Der Key wird dann gar nicht gelesen, ein fehlerhafter Wert hält also auch
diesen Node nicht auf.
:::

### `actor-ts.http`

| Key | Default | Zweck |
| --- | --- | --- |
| `http.backend` | `"fastify"` | Einer von `fastify` / `express` / `hono`. |
| `http.shutdown-grace-period` | `0ms` | Wie lange `unbind()` in-flight Requests leerlaufen lässt, bevor Verbindungen erzwungen geschlossen werden.  `0` erzwingt sofort. |
| `http.server` | *(siehe unten)* | Verbindungsschranken für den lauschenden Socket selbst. |
| `http.cors` | *(siehe unten)* | Pro-Route-Defaults für die [`cors()`](/de/http/middleware/cors/)-Direktive. |
| `http.client` | *(siehe unten)* | Defaults des ausgehenden [`HttpClient`](/de/http/overview/). |
| `http.websocket` | *(siehe unten)* | Serverseitige WebSocket-Defaults für [`websocket()`](/de/http/websocket/)-Routen. |

`http.backend` entscheidet nur darüber, was `newServerAt(...).bind()`
verwendet, wenn der Builder kein eigenes Backend bekommen hat —
`useBackend(new HonoBackend())` gewinnt immer und bleibt der einzige Weg,
ein selbst konfiguriertes oder selbst geschriebenes Backend zu übergeben.
Ein unbekannter Name lässt `bind()` mit einem `ConfigError` scheitern,
statt still auf Fastify zurückzufallen.  Express und Hono sind optionale
Peer-Dependencies und werden nur importiert, wenn du sie benennst.

Die Grace Period ist per Default `0` — sofort erzwingen —, weil `unbind()`
genau das in der Praxis immer getan hat.  Erhöhe sie, wenn in-flight
Requests fertig werden sollen.

Meist ist sie eine Obergrenze und keine Wartezeit: `unbind()` kehrt zurück,
sobald der Server tatsächlich geschlossen ist.  Wo das `close()` eines
Backends nicht settlen kann — etwa Express mit einem lebenden WebSocket —
wird das Fenster zu einer Deadline, die immer erreicht wird; ein großer Wert
ist dort also Zeit, die du immer bezahlst.  Ein Aufrufer, der einen eigenen
Wert übergibt — `binding.unbind(1_000)` — überschreibt die Config.

Die Schranken einer **Verbindung** — im Gegensatz zu einer Route darauf —
kommen aus `actor-ts.http.server`:

| Key | Default | Zweck |
| --- | --- | --- |
| `http.server.idle-timeout` | *(das des Backends)* | Wie lange eine untätige Keep-Alive-Verbindung gehalten wird, bevor sie zerstört wird.  Hat **kein Blatt** — siehe unten.  `0` schaltet ihn ab. |
| `http.server.header-timeout` | `60s` | Wie lange eine Verbindung brauchen darf, um ihren vollständigen Header-Block zu liefern, bevor sie mit `408` beantwortet und zerstört wird.  Der Slowloris-Schutz. |
| `http.server.request-timeout` | `300s` | Wie lange eine Verbindung brauchen darf, um einen Request vollständig zu liefern — Header und Body.  Begrenzt das *Empfangen*, nie das Antworten. |
| `http.server.max-connections` | *(unbegrenzt)* | Gleichzeitige Verbindungen, die der lauschende Socket annimmt, bevor er neue schließt.  Hat **kein Blatt** — siehe unten. |

Die übliche Reihenfolge gilt pro Feld:
`newServerAt(...).withServerOptions(...)` gewinnt, dann dieser Block, dann der
eingebaute Default.  Aufgelöst wird einmal bei `bind()`, installiert wird bei
`listen()` — deshalb erreichen die Werte ein Backend, das du selbst gebaut und
an `useBackend(...)` übergeben hast, genauso wie das, das das Framework für
dich baut.

```hocon
actor-ts.http.server {
  idle-timeout    = 5s
  request-timeout = 30s
  max-connections = 10000
}
```

:::caution[Nicht jedes Backend kann diese Werte umsetzen]
Es sind Eigenschaften eines `node:http`-Servers und gelten damit genau dort,
wo es einen gibt.

| Key | Fastify | Express | Hono / Node | Hono / Bun | Hono / Deno |
| --- | --- | --- | --- | --- | --- |
| `idle-timeout` | ja | ja | ja | **nein** | **nein** |
| `header-timeout` | ja | ja | ja | **nein** | **nein** |
| `request-timeout` | ja | ja | ja | **nein** | **nein** |
| `max-connections` | ja | ja | ja | **nein** | **nein** |

Hono besitzt keinen eigenen Server — es delegiert an einen Runner pro Runtime
—, und nur `@hono/node-server` gibt seinen `node:http`-Server heraus.
`Bun.serve` und `Deno.serve` bieten weder diesen Server noch einen
gleichwertigen Knopf; auf dem Hono-Backend unter Bun oder Deno wird deshalb
**keiner dieser vier Werte überhaupt installiert**.  Das ist eine Lücke und
kein stilles Halb-Ergebnis: es wird nichts geschrieben, und nichts tut so, als
wäre es geschrieben worden.  Bun hat auf `Bun.serve` durchaus ein
verbindungsweites `idleTimeout` — in *Sekunden* statt Millisekunden, nah genug
um verlockend und verschieden genug um falsch zu sein; es ist hier nicht
verdrahtet.
:::

Zwei Blätter liefern **keinen Wert** und stehen oben nur, damit die Namen
auffindbar sind — aus demselben Grund wie bei vier der CORS-Blätter: ein
veröffentlichtes Literal wäre eine Zahl, die niemand gewählt hat.

`idle-timeout` behält ungesetzt das, was das Backend gewählt hat, und die
Backends sind sich **absichtlich** uneinig: 72 s bei Fastify gegen die 5 s von
`node:http` bei Express und bei Hono-über-Node.  Fastifys Wert ist hoch, damit
der Server das Idle-Fenster eines Load Balancers überlebt und der Balancer nie
einen Request auf einen Socket schickt, der gerade schließt; fünf Sekunden sind
die der Plattform.  Keiner von beiden ist falsch, also kürt der Block keinen
Sieger.  Setz ihn, wenn sie sich einig sein sollen.

`max-connections` ist ungesetzt unbegrenzt — das, was jedes Release vor diesem
Key getan hat.  Der Wert gilt **serverweit**, anders als das
`http.websocket.max-connections` weiter unten, das pro Route gilt: er zählt
jede Verbindung, die der Prozess auf diesem Binding annimmt — WebSocket-Upgrades
eingeschlossen, und ein angehängter
[DevTools](/de/observability/devtools/overview/)-Server ebenso, denn DevTools
bindet über denselben `system.http(...)`-Pfad.

`header-timeout` und `request-timeout` werden von einem periodischen Sweep
durchgesetzt, dessen Intervall die Runtime auf 30 s festlegt und nicht
herausgibt.  Eine Verbindung wird also **nicht früher** als beim hier gesetzten
Wert geschlossen und **nicht später als einen Sweep danach**.  Beide liefern die
Zahl, die `http.createServer` ohnehin verwendet — auf Express und Hono hat das
Veröffentlichen also nichts geändert.  Fastify setzt `requestTimeout` aber auf
`0`, also gar keine Schranke; auf dem Default-Backend ist die veröffentlichte
`300s` damit eine Deadline, wo vorher keine war.  Bei der 1-MiB-Body-Grenze ist
das ein Client mit unter 3,5 KB/s; erhöhe sie, wenn du berechtigterweise
langsamere Uploads annimmst, oder setz `0`, um auszusteigen.

`request-timeout` begrenzt nur das *Empfangen* — die Uhr stoppt, sobald der
Request angekommen ist —, ein langsamer Handler, ein Long Poll und ein
SSE-Stream bleiben also unberührt.  Die Route-Middleware
[`timeout()`](/de/http/middleware/timeout/) ist die andere Hälfte und
absichtlich eine andere Fläche: sie begrenzt, wie lange ein *Handler* zum
Antworten braucht, dieser Key, wie lange ein *Peer* zum Fragen braucht.

Die Route-Direktive [`cors()`](/de/http/middleware/cors/) liest ihre Defaults
pro Feld aus `actor-ts.http.cors`:

| Key | Default | Zweck |
| --- | --- | --- |
| `http.cors.origins` | *(nicht gesetzt)* | Exakte Origin-Allowlist, z. B. `["https://app.example"]`. Hat **kein Blatt** — siehe unten. Ein `"*"`-Eintrag wird abgelehnt. |
| `http.cors.methods` | *(nicht gesetzt)* | `Access-Control-Allow-Methods`. Hat **kein Blatt** — ungesetzt folgt es den am jeweiligen Pattern registrierten Methoden. |
| `http.cors.allowed-headers` | *(nicht gesetzt)* | `Access-Control-Allow-Headers`. Hat **kein Blatt** — ungesetzt werden die sanitisierten Request-Header geechot. |
| `http.cors.exposed-headers` | `[]` | `Access-Control-Expose-Headers`. `[]` sendet keine. |
| `http.cors.credentials` | `false` | `Access-Control-Allow-Credentials: true`. Verboten mit `"*"`-Origins. |
| `http.cors.max-age` | *(nicht gesetzt)* | Preflight-Cache-Dauer in **Sekunden**, als blanke Ganzzahl. Hat **kein Blatt** — ungesetzt wird gar kein `Access-Control-Max-Age` gesendet. |

Es gilt die übliche Reihenfolge pro Feld: Was `cors(options, routes)` im Code
nennt, gewinnt, dann dieser Block, dann der eingebaute Default. Ein Deployment
kann die Allowlist also komplett aus dem Code herausziehen und
`withCredentials()` dort lassen, wo es steht.

Zwei der Options-Arme sind **nur im Code erreichbar und haben hier keinen Key**.
Der eine ist die `"*"`-Wildcard: `withAnyOrigin()` ist als ausdrücklicher
Opt-in dokumentiert, und eine Config-Datei, die `origins = ["*"]` schreiben
könnte, würde mit einer Zeile jede `cors()`-Route im Prozess auf jeden Origin
öffnen — ein `"*"` in dieser Liste wird deshalb mit einem `ConfigError`
abgelehnt, der den Key nennt. Der andere ist `withOriginPredicate(...)`: eine
Funktion hat in HOCON überhaupt keine Schreibweise.

Vier Blätter liefern **keinen Wert** aus und stehen oben nur, damit die Namen
auffindbar sind — ein publizierter Literalwert wäre schlechter als gar kein
Key. `methods` und `allowed-headers` haben Defaults, die pro Pattern bzw. pro
Request berechnet werden und die eine flottenweite Liste überschreiben würde;
ein ungesetztes `max-age` heißt, dass der Header nicht gesendet wird; und ein
ausgeliefertes `origins` würde die Pflichtprüfung für jede Route im Prozess
erfüllen und damit ein `cors()` ohne jede Allowlist von einem lauten Fehler in
ein stilles Deny-all verwandeln. Setz sie in deiner eigenen `application.conf`,
und sie werden ganz normal gelesen:

```hocon
actor-ts.http.cors {
  origins = ["https://app.example", "https://admin.example"]
  max-age = 600          # Sekunden — kein Duration-String
  exposed-headers = ["x-request-id"]
}
```

Die Werte werden auf dem gemergten Ergebnis validiert; ein falscher Wert wirft
also `OptionsError` mit dem Feldnamen, statt als Header beim Browser zu landen,
der ihn ablehnt.

Weil `cors()` eine Route-*Direktive* ist und keine Middleware, wird dieser
Block beim **Kompilieren** des Route-Baums aufgelöst — in `bind()`, dem ersten
Moment, in dem Baum und `ActorSystem` beide im Scope sind. Genau dort scheitert
jetzt auch ein `cors()`, das weder im Code noch in der Config `origins` nennt,
statt schon beim `cors(...)`-Aufruf.

Der gemeinsame `HttpClient` des Systems — und jedes `newClient(...)`, das ein
Feld offen lässt — liest seine Schranken aus `actor-ts.http.client`:

| Key | Default | Zweck |
| --- | --- | --- |
| `http.client.max-response-bytes` | `8M` | Größter Response-Body, der gepuffert wird, bevor der Request abgebrochen wird. |
| `http.client.default-timeout` | `30s` | Deadline für einen Aufruf, der kein eigenes `timeoutMs` nennt. |
| `http.client.redirect` | `"follow"` | Was mit einem 3xx samt `Location` passiert — `follow` / `error` / `manual`. |
| `http.client.max-redirects` | `5` | Hops, die eine verfolgte Kette gehen darf, bevor der Aufruf abgelehnt wird.  `0` lehnt den ersten ab. |

Das ist ein Boden und keine Policy: Eine Integration übergibt ihre eigenen
Schranken an `newClient(...)`, und ein einzelner Aufruf überschreibt sie mit
`maxResponseBytes` / `timeoutMs` / `redirect` / `maxRedirects`.  Was der Block
bringt, ist die Möglichkeit, die flottenweiten Zahlen ohne Codeänderung zu
bewegen — ein Endpunkt, der doch 60 s braucht, oder ein Deployment auf einer
Strecke, auf der 8 MiB die falsche Obergrenze sind, zwang bisher jeden Aufrufer
weg vom gemeinsamen Client.

Jedes Blatt ist das Feld aus `HttpClientOptions` in kebab-case, ohne
Einheiten-Suffix — die Einheit steht im Wert, also `default-timeout = 30s`.
Die camelCase-Schreibweisen, die dieser Block früher hatte, werden beim Start
**abgelehnt**, mit einem `ConfigError`, der beide Namen nennt, statt ignoriert
zu werden: `max-response-bytes` ist eine Obergrenze, die ein Deployment
bewusst senkt, und sie still auf den eingebauten Default zurückzusetzen wäre
genau der eine Fehlermodus, den eine Umbenennung nicht haben darf.

Die Werte werden beim Lesen auf den gemergten Settings validiert; ein falscher
Wert wirft also `OptionsError` mit dem Feldnamen, statt später mitten im
Request zu scheitern.  `max-response-bytes` und `default-timeout` müssen hier
beide positiv sein — anders als das `timeoutMs` eines *Requests*, wo `0` der
dokumentierte Weg ist, einen einzelnen Aufruf von jeder Deadline auszunehmen.
Eine `0` in diesem Block würde jeden Aufruf ohne eigene Deadline entschärfen —
genau der Zustand, den die Defaults verhindern sollen.

Serverseitige WebSocket-Routen (`websocket(path, actorRef)`) lesen
ihre Defaults aus `actor-ts.http.websocket`:

| Key | Default | Zweck |
| --- | --- | --- |
| `http.websocket.max-frame-bytes` | `1M` | Größter akzeptierter eingehender Frame (Bytes). |
| `http.websocket.on-oversize-frame` | `"close"` | Was passiert, wenn ein Frame das Limit überschreitet — `close` / `drop`. |
| `http.websocket.on-invalid-message` | `"close"` | Was passiert, wenn eine Nachricht nicht dekodiert werden kann — `close` / `drop` / `hook`. |
| `http.websocket.max-buffered-bytes` | `4M` | Outbound-Backpressure-Schwelle (Bytes). |
| `http.websocket.on-backpressure` | `"drop"` | Was passiert, wenn der Buffer überschritten wird — `drop` / `close`. |
| `http.websocket.max-connections` | *(unbegrenzt)* | Max. gleichzeitige Verbindungen pro Route; ein Upgrade darüber hinaus wird mit 1013 geschlossen. |
| `http.websocket.max-pre-attach-frames` | `256` | Eingehende Frames, die gehalten werden, während der Connection-Actor startet. |
| `http.websocket.max-pre-attach-bytes` | `4M` | Bytes, die gehalten werden, während der Connection-Actor startet; jenseits einer der beiden Grenzen wird der Socket mit 1013 geschlossen. |
| `http.websocket.accept-timeout` | `10s` | Wie lange ein zugelassenes Upgrade auf seinen Connection-Actor wartet, bevor der Socket geschlossen und sein `max-connections`-Platz freigegeben wird. |

Hier gelten dieselbe Blattregel und dieselbe Ablehnung beim Start: kebab-case,
Einheiten-Suffix weggelassen, und eine ausgemusterte camelCase-Schreibweise ist
ein `ConfigError` statt einer Obergrenze, die still auf den Default zurückfiel.

### `actor-ts.reliable-delivery`

| Key | Default | Zweck |
| --- | --- | --- |
| `reliable-delivery.producer.resend-timeout` | `500ms` | Wie lange der Producer auf eine Bestätigung wartet, bevor er dieselbe seq erneut sendet.  Ein festes Intervall, bei jedem Ausbleiben unverändert neu gestellt — es gibt kein Backoff. |
| `reliable-delivery.producer.window-size` | `16` | Flow-Control-Fenster: höchstens so viele unbestätigte Nachrichten gleichzeitig unterwegs.  Weitere Sends warten im Speicher, bis eine Bestätigung einen Platz freigibt. |
| `reliable-delivery.consumer.max-producers` | `1024` | Für wie viele Producer der Consumer gleichzeitig Deduplizierungs-Zustand hält.  An der Grenze wird der am längsten unbenutzte Eintrag verdrängt.  `0` = unbegrenzt. |
| `reliable-delivery.consumer.producer-idle-time-to-live` | `5m` | Wie lange der Deduplizierungs-Eintrag eines Producers ohne Zustellung von ihm überlebt; der Sweep läuft in genau diesem Intervall.  `0` schaltet den Sweep ab. |

Beide Blöcke liegen unter dem, was `ReliableDelivery.producer(...)` /
`ReliableDelivery.consumer(...)` übergeben bekommt — ein explizites
`withWindowSize(…)` gewinnt also weiterhin.  **Gelesen werden sie dort und
sonst nirgends.**  Kein Controller kann in seinem Konstruktor Konfiguration
lesen — `Actor.system` ist ein Getter über einen Kontext, den die Zelle erst
danach injiziert —, deshalb behält ein Controller, den du selbst konstruierst
und an `system.spawn` übergibst, seine eingebauten Defaults und sieht diesen
Block nie.

`0` ist die Schreibweise, mit der beide Consumer-Grenzen das `Infinity` ihrer
Optionsfelder ausdrücken, denn `Infinity` lässt sich in HOCON überhaupt nicht
schreiben: der Zahlen-Reader nimmt ein numerisches Literal, und der
Duration-Parser weist einen nicht-endlichen Wert ab.  Es ist dieselbe
Schreibweise, die `cluster.max-members` und `sharding.max-entities` bereits
verwenden.  Was sie kostet, gehört klar gesagt: die Deduplizierungs-Map ist auf
eine `producerId` geschlüsselt, die der *Sender* wählt — `0` überlässt damit
einem Peer die Entscheidung, wie viel dieser Consumer behält: ein Eintrag je
verschiedener Id, nie freigegeben.

`maxOutOfOrder`, die dritte Consumer-Grenze, bekommt bewusst noch keinen
Schlüssel: sie kam erst nach der Spezifikation dieses Blocks dazu und erhält
ein eigenes Folge-Issue statt eines Blatts, das niemand bemessen hat.

### `actor-ts.serialization`

| Key | Default | Zweck |
| --- | --- | --- |
| `serialization.read-constraints.max-nesting-depth` | `256` | Container-Ebenen, in die ein Decoder absteigt, bevor er das Payload ablehnt.  Nie über die eigene Obergrenze des Encoders hinaus. |
| `serialization.read-constraints.max-document-bytes` | `0` | Obergrenze für ein Dokument, das an `JsonSerializer` / `CborSerializer` übergeben wird, geprüft vor dem Parsen.  `0` = keine eigene Obergrenze. |
| `serialization.read-constraints.max-string-length` | `20M` | Obergrenze für einen CBOR-Byte-String, Text-String oder Map-Key, geprüft am Längen-Präfix, bevor die Bytes alloziert werden.  `0` hebt sie auf. |

Diese Grenzen binden, was dieser Knoten **liest**, nie was er schreibt.  Ein
Peer, der den Handshake abschließt, oder jeder Client, dessen Body einen
Serializer erreicht, wählt die Bytes; diese Werte entscheiden, wie viel Arbeit
der Prozess darauf verwendet, bevor er aufgibt.  Eine Grenze zu senken macht
diesen Knoten also strenger als seinen eigenen Encoder — am Wire-Format ändert
sich nichts.

`max-nesting-depth` ist die entscheidende, denn bis dahin gab es auf der
JSON-Seite überhaupt nichts: `JSON.parse` arbeitet in jeder von actor-ts
unterstützten Runtime iterativ und akzeptiert klaglos eine Million Ebenen — die
Rekursion, die überläuft, ist der eigene Tagged-Tree-Walker des Frameworks,
direkt vom Cluster-Wire aus erreichbar.  Der Wert darf beliebig gesenkt werden
und **kann nicht** über `256` angehoben werden: das ist zugleich die harte
Obergrenze des Encoders, und ein Knoten, der tiefer liest als er schreibt,
würde ein Payload akzeptieren, das er selbst nicht erzeugen kann.  Ein höherer
Wert ist ein `OptionsError` beim Start.

`max-document-bytes` wird als `0` ausgeliefert, weil jeder Pfad, den das
Framework selbst besitzt, bereits begrenzt ist — `remote.max-frame-bytes` auf
dem Cluster-Wire, das Body-Limit des Servers über HTTP.  Setze den Wert dort,
wo ein Serializer auf anderem Weg erreicht wird (ein Broker-Payload, eine
Queue-Nachricht) und stromaufwärts niemand eine Meinung dazu hat.

`max-string-length` bindet **nur bei CBOR**, und der Default liegt bewusst über
`remote.max-frame-bytes`: auf dem Cluster-Wire ist damit das Frame-Limit die
wirksame Obergrenze und diese hier greift nie.  Die Asymmetrie ist gewollt —
ein CBOR-Item kündigt seine Länge an, die Ablehnung kostet also nichts und
verhindert die Allokation, während `JSON.parse` den String längst
materialisiert hat, wenn der JSON-Walker ihn sieht.

Zwei Kanten liegen bewusst außerhalb dieses Blocks.  Der Persistence-`PayloadCodec`
dekodiert Bytes, die das Framework selbst geschrieben hat; eine verschärfte
Grenze würde dort wiederherstellbare Historie in unlesbare verwandeln.  Und die
HTTP-Body-Kante baut ihre Serializer ohne `ActorSystem`-Handle, über das sich
die Konfiguration lesen ließe — diese Naht ist Issue #967.

### `actor-ts.management`

| Key | Default | Zweck |
| --- | --- | --- |
| `management.enable-leave-endpoint` | `false` | `POST /cluster/leave` ausliefern ([HTTP-Endpunkte](/de/observability/management/http-endpoints/)). |
| `management.enable-down-endpoint` | `false` | `POST /cluster/down` ausliefern — operator-initiiertes Force-Down eines Peers. |
| `management.enable-metrics-endpoint` | `false` | `GET /metrics` im Prometheus-Textformat ausliefern. |
| `management.auth-protect-health` | `false` | Die `auth`-Middleware zusätzlich über `/health` und `/ready` legen, nicht nur über `/cluster/*`. |
| `management.liveness-path` | `"health"` | Einzelnes Pfadsegment, unter dem die Liveness-Probe antwortet. |
| `management.readiness-path` | `"ready"` | Einzelnes Pfadsegment, unter dem die Readiness-Probe antwortet. |
| `management.health-checks.check-timeout` | `1s` | Deadline für **einen** Health-Check; danach meldet dieser Check `status: false`, seine Geschwister melden weiterhin normal. |

Das sind die Einstellungen, die `managementRoutes(system, cluster, options)`
unter seine expliziten Optionen legt — die üblichen drei Ebenen: ein im Code
gesetzter Wert gewinnt, eine Datei füllt, was der Code offen gelassen hat, und
die eingebauten Defaults sind der Boden.  Port und Host stehen nicht hier: die
gehören zu `system.http(port, { host })`, nicht zum Route-Baum.

**`auth` und `ipAllowlist` haben keinen Key und können auch keinen bekommen.**
Beides sind `Middleware`-Funktionen, die HOCON nicht ausdrücken kann.  Der
Block entscheidet also, *welche* Endpunkte es gibt und *wo* die Probes
antworten — nie, *wer* sie erreichen darf.  Eine Config-Datei kann die
Zugriffskontrolle des Management-Servers damit nicht aufweichen, und genau
deshalb ist es unbedenklich, die beiden mutierenden Endpunkte überhaupt per
Config schaltbar zu machen.

Die beiden Probe-Pfade sind **einzelne Segmente**; ein Wert mit `/` wird beim
Bauen der Routen mit einem `OptionsError` abgelehnt.  Diese Regel ist nicht
kosmetisch: `path(segment, …)` entfernt nur umschließende Slashes.
`readiness-path = "k8s/ready"` würde also als ein Segment mit einem Slash darin
gespeichert, auf keine URL passen und den Endpunkt lautlos verschwinden lassen.
Ein Fehler beim Start ist die sichtbare Variante desselben Ausgangs.

`check-timeout` begrenzt einen einzelnen Check, nicht die gesamte Probe.  Eine
Probe aggregiert alle registrierten Checks zu einer Antwort — ohne die Deadline
*ist* der langsamste Check die Antwortzeit, und ein Check, der nie fertig wird,
ist eine Probe, die nie antwortet.  Kubernetes liest das als Fehlschlag, ohne
jeden Hinweis darauf, welche Abhängigkeit hängt.  Nach Ablauf antwortet die
Registry für diesen Check mit `{ name: 'unknown', status: false, detail: … }`;
`unknown` deshalb, weil der Name in genau dem Ergebnis steckt, das der Check nie
zurückgegeben hat.

| Key | Default | Zweck |
| --- | --- | --- |
| `persistence.journal.plugin` | `"...in-memory"` | Voll qualifizierter Key zur Konfig des Journals. |

Der `object-storage`-Block konfiguriert **beide** Stores, die
`registerObjectStoragePlugins(ext)` zurückgibt: Snapshot Store und
Durable-State-Store teilen sich ein Backend, also wird es einmal statt zweimal
deklariert.  Ist der Block gefüllt, braucht der Aufruf gar keine Options mehr —
`await registerObjectStoragePlugins(ext)`.  Explizite
`ObjectStoragePluginOptions` gewinnen weiterhin, Feld für Feld, und ein im Code
nicht gesetztes Feld fällt auf den Block durch, statt ihn zu überdecken.  Werte
werden einmal auf den gemergten Settings validiert, also wirft `backend = s3`
ohne Bucket schon bei der Registrierung einen `OptionsError`, der
`backend.bucket` benennt, statt erst beim ersten Snapshot zu scheitern.

**Für Schlüsselmaterial gibt es in diesem Block keinen Pfad, und das ist
strukturell und nicht bloß Konvention.**  Es existiert kein Blatt für
S3-Credentials, für einen clientseitigen Master Key oder für einen
Integritätsschlüssel — eine Config-Datei kann sie also gar nicht ausdrücken.
Lässt man die S3-Credentials weg, greift die Default-Chain des SDK:
`AWS_ACCESS_KEY_ID` / `AWS_SECRET_ACCESS_KEY`, ein EC2-Instance-Profile oder
IAM Roles for Service Accounts.  `encryption.mode = client-aes256-gcm` wird mit
einem `OptionsError` **abgelehnt** statt still ignoriert, denn ein Deployment,
das clientseitige Verschlüsselung angefordert hat und stillschweigend Klartext
bekommt, ist das schlechtere Ergebnis; konfiguriere diesen Modus im Code mit
`ObjectStoragePluginOptions.withEncryption(…)`.  `kms-key-id` ist unbedenklich —
eine ARN ist ein Name, und der Schlüssel selbst verlässt KMS nie.

**`durable-state.plugin` ist die dritte Achse**, und sie ist neu.  Durable State
war bislang der einzige Persistence-Vertrag ohne Registry: jeder
`registerXxxPlugins`-Helper baute seinen Store eifrig und gab ihn zurück, ein
`DurableStateActor` musste diese Instanz also im Code bekommen.  Jetzt wird er
genau wie Journal und Snapshot Store ausgewählt, und `DurableStateOptions.store`
ist optional — ein Actor, der keinen Store benennt, nutzt den, den dieser Key
auswählt.

**SQLite wird mit `registerSqlitePlugins(ext)` registriert** und braucht gar
keine Options mehr, wenn die drei Blöcke oben gefüllt sind:

```ts
const ext = system.extension(PersistenceExtensionId);
registerSqlitePlugins(ext);          // path, tables, retention … from HOCON
```

Es gelten die üblichen drei Ebenen — explizite
`RegisterSqlitePluginsOptions` stechen den Block, der Block sticht die
eingebauten Defaults, Feld für Feld, und ein im Code nicht gesetztes Feld fällt
durch, statt zu überdecken.  Ein im Code angegebener `path` gilt für alle drei
Stores als *Default*, ein Blatt mit eigenem `path` behält also seinen; eine
vorab geöffnete `database` ist dagegen ein Override, denn ein gemeinsames Handle
ist die spezifischere Anweisung.  Für `driver`, `database` und `serializer` gibt
es kein Blatt — das sind lebende Objekte, die eine Config-Datei nicht ausdrücken
kann.

**Auch die fünf relationalen Backends lesen ihre eigenen Blöcke** (#872).
Postgres, MariaDB, SQL Server, libSQL und Cloudflare D1 teilen sich ein Journal,
einen Snapshot-Store und einen Durable-State-Store, deshalb ist die
Tabellen-Hälfte jedes Blocks dieselben drei oder vier Blätter und nur die
Verbindungs-Hälfte unterscheidet sich.  `registerPostgresPlugins(ext)` — und
jedes seiner vier Geschwister — braucht damit gar keine Optionen mehr, sobald
die Blöcke unten gefüllt sind:

```ts
const ext = system.extension(PersistenceExtensionId);
registerPostgresPlugins(ext);        // url, tables, retention ... from HOCON
```

Die Verbindung wiederholt sich unter jedem der drei Plugin-Roots, statt auf einen
Backend-Root gehoben zu werden, denn eine Plugin-Id *ist* ihr Config-Abschnitt,
und die drei Achsen werden unabhängig ausgewählt — sie dürfen
berechtigterweise verschiedene Datenbanken benennen.  Wer eine Verbindung teilt,
schreibt sie einmal und substituiert:
`url = ${actor-ts.persistence.journal.postgres.url}`.

Drei Dinge haben bewusst **kein Blatt**.  Ein vorab gebauter `pool` oder `client`
und ein `serializer` sind lebende Objekte, eine Config-Datei kann sie nicht
ausdrücken.  `poolConfig` ist freie Treiber-Konfiguration ohne aufzählbare
Schlüsselmenge und ohne Default und bleibt deshalb code-only — was für
SQL Server heißt: ein rein per Config verdrahteter Store wird über `url`
erreicht, in der Form `Server=...;Database=...` oder `mssql://`.  Und
`tags-table` ist in der Referenzkonfiguration ein **Kommentar** statt eines
Schlüssels, weil sein Default aus `events-table` abgeleitet wird
(`<events-table>_tags`): genau die Abwesenheit hält beide im Gleichlauf.
Gelesen wird er trotzdem, eine `application.conf` kann ihn also weiterhin
festnageln.

Die beiden Credentials, die *doch* ein Blatt haben — libSQLs `auth-token` und
D1s `api-token` —, sind Strings, die der Betrieb von irgendwoher liefert; der
dokumentierte Weg ist eine Substitution (`api-token = ${?CLOUDFLARE_API_TOKEN}`).
Beide werden leer ausgeliefert, und leer heißt *nicht gesetzt*, damit der
Platzhalter nie zu einem Bearer-Token wird.

Framework liefert keinen Cassandra-Durable-State-Store aus, dieses Backend hat
also zwei Plugin-Achsen, wo die anderen beiden drei haben.

### `actor-ts.circuit-breaker`

| Key | Default | Zweck |
| --- | --- | --- |
| `circuit-breaker.default.max-failures` | `10` | Aufeinanderfolgende Fehler, bis ein Breaker öffnet ([Circuit Breaker](/de/patterns/circuit-breaker/)). |
| `circuit-breaker.default.reset-timeout` | `15s` | Wie lange er offen bleibt, bevor er eine Probe durchlässt. |
| `circuit-breaker.default.max-reset-timeout` | `60s` | Obergrenze des gewachsenen Fensters.  Muss mindestens `reset-timeout` sein — ein Breaker, dessen gemergte Settings das verletzen, startet nicht. |
| `circuit-breaker.default.backoff-factor` | `1.0` | Multiplikator je aufeinanderfolgendem Öffnen.  `1.0` = das flache Fenster jedes früheren Releases. |
| `circuit-breaker.default.random-factor` | `0.0` | Jitter-Anteil in `[0, 1]`, über dieses Fenster gestreut.  `0.0` = kein Jitter. |
| `circuit-breaker.default.ignored-error-names` | `[]` | `Error.name`-Werte, die nie als Fehler zählen. |
| `circuit-breaker.default.call-timeout` | *(nicht gesetzt)* | Bewusst ein Kommentar in `reference.conf` — siehe unten.  Ungesetzt gibt es keine Deadline pro Aufruf. |
| `circuit-breaker.<id>.*` | *(der Block oben)* | Dieselben Blätter für den einen Breaker, den `breaker('<id>')` auflöst — sticht den Default-Block Blatt für Blatt. |

Gelesen werden sie von der **`CircuitBreakerExtension`**, der Tür, die einen
Breaker über seine Id auflöst:

```ts
import { CircuitBreakerExtensionId } from 'actor-ts';

const payments = system.extension(CircuitBreakerExtensionId).breaker('payment-api');
await payments.call(() => fetch('https://payments.example/charge'));
```

`new CircuitBreaker({ … })` liest davon nichts und ist unverändert — das ist
die Tür für einen Breaker, dessen Settings im Code stehen.  Explizite Options
aus `breaker(id, options)` stechen weiterhin beide Blöcke, und genau das trägt
die zwei Dinge, die HOCON nicht ausdrücken kann: das `isFailure`-Prädikat und
die `random`-Naht.

**`default` ist reserviert**, und die beiden Lesarten fallen zusammen: es ist
der Block, von dem jeder Breaker erbt, *und* die Id, die `breaker()` ohne
Argument auflöst — ein Breaker namens `default` liest also genau den Block, der
ihn konfiguriert.  Deshalb liegen die Defaults in einem benannten Unterblock
und nicht direkt unter `actor-ts.circuit-breaker.*`: dort teilten sich Ids und
Blätter einen Namensraum, und `breaker('random-factor')` suchte seine Settings
in einer Zahl.

**`call-timeout` ist ein Kommentar statt eines Blattes**, weil das Weglassen
von `callTimeoutMs` den Timeout pro Aufruf *abschaltet* und der Validator `0`
ablehnt — „keine Deadline“ ist also ein Zustand, den nur ein fehlender Key
ausdrücken kann.  Geschrieben wirkt er ganz normal; der Block veröffentlicht
bloß keinen Default, der jedem aus Config aufgelösten Breaker eine Deadline
gäbe, die ein im Code gebauter nicht hat.

**`backoff-factor` und `random-factor` sind mit Absicht neutral.**  `1.0` und
`0.0` reproduzieren exakt das flache, ungejitterte Reopen-Fenster, der Block
ist also additiv, und beides einzuschalten ist eine bewusste Entscheidung des
Deployments.  Sind sie gesetzt, ist das Fenster
`reset-timeout × backoff-factor^(aufeinanderfolgende Öffnungen − 1)`, begrenzt
auf `max-reset-timeout` und dann um `± random-factor` gestreut; es fällt auf
`reset-timeout` zurück, sobald eine Probe gelingt und der Breaker schließt.

**`ignored-error-names` wird vor `isFailure` geprüft**, nicht danach.  Die
Liste ist die Hälfte des Klassifikators, die dem Betrieb gehört und aus einer
Config-Datei kommt, während das Prädikat einkompiliert ist — könnte das
Prädikat die Liste überstimmen, liefe der Key genau in den Deployments ins
Leere, die ihn gesetzt haben.

Diese `<id>`-Pfade tragen die Id, nach der dein Code `breaker(id)` fragt, und
lassen sich deshalb in `reference.conf` nicht aufzählen.

Prozess.  Die Optionen eines einzelnen Supervisors stechen sie, und sie
stechen die eingebauten Defaults — die üblichen drei Ebenen, pro Feld.  Ein
Supervisor als `BackoffSupervisor.factory({ child: Flaky })` übernimmt den
ganzen Block; einer, der `minBackoff` im Code nennt, den Rest davon.

Der Merge passiert im `preStart` des Supervisors — dem ersten Punkt, an dem
`system.config` erreichbar ist.  Ein Wert, den eine Konfigurationsdatei
außerhalb des zulässigen Bereichs setzt, lässt deshalb den Start des
Supervisors scheitern und nicht den Aufruf, der ihn gebaut hat.  Die Regel
ist dieselbe, die den im Code geschriebenen Wert ablehnt.

`drain-grace` und `child-name` fehlen bewusst.  Der erste hat einen aus
`min-backoff` abgeleiteten Default — ein publiziertes Literal würde ihn für
Supervisor mit kürzerem Fenster einfrieren; der zweite ist Identität der
Aufrufstelle, wo ein prozessweiter Wert schlicht falsch wäre.  Beide bleiben
im Code setzbar.

`url` zu einem `OptionsError`.  Schreibst du beides absichtlich, bekommst
du diesen Fehler weiterhin — genau darum geht es.

Diese `<name>`-Pfade nehmen den Namen, den dein Code an
`cache(name)` übergibt, und lassen sich deshalb nicht in
`reference.conf` aufzählen.  Einen Consumer allein für seinen eigenen
Key-Raum zu dimensionieren ist genau das, was die Empfehlung [ein Cache
pro Consumer](/de/cache/in-memory/#ein-cache-pro-consumer) braucht.

#### Eine Rolle wird benannt, nicht vergeben

`sharding.role` sagt, **welche** Rolle einen Typ hostet.  Der Key gibt dem
Node diese Rolle **nicht**.  Die eigenen Rollen eines Nodes sind Identität
statt Tuning, deshalb hat `ClusterOptions.roles` überhaupt keinen Config-Key
und bleibt im Code:

```ts
// On every node that should host the shards:
const clusterOptions = ClusterOptions.create()
  .withHost('10.0.0.7')
  .withPort(2551)
  .withRoles(['backend']);
```

```hocon
# In the config file every node shares:
actor-ts.sharding.role = "backend"
```

Setzt du nur die erste Hälfte, ändert sich nichts; setzt du nur die zweite,
wird **nie ein Shard zugeteilt** — der Koordinator findet kein passendes
Mitglied, jede Nachricht für den Typ sammelt sich im Routing-Puffer der Region,
und das einzige Anzeichen ist eine Warnung, die die Rolle und die Zahl der
ausgeschlossenen Regionen nennt.  Eine `role`, die kein Mitglied trägt, ist
dasselbe stille Versagen wie ein Tippfehler in `withRole` — nur dass sie aus
einer geteilten Config-Datei auf einen Schlag für jeden Sharded Type auf jedem
Node gilt.

Genau diese Asymmetrie ist auch der Grund für den Key: *welche* Rolle einen Typ
hostet, ist über ein Deployment hinweg einheitlich — *welche* Rollen ein Node
trägt, nicht.

Eine konfigurierte Rolle erreicht auch [Sharded Daemon
Processes](/de/cluster/sharding/sharded-daemon-process/), weil sie über
dasselbe `sharding.start(...)` gestartet werden.  Das ist so gewollt — wer
seine Entities auf `backend`-Nodes legt, meint in der Regel auch seine Daemons
— und `ShardedDaemonProcessOptions.withRole(...)` sticht sie pro Prozess
weiterhin.

`proxy` hat bewusst keinen Key.  Es ist Topologie pro Node und keine
deployment-weite Tatsache: ein zweites `start` mit abweichendem Wert wirft, und
ein von allen geteiltes `proxy = on` ließe niemanden mehr etwas hosten.

#### Einen Remember-Entities-Restore drosseln

Unter [`remember-entities`](/de/cluster/sharding/remember-entities/) bekommt
eine Region, der ein Shard zugeteilt wird, dessen komplettes Register
zugeschickt und startet daraus per Default jede Entität auf einmal — und das
für jeden Shard, den sie bekommt.  Ein Node-Neustart oder ein Rebalance öffnet
damit einen Journal-Replay pro erinnerter Entität, alle im selben Tick.
`constant-rate` verteilt diese Starts:

```hocon
actor-ts.sharding.entity-recovery {
  strategy = constant-rate
  constant-rate.frequency = 100ms
  constant-rate.number-of-entities = 5
}
```

Zwei Dinge an diesem Budget muss man deutlich sagen, weil beide sich leicht
andersherum lesen lassen:

- **Es gilt regionsweit.**  Fünf Entities pro 100 ms sind fünf *auf diesem
  Node*, egal wie viele Shards der Node hält.  Pro Shard gelesen hießen
  dieselben Zahlen 5 × die Shard-Anzahl, was auf einem 64-Shard-Cluster
  überhaupt keine Schranke mehr ist — dieselbe Verwechslung, derentwegen
  `max-entities` regionsweit gehalten wird.
- **Es drosselt Starts, keine Replays.**  Ein Replay läuft asynchron; einer,
  der länger dauert als das Fenster, überlappt also weiterhin den nächsten
  Batch.  Was dieser Key glättet, ist die Ankunftsrate; wie viele Recoveries
  gleichzeitig *laufen* dürfen, ist eine Sache der Persistenz und hier nicht
  einstellbar.

Nichts geht verloren: der Rückstand wird abgearbeitet, bis jede erinnerte
Entität wieder da ist, und eine Nachricht an eine Entität, die noch in der
Queue steht, erzeugt sie sofort — nur der Recovery-Schwall wartet.  Der Default
bleibt `all`, weil Drosseln verändert, *wann* eine Entität zurückkommt, und wie
schnell ein Journal die Replays verträgt eine Eigenschaft dieses Journals ist
und keine des Shardings.

#### Rebalance-Churn begrenzen

Die Default-[Allocation
Strategy](/de/cluster/sharding/allocation-strategy/) platziert einen Shard über
`shardId % candidates.length`; ein hinzukommender Node ändert die Antwort also
für die meisten Shards gleichzeitig.  Bei den ausgelieferten
`number-of-shards = 64` sind das 32 Shards bei einem Beitritt 1 → 2 Nodes,
**42 bei 2 → 3** und 46 bei 3 → 4 — jeder davon ein gestoppter Shard, jede
Entität darunter gestoppt, dann neu zugewiesen, neu erzeugt und, sofern sie
persistiert, neu abgespielt.  Angekündigt wird es auch nicht: der Koordinator
reagiert nicht auf ein `MemberUp`, der ganze Schwall kommt also mit dem
nächsten periodischen Tick.

Die beiden Limits begrenzen, wie viele davon **gleichzeitig in Bewegung** sein
dürfen:

```hocon
actor-ts.sharding {
  rebalance-absolute-limit = 0     # 0 = no absolute ceiling
  rebalance-relative-limit = 0.1   # fraction of number-of-shards
}
```

Drei Punkte dazu, die man ausdrücklich sagen sollte:

- **Gezählt wird, was gleichzeitig läuft, nicht was pro Tick startet.**  Ein
  Tick feuert alle `rebalance-interval`, während eine Übergabe ein ganzes
  `hand-off-timeout` stehen darf — sechs pro Tick ließen also rund dreißig
  gleichzeitig zu.  Der Koordinator budgetiert pro Tick die Obergrenze *minus
  dem, was schon unterwegs ist*.
- **Gedeckelt wird nur der freiwillige Pfad.**  Eine gestorbene Region
  hinterlässt Shards ganz ohne Besitzer; die werden sofort neu vergeben, mit
  oder ohne Obergrenze.  Diesen Pfad zu drosseln hieße, Shards unerreichbar zu
  lassen statt sie nur langsamer einschwingen zu lassen.
- **Nichts geht verloren, und kein Node wird zuerst leergeräumt.**  Was das
  Budget übrig lässt, schlägt die Strategy im nächsten Tick erneut vor, bis die
  Map ausgeglichen ist; und welche Shards zuerst gehen, wird im Round-Robin
  über ihre aktuellen Besitzer entschieden — eine Obergrenze, die einen Node
  leert, bevor sie den nächsten anfasst, ist schlechter als gar keine.

Setze `rebalance-relative-limit = 0` (das absolute Limit steht bereits auf
`0`), um das ungedeckelte Verhalten wiederherzustellen.

#### Eine verstummte Region erkennen

Lies erst den Geltungsbereich, bevor du danach greifst: das hier ist ein
**Auffangnetz für genau einen engen Fall**, und der Fall, den die meisten
meinen, ist schon ohne ihn abgedeckt.

Ein Node, der aufhört zu gossipen, wird vom [Failure
Detector](/de/cluster/failure-detector/) nach
`actor-ts.cluster.failure-detector.down-after` zwangsweise heruntergestuft — per
Default 5 s, und nicht abschaltbar — und der Koordinator vergibt seine Shards
aus dem daraus folgenden `MemberRemoved` neu.  Eine sauber gestoppte Region
sagt dem Koordinator auf ihrem Weg nach unten Bescheid.  Was beides nicht
abdeckt, ist eine Region, die **auf einem noch laufenden, noch gossipenden Node
verschwunden oder verklemmt** ist und deren Meldung nie ankam: sie geht genau
einmal raus, wird nicht quittiert, und ein Transportfehler auf dem Weg nach
unten wird nur geloggt und geschluckt.  Dann bleiben die Shards einem Actor
zugewiesen, den es nicht mehr gibt, und nichts heilt das — die Kandidatenmenge
wird ohne jede Lebendigkeitsprüfung aus der Registry abgeleitet.

```hocon
actor-ts.sharding.stale-region-detection {
  enabled = on
  heartbeat-interval = 5s
  stale-after = 20s
}
```

Vier Dinge sind vor dem Einschalten wissenswert:

- **Der Schalter steuert beide Hälften.**  Aus schlägt keine Region und fegt
  kein Koordinator, der Mechanismus kostet also überhaupt nichts.  An schickt
  jede Region jedes Sharded Type einen kleinen Frame pro `heartbeat-interval`.
- **Der Schlag geht pro Sharded Type, nicht pro Node.**  Zehn Typen auf einem
  Node sind zehn Frames pro Intervall, zusätzlich zu den Heartbeats des
  Clusters selbst.
- **Eine Region, die nie schlägt, wird nie entfernt.**  Genau das macht das
  Einschalten mitten in einem Rollout sicher: solange der Leader den Schalter
  an hat und einzelne Regionen noch nicht, sind diese Regionen schlicht noch
  nicht scharf — statt im Sekundentakt entfernt zu werden und sich in einer
  Schleife neu zu registrieren.
- **`stale-after` muss größer als `heartbeat-interval` sein**, und die
  ausgelieferten vier Intervalle sind Absicht: bei einem einzigen entfernt ein
  verlorener Frame eine gesunde Region und stoppt jede Entität unter jedem
  Shard, den sie hielt.  Ein Paar, das sich kreuzt, wird bei
  `sharding.start(...)` abgelehnt, und zwar gegen die *aufgelösten* Werte — das
  Überschreiben des einen kann den Default des anderen also nicht stillschweigend
  unterlaufen.

Ein `check-interval` gibt es bewusst nicht.  Der Sweep läuft auf dem
`rebalance-interval`-Tick mit, der ohnehin schon der Regler dafür ist, wie oft
der Koordinator auf die Shard-Map schaut — die Erkennungslatenz ist also
`stale-after` plus höchstens ein Tick.

Ein Setting für genau einen Typ gehört deshalb in den Builder; die
Config-Datei ist für die node-weite Grundeinstellung, die du ohne Rebuild
zwischen Staging und Produktion verschieben willst.  Die polymorphen Optionen
— der Entity-Actor, die Extraktoren, die Allocation Strategy, ein Lease, die
Stores — haben keine HOCON-Form und bleiben im Code.

### `actor-ts.coordinated-shutdown`

| Key | Default | Zweck |
| --- | --- | --- |
| `coordinated-shutdown.default-phase-timeout` | `5s` | Default-Timeout pro Phase.  Eine Phase, die es überschreitet, wird abgebrochen, damit die nächste noch läuft. |
| `coordinated-shutdown.terminate-actor-system` | `true` | Ob der eingebaute Terminator-Task in der finalen Phase `system.terminate()` aufruft. |
| `coordinated-shutdown.exit-process` | `false` | Ob nach Abschluss der Pipeline `process.exit(exit-code)` aufgerufen wird. |
| `coordinated-shutdown.exit-code` | `0` | Status, den der Exit trägt.  `0`–`255`; alles andere ist ein `ConfigError` beim Start. |
| `coordinated-shutdown.auto-register-tasks` | `true` | Ob Framework-Komponenten ihr eigenes Teardown registrieren — das HTTP-Unbind, das Schließen der Broker, das Cluster-Leave, das DevTools-Detach. |
| `coordinated-shutdown.run-by-process-signals` | `true` | Ob `runUntilTerminated()` und der Cluster-Bootstrap SIGTERM/SIGINT scharfschalten, wenn der Aufrufer keine Signale genannt hat. |
| `coordinated-shutdown.phases.<name>.timeout` | — | Budget für genau diese Phase; überschreibt `default-phase-timeout` nur für sie. |
| `coordinated-shutdown.phases.<name>.recover` | — | `false` lässt einen fehlgeschlagenen Task in dieser Phase die Pipeline anhalten, statt ihn zu loggen und weiterzugehen. |
| `coordinated-shutdown.phases.<name>.depends-on` | — | Phasen, die vorher laufen müssen.  Bei einer kanonischen Phase wird die Kante ergänzt; bei einem neuen Namen ist die Angabe Pflicht. |

`terminate-actor-system = false` entfernt nur den eingebauten Terminator —
in `ActorSystemTerminate` registrierte eigene Tasks laufen weiterhin.
Nutze es, wenn ein Host-Prozess die Lebensdauer des Systems besitzt und ein
Signal-Handler es nicht killen darf.

Der `phases`-Block ist das Config-Frontend zum Phasen-DAG und liefert selbst
keine Werte aus — seine Kinder sind nach *deinen* Phasen benannt, es gibt also
nichts, wofür sich ein Default veröffentlichen ließe:

```hocon
actor-ts.coordinated-shutdown.phases {
  service-requests-done { timeout = 30s }        # retime one canonical phase
  flush-metrics {                                # …and add one of your own
    timeout    = 3s
    recover    = false
    depends-on = ["before-actor-system-terminate"]
  }
  actor-system-terminate { depends-on = ["flush-metrics"] }
}
```

Ein Kind, das eine der zwölf kanonischen Phasen benennt, **verschmilzt** mit
ihr: weggelassene Felder behalten das, womit die Phase initialisiert wurde.
Jeder andere Name **deklariert** eine Phase, und dort ist `depends-on` Pflicht
— eine Phase ohne Kanten landet im ersten fertigen Batch und liefe vor
`before-service-unbind`, was nie gemeint war, wenn jemand eine Phase hinzufügt.
`depends-on` an einer kanonischen Phase wird der bestehenden Kante *hinzugefügt*
statt sie zu ersetzen; so kann eine Config-Datei `cluster-leave` nicht vor
`service-unbind` umhängen — die topologische Sortierung fängt Zyklen ab, nicht
eine Pipeline, die still in der falschen Reihenfolge läuft.  Die Reihenfolge in
der Datei spielt keine Rolle: zwei Phasen dürfen einander benennen und werden
abhängigkeitsweise registriert.  Ein nicht auflösbarer Name, ein Zyklus oder
ein unbekanntes Setting unter einer Phase ist ein `ConfigError` beim Start,
nicht beim Shutdown.

`run-by-process-signals` schaltet den *Default* um, nicht die Fähigkeit.  Wer
Signale explizit nennt — `runUntilTerminated(['SIGTERM'])` oder
`shutdownOnSignals` in den Bootstrap-Optionen —, installiert sie trotzdem, denn
explizite Optionen schlagen die Konfiguration.  Ausschalten ist für einen
Host-Prozess, der SIGTERM selbst besitzt: `runUntilTerminated()` wartet
weiterhin und hält die Event-Loop offen, es schaltet nur nichts scharf.

`exit-process` ist für den umgekehrten Fall: ein hängengebliebenes Handle
(ein offener Socket, eine gepoolte Verbindung, die ein Treiber nie
freigegeben hat) hält den Prozess am Leben, nachdem die Pipeline fertig
ist — von außen nicht von einem Hänger zu unterscheiden.  Per Default aus,
weil ein erzwungener Exit genau die Leaks verdeckt, die du eigentlich
finden willst.  `exit-code` ist der Status, den er übergibt — `0`, weil eine
bis zum Ende gelaufene Pipeline der Erfolgsfall ist; setze ihn dort, wo ein
Supervisor einen geplanten Drain von einem Absturz unterscheiden soll.

### `actor-ts.sharded-daemon-process`

| Key | Default | Zweck |
| --- | --- | --- |
| `sharded-daemon-process.liveness-interval` | `30s` | Takt des Sicherheitsnetz-Pings, der jeden Daemon-Index neu weckt — unabhängig davon, ob ein Cluster-Event gefeuert hat.  `0` schaltet ihn ab; das ereignisgetriebene Neuwecken bei `LeaderChanged` / `MemberRemoved` läuft ohnehin weiter.  Siehe [den Liveness-Heartbeat](/de/cluster/sharding/sharded-daemon-process/#liveness-heartbeat). |
| `sharded-daemon-process.role` | `""` | Nur Mitglieder mit dieser Rolle hosten Daemons.  `""` heißt hier **nicht** „unbeschränkt“ — siehe [eine nicht gesetzte Daemon-Rolle erbt die Sharding-Rolle](#eine-nicht-gesetzte-daemon-rolle-erbt-die-sharding-rolle) weiter unten.  Wie `sharding.role` benennt der Key eine Rolle, er vergibt sie nicht. |

Ein Daemon-Set ist ein Modul **auf** Sharding und keine Sharding-Stellschraube
— deshalb der eigene Block: `actor-ts.sharding.*` konfiguriert jeden
gesharderten Typ auf dem Knoten, diese beiden nur die Daemons.  Sie werden
einmal pro `ShardedDaemonProcess.init(...)` gelesen und unter das gelegt, was
der Aufruf explizit übergibt — die übliche Reihenfolge pro Feld:

```ts
// actor-ts.sharded-daemon-process.liveness-interval = 10s

const daemonOptions = ShardedDaemonProcessOptions.create<Tick>()
  .withName('reconciler')
  .withNumDaemons(8)
  .withActorFor((index) => () => new Reconciler(index));

ShardedDaemonProcess.init(system, cluster, daemonOptions);
// livenessIntervalMs 10_000 (config file) — nothing explicit overrides it
```

`name`, `numDaemons` und der Aktor pro Index haben kein Leaf.  Sie beschreiben
ein einzelnes Daemon-Set und kein Deployment, und eine Factory hat ohnehin
keine HOCON-Form.

#### Eine nicht gesetzte Daemon-Rolle erbt die Sharding-Rolle

`sharded-daemon-process.role` auf `""` heißt *keine daemon-spezifische
Meinung*, nicht *unbeschränkt*.  Das Daemon-Set startet als ganz normaler
gesharderter Typ, übernimmt also ohne Eintrag hier
[`actor-ts.sharding.role`](#actor-tssharding) genau wie jeder andere Typ:

```hocon
actor-ts.sharding.role = "backend"          # every sharded type
# sharded-daemon-process.role left at ""    # daemons follow along
```

Eine Rolle hier zu benennen schränkt *nur* die Daemons ein und überlässt die
übrigen gesharderten Typen dem globalen Key:

```hocon
actor-ts.sharding.role                = "backend"   # entities on the backend nodes
actor-ts.sharded-daemon-process.role  = "batch"     # daemons on the batch nodes
```

Derselbe Vorbehalt wie bei `sharding.role` gilt, und er trifft hier härter,
weil einem Daemon niemand eine erste Nachricht schickt: Eine Rolle, die kein
Up-Mitglied trägt, allokiert nichts — die Daemons starten also schlicht nie.
Der Coordinator loggt eine Zeile mit der Rolle, sobald sich eine Region
registriert hat und die Rolle sie herausgefiltert hat.

Extension — `DevTools.attach(system)` ist immer ein Aufruf im Code — die Keys
ändern also, *wie* eine Attachment sich verhält, nie *ob* es eine gibt.  Einen
`enabled`-Key gibt es bewusst nicht: ihn zu lesen hieße, das DevTools-Subsystem
samt eingebettetem UI-Bundle in jedes System zu importieren, das DevTools nie
öffnet.

**Ein konfigurierter Host trifft dieselbe Regel wie ein im Code gesetzter.**
Optionen werden einmal validiert, auf den gemergten Settings — `devtools.host
= "0.0.0.0"` wirft also einen `OptionsError` mit Feld `host`, genauso wie
`.withHost('0.0.0.0')` im Code.  `auth` und `ipAllowlist` sind Middleware und
haben keine HOCON-Form; genau deshalb ist `allow-remote` die einzige Antwort,
die eine Datei auf diese Regel geben kann.

Sieben Felder haben keinen Key.  `auth`, `ipAllowlist`, `backend`, `cluster`
und `replayFolds` sind Funktionen und lebende Objekte, die HOCON nicht
ausdrücken kann, und `uiDevelopmentRoot` ist eine Notluke für die
Panel-Entwicklung, deren eigene Doku sagt, sie in einer Anwendung nie zu
setzen.  Die letzten beiden sind eine Entscheidung, keine Unmöglichkeit:
`allow-ungated-mount` sagt etwas über den Code aus, der die Routen von
`mount()` bindet, nicht über ein Deployment, und `allow-message-sending` ist
die eine DevTools-Fähigkeit, die aus dem Browser *in* das laufende System
schreibt.  Beide bleiben neben dem Aufruf, den sie qualifizieren.

Ein im Code übergebenes `panels`-Objekt überschreibt die konfigurierten
Schalter **einzeln**, nicht als Ganzes: `.withPanels({ timeTravel: false })`
über einer Datei mit `panels { send = false }` lässt `send` aus.  Das ist die
übliche Präzedenz, eine Ebene tiefer angewandt — sonst würde ein einzelnes im
Code genanntes Panel jedes vom Betrieb abgeschaltete Panel wieder einschalten.

| Key | Default | Zweck |
| --- | --- | --- |
| `worker-cluster.workers` | `"auto"` | Anzahl Worker — `"auto"` verwendet `navigator.hardwareConcurrency`. |
| `worker-cluster.system-name` | `"worker-cluster"` | `ActorSystem`-Name, den jeder Worker hostet. |
| `worker-cluster.hostname` | `"worker"` | Hostname-Komponente der `NodeAddress` jedes Workers. |
| `worker-cluster.base-port` | `1` | Port des ersten Workers; jeder weitere Slot inkrementiert. |
| `worker-cluster.ready-timeout` | `10s` | Frist für den Hello/Init/Ready-Handshake pro Worker. |
| `worker-cluster.restart-policy` | `"on-failure"` | `always` / `on-failure` / `never`. |
| `worker-cluster.restart-min-backoff` | `200ms` | Wartezeit vor dem ersten Respawn eines abgestürzten Slots. |
| `worker-cluster.restart-max-backoff` | `10s` | Obergrenze für die Respawn-Wartezeit, die pro Versuch verdoppelt wird. |
| `worker-cluster.restart-random-factor` | `0.2` | ±-Jitter-Anteil auf jede Respawn-Wartezeit, in `[0, 1]`. |
| `worker-cluster.max-restarts` | `10` | Restarts pro Slot innerhalb des Fensters, bevor er stillgelegt wird; `-1` startet unbegrenzt neu. |
| `worker-cluster.restart-window` | `60s` | Gleitendes Fenster, über das das Restart-Budget zählt; `0` setzt es nie zurück. |

Die vier Duration-Keys lassen das `Ms`-Suffix ihrer Felder im Options-Objekt weg
(`ready-timeout` setzt `readyTimeoutMs`) und nehmen ein HOCON-Duration-Literal —
genauso, wie `logger.close-timeout` das Feld `closeTimeoutMs` speist.
`restart-random-factor` ist ein reiner Bruchteil, keine Duration.

Vier Felder haben bewusst keinen Key: `initData` ist Identität des einzelnen
Aufrufs, `backend` und `onWorkerPermanentlyDown` sind lebende Objekte, die eine
Config-Datei nicht ausdrücken kann, und `bootstrap` benennt ein Modul, das die
Runtime *ausführt* — `ACTOR_TS_CONFIG` und eine abgelegte `application.conf`
sind eine breitere Angriffsfläche als die Aufrufstelle, deshalb bleibt es ein
reines Code-Feld.

Die Validierung läuft auf den gemergten Settings, deshalb wird jeder dieser
Werte aus einer Datei mit einem `OptionsError` genauso abgelehnt wie aus Code:
ein leerer `system-name` oder `hostname`, ein `base-port` außerhalb von
`[1, 65535]`, ein `restart-random-factor` außerhalb von `[0, 1]`, ein negativer
Backoff oder ein negatives Fenster, ein `max-restarts` unter `-1` und ein
`restart-max-backoff` unterhalb von `restart-min-backoff`.

Diese Keys füllen `WorkerCluster.spawn(options)` für Felder auf, die der
Aufruf nicht setzt.  `spawn` ist ein Static ohne `ActorSystem` im Scope und
lädt die Config-Kette daher selbst — dieselbe, die `ActorSystem.create`
verwendet, inklusive `ACTOR_TS_CONFIG` und `./application.conf`.  Eine
unbekannte `restart-policy` wird mit einem `OptionsError` abgelehnt, statt
still „never" zu bedeuten.

```hocon
buffer = 64K
heap = 2G
```

Erkannte Einheiten: `B`, `K`, `M`, `G`, `T` — standardmäßig
binär (1024).

### Environment-Substitution

```hocon
port = ${?ACTOR_TS_PORT}              # nutze env, falls gesetzt, sonst fallback
log-level = ${?LOG_LEVEL}             # gleich
api-key = ${API_KEY}                  # required — Fehler, wenn env nicht gesetzt
fallback-port = ${?ENV_PORT}
fallback-port = ${fallback-port:-2552}  # default-if-empty Syntax
```

Verwende `${?ENV}` für optional, `${ENV}` für required.

### Includes werden nicht unterstützt

```hocon
include "shared-cluster.conf"   # Fehler: `include` wird nicht unterstützt
```

Eine Config-Quelle kann keine weitere Datei und keine URL benennen, die
hinzugeladen wird.  Das ist eine Entscheidung, keine Lücke: ein
aufgelöstes `include` überließe demjenigen, der die Config schreibt, die
Wahl, welche Pfade der Prozess liest — relativ zu einer Wurzel, die der
Parser gar nicht kennen kann.  Das Zusammenführen im Code belässt diese
Wahl beim Aufrufer.

```ts
import { Config } from 'actor-ts';

const shared = Config.parseFile('shared-cluster.conf');
const application = Config.parseFile('application.conf');
const config = shared.merge(application);
```

`merge` legt sein Argument obenauf, die lokale Datei gewinnt also — genau
die Reihenfolge, auf die das `include` oben hinauswollte.  Den geteilten
Inhalt in eine Datei zu kopieren funktioniert ebenfalls.

Der Parser sagt all das, wenn er auf ein `include` trifft, und zitiert
dabei Zeile und Ziel — eine aus Akka oder Pekko portierte Config
scheitert damit mit einer Antwort statt mit einem Rätsel.

### Reservierte Schlüssel

Drei Schlüssel werden in einer Config-Quelle überall abgelehnt — als
Schlüssel, als jedes Segment eines Pfadausdrucks und innerhalb einer
Substitution:

```hocon
__proto__.anything = 1   # Fehler: abgelehnt
constructor.x      = 1   # Fehler: abgelehnt
prototype          = 1   # Fehler: abgelehnt
value              = ${__proto__}   # Fehler: abgelehnt
```

Ein Schlüsselpfad wird auf ein einfaches Objekt expandiert, und eine
Zuweisung an `__proto__` schreibt in den Objekt-Prototypen statt einen
normalen Schlüssel anzulegen — würde man das zulassen, könnte eine
Config-Datei das Verhalten *jedes* Objekts im Prozess verändern. Der
Parser lehnt sie stattdessen mit der gewohnten Zeilen- und
Spaltenangabe ab.

Die Prüfung vergleicht exakt, ähnlich aussehende Schlüssel sind also
unproblematisch: `_proto_`, `constructorName` und `prototypes`
funktionieren normal.

#### Lesend sind nur eigene Schlüssel sichtbar

Drei abgelehnte Namen sichern die Schreibseite.  Die Leseseite ist
andersherum abgesichert — positiv — denn `Object.prototype` hat ein Dutzend
weitere Member, und eine Liste käme dabei nie hinterher:

```hocon
name = ${toString}    # Fehler: unaufgelöste Substitution — keine native Funktion
port = ${?valueOf}    # optional: fällt auf die Umgebung durch, dann weg
```

Jeder Zugriff — eine Substitution, `hasPath` und jeder typisierte Getter —
liest ausschließlich **eigene** Schlüssel, im Config-Baum wie in der
Umgebung.  Ein Name, der zufällig einem geerbten Member entspricht, geht
damit ins Leere, statt zu dem aufzulösen, was auf dem Prototypen liegt, und
`hasPath('toString')` ist `false`, solange die Config keinen eigenen
`toString`-Schlüssel deklariert.  Das bleibt erlaubt und funktioniert
weiterhin: ein eigener Schlüssel überdeckt den geerbten Member,
`toString = "mine"` liest sich also als `"mine"` zurück.

## Config im Code lesen

```ts
const actorSystemOptions = ActorSystemOptions.create().withConfig({
    'actor-ts.cluster.gossip-interval': '500ms',
  });
const system = ActorSystem.create(
  'my-app',
  actorSystemOptions,
);

// Innerhalb eines Actors / einer Extension:
const config = system.config;
const interval = config.getDuration('actor-ts.cluster.gossip-interval');
//      → 500 (in ms)
```

Das `Config`-Interface hat typisierte Getter: `getString`, `getNumber`,
`getBoolean`, `getDuration`, `getBytes`, `getStringList`, etc.
Fehlende Keys werfen, es sei denn, Du prüfst zuerst mit `hasPath`.

## Ladereihenfolge

```
1. REFERENCE_CONF                           ← gebündelte Defaults
2. application.conf (CWD)                   ← Projekt-Root, auto-geladen
3. Dateipfad aus `configFile`-Setting       ← expliziter Override
4. ENV-Var ACTOR_TS_CONFIG                  ← Pfad oder inline HOCON
5. Konstruktor `config: { ... }`            ← Code-Level-Override
6. Konstruktor-Feld-Overrides               ← explizite Felder schlagen Config
   (logLevel, dispatcher, scheduler, …)
```

Jede Schicht überlagert die vorherige.  Schicht 6
(Konstruktor-Felder) gewinnt immer für die Felder, die sie
abdeckt; alles andere fließt durch den HOCON-Merge.

### Wo der eingebaute Default steht

Schicht 1 ist `reference.conf` — aber nicht jede Einstellung hat dort
einen Key, und selbst die, die einen haben, brauchen einen Wert im Code
für den Fall, dass nichts konfiguriert ist.  Dieser Wert hat einen festen
Ort, damit immer auffindbar ist, worauf eine Einstellung zurückfällt:

- **Options-Defaults** stehen neben dem Feld, das sie belegen, in der
  passenden `XOptions.ts`.  `DEFAULT_MAX_ENTRIES` liegt in
  `InMemoryCacheOptions.ts`, `DEFAULT_NUM_SHARDS` in `ShardingOptions.ts`.
- **Alles andere** — Obergrenzen, Schranken und Timeouts ohne Option
  dahinter — steht in einer `Constants.ts`: `src/<subsystem>/Constants.ts`
  für ein einzelnes Subsystem, `src/util/Constants.ts` für Werte, die
  mehrere teilen.

Ein `reference.conf`-Blatt und sein Code-Fallback sind damit immer genau
zwei Dateien, und die zweite ist nach der ersten benannt.

## Validierung

Optionswerte werden **einmal validiert, zur Consume-Zeit, auf den
gemergten Settings** — nachdem die drei obigen Ebenen aufgelöst sind.
Weil die Prüfung auf dem gemergten Ergebnis läuft, gelten dieselben
Regeln, egal wie ein Wert ankam: über den fluenten Builder, ein einfaches
Settings-Objekt oder einen HOCON-Key.  Cross-Field-Regeln (z. B.
„`downThreshold` muss `unreachableThreshold` übersteigen") sehen die
finalen Werte.

Ein ungültiger Wert wirft einen **`OptionsError`** (aus dem
Paket-Root exportiert), der das betroffene Feld und die Erwartung nennt:

```text
MqttOptions: protocolVersion must be one of 4, 5 (got 6)
```

- Bei **Broker-Aktoren** (MQTT, Kafka, WebSocket-Client, …) wird der
  Fehler beim Start des Aktors (`preStart`) geworfen, nach der
  Pflichtfeld-Prüfung — ein *fehlendes* Pflichtfeld erscheint also
  weiterhin als `BrokerOptionsError`, und nur *vorhandene, aber
  ungültige* Werte werden zu `OptionsError`.
- Bei **Nicht-Broker-Konsumenten** (Caches, Leases, Sharding, …) wird der
  Fehler aus dem Konstruktor geworfen.

`OptionsError` ist verschieden von `ConfigError` (fehlerhaftes HOCON —
falscher Typ, fehlender Pfad) und `BrokerOptionsError` (ein
Broker-Pflichtfeld fehlt in jeder Ebene).  Ungesetzte optionale Felder
lösen ihn nie aus; sie fallen auf ihre Defaults zurück.

<Aside type="note" title="Eine abgelehnte URL wird mit maskierten Zugangsdaten gemeldet">
  ```text
  MqttOptions: brokerUrl must use protocol mqtt, mqtts (got "amqp://***@rabbit:5672/vhost")
  ```
  Jede Regel, die eine URL ablehnt — der Check-Helfer `url` und die
  Verbindungs-URL-Regeln der Mongo-, libSQL-, D1- und DynamoDB-Stores —
  ersetzt die Userinfo durch `***`, und zwar **sowohl** in der Meldung
  **als auch** in `OptionsError.value`.  Eine abgelehnte Broker-URL wird
  auf ERROR geloggt, wenn sie den `preStart` eines Aktors scheitern lässt,
  und ein Passwort, das einen Log-Aggregator erreicht hat, muss rotiert
  werden — löschen genügt nicht.

  Sonst wird am Wert nichts angefasst — keine Normalisierung, kein
  angehängter Schrägstrich, kein kleingeschriebener Host —, du erkennst
  also weiterhin, was du getippt hast, und ein Wert, der gar keine URL ist
  (`":memory:"`, `"file:local.db"`), kommt unverändert zurück.  Dieselbe
  Maskierung steht deinem eigenen Code als
  [`redactUrlCredentials`](/de/reference/utility-helpers/) zur Verfügung.
</Aside>

```ts
import { CircuitBreaker, CircuitBreakerOptions, OptionsError } from 'actor-ts';

// Nicht-Broker-Consumer validieren in ihrem Konstruktor, daher wird der
// Fehler synchron geworfen und ein einfaches try/catch funktioniert:
try {
  const options = CircuitBreakerOptions.create()
    .withMaxFailures(0);             // ungültig — muss eine positive Ganzzahl sein
  new CircuitBreaker(options);       // validiert im Konstruktor
} catch (e) {
  if (e instanceof OptionsError) {
    console.error(`bad option ${e.field}: ${e.message}`);
  }
}
// Bei einem Broker-Actor wird der OptionsError erst in preStart geworfen
// und als ActorInitializationError verpackt — er taucht also über die
// Supervision auf (nicht im try/catch des Spawn-Aufrufs).
```
