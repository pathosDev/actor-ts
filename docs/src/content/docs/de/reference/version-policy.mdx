actor-ts ist **pre-1.0**.  Die API-Oberfläche ist stabil genug, um
damit zu bauen, aber **erwarte Breaking Changes** bei Minor-Versions-
Bumps, bis 1.0 ausgeliefert wird.

Diese Seite ist die **ehrliche Einschätzung** dessen, was stabil ist,
was experimentell ist und was zu erwarten ist.

## Versionierung bis 1.0

Pre-1.0:

- **Patch-Versionen (0.x.Y)** — Bugfixes, keine Breaking Changes.
- **Minor-Versionen (0.X.0)** — neue Features, können Breaking
  Changes enthalten.
- **Major-Version (1.0.0)** — API-Stabilisierungs-Commitment.

Lies das
[CHANGELOG](https://github.com/pathosDev/actor-ts/blob/main/CHANGELOG.md)
vor dem Upgrade von Minor-Versionen.

Ein Minor-Bump kann auch den **Cluster-Wire** ändern. Das CHANGELOG hält
das pro Release fest, fasst es aber nicht über Releases hinweg zusammen —
und wenn ein Release ihn ändert, ist ein Rolling Deployment nicht sicher:
der Cluster muss in einem Schritt aktualisiert werden.
[Upgrade-Strategien](/de/operations/upgrades/upgrade-strategies/#cluster-wire-kompatibilität-pro-release)
trägt die Tabelle pro Release; zwei aufeinanderfolgende Releases stehen darauf.

## Security-Fixes

Es gibt **keine Maintenance-Branches**, "supported" heißt also die
jeweils letzte veröffentlichte Version und sonst nichts. Ein
Security-Fix landet auf `develop` und geht mit dem nächsten
Release raus; er wird nie auf ein älteres `0.x` zurückportiert.

[`SECURITY.md`](https://github.com/pathosDev/actor-ts/blob/main/SECURITY.md)
ist der Meldekanal und — vor dem Melden noch nützlicher — die
Scope-Grenze: Der klartextige, nicht authentifizierte
Cluster-Transport-Default ist ein dokumentierter Default und keine
Schwachstelle, eine dokumentierte Gegenmaßnahme, die nicht hält,
was sie verspricht, dagegen schon. Was die Release-Pipeline selbst
garantiert, steht auf der Seite
[Supply Chain](/de/operations/security/supply-chain/).

## Nach 1.0

Sobald 1.0 ausgeliefert ist, gilt **striktes SemVer**:

- **Patch (X.Y.Z+1)** — nur Bugfixes.
- **Minor (X.Y+1.0)** — Ergänzungen; rückwärtskompatibel.
- **Major (X+1.0.0)** — Breaking Changes; expliziter Migration
  Guide.

Das Framework folgt einer typischen konservativen SemVer-Kadenz —
Major-Versions-Bumps sind selten; Minor-Versionen fügen Features
hinzu, ohne bestehenden Code zu brechen.

## Was "stabil" hier bedeutet

**Stabil** = wir erwarten nicht, diese API zu brechen.  Aber
pre-1.0:

- Methodensignaturen können optionale Parameter erhalten.
- Config-Keys können neue Sub-Keys erhalten.
- Neue Return-Type-Felder können erscheinen (additiv).

**Nicht** stabil:

- Methoden oder Klassen umbenennen.
- Funktionalität entfernen.

Wenn ein Breaking Change an einer "stabilen" Oberfläche passiert,
wird das **CHANGELOG es prominent markieren** mit einer
Migrationsnotiz.

## Was "experimentell" bedeutet

**Experimentell** = wir iterieren noch an der API oder
Implementierung:

- Methodensignaturen können sich ändern.
- Verhalten kann sich auf nicht-offensichtliche Weise ändern.
- Performance-Charakteristiken sind noch nicht optimiert.

Experimentelle Features in der Produktion zu verwenden ist **OK**
— wir verwenden sie selbst — aber erwarte, Code bei
Minor-Versions-Bumps zu aktualisieren.

Wenn ein Feature **tief** experimentell ist (wir sind nicht
sicher, ob es überleben wird), sagt die Doku das explizit auf der
Feature-Seite.

## Deprecation-Politik

**Vor 1.0 gibt es keinen garantierten Deprecation-Zyklus.** Wenn etwas
umbenannt, ersetzt oder entfernt wird, kann das ein **harter Schnitt**
in einer Minor-Version sein — die alte API ist in genau der Version
weg, die die neue einführt. Dafür gibt es Ehrlichkeit: das
**CHANGELOG kennzeichnet jeden Breaking Change deutlich** (ein
`BREAKING`-Marker + eine kurze Migrationsnotiz), sodass ein Blick
hinein vor einem Minor-Upgrade genau zeigt, was sich geändert hat.
Beispiele und Doku werden in derselben Änderung auf die neue API
umgestellt.

**Nach 1.0** wird das zu einem echten Deprecation-Zyklus verschärft:
umbenannte oder ersetzte APIs funktionieren mindestens eine ganze
Major-Version weiter — mit einer Deprecation-Warnung vor der
Entfernung.

## Spezifische Roadmap-Items

Dinge, die wir hinzuzufügen / zu ändern planen:

- **OTel-Auto-Instrumentation-Politur** — bessere Default-Spans
  + Attribute.
- **Mehr Cluster-Transports** — WebSocket-Option für
  Browser-Bridge, QUIC für Edge.
- **Sharding Rebalance v2** — schlauere Strategien als
  Least-Shard.
- **Mehr CRDT-Typen** — Counter-Set, Sequence CRDT für
  geordnete Listen.

Keines davon bricht bestehenden Code; sie sind additiv.

## Issues melden

Für Bugs oder Feedback:

- **GitHub Issues** — für Bugs, Feature Requests,
  Designfragen.
- **Pull Requests** — werden nicht angenommen.  Der Issue-Tracker
  ist der Beitragskanal; öffne ein gut ausgearbeitetes Issue und
  stimme den Ansatz dort ab.

Tagge Issues mit dem relevanten Bereich (Cluster, Persistenz,
etc.), damit sie die richtigen Code-Owner schneller erreichen.
