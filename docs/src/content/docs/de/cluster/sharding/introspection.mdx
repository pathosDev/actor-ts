import { Aside } from '@astrojs/starlight/components';

Eine Region zu starten gibt dir genau eine Ref — die der Region — und
das war bisher die ganze Geschichte. Du konntest Nachrichten *durch*
das Sharding schicken, aber es nichts fragen: nicht "welche Shards gibt
es", nicht "wo liegt Shard 7", nicht "gib mir einen Handle auf Entity
`user-42`".

Vier APIs auf `ClusterSharding` schließen diese Lücke, dazu ein
Cluster-Event für die Push-Seite.

## Die Shards auflisten

`shards(typeName)` antwortet clusterweit, von jedem Node aus:

```ts
const shards = await cluster.sharding.shards<CounterCommand>('counter');

for (const shard of shards) {
  console.log(
    `shard ${shard.shardId} on ${shard.node}`,
    `— ${shard.entityCount} entities`,
    shard.local ? '(here)' : '',
  );
}
```

Jeder Eintrag ist ein `ShardInfo`:

```ts
type ShardInfo<TMessage = unknown> = {
  readonly shardId: number;
  readonly node: NodeAddress;      // node currently hosting the shard
  readonly regionPath: string;     // region on that node
  readonly entityCount: number;    // live entities when its region answered
  readonly resident: boolean;      // shard actor materialised at that moment
  readonly local: boolean;         // hosted by the node that asked
  readonly ref: ActorRef<ShardMessage<TMessage>>;
};
```

`resident` unterscheidet einen Shard, der läuft und gerade leer ist, von
einem, der
[leer passiviert wurde](/de/cluster/sharding/overview/#shards-passivieren-ebenfalls)
— `entityCount: 0` meldet beides. Auf die Erreichbarkeit hat es keinen
Einfluss: `ref` funktioniert so oder so. Lies es, wenn du
`shardPassivationIdleMs` einstellst oder zählen willst, wie viele Actors
ein Node tatsächlich hält.

Der Eintrag trägt eine **lebende Ref**, nicht nur Platzierungsdaten —
eine Abfrage beantwortet also sowohl "was gibt es da draußen" als auch
"wie rede ich damit". Der Preis: `ShardInfo` ist nicht
JSON-serialisierbar. Wenn du eine serialisierbare Sicht brauchst, nimm
[`shardMap(typeName)`](#die-letzte-karte-ohne-abfrage) oder den
Management-Endpunkt
[`GET /cluster/shards`](/de/observability/management/http-endpoints/),
der genau diese serialisiert.

Shards ohne Zuhause **fehlen** in der Liste. Niemand hat nach ihnen
gefragt, also hatte der Koordinator keinen Anlass, sie zu platzieren:
ein Typ mit 64 Shards, der drei Entity-IDs gesehen hat, meldet ein bis
drei Shards, nicht 64.

<Aside type="caution" title="Ein Schnappschuss, kein Abonnement">
  `entityCount` stimmte in dem Moment, in dem die hostende Region
  geantwortet hat, und `node` hält nur bis zum nächsten Rebalance. Halte
  die `ref` fest, wenn du weiter mit einem Shard reden willst — die Ref
  überlebt es, dass die Entity-Zahl veraltet, die Node-Adresse nicht.
</Aside>

### Was es kostet

Der Koordinator besitzt die Shard-Karte, aber **nicht** die
Entity-Zahlen — die kennt nur die Region, die den Shard hostet. Der
Aufruf fächert deshalb an alle registrierten Regions aus und joint die
Antworten gegen die Allokationskarte. Also ein zusätzlicher Round-Trip.

Die Fan-out-Frist ist eine *Teilantwort*-Frist: eine Region, die zu
langsam ist oder zwischen Karten-Schnappschuss und Fan-out gegangen ist,
steuert `entityCount: 0` bei, statt den ganzen Aufruf scheitern zu
lassen. Du bekommst eine vollständige Shard-Liste mit einer
konservativen Zahl, keine Exception.

## Eine Ref auf einen Shard

```ts
const shard = await cluster.sharding.shardRefFor<CounterCommand>('counter', 7);
```

Hat Shard 7 noch kein Zuhause, **platziert** dieser Aufruf ihn — genau
das, was eine erste Nachricht an ihn auch getan hätte — und antwortet,
sobald der Koordinator entschieden hat.

Ein Shard, der
[leer passiviert wurde](/de/cluster/sharding/overview/#shards-passivieren-ebenfalls),
braucht keine Sonderbehandlung: die Ref bleibt über die Lücke hinweg
gültig, und der Shard wird neu erstellt, sobald etwas für ihn eintrifft.
Lokal passiert das schon beim Fragen, denn ein Handle auf einen nicht
laufenden Actor wäre ein Handle auf nichts; bei einem Shard auf einem
anderen Node stellt die Ref über dessen Region zu, die den Shard vor dem
Weiterleiten materialisiert. `shardRefFor()` weckt einen lokalen Shard
also sofort, einen entfernten das erste `tell`.

Die Ref ist das echte Ding. Ein Shard ist ein Actor
(`/system/cluster/sharding/region-counter/shard-7`), und die Ref trägt diesen Pfad als
Identität, egal von welchem Node du gefragt hast — was sich unterscheidet,
ist der Weg: direkt zum Actor, wenn dieser Node ihn hostet, über die
besitzende Region, wenn nicht. `tell` funktioniert damit von überall:

```ts
// Bring an entity up without sending it a message.
shard.tell({ kind: 'sharding.StartEntity', entityId: 'user-42' });

// Address one entity through the shard.
shard.tell({
  kind: 'sharding.EntityEnvelope',
  entityId: 'user-42',
  message: { id: 'user-42', kind: 'increment' },
});
```

Und um zu fragen, was ein Shard hält:

```ts
const stats = await shard.ask<ShardStats>({ kind: 'sharding.GetShardStats' });
// { shardId: 7, entityCount: 2, entityIds: ['user-42', 'user-99'] }
```

<Aside type="caution" title="`ask` auf eine *entfernte* Shard-Ref läuft in den Timeout">
  `ask` erzeugt eine Einweg-Antwort-Ref, und die ist von einem anderen
  Node aus nicht adressierbar — sie hat keinen Platz im Actor-Baum,
  gegen den die Antwort aufgelöst werden könnte. Zwei Auswege: schicke
  `GetShardStats` mit dem `self` deines eigenen Actors als `replyTo`
  (ein echter Actor-Pfad, von überall erreichbar), oder nimm `shards()`,
  dessen Antwort die Region nach Hause routet. `ask` auf eine *lokale*
  Shard-Ref ist unproblematisch.
</Aside>

## Eine Ref auf eine Entity

`entityRefFor` ist das Gegenstück zur Region-Ref — ein Handle auf eine
einzelne Entity, wo immer sie gerade liegt:

```ts
const entity = cluster.sharding.entityRefFor<CounterCommand>('counter', 'user-42');

entity.tell({ kind: 'increment', by: 1 });
const value = await entity.ask<number>({ kind: 'get' });
```

Zwei Dinge sind anders als beim Reden mit der Region:

- **Die Nachricht trägt ihren Routing-Key nicht mehr selbst.** An eine
  Region zu senden heißt, dass `extractEntityId` die ID wieder aus
  deiner Nachricht herausgraben muss — jeder Nachrichtentyp braucht also
  eine. Der Handle benennt seine Entity direkt, `extractEntityId` wird
  nie befragt.
- **Er ist synchron zu bekommen.** Der Shard ist
  `hash(entityId) % numShards`, es muss also nichts nachgeschlagen
  werden. Eine Nachricht für einen Shard, dessen Zuhause noch unbekannt
  ist, puffert die Region — genau wie bisher.

Location-transparent ist er, weil er über die lokale Region routet, und
die weiß bereits, wie sie jeden Node erreicht. Eine Proxy-Region
(`startProxy`) reicht aus, um einen auszugeben — der Node muss selbst
nichts hosten.

`ask` funktioniert auf einer Entity-Ref unabhängig davon, wo die Entity
liegt: die Region reicht deinen Sender an die Entity durch, die Antwort
kommt also direkt zu dir zurück.

## Der Karte folgen

Für die Push-Seite abonnierst du `ShardMapChanged`:

```ts
import { match, P } from 'ts-pattern';
import { ShardMapChanged } from 'actor-ts/cluster';

cluster.subscribe((event) =>
  match(event)
    .with(P.instanceOf(ShardMapChanged), (e) => onShardMapChanged(e))
    .otherwise(() => onOtherEvent()));

function onShardMapChanged(event: ShardMapChanged): void {
  // event.type     — the sharded type name
  // event.shards   — ReadonlyMap<shardId, regionKey>
  // event.regions  — the region table, with per-region shard counts
  // event.version  — increments once per broadcast
}
```

Das Event feuert auf **jedem** Node, nicht nur auf dem Leader: der
Koordinator broadcastet an jede Region, und die Region publiziert lokal.
Genau das macht es für einen Anwendungs-Listener oder ein
Per-Node-Dashboard überhaupt brauchbar.

Broadcasts werden **zusammengefasst**. Allokationsänderungen kommen
einzeln pro Shard, und ein frischer Cluster platziert alle Shards auf
einmal — `version` zählt deshalb Broadcasts, nicht einzelne Zuweisungen.
Lies sie nicht als "wie viele Shards sind umgezogen".

### Die letzte Karte, ohne Abfrage

Weil das Event jeden Node erreicht, kann `ClusterSharding` sich einfach
das letzte merken — genau das gibt `shardMap(typeName)` als reines JSON
zurück:

```ts
const map = cluster.sharding.shardMap('cart');
if (map !== null) {
  // map.regions   — one entry per region, with its shard ids
  // map.shardHome — [{ shard, regionKey }], one per placed shard
  // map.version   — the coordinator's broadcast counter
  // map.leader, map.takenAt — who published it, and when it arrived here
}
```

Synchron und kostenlos: kein Round-Trip, kein `DistributedData`, kein
`coordinatorStateStore`. Es ist das, was der Endpunkt
[`GET /cluster/shards`](/de/observability/management/http-endpoints/)
serialisiert.

Der Rückgabewert ist `null`, bis der Koordinator einmal für den Typ
publiziert hat — das schließt jeden Node ein, der weder Region noch
Proxy dafür gestartet hat, denn der Koordinator broadcastet nur an
registrierte Regionen. Und `shardHome` bleibt leer, bis wirklich ein
Shard platziert ist, während sich `regions` schon bei der Registrierung
füllt: lies `regions` für "wer nimmt teil", `shardHome` für "was ist
platziert".

Greif stattdessen zu [`shards()`](#die-shards-auflisten), wenn du
Entity-Zahlen oder lebende Refs brauchst, und zu `ShardMapChanged`, wenn
du die Änderungen statt des letzten Stands willst.

## Kann die Region schon routen?

Eine Region registriert sich beim Coordinator, der auf dem Leader läuft —
über einen eigenen Retry-Timer. Das ist ein anderer Schritt als der
Cluster-Beitritt, und **Membership-Konvergenz ist kein Ersatz dafür**: ein
vollständig konvergierter Cluster kann sehr wohl eine Region halten, die
sich noch nicht registriert hat.

```ts
if (cluster.sharding.isRegistered('cart')) { /* the coordinator knows this region */ }
```

Synchron und gratis, wie [`shardMap`](#der-karte-folgen), und auf demselben
Weg gespeist — aus einem `ShardRegionRegistered`-Event, das die Region
dieser Node publisht, sobald der Coordinator sie bestätigt. `false` für
einen Typ, den diese Node nie gestartet hat, und für einen, dessen
Registrierung wegen eines `numShards`-Mismatch abgelehnt wurde.

```ts
cluster.subscribe((event) => {
  if (event instanceof ShardRegionRegistered) console.log(event.type, 'can route');
});
```

Das Event ist node-lokal wie jedes Cluster-Event: es sagt etwas über die
Region *dieser* Node. Wer die Registrierungen aller Nodes an einer Stelle
sehen will, bridgt es — es entsteht auf genau einer Node, ist also ein
sinnvoller Bridge-Kandidat:

```ts
cluster.eventStream.bridge(ShardRegionRegistered);
```

<Aside type="note" title="Keine Voraussetzung fürs Senden">
  Eine Nachricht, die vor Abschluss der Registrierung gesendet wird, geht
  **nicht** verloren. Die Region puffert alles, dessen Shard-Home unbekannt
  ist, und fragt den Coordinator danach; sobald sie registriert ist, fragt
  sie für alles bereits Gepufferte erneut — die Nachricht kommt also
  verspätet an, statt verworfen zu werden.

  Ablaufen kann ein `ask`, das um eine solche Nachricht herumliegt: es
  trägt seine eigene Frist, und die läuft, während die Nachricht im Puffer
  wartet. Dies ist also das Signal, auf das man vor einem `ask` mit knappem
  Budget wartet — und das, was eine Readiness-Probe melden sollte — kein
  Gate vor einem `tell`.
</Aside>
