Der Cluster-Transport ist die **Leitung** zwischen Cluster-Nodes —
er liefert Gossip-Nachrichten, Heartbeats und Anwendungs-Envelopes
(deine `tell`s an Remote-Actors). Zwei Implementierungen liegen
dem Framework bei:

| Transport | Verwendung |
| --- | --- |
| **`TcpTransport`** | Produktion. Echte TCP-Sockets, optional TLS. |
| **`InMemoryTransport`** | Tests. Schleift Frames durch In-Process-JS-Strukturen — kein Networking. |

Beide implementieren dieselbe `Transport`-Schnittstelle, sodass das
Cluster-Verhalten unabhängig vom eingesteckten Transport identisch
ist.

## Die Schnittstelle

```ts
interface Transport {
  readonly self: NodeAddress;
  start(): Promise<void>;
  shutdown(): Promise<void>;
  setHandler(handler: (from: NodeAddress, message: WireMessage) => void): void;
  send(to: NodeAddress, message: WireMessage): void;
  disconnect(peer: NodeAddress): void;
  peers(): NodeAddress[];
  holdsConnectionTo?(peer: NodeAddress): boolean;
}
```

Kleine Oberfläche — Bootstrap, Senden, Empfangen, Trennen. Der
Cluster steckt einen Handler ein und bekommt einen Strom
eingehender Wire-Nachrichten samt Absenderadresse.

`holdsConnectionTo` ist optional. Die Methode beantwortet, ob
`send(peer, …)` über eine Verbindung hinausginge, die der Transport
bereits hält — bestätigt oder noch im Handshake —, statt eine neue
aufzubauen, und der Cluster fragt sie, bevor ein Anwendungs-Frame an
einen Node geht, der kein Member ist (siehe
[Cluster-Sicherheit](/de/operations/security/cluster-security/)).
Ein eigener Transport ohne sie funktioniert weiterhin: Der Cluster
fällt auf `peers()` zurück, das nur bestätigte Verbindungen auflistet,
sodass ein Frame an einen Nicht-Member in diesem Handshake-Fenster
abgelehnt statt eingereiht wird.

## TcpTransport (Standard)

```ts
import { Cluster, ClusterOptions, TcpTransport, TcpTransportOptions } from 'actor-ts/cluster';

const clusterOptions = ClusterOptions.create()
  .withHost('0.0.0.0')
  .withPort(2552)
  .withSeeds(['...']);
const cluster = await Cluster.join(
  system,
  clusterOptions,
  // transport defaultet auf TcpTransport — kein expliziter Pass nötig
);
```

Was er tut:

- **Lauscht** auf `host:port` auf eingehende Verbindungen — das ist das
  Paar, an das gebunden wird, ein Wildcard-Host gehört also hierher.
- **Kündigt** `advertisedHost:advertisedPort` in seinem Handshake an und
  schlüsselt Peers danach. Das ist die Identität des Nodes, wird deshalb
  getrennt aufgelöst und ist nie eine Wildcard; ungesetzt folgt der Host
  `host`, sofern der routebar ist, und der Port ist `port`. Siehe
  [Cluster — Überblick](/de/cluster/overview/).
- **Verbindet** sich nach Bedarf mit Peers (beim ersten Send oder
  zu Seeds bei Join-Zeit).
- **Frame-Größen-Cap** (Standard 16 MiB) — Frames, die größer sind,
  werden abgelehnt, um DoS via gefälschtem Längenpräfix zu
  verhindern.
- **Auto-Reconnect** — fällt eine Verbindung mitten im
  Cluster-Leben aus, wird beim nächsten Send neu verbunden.

### Was ein Hop kostet

Gemessen auf diesem Transport über Loopback, mit dem fernen Node auf einem
Worker-Thread (Bun 1.4.2, Windows 11, 18.09.2026): ein Cross-Node-`tell`
kostet rund **22 µs** pro Nachricht, ein Cross-Node-`ask` rund **245 µs**
pro Roundtrip — gegenüber ~260 ns und ~6 µs für denselben Actor im Prozess.
Das ist der ganze Draht — Envelope, getaggter JSON-Frame, Socket,
`FrameDecoder` samt Guards, Zustellung — und liegt im Rauschen des
`MessageChannelTransport`-Hops, den das
[Worker-Mesh](/de/cluster/worker-mesh/) bezahlt; der Socket selbst ist also
nicht der teure Teil.  Quelle ist `benchmarks/cluster/tcp-message-cost.ts`,
der einzige Benchmark, der diesen Transport überhaupt übt: der
Framing-Round-Trip braucht `TcpTransport` über Loopback, wie die Grenzen des
In-Memory-Transports weiter unten sagen, und der ferne Node läuft auf einem
eigenen Thread, weil zwei Nodes auf einer Event-Loop nicht lesen können,
während ein Burst geschrieben wird — ein Burst, der länger ist als
`outbound-queue-size`, verliert seine ältesten Frames an diese Grenze (#931).
Der Benchmark prüft jeden Batch, das wird also ein Throw und keine Zahl.

### Runtime-Backends

`TcpTransport` redet nicht direkt mit dem OS — er läuft über ein
`TcpBackend`-Interface mit jeweils einer Implementierung pro
Runtime:

| Runtime | Backend | Zugrundeliegende API |
| --- | --- | --- |
| Bun | `bunTcpBackend` | `Bun.listen` / `Bun.connect`, und Buns `node:net` / `node:tls` für einen Dial, der abgebrochen werden kann |
| Node | `nodeTcpBackend` | `node:net` / `node:tls` |
| Deno | `denoTcpBackend` | `Deno.listen` / `Deno.connect` |

Automatisch erkannt über `getTcpBackend()`. Normalerweise denkst du
nicht darüber nach — derselbe `TcpTransport` läuft auf jeder
Runtime. Auf Bun nutzen die Dials des Transports allerdings nicht
`Bun.connect`: Jeder Dial trägt seine Connect-Frist als Abort-Signal (siehe
[Assoziations-Lebenszyklus](#assoziations-lebenszyklus)), und ein natives
`Bun.connect` lässt sich nicht abbrechen — sie laufen deshalb über Buns eigenes
`node:net` / `node:tls`, das es kann. Der Listener bleibt bei `Bun.listen`.

#### Backpressure

Jedes Backend hält, was der Kernel noch nicht annimmt, und sagt es auch:
`TcpSocketLike.write` antwortet `false`, sobald ein Socket mehr hält als die
High-Water-Mark seiner Runtime, und `onDrain` des Backends meldet, wann er
wieder mehr annehmen kann (#931). `TcpTransport` hört bei diesem `false` auf,
an den Peer zu schreiben, und hält für ihn höchstens `outbound-queue-size`
ganze Frames — dieselbe Grenze und dieselbe Drop-Oldest-Policy wie der Puffer
vor dem Handshake —, die er beim Drain in Reihenfolge schreibt. Ein Frame wird
nie abgeschnitten: Ein Peer, der nicht mehr liest, sieht einen Frame-Strom mit
Lücken, und dieser Node loggt eine WARN, wenn eine Backpressure-Episode zu
verwerfen beginnt, und eine mit der Zahl der verworfenen Frames, wenn der
Socket wieder abläuft. Ein geordnetes Schließen (`disconnect`, `shutdown`)
schreibt das Gehaltene vor seinem FIN, damit die `leave`-Frames, die
`Cluster.leave` kurz vor dem Herunterfahren sendet, nicht hinter einem
langsamen Leser verloren gehen.

Vor 0.19 bremste nichts den Sender, und die beiden Enden einer
Bun-Verbindung versagten unterschiedlich: Die Seite, die gewählt hat, schreibt
über `node:net`, das ohne Grenze hielt, was der Peer nicht abnehmen konnte, und
ein Socket, den `Bun.listen` angenommen hat, schrieb nativ und verwarf, was der
Kernel nicht annahm — der Decoder des Empfängers las den Rest des Streams dann
ab der Mitte eines Frames, und die Verbindung wurde getrennt. Node und Deno
pufferten an beiden Enden ohne Grenze.

### Optionales TLS

```ts
import { Cluster, ClusterOptions, NodeAddress, TcpTransport, TcpTransportOptions } from 'actor-ts/cluster';

const transportOptions = TcpTransportOptions.create().withTls({
  cert:           '...',     // PEM
  key:            '...',     // PEM
  ca:             '...',     // optionales CA-Bundle
  rejectUnauthorized: true,
});
const transport = new TcpTransport(
  NodeAddress.parse('my-app@10.0.0.5:2552'),
  system.log,
  transportOptions,
);

const clusterOptions = ClusterOptions.create()
  .withHost('10.0.0.5')
  .withPort(2552)
  .withSeeds(seeds)
  .withTransport(transport);
await Cluster.join(
  system,
  clusterOptions,
);
```

TLS-gewrapptes TCP, alles-oder-nichts pro Cluster. Die Adresse des
Transports ist die eigene des Knotens: `my-app` ist der Name, mit dem
das Actor-System erzeugt wurde, und `withHost` / `withPort` nennen
denselben Host und Port.

Ein Peer, der wie hier über ein IP-Literal adressiert wird, wird gegen
ein **IP-SAN** in seinem Zertifikat geprüft. Gib dem Zertifikat jedes
Knotens deshalb seine Adresse als Subject Alternative Name mit
(`IP:10.0.0.5`) und lass `serverName` ungesetzt — SNI transportiert nur
Hostnamen, ein Dial zu einer IP kündigt also keinen an. Ein Dial zu
einem Hostnamen kündigt ihn per SNI an und prüft den Peer gegen ein
DNS-SAN; setze `serverName` nur, wenn der zu prüfende Name vom
gewählten Host abweicht. Auf Deno wird er zugleich zum gewählten Host,
weil `Deno.connectTls` für beides nur ein Feld hat. Siehe
[Cluster-Sicherheit](/de/operations/security/cluster-security/)
für das Produktionsrezept.

### Frame-Größe

```ts
const transportOptions = TcpTransportOptions.create().withMaxFrameBytes(64 * 1024 * 1024);
const transport = new TcpTransport(self, log, transportOptions);
```

Überschreibe den Frame-Größen-Cap pro Frame. Standard 16 MiB reicht
für typischen Cluster-Traffic (Gossip, Heartbeats, kleine
Envelopes). Größere Werte verbessern *nicht* den allgemeinen
Durchsatz — sie sind nur für einzelne große Nachrichten relevant.

### Assoziations-Lebenszyklus

Vier Schranken entscheiden, was eine Gegenstelle, die eine TCP-Verbindung zu
diesem Port aufbauen kann, den Knoten halten lassen darf. Sie gelten für jeden
`TcpTransport` und sind dieselben vier, die ein Betreiber unter
[`actor-ts.remote`](/de/reference/configuration/#actor-tsremote) für den
Transport setzt, den der Cluster sich selbst baut — neben einer fünften,
`connectTimeoutMs`, die die eigenen Dials dieses Knotens begrenzt statt dessen,
was ein Fremder ihn halten lassen kann:

```ts
const transportOptions = TcpTransportOptions.create()
  .withHandshakeTimeoutMs(5_000)
  .withOutboundQueueSize(1_000)
  .withMaxInboundConnections(1_024)
  .withIncompleteFrameIdleMs(30_000);
const transport = new TcpTransport(self, log, transportOptions);
```

| Schranke | Deckt ab | Löst aus mit |
| --- | --- | --- |
| `handshakeTimeoutMs` | Eine Verbindung, die ihre Hälfte des Handshakes nie spricht — ein Dial, der aufging und nie sein `hello-ack` bekommt, ein angenommener Socket ohne `hello`. | Ein `WARN`, das die Frist und die mit ihr verworfenen Frames nennt. |
| `connectTimeoutMs` | Ein Dial, der nie aufgeht — kein TCP-Connect, oder ein TLS-Handshake, der nie fertig wird.  Ungesetzt ist sie `handshakeTimeoutMs`. | Ein `WARN`, dass der Dial nicht verbinden konnte, und der Dial wird abgebrochen. |
| `outboundQueueSize` | Frames, die für einen Peer gehalten werden, der sie gerade nicht annehmen kann. | Die ältesten fallen weg, plus ein `WARN` je Verbindung. |
| `maxInboundConnections` | Dass sich die Kosten pro Verbindung durch Sockets im Loop vervielfachen. | Der neueste Socket wird abgelehnt, ein `WARN` je Sättigungsepisode. |
| `incompleteFrameIdleMs` | Eine Verbindung, die gesprochen hat und dann mitten im Frame verstummt ist. | Ein `WARN` mit der Zahl gepufferter Bytes, dann wird die Verbindung verworfen. |

`handshakeTimeoutMs` ist bewusst **ein** Wert für beide Richtungen. Die
wählende Seite startet ihre Uhr vor dem TCP-Connect und dem TLS-Handshake, die
annehmende erst nach dem Accept — mit einer Zahl hat der Peer, der es noch
versucht, also immer zuerst aufgegeben. `incompleteFrameIdleMs` muss darüber
bleiben — ein Socket, der überhaupt nichts sendet, erreicht die Stall-Frist nie,
der Handshake-Timer ist also das Einzige, was ihn zurückholt — und die
Konstruktion wirft, wenn das nicht gilt. Geprüft wird das Paar, mit dem der
Transport *läuft*: Setzt man nur einen der beiden Werte, wird er gegen den
eingebauten Default des anderen geprüft. `.withIncompleteFrameIdleMs(1_000)`
allein wird also abgelehnt, weil die Handshake-Frist, gegen die er liefe, der
Default von 5 s ist. Keine der fünf hat eine „Aus"-Schreibweise: `0` wird für
jede abgelehnt.

Ein Dial läuft gegen zwei Fristen, die zusammen gestellt werden, sobald er
beginnt. `connectTimeoutMs` gibt einen Dial auf, der nicht aufgegangen ist — der
TCP-Connect und bei einem TLS-Dial der TLS-Handshake —, und sein `WARN` lautet
`could not connect to … within N ms`. Ist der Dial aufgegangen, gibt
`handshakeTimeoutMs` ihn auf, wenn kein `hello-ack` kommt, mit
`connected to …, but no hello-ack came within N ms`. Ungesetzt ist die
Connect-Frist die Handshake-Frist, die eine Frist, die ein Dial vorher hatte;
setze sie niedriger, um früher zu erfahren, dass ein Peer nicht da ist, während
ein langsamer weiterhin die ganze Handshake-Frist zum Antworten bekommt. Sie darf
`handshakeTimeoutMs` nicht überschreiten, das denselben Dial vom selben Moment an
begrenzt — die Konstruktion wirft, und ein alleiniges
`.withConnectTimeoutMs(10_000)` wird gegen den Default von 5 s abgelehnt.

Wer eine der beiden Fristen verpasst, wird aufgegeben statt nur vergessen: Der
Transport bricht den Connect ab, und der Socket darunter wird zerstört, statt so
lange weiterzuverbinden, wie das OS es versucht. Ein Dial, der vor seiner
Connect-Frist scheitert — abgelehnt, nicht auflösbar, ein Zertifikat, das die CA
nicht signiert —, meldet ebenfalls die `could not connect`-Zeile, mit dem Fehler
der Runtime als Anhang statt zitiert, weil der Fehlercode einer Runtime die
Ursache falsch benennen kann: Bun meldet unter Windows einen unbeantworteten
Connect als `ECONNREFUSED`. Das gilt auf jeder Runtime, weil jedes Backend einen
TLS-Dial erst dann als aufgegangen meldet, wenn sein Handshake abgeschlossen
ist, Deno eingeschlossen: `Deno.connectTls` löst schon beim TCP-Connect auf,
also führt das Deno-Backend den Handshake selbst aus, bevor es die Verbindung
herausgibt. Ein Zertifikat, das die CA nicht signiert, ist deshalb auch dort ein
Dial, der nicht verbinden konnte, und ein Peer, der den Connect annimmt und den
Handshake verschleppt, fällt der Connect-Frist zu.

Ein Teil einer Kombination lässt sich nicht abbrechen. Deno hat keinen Weg, den
TCP-Connect eines TLS-Dials abzubrechen (`Deno.connectTls` nimmt kein Signal);
ein Dial, der noch beim Verbinden aufgegeben wird, wird deshalb verworfen und
seine Verbindung geschlossen, sobald sie auftaucht, während der Connect selbst
weiterläuft, bis er gelingt oder das OS aufgibt. Ein Dial, der während seines
Handshakes aufgegeben wird, wird sofort verworfen, doch Deno beendet die
TCP-Verbindung darunter nicht: Unter Deno 2.6.8 behält die Gegenseite diesen
Socket, bis sie ihn selbst schließt.

Ein selbst gebauter Transport trägt seine eigenen Werte. Der Cluster reicht die
des Config-Blocks nur an einen Transport weiter, den *er* konstruiert hat, nie
an einen per `withTransport(…)` übergebenen.

## InMemoryTransport (Tests)

```ts
import { InMemoryTransport, NodeAddress, Cluster, ClusterOptions } from 'actor-ts/cluster';
import { TestKit } from 'actor-ts/testkit';

// Kein Bus zu verdrahten — In-Memory-Transports finden einander über eine
// prozessglobale Registry, indiziert nach der eigenen NodeAddress jedes Transports.
const tk1 = TestKit.create('node-1');
const tk2 = TestKit.create('node-2');

// Die self-Adresse jedes Transports muss dem system@host:port seines Knotens entsprechen.
const clusterOptions = ClusterOptions.create()
  .withHost('1')
  .withPort(0)
  .withSeeds(['1:0'])
  .withTransport(new InMemoryTransport(new NodeAddress('node-1', '1', 0)));
await Cluster.join(
  tk1.system,
  clusterOptions,
);

const cluster2Options = ClusterOptions.create()
  .withHost('2')
  .withPort(0)
  .withSeeds(['1:0'])
  .withTransport(new InMemoryTransport(new NodeAddress('node-2', '2', 0)));
await Cluster.join(
  tk2.system,
  cluster2Options,
);
```

Die Factory `inMemoryTransport(system, host, port)` ist eine Kurzform für
dieselbe Konstruktion — sie leitet die `NodeAddress` aus `system.name` ab.

Wie es funktioniert:

- Eine **prozessglobale Registry** routet Nachrichten zwischen
  In-Process-Transports.
- Jeder Transport registriert sich beim Start per Adresse in der Registry.
- `send(to, message)` schlägt den Empfänger in der Registry nach und ruft
  dessen Handler direkt auf — keine Sockets, keine Serialisierung
  zu Bytes.

Wird von [MultiNodeSpec](/de/testing/multi-node-spec/) — dem
Multi-Node-Test-Harness — verwendet, um Multi-Node-Cluster in
**einem Prozess** hochzufahren.

### Was er nicht simuliert

- **Netzwerkausfälle.** Per Default liefert die Registry zuverlässig.
  Für Fault Injection würdest du einen eigenen `Transport` mit
  Drop-/Delay-/Reorder-Logik implementieren.
- **Latenz.** Die Zustellung ist synchron innerhalb einer
  Event-Loop-Drehung.
- **Serialisierung.** Nachrichten werden per Referenz, nicht in
  Bytes übergeben — und `TcpTransport` ist der einzige Transport,
  der überhaupt serialisiert: `MessageChannelTransport` reicht das
  Envelope an `postMessage`, dieser hier gibt das Objekt direkt an
  den Handler des Empfängers. Um also den echten
  Framing-Round-Trip (`encodeFrame` / `FrameDecoder`, der einen
  **getaggten JSON-Tree** rahmt, nicht rohes JSON) zu üben,
  brauchst du `TcpTransport` über Loopback. Der CBOR-Codec ist von
  *keinem* Cluster-Transport aus erreichbar; teste ihn direkt oder
  über [HTTP-Marshalling](/de/http/marshalling/).

## Eigener Transport

`Transport` gegen eine andere Drahtverbindung zu implementieren ist
selten, aber möglich. Beispiele:

- **WebSocket-Transport** — für Cluster-Teilnehmer im Browser
  (theoretisch; nicht implementiert).
- **MessageChannel-Transport** — für Cluster mit Worker-Threads in
  einem einzelnen OS-Prozess. Wird vom "Worker-Mesh"-Muster
  genutzt.

Die Schnittstelle ist klein genug, dass eine kompetente
Implementierung ~200 Zeilen Code ist; die Schwierigkeit liegt
darin, die Framing- und Heartbeat-Semantik zu treffen, die der
Cluster erwartet.

## Diagnostik

```ts
const peers = transport.peers();   // aktuell verbundene Adressen
```

`peers()` ist auch das, was der Readiness-Check
`cluster-transport` des Frameworks liest: ein Knoten, der noch
Member erwartet und zu keinem davon eine Verbindung hat, ist
abgeschnitten — `/ready` antwortet dann mit 503, damit ein Load
Balancer nicht mehr dorthin routet.  Siehe
[Health Checks](/de/observability/management/health-checks/).
Beachte: `InMemoryTransport.peers()` meldet jeden im Prozess
registrierten Transport unabhängig vom Verbindungszustand — ein
dagegen geschriebener Test kann dieses Fehlschlagen nicht
beobachten.

Der Transport legt keine Metriken pro Verbindung direkt offen —
nutze die Metrik-Extension des Clusters, um Verbindungszahlen und
gesendete/empfangene Bytes pro Peer zu bekommen.

Für tiefergehende Inspektion (spezifische Frame-Inhalte) aktiviere
Debug-Logging am System:

```ts
const actorSystemOptions = ActorSystemOptions.create().withLogLevel(LogLevel.Debug);
const system = ActorSystem.create('my-app', actorSystemOptions);
// Suche nach [tcp-transport] Log-Zeilen
```

## Multiplexing

Eine einzige TCP-Verbindung zwischen zwei Nodes trägt:

- **Gossip-Nachrichten** — Cluster-Mitgliedschaftsaustausche.
- **Heartbeat-Nachrichten** — Failure Detection.
- **Envelope-Nachrichten** — deine `tell`s, mit Routing-Info
  kodiert.
- **Subsystem-Nachrichten** — Sharding-Protokoll, PubSub-Gossip,
  DistributedData-Replikation.

Alles auf denselben TCP-Stream gemultiplext. Es gibt kein
Prioritäts-Routing — Heartbeats und dein Bulk-Traffic teilen sich
die Leitung. Für die meisten Workloads ist das in Ordnung; für
explizite Isolation (Bandbreite für Cluster-Steuerung reservieren)
bräuchte man einen eigenen Transport mit Per-Channel-Framing.

import { Aside } from '@astrojs/starlight/components';

<Aside type="caution" title="Transports sind standardmäßig nicht authentifiziert">
  ```ts
  new TcpTransport(self, log);   // ← kein TLS, keine Auth
  ```
  Plain TCP ist in einem privaten Netzwerk in Ordnung. Auf jeder
  Internet-Strecke (selten für Cluster, aber möglich) konfiguriere
  TLS + ein Shared Secret. Siehe
  [Cluster-Sicherheit](/de/operations/security/cluster-security/).
</Aside>

<Aside type="caution" title="MTU und Frame-Größe">
  ```ts
  // Ein 1,5 MB großer tell geht durch einen einzelnen TCP-Frame-Versuch
  remoteRegistry.tell({ kind: 'upload', data: bigBuffer });
  ```
  Große Envelopes werden auf TCP-Ebene fragmentiert und auf der
  Empfangsseite wieder zusammengesetzt. Der Frame-Größen-Cap am
  Transport lehnt sie ab, wenn sie das konfigurierte Limit (16 MiB
  Standard) überschreiten. Für große Daten nutze einen Nebenkanal
  (S3, HTTP) und übergib Referenzen.
</Aside>

<Aside type="caution" title="Localhost-Loopback ist speziell">
  ```ts
  // Zwei Nodes auf derselben Maschine:
  host: '127.0.0.1', port: 2552      // Node 1
  host: '127.0.0.1', port: 2553      // Node 2
  ```
  Das funktioniert (TCP-Loopback ist echtes Networking), aber
  jeder Node braucht einen **eindeutigen Port**. Für
  Cluster-in-einem-Prozess-Tests ohne Ports nutze
  `InMemoryTransport`.
</Aside>
