description: Wie oft Cluster-Mitglieder Gossip austauschen — steuert Konvergenzgeschwindigkeit vs Netzwerk-Geschwätz. Default 1 s passt für die meisten Cluster. Für große Cluster hochdrehen, für latenz-sensitiven Failover runter.
---

Cluster-Membership propagiert per **Gossip** — alle
`gossipIntervalMs` schickt jedes Mitglied seine Membership-Sicht an
einen zufälligen erreichbaren Peer, der sie mit seiner eigenen
zusammenführt und nichts zurückschickt. Nach ein paar Runden
konvergiert der Cluster.

```ts
const clusterOptions = ClusterOptions.create()
  .withHost(host)
  .withPort(port)
  .withSeeds(seeds)
  .withGossipIntervalMs(1_000);
Cluster.join(system, clusterOptions);    // default
```

Der Default ist **1 Sekunde**. Die meisten Cluster müssen ihn nie
ändern.

## Was er steuert

| Niedriger (z. B. 250 ms) | Default (1 s) | Höher (z. B. 5 s) |
| --- | --- | --- |
| Schnellere Konvergenz | Ausgewogen | Langsamere Konvergenz |
| Mehr Gossip-Nachrichten | Moderater Traffic | Weniger Traffic |
| Ausfall-Urteile verbreiten sich früher | Standard | Ausfall-Urteile verbreiten sich später |

Gossip verbreitet ein Ausfall-Urteil; es fällt keines. Der Failure
Detector jedes Nodes entscheidet auf seinem eigenen Tick, alle
`actor-ts.cluster.failure-detector.heartbeat-interval`, anhand dessen,
was er von jedem Peer gehört hat, und ein niedrigeres Gossip-Intervall
bringt dieses Urteil nur früher zu den anderen Nodes. Wer Ausfälle
früher erkennen will, tunt stattdessen den
[Failure Detector](/de/operations/tuning/failure-detector/).

Konkret:

- Ein 5-Node-Cluster bei 1 s Gossip → typische Konvergenz nach
  einem Join: 2-3 Sekunden.
- Bei 250 ms Gossip: ~700 ms.
- Bei 5 s: ~10-15 Sekunden.

## Wann senken

Unter 1 Sekunde drücken, wenn:

- **Latenz-sensitiver Failover** — Singleton- oder Sharding-Muster,
  bei denen ein Leader-Wechsel im Sub-Sekunden-Bereich propagieren
  soll. 500 ms ist vernünftig; 250 ms ist aggressiv.
- **Kleiner Cluster (≤5 Nodes)** — das Gossip-Volumen bleibt
  handhabbar.
- **Ruhiges Netzwerk** — keine sonstigen Einschränkungen;
  schneller ist okay.

## Wann erhöhen

Über 1 Sekunde anheben, wenn:

- **Großer Cluster (20+ Nodes)** — das Gossip-Volumen wächst im
  Worst Case clusterweit O(N²). 5 s verlangsamt die Konvergenz
  proportional, reduziert aber den Netzwerkrauschpegel deutlich.
- **Bandbreiten-beschränktes Netzwerk** — Cross-Region- oder
  Cross-WAN-Cluster, in denen schwatzhaftes Gossip Verschwendung
  ist.
- **Stabiler Cluster** — ändert sich selten; schnelleres Gossip
  hilft nicht.

## Die Bandbreiten-Mathematik

Per-Node-Gossip-Bandbreite grob:

```
   gossip_size × (1 / gossipIntervalMs) × peers_per_round
```

Per-Cluster:

```
   N × gossip_size × (1 / gossipIntervalMs)
```

Mit:

- **gossip_size** ~100-500 Bytes pro Mitglied in der Sicht. In einem
  10-Node-Cluster liegen Gossip-Nachrichten bei ~1-2 KB.
- **peers_per_round** = 1 (ein zufälliger Peer pro Tick).
- **N** = Cluster-Größe.

Für einen 50-Node-Cluster bei 1 s Default-Gossip:

```
   50 × ~5 KB × 1/s = 250 KB/s gesamt
```

Vernachlässigbar im LAN. Im High-Latency-WAN bei 10 ms RTT
verlängert jede Gossip-Runde die In-Flight-Zeit um 10 ms —
konvergiert langsamer als man hoffen würde.

## Wechselwirkung mit anderen Timings

Der Großteil der periodischen Arbeit des Clusters läuft auf **eigenen
Timern**; die Gossip-Kadenz taktet also weniger, als es scheinen mag:

| Operation | Getaktet durch | Was Gossip dafür tut |
| --- | --- | --- |
| Konvergenz nach `join` | `gossipIntervalMs` | Direkt — langsameres Gossip = langsameres Up. |
| Beförderung zu `up` (Leader-Aktionen) | `gossipIntervalMs` | Direkt — sie läuft bei jedem Gossip-Tick, siehe unten. |
| Unreachable-Erkennung | `actor-ts.cluster.failure-detector.heartbeat-interval` | Verbreitet das Urteil an die anderen Nodes. Ein Gossip-Frame ist ein Lebenszeichen für den Peer, der ihn gesendet hat, nicht für die Mitglieder, die er nennt, und trägt keine Last-Seen-Zeiten. |
| Abräumen unerreichbarer Mitglieder | `actor-ts.cluster.failure-detector.heartbeat-interval` | Nichts — der Reaper ist derselbe Detector-Tick. |
| Sharding-Rebalance | `actor-ts.sharding.rebalance-interval` | Verbreitet die Membership-Änderungen, auf die der Coordinator reagiert. |
| DistributedPubSub-Topic-Propagation | `actor-ts.cluster.pub-sub.gossip-interval` (1 s) | Nichts — der Mediator gossipt auf seinem eigenen Timer. |
| Receptionist-Service-Registry | `actor-ts.cluster.receptionist.gossip-interval` (1 s) | Nichts — der Receptionist gossipt auf seinem eigenen Timer. |

Ein langsameres `gossipIntervalMs` verlangsamt, wie schnell sich
Membership-Neuigkeiten verbreiten — Joins, Beförderungen und die
Urteile, zu denen der Detector jedes Nodes kommt —, und sonst nichts in
dieser Tabelle. Erkennung, Rebalancing und die beiden Registries
behalten ihre eigene Kadenz; tune sie über ihre eigenen Keys. Wie der
Detector von einem Peer hört, steht auf der
[Failure-Detector-Seite](/de/cluster/failure-detector/#heartbeats-sind-explizit-lebenszeichen-ist-jeder-frame).

### Was tatsächlich auf dem Gossip-Tick läuft

**Leader-Aktionen.** Zu Beginn jedes Gossip-Ticks, vor dem Push dieses
Ticks, befördert der Leader `joining`- und `weakly-up`-Mitglieder zu
`up` (sobald `actor-ts.cluster.minimum-members-before-up` es erlaubt),
und dasselbe tut er noch einmal, nachdem er einen angenommenen
Gossip-Frame gemergt hat. Eine Beförderung auf dem Tick geht mit dem
Push dieses Ticks hinaus; `gossipIntervalMs` bestimmt also auch, wie
schnell ein neues Mitglied `up` erreicht. Ein eigenes Intervall für
Leader-Aktionen gibt es nicht.

Jeder periodische Cluster-Timer — Gossip, Heartbeats,
Failure-Detection, Tombstone-Pruning und die optionale
Statistik-Stichprobe aus `actor-ts.cluster.publish-stats-interval` —
feuert seinen ersten Tick ein volles Intervall nach dem Start des
Nodes, nie sofort. Die Ausnahme ist der Seed-Kontakt: Der erste
Versuch passiert beim Start, nur die Wiederholungen warten auf
`actor-ts.cluster.seed-retry-interval`.

## Empfohlene Werte

| Cluster-Größe | Netzwerk | Empfohlenes `gossipIntervalMs` |
| --- | --- | --- |
| 3-5 Nodes | LAN | 250-500 ms |
| 5-15 Nodes | LAN | 1 s (Default) |
| 15-50 Nodes | LAN | 1-2 s |
| 50+ Nodes | LAN | 2-5 s |
| Cross-Region | WAN | 2-5 s |
| Latenz-sensitiv | LAN | 250-500 ms |

<Aside type="caution" title="Tuning per Bauchgefühl">
  ```ts
  gossipIntervalMs: 100;   // ✗ "machen wir's schnell"
  ```
  Tune nicht blind. Miss Konvergenzlatenz (`SelfUp` bis
  voll-konvergiert) und Gossip-Bandbreite in deiner echten
  Umgebung. Die Defaults sind vernünftig — ändere nur mit Evidenz.
</Aside>

<Aside type="caution" title="Asymmetrische Werte über Nodes hinweg">
  ```ts
  // node-A: gossipIntervalMs: 250
  // node-B: gossipIntervalMs: 1000
  ```
  Jeder Node nutzt sein eigenes Intervall zum **Senden**, empfängt
  aber in der Kadenz, in der die Peers senden. Asymmetrische Werte
  erzeugen verwirrendes Konvergenzverhalten. Lass jeden Node dasselbe
  `gossipIntervalMs` nutzen.
</Aside>

<Aside type="caution" title="Sehr schnelles Gossip + viele Mitglieder">
  ```ts
  // 100-Node-Cluster bei 100ms Gossip
  ```
  100 ms × 100 Nodes = 1000 Nachrichten/sec clusterweit. Jede trägt
  die volle Membership. Bei genügend Skala dominiert das den
  eigentlichen Workload-Traffic. Bei großen Clustern auf 500 ms
  deckeln.
</Aside>
