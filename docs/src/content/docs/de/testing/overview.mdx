Actor-Systeme sind naiv schwer zu testen, weil zwei Dinge von
außen schwer sind:

- **Asynchronität** — jedes `tell` passiert später; Assertions
  müssen warten.
- **Zeit** — Receive-Timeouts, geplante Retries, Gossip-Runden
  hängen alle von der Uhr ab.

Das **TestKit** des Frameworks gibt dir Werkzeuge, um beides zu
kontrollieren:

| Werkzeug | Löst |
| --- | --- |
| **`TestKit`** | Ein einsatzbereites ActorSystem mit leisem Logging + Helper-Methoden. |
| **`TestProbe`** | Ein Fake-Actor, der Nachrichten für Assertions erfasst. |
| **`ManualScheduler`** | Ein Virtual-Clock-Scheduler — Zeit schreitet nur fort, wenn du es sagst. |
| **`MultiNodeSpec`** | Mehrere Cluster-Nodes in **einem Prozess** für Cluster-Szenario-Tests hochfahren. |
| **`ParallelMultiNodeSpec`** | Nodes in separaten Prozessen laufen lassen, wenn Isolation zählt. |

Die ersten drei sind für **Unit- + Integrationstests** eines
einzelnen Actor-Systems; die letzten zwei für **verteilte
Szenarien**.

## Ein minimaler Test

```ts
import { describe, it, expect } from 'bun:test';
import { match } from 'ts-pattern';
import { Actor, ActorRef } from 'actor-ts';
import { TestKit } from 'actor-ts/testkit';

type IncrementCommand = { kind: 'increment' };
type GetCommand = { kind: 'get'; replyTo: ActorRef<number> };
type Command = IncrementCommand | GetCommand;

class Counter extends Actor<Command> {
  private count = 0;
  override onReceive(command: Command): void {
    match(command)
      .with({ kind: 'increment' }, () => this.onIncrement())
      .with({ kind: 'get' }, (c) => this.onGet(c))
      .exhaustive();
  }

  private onIncrement(): void { this.count++; }
  private onGet(command: GetCommand): void { command.replyTo.tell(this.count); }
}

describe('Counter', () => {
  it('inkrementiert und antwortet', async () => {
    const tk = TestKit.create('counter-spec');
    const probe = tk.createTestProbe();

    const counter = tk.system.spawnAnonymous(Counter);
    counter.tell({ kind: 'increment' });
    counter.tell({ kind: 'increment' });
    counter.tell({ kind: 'get', replyTo: probe as ActorRef<number> });

    await probe.expectMessage(2);
    await tk.shutdown();
  });
});
```

Zwei Dinge, die das TestKit hier erledigt:

- **`TestKit.create(name)`** baut ein frisches ActorSystem mit
  leisem Logging — kein Konsolen-Spam während Test-Läufen.
- **`probe.expectMessage(2)`** assertet, dass die nächste Nachricht,
  die die Probe empfängt, exakt `2` ist, mit einem
  Default-Timeout von 3 Sekunden.

`tk.shutdown()` am Ende ist kritisch — ohne ihn hinterlässt der
Test ein lebendes System + laufenden Dispatcher, und der
Test-Prozess kann hängen.

## Die drei Schichten

### Unit — Actor isoliert

```ts
const tk = TestKit.create();
const probe = tk.createTestProbe();
const ref = tk.system.spawnAnonymous(() => new MyActor(probe));
ref.tell({ kind: 'do' });
await probe.expectMessage('done');
await tk.shutdown();
```

`MyActor` ist mit `probe` als Callback-Ziel konstruiert — er
`tell`t die Probe anstelle dessen, was er in Produktion `tell`en
würde. Tests asserten auf das, was die Probe sieht.

Das ist die kanonische Form — siehe
[TestKit](/de/testing/testkit/) und
[TestProbe](/de/testing/test-probe/).

### Zeit-deterministisch — `ManualScheduler`

```ts
const { kit, scheduler } = TestKit.withManualScheduler();
const probe = kit.createTestProbe();

const ref = kit.system.spawnAnonymous(() => new ScheduledThing(probe));
ref.tell({ kind: 'start' });

scheduler.advance(5_000);   // virtuelle Zeit springt 5 Sekunden
await probe.expectMessage({ kind: 'fired' });

await kit.shutdown();
```

Actor, die `context.timers.startSingleTimer` oder
`system.scheduler.scheduleOnce` nutzen, bekommen ihr Feuern vom
Manual-Scheduler getrieben — kein echtes `setTimeout`, keine
Flakiness.

Siehe [ManualScheduler](/de/testing/manual-scheduler/).

### Verteilt — `MultiNodeSpec`

```ts
import { MultiNodeSpec, TestProbe } from 'actor-ts/testkit';

const spec = new MultiNodeSpec({ roles: ['frontend', 'worker-1', 'worker-2'] });
await spec.start();
await spec.awaitMembers('frontend', 3);   // warten, bis alle drei konvergieren

// Jede Rolle ist ein vollständiges ActorSystem — via systemFor(role) erreichen:
const probe = new TestProbe(spec.systemFor('frontend'));
const remote = spec.systemFor('worker-1').spawnAnonymous(Worker);
remote.tell({ kind: 'do', replyTo: probe });
await probe.expectMessage({ kind: 'done' });

await spec.stop();
```

Drei Actor-Systeme joinen einen Cluster innerhalb eines Test-
Prozesses, mit dem In-Memory-Transport. Nützlich zum
Verifizieren von Sharding-Verhalten, Cluster-Singleton-
Failover, Distributed-Data-Merge-Semantik — alles ohne ein
Docker-Compose-Setup.

Siehe [MultiNodeSpec](/de/testing/multi-node-spec/).

## Was testen

Drei Kategorien:

1. **Reines Verhalten** — gib dem Actor eine Sequenz von
   Nachrichten, assertete auf die Probe. Die meisten
   Actor-Unit-Tests sehen so aus.
2. **State + Persistenz** — für PersistentActor teste den
   Recovery-Pfad explizit, indem du den Actor stoppst und neu
   spawnst. Assertete, dass der wiederhergestellte State mit dem
   übereinstimmt, was du aus der Event-Sequenz erwarten würdest.
3. **Verteiltes Verhalten** — für Cluster-Features gibt dir
   MultiNodeSpec einen „real genug"-Cluster, um Sharding-
   Placement, Singleton-Failover usw. zu testen.

## Auf Zustand warten, nicht auf verstrichene Zeit

Fast jeder flakige Actor-Test hat dieselbe Form: ein fester Sleep als
Platzhalter für einen Hintergrundschritt, danach eine Assertion auf den
Zustand, den dieser Schritt erzeugt.

```ts
// ✗ 100 ms ist die Latenz einer unbelasteten Maschine
await new Promise((resolve) => setTimeout(resolve, 100));
expect(store.saved).toEqual(['a', 'b']);
```

Die Zahl stammt aus einem Lauf, der grün war — sie kodiert also eine Maschine
an einem Tag. Unter Last dauert der Schritt länger, und die Assertion liest
einen Zustand, den das System noch gar nicht erreicht hat — gemeldet als
*falscher* Wert statt als verspäteter. Die Zahl zu erhöhen versteckt den Flake
und verlängert jeden Lauf, auch die überwältigende Mehrheit, der ein Bruchteil
gereicht hätte.

Stattdessen den beobachtbaren Zustand pollen:

```ts
// ✓ kehrt zurück, sobald die Bedingung hält; das Timeout begrenzt nur den defekten Fall
await awaitCondition(() => store.saved.length === 2, {
  timeoutMs: 5_000,
  label: 'both events were written',
});
expect(store.saved).toEqual(['a', 'b']);
```

Daraus folgen zwei Dinge:

- **Das Timeout ist ein Fehlerbudget, keine erwartete Dauer.** Ein grüner Test
  kehrt nach einem Poll-Intervall zurück, also setze es komfortabel über die
  schlimmste plausible Latenz unter Last. Es zu erreichen bedeutet dann, dass
  die Bedingung wirklich nie wahr wurde — das macht es zur Diagnose statt zum
  Münzwurf.
- **Warte auf die stärkste Bedingung, die der Test beobachten kann** — eine
  Probe-Antwort, ein Recovery-Callback, ein Spy-Array — nie auf einen Stellvertreter,
  den ein halb fertiger Schritt schon erfüllt. Ein Stellvertreter, der bereits
  bei der *ersten* Hälfte eines Schritts umschlägt, ist schlechter als der
  Sleep, den er ersetzt hat.

Greif zum passenden Werkzeug, bevor du selbst pollst:

| Statt zu schlafen auf… | nimm |
| --- | --- |
| das Eintreffen einer Nachricht | [`TestProbe.expectMessage`](/de/testing/test-probe/) |
| das Feuern eines Timers oder Retrys | [`ManualScheduler`](/de/testing/manual-scheduler/) |
| die Konvergenz eines Clusters | `spec.awaitMembers` / `awaitLeader` / `awaitMemberStatus` |
| mehrere Nodes am selben Punkt | [`spec.enterBarrier`](/de/testing/multi-node-spec/) |

Für alles, was die nicht abdecken, genügt ein eigenes `awaitCondition` von
einem Dutzend Zeilen — `actor-ts` hält eines in `tests/util/AwaitCondition.ts`.

### Wann ein fester Sleep weiterhin richtig ist

Warten ist korrekt, wenn die verstrichene Zeit *selbst* das Prüfobjekt ist oder
wenn es überhaupt keinen Zustandsübergang gibt, auf den man warten könnte:

- **Es darf nichts passieren.** `expectNoMessage(150)`, oder „das Heilen einer
  Partition erweckt einen heruntergefahrenen Node nicht wieder" — man kann dem
  Falschen nur ein Zeitfenster geben, in dem es eintreten könnte.
- **Eine Dauer ist die Assertion.** Ein Debounce-Fenster, das Ablaufen einer
  Lease-TTL, die Schwelle eines Failure Detectors, eine Gossip-Kadenz.
- **Ein Szenario braucht eine bestimmte Verschränkung.** „Crashe einen Node
  20 ms nach dem Start eines Ask-Batches" legt den Crash mitten in den Flug;
  diese Verzögerung *ist* das Experiment.
- **Das Warten ist ein Warm-up, auf das nichts assertet**, und die folgende
  Operation bringt ihr eigenes Timeout mit, das einen langsamen Start abfängt.

Schreib in einem Kommentar dazu, welcher der Fälle es ist. Ein Sleep mit
Begründung ist Dokumentation; ein Sleep ohne ist eine Wette. Das wird geprüft
und nicht nur erbeten: `tests/unit/ci/SleepRatchet.test.ts` zählt pro Modul die
Wartezeiten mit fester Dauer, die keinen Grund nennen, und schlägt fehl, sobald
die Zahl steigt — ein neuer Sleep kommt also durch, indem er sagt warum, und
die bestehenden können nur weniger werden.

Das alles ist Vorbeugung. Wenn ein Test *bereits* zeitweise umfällt, hat
[Test-Flakes diagnostizieren](/de/testing/diagnosing-flakes/) das
Repeat-Run-Harness, das einen Flake von einem kaputten Test unterscheidet, und
den Katalog der Ursachen, die diese Suite tatsächlich hatte.

## Unterscheidet der Test überhaupt?

Line-Coverage sagt, dass eine Zeile *gelaufen* ist. Sie sagt nicht, ob eine
Assertion bemerken würde, dass die Zeile falsch ist: Ein Test, der eine
Funktion aufruft und nichts prüft, hebt die Coverage-Zahl und bindet nichts.
Herausfinden lässt sich das nur, indem man die Zeile absichtlich kaputt macht
und schaut, ob ein Test rot wird. Das ist Mutation Testing, und das Repository
hat einen Runner dafür:

```sh
# eine Datei oder mehrere
bun run test:mutation -- src/Supervision.ts

# ein Glob
bun run test:mutation -- --files='src/mailbox/*.ts'

# alles, was dein Branch geändert hat, committet oder nicht
bun run test:mutation -- --since=origin/develop

# nur die seit einem Release geänderten Zeilen, nicht den Rest jeder Datei
bun run test:mutation -- --since=v0.18.0 --changed-lines

# die Mutanten auflisten, ohne etwas auszuführen
bun run test:mutation -- --dry-run src/util/OptionsMerge.ts
```

Für jede Datei wendet `scripts/mutation-run.mjs` jeweils eine kleine Änderung
an, führt die Tests aus, die die Datei abdecken, und stellt das Original
wieder her:

| Operator | Änderung |
|---|---|
| `relational-boundary` | `<` ↔ `<=`, `>` ↔ `>=` |
| `equality` | `===` ↔ `!==`, `==` ↔ `!=` |
| `logical` | `&&` ↔ `\|\|` |
| `boolean-literal` | `true` ↔ `false` |
| `removed-call` | ein einzeiliges Aufruf-Statement wird zu `;` |
| `removed-return` | ein einzeiliges `return …;` wird zu `;` |

Kommentare, Strings und Template-Literale werden nie mutiert, eine Log-Zeile
oder eine Fehlermeldung kann also keinen Befund erzeugen. Ein Mutant, der sich
nicht parsen lässt oder zu demselben JavaScript kompiliert wie das Original
(ein `true` innerhalb eines `type`), wird verworfen, bevor er läuft.
`scripts/mutation-config.json` enthält die übrigen Filter, etwa entfernte
Log-Aufrufe, jeweils mit Begründung.

**Welche Mutanten laufen:** jeder Mutant der Datei. Mit `--changed-lines`,
das `--since=<ref>` voraussetzt, nur die Mutanten auf einer Zeile, die
`git diff -U0` seit der Merge-Base als hinzugefügt oder geändert meldet. So
lässt sich der Diff eines Releases messen, ohne für den unveränderten Rest
jeder berührten Datei zu bezahlen. Der Lauf gibt aus und der Bericht hält fest,
wie viele Mutanten pro Datei weggelassen wurden.

**Welche Tests laufen:** die Tests, die die Datei direkt importieren, und der
Test mit dem Namen der Datei (`Supervision.ts` → `Supervision.test.ts`). Der
transitive Importgraph wird nicht benutzt, weil fast jeder Test `ActorSystem`
erreicht. Eine Datei ohne beides, die nur über ein Barrel oder ein Aggregat
erreicht wird (`ShardCoordinator.ts` über `ClusterSharding.ts`), bekommt die
Tests der Module, die sie importieren oder re-exportieren, einen Schritt weit
und nicht weiter.

Die abgeleitete Liste ist auf `maxTestsPerFile` aus
`scripts/mutation-config.json` (25) begrenzt, oder auf
`--max-tests-per-file=<n>`. Die Grenze behält die spezifischsten Tests: zuerst
den gleichnamigen Test, dann Tests im Verzeichnis, das dem der Datei
entspricht (`tests/unit/cluster/sharding/` für `src/cluster/sharding/`), dann
die nach Importabstand nächsten. Der Lauf gibt aus, was die Grenze weggelassen
hat. Wo keine der beiden Regeln eine gute Liste ergibt, nennt `testMap` in
derselben Datei die Tests einer Datei direkt; ein solcher Eintrag gewinnt immer
und wird nie begrenzt. `--tests=a.test.ts,b.test.ts` gewinnt über beides.
Multi-Node-, Broker-, Smoke- und Beispiel-Suiten werden nie gewählt.

**Den Bericht lesen.** Der Lauf gibt pro Datei eine Tabelle aus und schreibt
`.mutation/report.md` und `.mutation/report.json`. Jeder Mutant landet in einem
dieser Zustände:

- **killed** — ein Test wurde rot. Das ist das gewünschte Ergebnis.
- **survived** — alle Tests blieben grün. Das ist der Befund: Entweder fehlt
  eine Assertion, oder der Mutant ist *äquivalent*, die Änderung ist also
  nicht beobachtbar (etwa eine Grenze, die zwei Codepfade gleich behandeln).
  Beides ist es wert, festgehalten zu werden.
- **timed-out** — der Mutant hat die Tests hängen lassen, und der Watchdog
  hat sie beendet. Das zählt als erkannt, aber zufällig, deshalb steht er
  neben den Überlebenden.
- **no-coverage** — der Baseline-Lauf hat die Zeile nie ausgeführt, oder der
  Datei ist kein Test zugeordnet. Er läuft nicht und zählt nicht zur Quote.
- **not-run** — `--budget-minutes` war aufgebraucht, bevor der Mutant dran war.
  Das Budget wird zwischen den Mutanten und vor dem Baseline-Lauf jeder Datei
  geprüft, und der Bericht wird trotzdem geschrieben.

Die Quote ist (killed + timed-out) ÷ (killed + timed-out + survived). Ein
Überlebender ist nur so aussagekräftig wie die Zuordnung dahinter: Er heißt,
dass *die zugeordneten Tests* nichts bemerkt haben. Bevor du ihn meldest, prüfe,
ob eine Suite außerhalb der Zuordnung die Zeile abdeckt. Dabei hilft die
Tabelle *Test mapping* im Bericht: Sie zeigt pro Datei, wie die Tests gewählt
wurden (`direct`, `one-hop`, `override`), wie viele die Grenze weggelassen hat
und, mit `--changed-lines`, wie viele Mutanten auf und neben den geänderten
Zeilen lagen. `report.json` führt die Tests selbst auf.

**Sicherheit.** Der Runner mutiert den Working Tree direkt, einen Mutanten
nach dem anderen. Bevor er eine Datei anfasst, sichert er die Originalbytes in
`.mutation/journal/`. Er stellt die Datei nach jedem Mutanten wieder her, bei
Strg-C und beim Beenden. Wurde ein Lauf hart abgebrochen, stellt der nächste
Lauf zuerst aus dem Journal wieder her. `--recover` tut nur das. Committe deine
Arbeit vor einem langen Lauf trotzdem.

**Einen langen Lauf anhalten.** Strg-C, `SIGTERM` oder `SIGHUP` stellen zuerst
den Working Tree wieder her, schreiben dann `report.md` und `report.json` für
die bis dahin fertigen Mutanten und beenden den Lauf mit 128 + Signalnummer.
Der Bericht ist als unvollständig markiert: durch ein Feld `interrupted` im
JSON und eine Zeile oben im Markdown. Unter Windows beendet ein an einen
anderen Prozess gesendetes Signal diesen, ohne die Handler auszuführen. Einen
abgekoppelten Lauf hältst du dort deshalb mit `--stop-file=<pfad>` an. Der
Runner prüft zwischen den Mutanten und vor dem Baseline-Lauf jeder Datei, ob
die Datei existiert. Sobald sie da ist, löscht er sie, schreibt denselben
unvollständigen Bericht und endet mit 143, wie bei `SIGTERM`.

Ein Quoten-Gate gibt es noch nicht. Der nächtliche Workflow `mutation` führt
das Set `nightly` aus `scripts/mutation-config.json` aus und lädt den Bericht
als Artefakt hoch. `scripts/mutation-baseline.json` enthält die Zahl der
Überlebenden pro Datei aus dem ersten gemessenen Lauf, und der Bericht zeigt
für jede Datei die Baseline neben der heutigen Zahl, damit ein späterer Lauf
erkennen kann, ob die Zahl gestiegen oder gesunken ist.

## Was nicht testen

import { Aside } from '@astrojs/starlight/components';

<Aside type="caution" title="Teste nicht das Framework selbst">
  ```ts
  // ✗ teste, dass `tell` tatsächlich eine Nachricht zustellt
  ref.tell({ kind: 'do' });
  await probe.expectMessage({ kind: 'do' });
  ```
  Vertraue dem Framework; teste das Verhalten *deines* Actors.
  Solche Tests bestehen, wenn das Framework auf eine Art kaputt
  ist, die deine App nicht betrifft.
</Aside>

<Aside type="caution" title="Schreib keine Integrationstests, die echte I/O brauchen">
  Bun-Kafka, Bun-Redis usw. Tests gegen echte Broker sind
  langsam und flakey. Nutze den **In-Memory-Transport** für
  Cluster-Tests und stubbe Broker-Calls hinter schlichten
  Interfaces. Reserviere echte-I/O-Tests für eine separate
  „Smoke-Test"-Stufe außerhalb der Unit-Test-Suite.
</Aside>

<Aside type="caution" title="Echte Timer in Actor-Tests">
  ```ts
  // ✗ nutzt echtes setTimeout
  await new Promise(r => setTimeout(r, 100));
  expect(probe.messageCount).toBe(1);
  ```
  „Lang genug" zu schlafen macht Tests langsam und flakey. Nutze
  `await probe.expectMessage(...)` (es wartet-dann-assertet) oder
  `ManualScheduler` (er bringt virtuelle Zeit voran) — siehe
  [Auf Zustand warten, nicht auf verstrichene Zeit](#auf-zustand-warten-nicht-auf-verstrichene-zeit).
</Aside>

## TestKit vs rohes ActorSystem in Tests

Beides funktioniert. `TestKit` ist Convenience:

- Default ist `NoopLogger` — kein Konsolen-Spam.
- Bietet `createTestProbe()`, `within(ms, callback)`, `shutdown()`.
- One-Liner-Setup via `TestKit.create()`.

Für komplexe Test-Setups (eigener Logger, mehrere Systeme,
spezifische Extensions) liest sich rohes `ActorSystem.create(...)`
manchmal klarer. Beides produziert dasselbe Actor-Verhalten.
