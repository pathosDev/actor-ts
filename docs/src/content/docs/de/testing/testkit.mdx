`TestKit` ist ein dünner Convenience-Wrapper um `ActorSystem`
für Tests. Er gibt dir ein einsatzbereites System mit
sinnvollen Test-Defaults — leiser Logger, einfache
Probe-Erzeugung, deterministischer Shutdown.

```ts
import { TestKit } from 'actor-ts/testkit';

const tk = TestKit.create('my-spec');
const probe = tk.createTestProbe();
const ref = tk.system.spawnAnonymous(() => new Worker(probe));

ref.tell({ kind: 'do' });
await probe.expectMessage('done');

await tk.shutdown();
```

Drei Dinge, die das Kit für dich macht:

- Baut das `ActorSystem` standardmäßig mit einem `NoopLogger` —
  kein Konsolen-Spam während Test-Läufen.
- Stellt `createTestProbe()` bereit, sodass du das System nicht
  durch jeden Probe-Konstruktor fädeln musst.
- Besitzt `shutdown()` — einmal am Test-Ende aufrufen; baut
  System, Scheduler und Dispatcher sicher ab.

## Die API

```ts
class TestKit {
  static create(name?: string, options?: TestKitOptions): TestKit;
  static withManualScheduler(name?, options?): { kit: TestKit; scheduler: ManualScheduler };

  readonly system: ActorSystem;

  createTestProbe(options?: TestProbeOptions): TestProbe;
  within<T>(durationMs: number, callback: () => Promise<T>): Promise<T>;
  shutdown(): Promise<void>;
}

interface TestKitOptions extends ActorSystemOptionsType {
  quiet?: boolean;   // Default true — NoopLogger nutzen
}
```

### `TestKit.create(name?, options?)`

Baut ein Kit mit frischem System. Der `name` ist der System-Name
— nützlich, wenn parallele Test-Suites keinen geteilten State
haben dürfen. Default ist `'test-kit'`.

```ts
const testKitOptions = TestKitOptions.create()
  .withQuiet(false)                   // Logging einschalten
  .withLogLevel(LogLevel.Debug)
  .withConfig({ /* HOCON-Overrides */ });
const tk = TestKit.create('my-spec', testKitOptions);
```

Mit `quiet: false` bekommst du Konsolen-Logs — nützlich beim
Debuggen eines fehlschlagenden Tests. Andernfalls sind
Log-Aufrufe No-Ops, was deine Test-Ausgabe sauber hält.

Das Kit ist außerdem der eine Ort, an dem der
[Message-Boundary-Check](/de/fundamentals/messages/#drei-grenzen-und-der-check-der-für-sie-einsteht)
standardmäßig an ist: `structured-clone = fail`, sodass eine Nachricht,
die auf einem Worker-Hop ihren Prototyp verlöre — eine Klasseninstanz,
wo ein plain Object gemeint war —, einen `MessageBoundaryError` aus dem
`tell` wirft, das sie sendet.
`TestKitOptions.withMessageBoundary({ structuredClone: 'off' })` hält
eine Suite grün, die absichtlich Klasseninstanzen sendet.

### `tk.createTestProbe(options?)`

```ts
const testProbeOptions = TestProbeOptions.create()
  .withDefaultTimeoutMs(5_000)        // Default-Wartezeit für expect/receive
  .withName('order-probe');
const probe = tk.createTestProbe(testProbeOptions);           // sichtbar in Logs

ref.tell({ kind: 'do', replyTo: probe });
await probe.expectMessage({ kind: 'done' });
```

Gibt einen `TestProbe` zurück, gescoped auf das System dieses
Kits. Siehe [TestProbe](/de/testing/test-probe/) für die volle
Expectations-API.

### `tk.within(durationMs, callback)`

```ts
await tk.within(1_000, async () => {
  ref.tell({ kind: 'do' });
  await probe.expectMessage('done');
});
```

Führe `callback` aus und assertete, dass es **in weniger als
`durationMs` abgeschlossen wurde**. Wirft, wenn es länger
gedauert hat. Nützlich für „das sollte schnell sein"-SLAs
innerhalb von Tests, ohne vom Per-Test-Timeout des Test-Runners
abzuhängen.

Hinweis: das ist eine *weiche* Deadline — `callback` läuft auch dann
zu Ende, wenn es überzieht. Es wirft nur im Nachhinein.

### `tk.shutdown()`

```ts
afterEach(async () => {
  await tk.shutdown();
});
```

Terminiert das zugrundeliegende System. **Rufe das immer** in
einem Fixture-Teardown — ohne ihn leakt der Test-Prozess ein
lebendes System, das die Event-Loop am Leben hält. Manche
Test-Runner (Bun, Vitest) erkennen das und lassen die Suite
fehlschlagen; andere hängen.

### `TestKit.withManualScheduler()`

```ts
const { kit, scheduler } = TestKit.withManualScheduler('my-spec');

const ref = kit.system.spawnAnonymous(() => new Heartbeat(probe));
ref.tell({ kind: 'start' });

scheduler.advance(5_000);   // 5 virtuelle Sekunden springen
await probe.expectMessage('tick');
```

Gibt sowohl das Kit als auch seinen `ManualScheduler` zurück,
damit der Test virtuelle Zeit voranbringen kann. Siehe
[ManualScheduler](/de/testing/manual-scheduler/) für die volle
Virtual-Clock-Semantik.

## Fixture-Muster

### Per-Test-Fixture (Bun, Vitest, Jest)

```ts
import { describe, it, beforeEach, afterEach } from 'bun:test';

describe('Counter', () => {
  let tk: TestKit;
  let probe: TestProbe;

  beforeEach(() => {
    tk = TestKit.create();
    probe = tk.createTestProbe();
  });

  afterEach(async () => {
    await tk.shutdown();
  });

  it('inkrementiert', async () => {
    const ref = tk.system.spawnAnonymous(Counter);
    ref.tell({ kind: 'increment' });
    ref.tell({ kind: 'get', replyTo: probe as ActorRef<number> });
    await probe.expectMessage(1);
  });
});
```

Ein frisches Kit pro Test — kein State-Leakage zwischen Tests,
leicht langsamer als ein geteiltes Kit, aber wert für die
Isolation.

### Geteiltes Fixture für read-only-Tests

```ts
describe('PureBehaviorTests', () => {
  let tk: TestKit;

  beforeAll(() => { tk = TestKit.create(); });
  afterAll(async () => { await tk.shutdown(); });

  // jedes `it` nutzt tk.createTestProbe() für seine eigene Probe, aber
  // das zugrundeliegende ActorSystem wird geteilt.
});
```

Schneller als Per-Test-Setup; nur sicher, wenn Tests keine
geteilten Actor mutieren.

## Was TestKit nicht macht

import { Aside } from '@astrojs/starlight/components';

<Aside type="caution" title="Multi-Node-Cluster-Tests">
  TestKit erzeugt **ein** ActorSystem. Für Cluster-Szenarien
  (Sharding-Placement, Singleton-Failover, Gossip-Konvergenz)
  nutze [MultiNodeSpec](/de/testing/multi-node-spec/), das N
  Systeme in einem Prozess hochfährt.
</Aside>

<Aside type="caution" title="Echte I/O-Integration">
  TestKit ist für **reine Unit- + kleine Integrationstests**.
  Tests, die echtes Kafka / Redis / Postgres brauchen, sollten in
  einer separaten Suite sein, angemessen markiert für langsame
  Läufe. Mische keine In-Memory-Probe-Tests mit broker-
  abhängigen Tests in derselben Datei.
</Aside>

<Aside type="caution" title="Test-Isolation bei Namens-Kollision">
  ```ts
  // ✗ beide Tests nutzen denselben Namen → Cluster-Identitäts-Konflikt
  const tk1 = TestKit.create('my-app');
  const tk2 = TestKit.create('my-app');
  ```
  Zwei Systeme mit demselben Namen + demselben Netzwerk = sie
  würden einander joinen, wäre Cluster aktiviert. Für
  Nicht-Cluster-Tests okay, aber gewöhne dir eindeutige Namen pro
  Test an oder nutze den Default `'test-kit'`.
</Aside>

## Alle Deadlines auf einmal skalieren

Jede Deadline im Testkit — der 3-s-Default von `TestProbe`, `awaitTimeoutMs` mit
10 s in `MultiNodeSpec`, die 30 s von `ParallelMultiNodeSpec` samt Handshake und
Control-RPC, und jedes `awaitCondition`-Budget — läuft durch einen einzigen
Multiplikator. Für einen ganzen Lauf setzen:

```bash
ACTOR_TS_TEST_TIME_FACTOR=3 bun test tests/multi-node/
```

Der Default ist `1`, das Feature ist also wirkungslos, bis jemand danach fragt.
Ein fehlerhafter Wert wirft, statt auf `1` zurückzufallen: Die Variable setzt
jemand, der längere Deadlines will, und einen Tippfehler zu ignorieren hieße,
ihm genau den Fehlschlag zurückzugeben, den er beheben wollte. Jede Meldung, die
der Faktor verlängert hat, nennt ihn:

```
awaitCondition: the cluster converged did not become true within 6000ms
  (ACTOR_TS_TEST_TIME_FACTOR=3, so this budget is 3x the declared one)
```

### Wo virtuelle Zeit passt, nimm virtuelle Zeit

Das ist kein Ersatz für [`ManualScheduler`](/de/testing/manual-scheduler/). Wo
ein Test eine Uhr vorstellen kann, soll er das tun: Virtuelle Zeit *entfernt*
das Rennen, statt es zu verbreitern, und eine Deadline, die gar nicht erreicht
werden kann, ist besser als eine bloß großzügige. Der Faktor ist für den Rest —
Konvergenz-Waits, Probe-Timeouts, Barrier-Waits —, wo ein echter Cluster
tatsächlich echte Zeit braucht.

Das sind **Fehlerbudgets, keine erwarteten Dauern.** Auf ihnen wird nichts
zugesichert; sie existieren, um ein Hängen in eine Meldung zu verwandeln. Genau
das macht sie skalierbar — und aus demselben Grund gilt für eine
Elapsed-Time-Zusicherung das Gegenteil: Ein Test, der zusichert, dass etwas
*weniger* als N ms gedauert hat, sichert die Geschwindigkeit der Maschine zu,
und kein Faktor macht das richtig.

### Das Per-Test-Cap skaliert nicht — und der Guard sagt das

Buns Per-Test-Timeout erreicht der Faktor nicht: Es ist entweder der Default von
5 000 ms oder ein Literal als drittes Argument von `test()`. Ein Faktor, der
stillschweigend ein 4-000-ms-Budget verdreifacht, während das 5-000-ms-Cap
unverändert bleibt, erzeugt genau den Fehlschlag, den `AwaitConditionBudgets`
verhindern soll: Das Timeout des Runners gewinnt das Rennen, und die Meldung des
Budgets — die, die sagt, worauf gewartet wurde — wird nie gedruckt.

Der Guard skaliert deshalb mit. Läuft er unter einem erhöhten Faktor, meldet er
jeden Test, dessen Budget nicht mehr berichten kann, statt ihn abzunicken. Ein
Test, der unter erhöhtem Faktor weiterlaufen soll, deklariert sein Cap über
`scaledMs`, das der Guard erkennt:

```ts
test('the cluster converges', async () => {
  await spec.awaitMembers('a', 3);
}, scaledMs(30_000));      // steigt mit dem Faktor, wie die Budgets darin
```

Damit ist ein erhöhter Faktor ein Werkzeug **pro Suite**, kein globaler Schalter:
Bei Faktor 3 über den ganzen Baum meldet der Guard rund 1 200 Tests, deren
literale Caps ihre Budgets nicht mehr fassen — zu Recht. Die drei Suites, die
`nightly-flakes.yml` mit Faktor 3 fährt, deklarieren genau deshalb
`scaledMs`-Caps.
