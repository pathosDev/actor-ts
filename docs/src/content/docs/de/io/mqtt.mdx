title: MQTT
description: MQTT-3.1.1-/-5-Broker-Actor — eine subclass-first, typisierte API. Subscribe im Konstruktor, eingehende Nachrichten in onMessage, typisierte Entities über einen Codec publishen. QoS 0/1/2, Wildcards, Retained Messages, Last-Will. Umschließt das Paket `mqtt`.
---

`MqttActor` integriert mit MQTT-Brokern (Mosquitto, EMQ X, HiveMQ,
AWS IoT Core).  Unterstützt sowohl MQTT 3.1.1 als auch 5; Topic-
Wildcards (`+`, `#`); QoS 0/1/2; Retained Messages.

Es ist das MQTT-Gegenstück zu
[`WebsocketClientActor`](/de/io/websocket/): eine **abstrakte
Basisklasse, von der du ableitest**.  Deklariere Subscriptions im
Konstruktor, verarbeite eingehenden Traffic in `onMessage` und publishe
mit `this.publish(...)`.  Von außen bleibt er per `ref.tell(...)`
steuerbar.

```ts
import { ActorSystem, ActorSystemOptions } from 'actor-ts';
import { MqttActor, MqttOptions, type MqttMessage } from 'actor-ts/io';

type Reading = { sensor: string; celsius: number };

const actorSystemOptions = ActorSystemOptions.create().withConfig({
    'actor-ts': { io: { broker: { mqtt: { brokerUrl: 'mqtt://localhost:1883' } } } },
  });
class TemperatureHub extends MqttActor<Reading> {
  constructor(options: MqttOptions) {
    super(options.withQos(1).withClientId('temperature-hub'));
    this.subscribe('sensors/+/temp');
    this.subscribe('alerts/#', { qos: 2 });
  }

  override onMessage(message: MqttMessage<Reading>): void {
    const { sensor, celsius } = message.payload.entity();   // via den Codec dekodiert
    this.log.info(`${sensor}: ${celsius}°C`);
    this.publish(`ack/${sensor}`, 'ok');                // roher String
    this.publish('rollup', { sensor, celsius });        // kodierte Entity
  }
}

const system = ActorSystem.create('demo', actorSystemOptions);

system.spawn(() => new TemperatureHub(MqttOptions.create()), 'hub');
```

`T` (hier `Reading`) typisiert das eingehende Payload —
`message.payload.entity()` liefert ein `T` zurück.  Ein zweiter Generic,
`TSelf`, typisiert Anwendungsnachrichten, die andere Aktoren dem Ref
`tell`en können (siehe *Externe Steuerung* unten); Default ist `never`.

## Hooks

Diese überschreibst du in deiner Subklasse.  `onReceive` und `onCommand`
sind **versiegelt** — die Basisklassen dispatchen an die Hooks unten;
überschreibe sie nicht.

| Hook | Wann |
| --- | --- |
| `onMessage(message)` | Eine Nachricht traf auf einer eigenen Subscription dieses Aktors ein.  **Erforderlich.** |
| `onConnected()` | Die Verbindung wurde (neu) geöffnet; die Subscription-Registry ist beim Broker erneut angewendet. |
| `onDisconnected(cause?)` | Die Verbindung brach ab; ein Reconnect-Zyklus kann folgen (gemäß Settings). |
| `onInvalidMessage(err, message)` | `onMessage` warf einen `MqttDecodeError` (ein lazy `entity()` auf einem fehlerhaften Payload).  Default: loggen + verwerfen.  Erneut werfen zum Eskalieren. |
| `onSelfMessage(message)` | Eine Anwendungsnachricht (`TSelf`) wurde diesem Ref getellt. |
| `onTerminated(signal)` | Ein Aktor, den du mit `context.watch` beobachtest, hat gestoppt.  Von `BrokerActor` geerbt; die Zustellziele, die dieser Aktor selbst beobachtet, sind bereits erledigt. |

Eingehende und Lifecycle-Ereignisse werden über die Mailbox zugestellt,
sodass `onMessage` und die Hooks stets auf dem Aktor-Thread laufen
(single-threaded, Reihenfolge pro Verbindung erhalten: connected →
Nachrichten → disconnected).

## Konfiguration

Settings lösen mit der üblichen Präzedenz auf: **Konstruktor / Builder >
HOCON (`actor-ts.io.broker.mqtt`) > eingebaute Defaults.**  Nutze den
Fluent-Builder `MqttOptions` oder übergib ein einfaches
`Partial<MqttOptionsType>`.

```ts
const options = MqttOptions.create()
  .withBrokerUrl('mqtts://mqtt.example.com:8883')
  .withClientId('my-app')
  .withCredentials(process.env.MQTT_USER, process.env.MQTT_PASS)
  .withQos(1)                 // Default-QoS für publish/subscribe
  .withProtocolVersion(5)     // MQTT 5.0 aktivieren
  .withCleanSession(false)
  .withKeepAlive(30);
```

```ts
interface MqttOptionsType extends BrokerCommonOptionsType {
  brokerUrl?:  string;          // mqtt:// mqtts:// ws:// wss://
  clientId?:   string;
  credentials?: { username?: string; password?: string };
  qos?: 0 | 1 | 2;              // Default-QoS für publish/subscribe
  cleanSession?: boolean;       // Default true
  keepAlive?: number;           // Sekunden; Default 60
  protocolVersion?: 4 | 5;      // Default 4 (= MQTT 3.1.1)
  codec?: MqttCodec<unknown>;   // Default mqttJsonCodec()
  will?: { topic: string; payload: string | Uint8Array; qos?: 0 | 1 | 2; retain?: boolean };
  tls?: TlsTransportOptionsType;  // Cert-Material für mqtts:// / wss://; nur im Code
}
```

Häufige Muster:

- **`withCleanSession(false)`** — die Session bleibt bestehen; der Broker
  liefert Nachrichten, die während der Trennung verpasst wurden (abhängig
  von der Broker-Konfiguration).
- **`withWill({ ... })`** — der Broker publisht das, wenn der Client
  unsauber die Verbindung verliert.  Nützlich für Präsenz
  ("device-42-offline").
- **`withProtocolVersion(5)`** — aktiviert MQTT-5-Features (User-
  Properties, Reason-Codes auf `MqttMessage`).  Braucht einen v5-fähigen
  Broker.

## Typisierte Payloads

Eingehende `MqttMessage<T>` tragen ein lazy dekodierendes
`MqttPayload<T>`:

```ts
override onMessage(message: MqttMessage<Reading>): void {
  message.payload.bytes;          // rohes Uint8Array
  message.payload.text();         // UTF-8-String (gecacht)
  message.payload.entity();       // dekodiertes T via den Codec (gecacht)
  message.payload.entity<Acknowledgment>();  // auf einem bestimmten Topic als anderen Typ dekodieren
}
```

Das Dekodieren ist **lazy** — es passiert erst, wenn du `text()` /
`entity()` aufrufst.  Ein fehlerhaftes Payload lässt `entity()` einen
`MqttDecodeError` werfen; weil das innerhalb von `onMessage` geschieht,
fängt die Basisklasse ihn und leitet ihn an `onInvalidMessage` weiter
(Default: loggen + verwerfen, kein Neustart):

```ts
protected override onInvalidMessage(err: MqttDecodeError, message: MqttMessage<Reading>): void {
  this.log.warn(`bad payload on ${err.topic}: ${err.message}`);
}
```

## Publishen

`this.publish(topic, payload, options?)` gibt `false` zurück, wenn die
Nachricht verworfen wurde (Encode-Fehler oder Überlauf des Outbound-
Puffers):

- ein `string`- oder `Uint8Array`-Payload wird **roh** gesendet;
- jeder andere Wert wird **via den Codec kodiert** (Default JSON).

```ts
this.publish('ack/1', 'ok');                    // rohe Bytes: ok
this.publish('rollup', { sensor, celsius });    // JSON: {"sensor":...,"celsius":...}
this.publish('cfg', data, { qos: 1, retain: true });
```

Um einen nackten String *als JSON-Entity* zu publishen (die Wire-Bytes
`"pong"` statt `pong`), kodiere ihn explizit:

```ts
this.publish('topic', this.codec().encode('pong'));
```

## Codecs

Der Codec wandelt Entities in Bytes und zurück.  Default ist
`mqttJsonCodec()` (einfaches JSON über UTF-8).  Übergib deinen eigenen
via `withCodec(...)` — z. B. einen JSON-Codec mit Laufzeit-Validierung:

```ts
import { mqttJsonCodec, MqttOptions } from 'actor-ts/io';

const codec = mqttJsonCodec<Reading>({
  validate: (v) => ReadingSchema.parse(v),   // zod usw.; wirft → MqttDecodeError
});

MqttOptions.create().withBrokerUrl('mqtt://localhost:1883').withCodec(codec);
```

## Externe Steuerung

Über die Subklassen-API hinaus kann jeder Aktor einen `MqttActor`
steuern, indem er ihm ein `MqttCommand` `tell`t:

```ts
ref.tell({ kind: 'publish', publish: { topic: 't', payload: 'hi', qos: 1 } });

// Subscribe und an das eigene onMessage dieses Aktors routen (kein target):
ref.tell({ kind: 'subscribe', topic: 'x/#', qos: 1 });

// Subscribe und an einen anderen Aktor fan-outen (externes target):
ref.tell({ kind: 'subscribe', topic: 'y/#', target: someHandler });

ref.tell({ kind: 'unsubscribe', topic: 'y/#', target: someHandler });
```

- Ein `subscribe` **ohne `target`** liefert passende Nachrichten an das
  eigene `onMessage` des Aktors; mit `target` fan-outet es an jenen
  Aktor.  Überlappende Patterns liefern an jedes Ref höchstens einmal.
- Ein `unsubscribe` mit `target` entfernt jenes Target.  **Ohne
  `target`** entfernt es alle *fremden* Targets, lässt aber die eigene
  Subscription des Aktors bestehen — ein externer Controller kann die
  im Konstruktor deklarierte Subscription der Subklasse nicht stummschalten.
- Das `qos` eines `subscribe` gilt nur für ein Pattern, **das das Kommando
  selbst anlegt**.  Nennt es ein bereits vorhandenes Pattern, hängt es sich
  mit dem dort registrierten QoS an; sein eigenes `qos` wird dabei
  ignoriert.  Das ist das additive Gegenstück zur Regel darüber: Wer die
  Subscription der Subklasse nicht stummschalten kann, soll sie auch nicht
  unbemerkt herunterstufen können — eine mit QoS 0 neu ausgestellte
  QoS-2-Subscription ließe die Anwendung an Exactly-once-Zustellung glauben,
  während der Broker verwerfen darf.  Um das QoS des eigenen Patterns zu
  ändern, ruf in der Subklasse `subscribe(topic, { qos })` auf.
- Fan-out-Targets werden per Deathwatch beobachtet: stoppt ein Target-
  Aktor, wird er automatisch entfernt (und ein Broker-UNSUBSCRIBE feuert,
  sobald ein Pattern keine Konsumenten mehr hat).
- Ein externes `subscribe`, das ein Filter einführt, das der Aktor **noch
  nicht** hielt, wird auf Info-Level geloggt.  Hängt es sich an ein bereits
  vorhandenes Filter an, bleibt es still — das ändert am Broker nichts —
  und ebenso das eigene `subscribe()` der Subklasse, im Konstruktor wie zur
  Laufzeit.

Der Eintrag nennt das Filter, das QoS, das das SUBSCRIBE tatsächlich trägt,
und ob passende Nachrichten an das eigene `onMessage` des Aktors gehen oder
an einen anderen Aktor fan-outen:

```text
MqttActor: external subscribe introduced broker filter 'tele/#' at QoS 1, delivering to actor 'actor-ts://sensors/user/mirror'
```

Das ist das Gegengewicht zur ersten Regel, keine Einschränkung davon.  Einen
Handler an ein beliebiges Filter zu hängen, `#` eingeschlossen, bleibt offen,
weil es der Vertrag des Aktors ist und wer das Ref hält ohnehin überallhin
publishen kann — vertretbar ist das genau so lange, wie ein Betreiber es
sehen kann.  Aus einer Nachricht wird nichts geloggt: der Eintrag beschreibt
eine Subscription, keinen Verkehr, damit aus einer Zeile pro neuem Filter nie
eine Zeile pro Payload wird.  Das Filter wird vorher escaped und in der Länge
gekappt, denn es ist Text, den der *Sender* gewählt hat — ein Zeilenumbruch
darin würde sonst eine zweite Logzeile fälschen, die wie eine echte aussieht.
Wenn dein Topic-Schema ein Credential enthält (manche Broker legen einen
API-Key in den Pfad), beachte: es landet hier auf Info-Level im Log, genau so
wie bereits in den Warnungen dieses Aktors zu fehlgeschlagenem Subscribe und
nicht dekodierbarem Payload.

Da diese Kommandos einfache Objekte sind, halte ein selbst definiertes
`TSelf` von den `kind`-Werten `publish` / `subscribe` / `unsubscribe`
fern — sonst würde es als Kommando dispatcht, statt `onSelfMessage` zu
erreichen.

## QoS-Level

| QoS | Zustellung | Kosten |
| --- | --- | --- |
| **0** | At-most-once.  Fire-and-Forget. | Am günstigsten; Nachrichten können verloren gehen. |
| **1** | At-least-once.  Broker speichert bis ACK. | Default für die meisten Anwendungsfälle.  Duplikate möglich. |
| **2** | Exactly-once.  Voller Handshake. | Am langsamsten; selten nötig. |

Für IoT-Telemetrie ist **QoS 1** die typische Balance.  Befehle an
Geräte: ebenfalls QoS 1 (oder QoS 2, falls Duplikate schädlich wären).
Statusupdates, die schnell überholt werden (Sensorwerte): QoS 0 ist okay.

## Topic-Wildcards

```ts
this.subscribe('sensors/+/temp');   // passt zu sensors/dev1/temp, sensors/dev2/temp, ...
this.subscribe('devices/#');        // passt zu devices/irgendwas/irgendwo/...
```

| Wildcard | Trifft |
| --- | --- |
| `+` | Genau eine Ebene. |
| `#` | Mehrere Ebenen (muss das letzte Segment sein). |

## Retained Messages

```ts
this.publish('config/device-42', { mode: 'eco' }, { retain: true });
```

Eine Retained Message wird **vom Broker gespeichert** und an jeden neuen
Subscriber sofort ausgeliefert.  Verwende sie für Konfiguration (Geräte,
die beim Verbinden die aktuellste Config lesen) oder den letzten
bekannten Status.  Lass `retain` bei normalem Pub/Sub weg — sonst hält
der Broker jede alte Nachricht für immer sichtbar.

## TLS

Eine `mqtts://`- oder `wss://`-URL startet den Handshake, und mqtt.js
verifiziert den Broker per Default gegen den **System-Trust-Store**.
Hinter einer privaten CA oder für Client-Zertifikats-Auth kommt
`withTls` dazu:

```ts
const mqttOptions = MqttOptions.create()
  .withBrokerUrl('mqtts://mqtt.example.com:8883')
  .withTls({
    ca: fs.readFileSync('./tls/ca.crt', 'utf8'),
    cert: fs.readFileSync('./tls/device.crt', 'utf8'),
    key: fs.readFileSync('./tls/device.key', 'utf8'),
  });
```

Jedes Feld trägt **das Material selbst**, nie einen Pfad darauf —
deshalb liest das Beispiel die Dateien.  `cert` und `key` ergeben nur
gemeinsam Sinn; eines ohne das andere wird beim Start des Actors
abgelehnt.

`withTls` konfiguriert den Handshake, statt einen zu starten — das
`mqtts://`- bzw. `wss://`-Schema bleibt also nötig.  Einen Config-Key
hat es bewusst nicht: Ein Private Key gehört nicht in die
`application.conf`.

## Wann MQTT

1. **IoT / Telemetrie** — Geräte publishen Sensordaten und subscribieren
   Befehle.
2. **Brücken aus bestehender MQTT-Infrastruktur** — wenn der Broker schon
   da ist.
3. **Leichtgewichtiges Pub/Sub** — wenn Kafka Overkill ist (kleine
   Payloads, keine Replay-Historie nötig).

Für clusterinternes Pub/Sub ist
[DistributedPubSub](/de/cluster/pubsub/) einfacher (kein externer Broker).

import { Aside } from '@astrojs/starlight/components';

<Aside type="tip" title="Migration vom alten MqttActor">
  `MqttActor` war früher eine konkrete Klasse, die du gespawnt und nur
  per `tell` gesteuert hast.  Er ist jetzt **abstrakt** — leite ab und
  überschreibe `onMessage`.

  - `new MqttActor({...})` → `class X extends MqttActor<T> { onMessage(m) {…} }`.
  - `message.payload` (ein `Uint8Array`) → `message.payload.bytes`;
    `new TextDecoder().decode(message.payload)` → `message.payload.text()`;
    JSON → `message.payload.entity()`.
  - `settings.subscriptions: [{ topic, target }]` (entfernt) →
    `this.subscribe(topic, { target })` im Konstruktor, oder ein
    `subscribe`-Kommando.
</Aside>

<Aside type="caution" title="Persistente Session und `cleanSession: false`">
  Persistente Sessions brauchen über Reconnects hinweg **dieselbe
  clientId** — der Broker tracked Subscriptions + gequeuete Nachrichten
  pro clientId.  Eine zufällige clientId pro Connect macht
  `cleanSession: false` nutzlos.
</Aside>

<Aside type="caution" title="Wildcard-Subscriptions vervielfachen Traffic">
  `#` an der Wurzel subscribiert jede Nachricht auf dem Broker.  In einem
  multi-tenant Broker ist das selten, was du willst.  Halte Wildcards eng.
</Aside>
