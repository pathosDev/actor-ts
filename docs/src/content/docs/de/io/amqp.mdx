`AmqpActor` integriert mit RabbitMQ (und anderen AMQP-0.9.1-
Brokern).  Unterstützt Exchanges (direct / topic / fanout /
headers), Queues, Routing-Keys, ACK/NACK-Semantik.

```ts
import { ActorSystem } from 'actor-ts';
import { AmqpActor, AmqpOptions } from 'actor-ts/io';

const amqpOptions = AmqpOptions.create()
  .withUrl('amqp://guest:guest@rabbitmq:5672')
  // Queue → Consumer-Actor-Verdrahtung läuft über `bindings` in
  // den Settings — einmal beim Connect deklariert.  Ein
  // Runtime-Subscribe/Unsubscribe ist kein v1-Surface; wenn Du
  // nach dem Start einen neuen Consumer anhängen musst, starte
  // den Actor mit aktualisierten Bindings neu.
  .withBindings([
    { queue: 'order-processor', exchange: 'orders', routingKey: 'placed.#', target: handler },
  ]);
const amqp = system.spawn(
  () => new AmqpActor(
    amqpOptions,
  ),
  'amqp',
);

// An einen Exchange publishen:
amqp.tell({
  kind: 'publish',
  publish: {
    exchange:   'orders',
    routingKey: 'placed.priority',
    content:    JSON.stringify(order),
  },
});
```

## Settings

```ts
interface AmqpOptionsType extends BrokerCommonOptionsType {
  url:        string;                          // amqp:// oder amqps://
  prefetch?:  number;                          // ungeackte Nachrichten pro Consumer; Default 1
  autoAcknowledge?:      boolean;                         // der Actor ackt (Default true) vs. Deine expliziten Kommandos
  acknowledgment?:       'on-reply' | 'on-delivery';      // wann der Actor ackt; Default 'on-reply'
  acknowledgmentTimeoutMs?: number;                       // wie lange 'on-reply' wartet; Default 30_000
  bindings?:  ReadonlyArray<AmqpQueueBinding>; // Queue ↔ Exchange ↔ Routing-Key ↔ Target
  tls?:       TlsTransportOptionsType;         // Cert-Material für einen amqps://-Dial; nur im Code
}

type AmqpQueueBinding = {
  queue:       string;
  exchange?:   string;                         // weglassen für den Default-Exchange
  routingKey?: string;
  target:      ActorRef<AmqpDelivery>;         // Consumer-Actor für diese Queue
};
```

Bindings deklarieren die Queue, das Exchange-Binding UND den
Consumer-Actor-Target auf einen Schlag — der Actor verdrahtet alles
beim Connect (idempotente erneute Deklaration).

Dieselben Settings kommen auch aus HOCON, unter `actor-ts.io.broker.amqp`,
unterhalb expliziter Optionen und oberhalb der eingebauten Defaults:

```hocon
actor-ts.io.broker.amqp {
  url              = ${?ACTOR_TS_AMQP_URL}  # amqp://user:password@rabbitmq:5672/vhost, or amqps://
  prefetch         = 10                     # default 1; 0 = unlimited
  auto-acknowledge = true                   # the default; false = explicit commands
  acknowledgment   = "on-reply"             # the default; or "on-delivery"
  acknowledgment-timeout = 30s              # the default; on-reply only
}
```

Die URL trägt die Zugangsdaten, deshalb nimmt das Beispiel sie aus der
Umgebung statt aus der Datei.  Ein Wert aus der Umgebung wird zuerst als JSON
gelesen, wo immer er sich als JSON parsen lässt; eine `amqp://`-URL tut das nie
und kommt deshalb so an, wie sie geschrieben ist.  Ein Wert, der es tut, käme
verändert an oder ließe den Start scheitern: Einer, der sich wie eine Zahl
liest, kommt in der Schreibweise dieser Zahl zurück — `1e3` als `1000`, und
eine ganze Zahl jenseits von `Number.MAX_SAFE_INTEGER` womöglich mit anderen
letzten Ziffern (`20261104123456789` als `20261104123456788`) —, und einer, der
sich wie `null`, eine Liste oder ein Objekt liest, lässt den Start mit einem
`ConfigError` scheitern.  Einen solchen Wert in der Variablen selbst quoten
oder im Code setzen.

`bindings` und `tls` haben kein Blatt: Ein
Binding benennt den Actor, an den seine Queue ausliefert, und TLS-Material ist
ein privater Schlüssel — beides wird im Code gesetzt.  Die Reconnect-,
Circuit-Breaker- und Outbound-Buffer-Blätter, die sich alle Broker teilen,
gehören unter denselben Root — siehe
[BrokerActor-Basis](/de/io/broker-actor-base/#reconnect-mit-backoff).

## Exchanges und Routing

| Typ | Routing |
| --- | --- |
| **`direct`** | Exakter Match auf den Routing-Key. |
| **`topic`** | Wildcard-Pattern-Match (`*` = ein Segment, `#` = viele). |
| **`fanout`** | Alle gebundenen Queues, Routing-Key ignoriert. |
| **`headers`** | Match auf Nachrichten-Header, nicht Routing-Key. |

`AmqpActor` deklariert **keine** Exchanges — sie müssen bereits
auf dem Broker existieren (angelegt über die
RabbitMQ-Konfiguration, das Management-UI oder dein
Infrastruktur-Tooling).  Beim Connect deklariert der Actor nur die
in `bindings` genannten Queues und bindet sie an den angegebenen
Exchange; das Publishen routet dann über diesen bestehenden
Exchange per Name.

Häufigstes Muster: **`topic`**-Exchanges mit hierarchischen
Routing-Keys (`orders.placed.priority`, `orders.cancelled`,
`payments.failed`).

## Acknowledgment

Standardmäßig ackt der Actor eine Delivery **erst, wenn ihr Target sie
verarbeitet hat**: Er `ask`t das Target des Bindings mit der Delivery, und
das Target antwortet auf das `replyTo` der Delivery.  Damit ist der Default
**at-least-once** — und `prefetch` wird zu einer echten Schranke, weil eine
Delivery ungeackt bleibt, bis sie erledigt ist.

```ts
import { acknowledgeDelivery, negativelyAcknowledgeDelivery } from 'actor-ts/io';

class OrderHandler extends Actor<AmqpDelivery> {
  override async onReceive(delivery: AmqpDelivery): Promise<void> {
    try {
      await processOrder(delivery);
      acknowledgeDelivery(delivery);             // antwortet { kind: 'acknowledgment' }
    } catch (err) {
      negativelyAcknowledgeDelivery(delivery, String(err));
    }
  }
}
```

| Das Target … | Der Actor … |
| --- | --- |
| antwortet `{ kind: 'acknowledgment' }` | ackt die Delivery |
| antwortet `{ kind: 'negativeAcknowledgment', reason? }` | nackt sie mit Requeue — RabbitMQ liefert sie erneut aus |
| antwortet irgendetwas anderes | nackt sie mit Requeue und loggt, dass die Antwort nicht zum Vertrag gehört |
| antwortet nicht innerhalb von `acknowledgmentTimeoutMs` (30 s) | nackt sie mit Requeue |

Ein Handler, der wirft, antwortet einfach nie und landet damit in der
letzten Zeile.  Handler müssen idempotent sein: Eine Delivery kann nach
ihrer Verarbeitung wiederkommen, wenn die Antwort oder der ACK verloren
geht.  Ein ACK, den der Broker ablehnt, wird nie verschluckt — er wird mit
der Queue auf `warn` geloggt und als `BrokerAcknowledgmentFailed`-Event
veröffentlicht, damit man ihn zählen kann.

**`acknowledgment: 'on-delivery'`** ackt jede Delivery bei der Übergabe an
die Mailbox des Targets und erwartet keine Antwort (`replyTo` fehlt, beide
Helfer tun nichts).  Das ist at-most-once: Eine Delivery, die nach der
Übergabe verloren geht — ein Crash, ein Mailbox-Überlauf —, wird nicht
erneut ausgeliefert, und `prefetch` begrenzt nichts.  Auf einen
fehlgeschlagenen ACK folgt keine Übergabe, weil RabbitMQ diese Delivery
ohnehin erneut ausliefert.

### Explizite Kommandos

Setze `autoAcknowledge: false` in den Settings; dann teilt der Handler das
Ergebnis per `{ kind: 'acknowledgment', delivery }` oder `{ kind: 'negativeAcknowledgment',
delivery, requeue }` an die Ref des AMQP-Actors mit.  `acknowledgment`
greift in diesem Modus nicht.

```ts
class OrderHandler extends Actor<AmqpDelivery> {
  constructor(private readonly amqp: ActorRef<AmqpCommand>) { super(); }

  override async onReceive(delivery: AmqpDelivery): Promise<void> {
    try {
      await processOrder(delivery);
      this.amqp.tell({ kind: 'acknowledgment', delivery });
    } catch (err) {
      this.amqp.tell({ kind: 'negativeAcknowledgment', delivery, requeue: true });
    }
  }
}
```

Jede eingehende `AmqpDelivery` trägt einen opaken `ackToken`, mit
dem der Actor die Broker-seitige Nachricht identifiziert — Du
fasst ihn nicht direkt an, sondern reichst das ganze `delivery`-
Objekt im `ack`/`nack`-Tell wieder zurück.

Der Broker hält die Nachricht im **Unacked-Zustand**, bis der
Handler antwortet — wenn der Consumer crasht, liefert der Broker
bei der nächsten Verbindung erneut aus.  Nutze `requeue: false`,
um an eine Dead-Letter-Queue zu senden (falls konfiguriert) —
nützlich, wenn ein Retry nicht hilft.

## Prefetch

```ts
prefetch: 10   // bis zu 10 ungeackte gleichzeitig pro Consumer konsumieren
```

Der Framework-Default ist **1** — eine einzige ungeackte
Nachricht pro Consumer zur selben Zeit.  Er begrenzt nur dann etwas,
wenn Deliveries bis zur Verarbeitung ungeackt bleiben — unter dem Default
`'on-reply'` und mit expliziten Kommandos, nicht unter `'on-delivery'`.  (Der reine
AMQP-Protokoll-Default ist 0 = unbegrenzt, aber der Actor setzt
`prefetch` auf 1, sofern Du ihn nicht überschreibst.)  Erhöhe ihn
auf eine sinnvolle Batch-Größe (10–50), damit der Consumer
ausgelastet, aber nicht überfordert wird.

## TLS

Eine `amqps://`-URL startet den Handshake, und amqplib verifiziert
den Broker gegen den **System-Trust-Store**.  Hinter einer privaten
CA — oder wenn der Broker ein Client-Zertifikat verlangt — kommt
`withTls` dazu; es erreicht amqplib als dessen
`socketOptions`-Argument:

```ts
const amqpOptions = AmqpOptions.create()
  .withUrl('amqps://rabbitmq.example.com:5671')
  .withTls({
    ca: fs.readFileSync('./tls/ca.crt', 'utf8'),
    cert: fs.readFileSync('./tls/client.crt', 'utf8'),
    key: fs.readFileSync('./tls/client.key', 'utf8'),
  });
new AmqpActor(amqpOptions);
```

Jedes Feld trägt **das Material selbst**, nie einen Pfad darauf —
deshalb liest das Beispiel die Dateien.  `cert` und `key` ergeben nur
gemeinsam Sinn; eines ohne das andere wird beim Start des Actors
abgelehnt, statt im Handshake zu werfen.

AMQP-URL-Query-Parameter tragen `heartbeat`, `frameMax`,
`channelMax` und `locale` — nie Zertifikatsmaterial —, `withTls` ist
also der einzige Weg dafür.  Einen Config-Key hat es bewusst nicht:
Ein Private Key gehört nicht in die `application.conf`.

## Wann AMQP

Drei primäre Szenarien:

1. **Work-Queues** — mehrere Consumer konkurrieren um Nachrichten
   auf einer Queue, pro Nachricht gewinnt ein Consumer.
2. **Routing + Filterung** — Topic-Exchanges mit reichen
   Routing-Keys.
3. **Brücken zu bestehender RabbitMQ-Infrastruktur**.

Für hochvolumiges Streaming skaliert Kafka besser.  Für
leichtgewichtiges Pub/Sub sind NATS oder MQTT schlanker.  AMQP
glänzt bei **Enterprise-Style Queue + Routing**, wo Features
(DLQ, TTL, Prefetch, ACK-Semantik) zählen.

import { Aside } from '@astrojs/starlight/components';

<Aside type="caution" title="Ungeackte Nachrichten binden Speicher">
  ```ts
  // Handler ruft nie ack/nack — ungeackte Nachrichten stapeln sich
  ```
  Ohne ACK geht dem Broker irgendwann der Speicher aus.  ACKe oder
  NACKe immer innerhalb eines vernünftigen Fensters (begrenzt
  durch das Consumer-Timeout des Brokers).
</Aside>

<Aside type="caution" title="Durability ist Alles-oder-nichts">
  ```ts
  { name: 'q', durable: true },
  // aber Nachricht publisht mit persistent: false → trotzdem verloren beim Broker-Neustart
  ```
  Durable Queues + Durable Exchanges + persistente Nachrichten —
  alle drei nötig, um Neustarts zu überleben.  Das `publish` des
  Frameworks ist für durable Exchanges per Default persistent,
  aber prüf deine Settings, wenn Nachrichten nach einem
  Broker-Reboot verschwinden.
</Aside>
