---
title: Kafka
description: Apache-Kafka-Broker-Actor — publisht Records an ein Topic, konsumiert ein Topic über eine Consumer Group. SASL + TLS unterstützt; standardmäßig at-least-once (Commit auf die Antwort des Targets) oder Manual-Commit. Umschließt `kafkajs` unter der Haube.
---

`KafkaActor` integriert mit Apache Kafka.  Umschließt intern
`kafkajs`; du importierst es nicht direkt.

```ts
import { ActorSystem } from 'actor-ts';
import { KafkaActor, KafkaOptions } from 'actor-ts/io';

const system = ActorSystem.create('my-app');

const kafkaOptions = KafkaOptions.create()
  .withBrokers(['kafka-1:9092', 'kafka-2:9092'])
  .withClientId('my-app')
  // Consumer-Actor-Target wird einmalig hier konfiguriert.
  .withConsumer({ groupId: 'my-app-orders' })
  .withTopics(['orders', 'payments'])
  .withTarget(orderHandler);
const kafka = system.spawn(
  () => new KafkaActor(
    kafkaOptions,
  ),
  'kafka',
);

// Ein weiteres Topic zur Laufzeit hinzufügen (das `topics` aus dem
// Konstruktor deckt den Normalfall ab; `subscribe` ist für späte
// Ergänzungen).
kafka.tell({ kind: 'subscribe', topic: 'audit' });

// Publishen:
kafka.tell({ kind: 'publish', publish: { topic: 'audit', value: 'something' } });
```

## Settings

```ts
interface KafkaOptionsType extends BrokerCommonOptionsType {
  brokers:    string[] | string;           // Bootstrap-Server
  clientId?:  string;
  sasl?:      {
    mechanism: 'plain' | 'scram-sha-256' | 'scram-sha-512';
    username:  string;
    password:  string;
  };
  ssl?:        boolean | TlsTransportOptionsType;   // true, or cert material
  producer?: {
    idempotent?:               boolean;
    allowAutoTopicCreation?:   boolean;
  };
  consumer?: {
    groupId?:        string;
    fromBeginning?:  boolean;
    commitMode?:     'auto' | 'manual';
    commitTimeoutMs?: number;
  };
  target?:  ActorRef<KafkaRecord>;     // Consumer-Actor für eingehende Records
  topics?:  ReadonlyArray<string>;
  acknowledgment?:          'on-reply' | 'on-delivery';  // wann ein Auto-Commit-Record committen darf; Default 'on-reply'
  acknowledgmentTimeoutMs?: number;                      // wie lange 'on-reply' wartet; Default 30_000
}
```

Der Parent `BrokerCommonOptionsType` gibt dir Reconnect, Buffer,
Breaker — siehe [BrokerActor-Basis](/de/io/broker-actor-base/).

### Verbindung, Consumer und Topics aus HOCON

Dieselben Einstellungen kommen aus HOCON, unter `actor-ts.io.broker.kafka`,
unterhalb expliziter Optionen und oberhalb der eingebauten Defaults:

```hocon
actor-ts.io.broker.kafka {
  brokers   = ["kafka-1:9092", "kafka-2:9092"]   # a list, even for one broker
  client-id = "my-app"
  ssl       = false                              # the default; certificate material is code-only
  sasl {                                         # all three leaves, once the block is there
    mechanism = "scram-sha-256"                  # "plain", "scram-sha-256" or "scram-sha-512"
    username  = "my-app"
    password  = ${?ACTOR_TS_KAFKA_PASSWORD}
  }
  consumer {
    group-id       = "my-app-orders"             # no consumer without one
    from-beginning = false                       # the default
    commit-mode    = "auto"                      # the default; or "manual"
    commit-timeout = 30s                         # the default; manual mode only
  }
  topics = ["orders", "payments"]
  acknowledgment         = "on-reply"            # the default; or "on-delivery"
  acknowledgment-timeout = 30s                   # the default; on-reply only
}
```

`brokers` und `topics` sind Listen, und `commit-timeout` und
`acknowledgment-timeout` sind Dauern, `30s` und `30000` meinen also dasselbe.
Bleibt `group-id` ungesetzt, ist der Actor nur Producer.

Der `consumer`-Block wird mit `withConsumer({ … })` **Blatt für Blatt**
zusammengeführt: Ein im Code gesetzter Block behält jedes Blatt, das er nicht
nennt, aus der Datei — `withConsumer({ groupId: 'orders' })` über einem
HOCON-`commit-mode = "manual"` bleibt also manuell.

### Der Producer-Block aus HOCON

Idempotenz und automatische Topic-Erzeugung sind eher Cluster-Policy als
Anwendungscode, deshalb sind beide unter `actor-ts.io.broker.kafka` lesbar:

```hocon
actor-ts.io.broker.kafka {
  producer {
    idempotent                 = true
    allow-auto-topic-creation  = false
  }
}
```

Nennst du nur eines von beiden, behält das andere seinen eingebauten Default,
ein HOCON-`producer { idempotent = true }` kann `allowAutoTopicCreation` also
nicht ausleeren.

`withProducer({ … })` im Code wird genauso geschichtet: Die Blätter, die es
nennt, gewinnen (Konstruktor > HOCON > Defaults), und die, die es weglässt,
behalten ihren HOCON- oder eingebauten Wert.

`target` hat keinen Config-Key — es ist eine `ActorRef`, die einen lebenden
Actor in diesem Prozess benennt, und dafür hat eine Config-Datei keine
Schreibweise.  Ebenso wenig die Zertifikatsform von `ssl`: das HOCON-Blatt ist
nur boolesch, denn eine Config-Datei ist der falsche Ort für einen Private
Key.

## Producen

```ts
kafka.tell({
  kind: 'publish',
  publish: {
    topic:   'orders',
    key:     orderId,        // optional — partitioniert nach Key
    value:   JSON.stringify(order),
    headers: { 'x-trace': traceId },
  },
});
```

Bei getrennter Verbindung gepuffert; beim Reconnect in
Reihenfolge geflusht.

Für **strikte Reihenfolge** innerhalb einer Partition setze
`producer.idempotent: true` und gib einen konsistenten `key` für
zusammengehörige Records — kafkajs dedupliziert Retries innerhalb
der Producer-Session.

## Consumen

```ts
// Das Consumer-Actor-Target wird über die Settings verdrahtet
// (siehe oben); `subscribe` ergänzt zur Laufzeit nur weitere
// Topics, wenn nötig.
kafka.tell({ kind: 'subscribe', topic: 'orders' });

class OrderHandler extends Actor<KafkaRecord> {
  override onReceive(record: KafkaRecord): void {
    // record.topic / partition / offset / key / value / timestamp / headers
    const order = JSON.parse(new TextDecoder().decode(record.value!));
    this.process(order);
    acknowledgeDelivery(record);   // erlaubt den Commit des Offsets — siehe unten
  }
}
```

Der Actor liefert jeden konsumierten Record an `target`.
Für Kafkas Consumer-Group-Work-Sharing nimm **mehrere
Actor-Instanzen** mit derselben `groupId` — jede Instanz
übernimmt eine Teilmenge der Partitionen.

`topics` und das `subscribe`-Kommando zur Laufzeit speisen dieselbe
gewünschte Menge, die von der
[BrokerActor-Basisklasse](/de/io/broker-actor-base/#desired-subscriptions)
gehalten wird und nicht vom Consumer: ein zur Laufzeit hinzugefügtes Topic
wird nach einem Reconnect **neu subscribed**, und ein `subscribe`, das
gesendet wird während der Actor getrennt ist, wird beim nächsten Connect
angewandt statt verworfen.  Konfigurierte Topics erben
`consumer.fromBeginning`; eine Ergänzung zur Laufzeit startet beim
aktuellen Offset.

Ein `unsubscribe` gibt es nicht — kafkajs kann einem laufenden Consumer
kein einzelnes Topic entziehen.  Stoppe den Actor (oder starte einen
zweiten mit einer anderen `groupId`), wenn ein Consumer wirklich eine
andere Topic-Menge braucht.

## Commit-Modi

```ts
consumer: { commitMode: 'auto' }    // at-least-once (with the default acknowledgment)
consumer: { commitMode: 'manual' }  // exactly-once-with-processing
```

**`auto`** (Default): kafkajs committed den Offset eines Records, sobald der
Actor es erlaubt, und wann das ist, hängt von `acknowledgment` ab:

- **`'on-reply'`** (Default) — der Actor `ask`t das Target mit jedem Record
  und lässt kafkajs erst committen, wenn das Target auf das `replyTo` des
  Records mit `{ kind: 'acknowledgment' }` geantwortet hat — genau das
  schickt `acknowledgeDelivery(record)`.  Eine Antwort
  `{ kind: 'negativeAcknowledgment', reason? }`, jede andere Antwort oder
  keine Antwort innerhalb von `acknowledgmentTimeoutMs` (30 s) lässt den
  Offset uncommitted, und kafkajs liest den Record erneut.
  **At-least-once** — Handler müssen idempotent sein.  Ein Record, dessen
  Verarbeitung wirft, bekommt nie seine Antwort, läuft also in den Timeout
  und kommt wieder.
- **`'on-delivery'`** — der Actor lässt kafkajs committen, sobald der Record
  in der Mailbox des Targets liegt; eine Antwort wird nicht erwartet
  (`replyTo` fehlt, die Helfer tun nichts).  **At-most-once**: Ein Record,
  der aus der Mailbox verloren geht — ein Crash, ein Überlauf —, wird nie
  wieder gelesen.

Kafka verarbeitet pro Partition einen Record nach dem anderen, unter
`'on-reply'` bremst ein langsames Target also seine Partitionen, statt
Records in seiner Mailbox aufzustauen.  Der Start des Consumers wird auf
`info` mit dem wirksamen Commit-Modus und Acknowledgment geloggt, damit im
Log steht, was der Actor garantiert.

**`manual`**: der Consumer pausiert bei jedem Record und wartet
auf eine explizite Commit-Nachricht:

```ts
override async onReceive(record: KafkaRecord): Promise<void> {
  await processIdempotently(record);
  this.kafka.tell({
    kind:      'commit',
    topic:     record.topic,
    partition: record.partition,
    offset:    record.offset,
  });
}
```

Liefert **Exactly-once-with-processing**-Semantik, wenn deine
Verarbeitung selbst transaktional ist.  `commitTimeoutMs`
(Default 30 s) deckelt, wie lange die Pumpe wartet, bevor sie
aufgibt und einen Rebalance auslöst.

## Auth + TLS

```ts
const kafkaOptions = KafkaOptions.create()
  .withBrokers(['kafka-1:9093'])
  .withSsl(true)
  .withSasl({
    mechanism: 'scram-sha-512',
    username:  process.env.KAFKA_USER!,
    password:  process.env.KAFKA_PASS!,
  });
new KafkaActor(
  kafkaOptions,
);
```

Sowohl TLS als auch SASL-Credentials werden an kafkajs
durchgereicht.  Nimm Env-Variablen für Secrets; hardcode sie nicht in
`application.conf`.

`withSsl(true)` verifiziert den Broker gegen den
**System-Trust-Store**.  Hinter einer privaten CA — oder wenn der
Broker ein Client-Zertifikat verlangt — übergibst du das Material
statt des Booleans:

```ts
const kafkaOptions = KafkaOptions.create()
  .withBrokers(['kafka-1:9093'])
  .withSsl({
    ca: fs.readFileSync('./tls/ca.crt', 'utf8'),
    cert: fs.readFileSync('./tls/client.crt', 'utf8'),
    key: fs.readFileSync('./tls/client.key', 'utf8'),
  });
new KafkaActor(kafkaOptions);
```

Jedes Feld trägt **das Material selbst**, nie einen Pfad darauf —
deshalb liest das Beispiel die Dateien. `cert` und `key` ergeben nur
gemeinsam Sinn; eines ohne das andere wird beim Start des Actors
abgelehnt.

Der `ssl`-**Config**-Key bleibt bewusst boolean-only: Ein Private Key
gehört nicht in die `application.conf`, die Material-Form ist also nur
aus dem Code erreichbar.

## Peer-Dependency

```bash
npm install kafkajs
# oder: bun add kafkajs
```

`kafkajs` ist eine Peer-Dependency — das Framework bundelt es
nicht.  Du installierst es, wenn du `KafkaActor` nutzt.

## Wann Kafka

Drei primäre Anwendungsfälle:

1. **Durables Event-Streaming** — mehrere Consumer lesen denselben
   Stream mit verschiedenen Offsets; wiederabspielbare Historie.
2. **Producer und Consumer entkoppeln** — High-Volume-Downstreams,
   die nicht das Tempo des Producers vorgeben sollten.
3. **Brücken zu bestehender Kafka-Infrastruktur** — actor-ts an
   ein bereits Kafka nutzendes System anbinden.

Für clusterinternes Pub/Sub bevorzuge
[DistributedPubSub](/de/cluster/pubsub/) — keine Broker-
Abhängigkeit.

import { Aside } from '@astrojs/starlight/components';

<Aside type="caution" title="Rebalancing der Consumer Group">
  ```ts
  // Ein neues Consumer-Group-Mitglied löst einen Rebalance aus
  ```
  Kafka-Rebalances verursachen kurze Nichtverfügbarkeit (typisch
  Sekunden).  Bestehende Handler beenden In-Flight-Arbeit; neue
  Partitionen werden neu zugewiesen.  Halte deine Handler-Latenz
  innerhalb von Kafkas Session-Timeout (Default 30 s), um nicht
  mitten im Handler aus der Gruppe geworfen zu werden.
</Aside>

<Aside type="caution" title="Langsame Handler fallen zurück">
  Kafkajs deckelt die In-Flight-Rate — wenn dein Handler 500 ms
  pro Record braucht, verarbeitet der Consumer ~2 Records/s.  Für
  hochvolumigen Konsum parallelisiere innerhalb des Handlers
  (Promise.all-Batches) oder skaliere durch Hinzufügen von
  Consumer-Group-Mitgliedern.
</Aside>
