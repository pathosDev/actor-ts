description: Fixed-Window-Rate-Limiting pro Key auf HTTP-Routen. Standard pro IP; konfigurierbarer Key (pro User, pro Mandant). Auf der Cache-Abstraktion aufgebaut, sodass Single-Pod den Speicher und Multi-Pod Redis nutzt.
---

`rateLimit` ist ein Request-Limiter pro Key.  Er gibt einen
**Handler-Wrapper** zurück — rufe ihn mit den Optionen auf und
übergib der zurückgegebenen Funktion den Handler, den Du schützen
willst.  Überschüssige Requests bekommen **429** mit einem
`Retry-After`-Header.

```ts
import { rateLimit } from 'actor-ts/http';
import { InMemoryCache } from 'actor-ts/cache';

const limited = rateLimit({
  cache:    new InMemoryCache(),
  windowMs: 60_000,                       // 1-Minuten-Fenster
  max:      100,                          // 100 Requests pro Key pro Minute
  key:      (request) => request.remoteAddress ?? 'unknown',   // Socket-Peer — kein spoofbarer Header
});

const routes = path('api', post(limited(apiHandler)));
```

Jede eindeutige IP (hier: der Socket-Peer `request.remoteAddress`) bekommt ein
Budget von 100/Minute.  Überschüssige Requests bekommen 429 mit einem
`Retry-After`-Header.  **Nutze als Key einen Wert, den der Client nicht
fälschen kann** — niemals einen rohen `x-forwarded-for` (siehe
Sicherheitshinweis unten), sonst rotiert ein Angreifer den Header pro
Request und umgeht das Limit.

## Konfiguration

```ts
type RateLimitOptions = {
  cache:       Cache;
  windowMs:    number;
  max:         number;
  key:         (request: HttpRequest) => string | Promise<string>;
  keyPrefix?:  string;                    // Default 'rl:'
  onLimit?:    (context: RateLimitContext) => HttpResponse;
};

type RateLimitContext = {
  key:               string;
  count:             number;
  max:               number;
  windowMs:          number;
  retryAfterSeconds: number;
};
```

| Feld | Zweck |
| --- | --- |
| `cache` | Backing-Store (In-Memory oder Redis). |
| `windowMs` | Größe des Fixed-Windows. |
| `max` | Maximale Requests pro Key pro Fenster. |
| `key(request)` | Leitet den Rate-Limit-Key her — typischerweise Client-IP, User-ID oder API-Key. **Erforderlich.** |
| `keyPrefix` | Cache-Key-Namespace.  Default `'rl:'`, damit mehrere Limiter im selben Redis nicht kollidieren. |
| `onLimit(context)` | Überschreibt die 429-Response — volle Kontrolle über Status / Body / Header. |

## Eigenes Keying

```ts
rateLimit({
  cache,
  windowMs:    60_000,
  max: 100,
  key:    (request) => {
    const userId = extractUserId(request);
    return userId ? `user:${userId}` : `ip:${request.remoteAddress ?? 'unknown'}`;
  },
});
```

Pro User bei Authentifizierung; pro IP, wenn nicht.  Häufiges
Muster:

- **Authentifizierte Routen** — Limit pro User.
- **Öffentliche Routen** — Limit pro IP.

Kombiniere mit der [Cache](/de/cache/overview/)-Abstraktion des
Frameworks, damit der Limiter über Pods hinweg mit Redis-Backing
funktioniert.

## Wie das Zählen funktioniert

```
Fixed-Window (Default):
  - Das Fenster startet, wenn der erste Request für einen Key kommt.
  - Inkrementiert einen Zähler im Cache.
  - Wenn der Zähler max übersteigt, bekommen weitere Requests
    im Fenster 429.
  - TTL auf dem Zähler sorgt dafür, dass frische Fenster sauber starten.
```

Die Implementierung nutzt das **`incr` mit TTL** des Caches —
atomar über Pods hinweg, wenn Redis im Backing steht.

## Response-Header

Die Middleware setzt:

```
X-RateLimit-Limit:     100
X-RateLimit-Remaining: 47
Retry-After:           23           ← (nur bei 429) Sekunden bis zum Reset
```

Clients nutzen die, um zu backoffen, statt zufällig zu retrien.

## Cluster-fähiges Rate-Limiting

```ts
import { RedisCache, RedisCacheOptions } from 'actor-ts/cache';

const redisCacheOptions = RedisCacheOptions.create().withUrl('redis://...');
rateLimit({
  cache:       new RedisCache(redisCacheOptions),
  windowMs:    60_000,
  max: 100,
});
```

Mit Redis-gestütztem Cache **teilen sich alle Pods den Zähler** —
ein Client, der irgendeinen Pod trifft, sammelt gegen dasselbe
Budget an.

Mit `InMemoryCache` hat jeder Pod seinen eigenen Zähler — ein
Client, der über 4 Pods verteilt ist, bekommt effektiv das
**4-fache** Limit.  Für großzügige Limits akzeptabel; für strikte
problematisch.

## Wann einsetzen

Drei gute Einsatzfälle:

1. **Öffentliche APIs** — Missbrauch / DoS verhindern.
2. **Tier-basierte Limits** — unterschiedliche `key` pro
   Tier (free / paid / enterprise).
3. **Per-Aktion-Limits** — Login-Versuche, Passwort-Resets,
   E-Mail-Versandraten.

## Geschichtete Rate-Limits

```ts
// Unterschiedliche Limits pro Handler:
const apiLimited = rateLimit({
  cache, windowMs: 60_000, max: 1000,
  key: (request) => request.headers['x-user-id'] ?? request.remoteAddress ?? 'anon',
});

const loginLimited = rateLimit({
  cache, windowMs: 60_000, max: 10,
  key: (request) => `login:${request.remoteAddress ?? 'unknown'}`,
});

const routes = concat(
  path('login',  post(loginLimited(loginHandler))),
  path('orders', get(apiLimited(ordersHandler))),
);
```

Strengere Limits auf sensiblen Handlern; großzügigere auf
allgemeinem Traffic.  Komponiere, indem Du jeden Handler mit dem
passenden Limiter einwickelst.

import { Aside } from '@astrojs/starlight/components';

<Aside type="caution" title="X-Forwarded-For vertrauen">
  ```ts
  key: (request) => request.headers['x-forwarded-for'];   // ✗ spoofbar
  ```
  Hinter einem Load-Balancer / Proxy steht die echte IP in
  `X-Forwarded-For` (oder ähnlich) — aber nicht an einer Position, die der
  Request benennen darf: NGINX, AWS ALB und Cloudflare **hängen** alle an
  den Header an, was der Client geschrieben hat bleibt also links davon.
  Nimm `request.remoteAddress` als Key, oder löse die Client-Adresse so
  auf, wie [`IpAllowlist`](/de/http/middleware/ip-allowlist/) es tut —
  benenne die Proxys und lies die Kette vom Socket-Ende nach innen.
</Aside>

<Aside type="caution" title="In-Memory-Cache über Pods">
  ```ts
  // 4 Pods × 100-Req-Limit = effektiv 400/min für einen User
  ```
  Nimm einen Redis-gestützten Cache für produktive Multi-Pod-
  Deployments.  Der In-Memory-Cache reicht nur für Single-Pod
  oder "grobes" Limiting.
</Aside>

<Aside type="caution" title="Teile den Cache nicht mit cached() oder idempotent()">
  ```ts
  const limiterCache = new InMemoryCache();   // ✓ the limiter's own instance
  ```
  `InMemoryCache` behandelt den Zähler als Garantie-Träger — `incr` mit
  einem `windowMs` hat ihn erzeugt — und evictet zuerst Einträge, die
  keine tragen; eine Key-Flut über `cached` setzt die Fenster anderer
  Clients also nicht mehr zurück.  Das ordnet, wofür ein Eintrag da ist,
  nicht, wem er gehört: in einer ungeteilten, mit `idempotent`
  geteilten Instanz ist eine Flut angreiferseitig gewählter
  `Idempotency-Key`s eine Flut von Claims, und sobald die Map nichts
  Billigeres mehr hält, gehen die Zähler mit.

  **Ein Fluter kann sein eigenes Limit zurücksetzen — aber nur von
  außerhalb des Limiters.**  Requests, die *durch* diese Middleware
  laufen, führen `incr` vor dem `max`-Vergleich aus und markieren den
  Zähler des Fluters damit als zuletzt genutzt; eine Flut durch den
  Limiter kann ihren eigenen Zähler also nie evictieren — auch nicht,
  nachdem die 429er begonnen haben.  Eine Key-erzeugende Route am
  gleichen `Cache`, die der Limiter **nicht** umschließt, liefert diesen
  Bump nicht: der Zähler altert wie jeder andere, und trägt die Flut
  selbst eine Garantie (etwa eine Flut von `idempotent`-Claims), sind die
  Zähler das, was bleibt, sobald die opportunistische Hälfte leer ist.
  Gemessen an einer geteilten Instanz mit `maxEntries: 4`: ein Client,
  den `max: 2` gerade mit 429 abgewiesen hatte, bekam nach zwanzig
  `Idempotency-Key`-Requests außerhalb des Limiters wieder 200.

  Übergib eine eigene Instanz — oder `ext.cache('rate-limit')` — und
  dimensioniere deren `max-entries` oberhalb der Zahl eindeutiger Keys,
  die du innerhalb eines `windowMs` erwartest, unter dem Namen dieses
  Caches:

  ```hocon
  actor-ts.cache.rate-limit.in-memory.max-entries = 50000
  ```

  Wo eine Instanz wirklich geteilt werden muss, reserviere stattdessen
  den `keyPrefix` dieser Middleware daraus — dieselben zwanzig Requests
  außerhalb des Limiters evictieren dann innerhalb von `idem:`, und der
  429er bleibt stehen:

  ```hocon
  actor-ts.cache.shared.in-memory {
    max-entries   = 10000
    prefix-quotas { "rl:" = 5000, "idem:" = 5000 }
  }
  ```

  Keines von beidem schützt vor einem Mitbewohner desselben Präfixes:
  ein Client mit einem IPv6-`/64` erzeugt Zähler beliebig, und jeder
  davon ist ein Zähler, den der Cache unter derselben
  `rl:`-Reservierung schützt.  Siehe
  [was Eviction schützt und was nicht](/de/cache/in-memory/#was-eviction-schützt-und-was-nicht)
  und [eine Instanz nach Key-Präfix aufteilen](/de/cache/in-memory/#eine-instanz-nach-key-präfix-aufteilen).
</Aside>

<Aside type="caution" title="Randeffekte bei Fixed-Window">
  ```ts
  // Limit ist 100/Minute.
  // Bei t=59s: User trifft 100; bei t=60s: Fenster reset; bei t=61s: User trifft weitere 100.
  // → 200 Requests in 2 Sekunden
  ```
  Fixed-Windows haben Randeffekte, wenn Bursts Fenstergrenzen
  überschreiten.  Für strikten Burst-Schutz liefert das Framework
  derzeit keine Sliding-Window- oder Token-Bucket-Variante —
  falls nötig, manuell umsetzen.
</Aside>
