`cached` umhüllt einen Handler mit **Response-Caching**, verschlüsselt
über eine selbst gelieferte `key(req)`-Funktion.  Ein Cache-Treffer
liefert die gespeicherte Response, ohne den darunterliegenden Handler
aufzurufen.

```ts
import { cached, path, get } from 'actor-ts/http';
import { InMemoryCache } from 'actor-ts/cache';

const productCache = cached({
  cache: new InMemoryCache(),
  ttlMs: 30_000,
  key:   (req) => `products:${pathParam(req, 'id')}`,
});

const routes = path('api',
  path('products',
    get(productCache(async (req) => /* expensive lookup */)),
  ),
);
```

30 Sekunden Cache pro Produkt-ID.  Der erste Request trifft den
Handler; nachfolgende GETs in den nächsten 30 s liefern die gecachte
Response.

## Konfiguration

```ts
type ResponseCacheOptions = {
  cache:          Cache;
  ttlMs:          number;
  key:            (req: HttpRequest) => string | Promise<string>;
  keyPrefix?:     string;                            // default 'rsp:'
  cacheStatuses?: ReadonlyArray<number>;             // default [200]
  identity?:      (req: HttpRequest) => string | Promise<string>;
};
```

| Feld | Zweck |
| --- | --- |
| `cache` | Das [Cache](/de/cache/overview/)-Backend.  `InMemoryCache` für Single-Node; Redis für geteilt. |
| `ttlMs` | Wie lange jede gecachte Response gültig bleibt. |
| `key(req)` | Leitet den Cache-Key aus dem Request ab — enthält typischerweise URL-Params, Tenant-ID, Accept-Header usw.  **Pflicht.** |
| `keyPrefix` | Cache-Key-Namespace.  Default `'rsp:'`, damit sich mehrere Response-Caches im selben Redis nicht überschneiden. |
| `cacheStatuses` | Welche Status-Codes cachebar sind.  Default `[200]` — nur 2xx-Responses werden gecacht. |
| `identity(req)` | Optionaler Scope pro Aufrufer, der in den Key gefaltet wird, damit eine Response nur dem Aufrufer wieder ausgeliefert wird, für den sie entstand.  Zugleich das Opt-in, Requests mit Credentials zu cachen — siehe [was nie geteilt wird](#was-nie-geteilt-wird).  **Leite ihn aus einer verifizierten Identität ab**, nie aus einem rohen Header. |

## Cache-Key-Zusammensetzung

Die `key(req)`-Funktion ist der gesamte Cache-Key-Vertrag — was du
dort aufnimmst, bestimmt, was separat gecacht wird.  Gängige Muster:

```ts
// Per-URL-path key:
key: (req) => req.path,

// Per-tenant:
key: (req) => `${req.headers['x-tenant-id'] ?? 'public'}:${req.path}`,

// Per-locale + content type:
key: (req) => `${req.headers['accept-language']}:${req.headers['accept']}:${req.path}`,

// Query-sensitive — the query is NOT part of req.path:
key: (req) => `${req.path}|page=${req.query.page ?? '1'}`,
```

`req.path` ist **nur der Pfadname** — `/api/products`, nie
`/api/products?page=2`.  Ein Endpunkt, dessen Response von einem
Query-Parameter abhängt, muss diesen Parameter selbst in den Key
falten; sonst teilen sich alle Seiten einen Eintrag und Seite 2
bekommt Seite 1 ausgeliefert.

Baue den Key so, dass er über äquivalente Requests deterministisch,
aber über getrennt zu cachende Responses eindeutig ist.

## Wann cachen

```
GET /api/products       → cache (stable, read-heavy)
POST /api/orders        → passes straight through — only GET is stored
GET /api/users/me       → cache only with identity (per-caller scope)
GET /api/feed?cursor=X  → cache (one entry per cursor)
```

Der Wrapper ist eine Handler-Ebenen-Entscheidung — du wählst, welche
Handler du umhüllst.  Mutationen sollten typischerweise
[`idempotent`](/de/http/middleware/idempotency-key/) verwenden.

## Was nie geteilt wird

Ein Cache-Treffer kehrt zurück, **bevor der umhüllte Handler läuft**.
Jede Prüfung im Handler — Authentifizierung, Autorisierung, ein
Lookup pro Aufrufer — läuft deshalb nur für den ersten Aufrufer.
**Die Autorisierung muss `cached(...)` umhüllen, nie darin sitzen:**

```ts no-compile — ext, jwtOptions and loadProfile belong to the surrounding application
import { cached, get, JwtAuth, jwtClaimsOf, path, withMiddleware } from 'actor-ts/http';

const profileCache = cached({
  cache:    ext.cache('response-cache'),
  ttlMs:    30_000,
  key:      () => 'users:me',
  identity: (req) => jwtClaimsOf(req)?.sub ?? 'anonymous',
});

// ✓ JwtAuth verifies the token on every request, hit or miss
const routes = withMiddleware(JwtAuth(jwtOptions),
  path('me', get(profileCache(loadProfile))),
);
// ✗ a check inside loadProfile is skipped by every hit
```

Darüber hinaus verweigert der Wrapper von sich aus jeden Fall, in dem
die Response eines Aufrufers einen anderen erreichen könnte:

| Regel | Warum |
| --- | --- |
| Nur `GET` wird gespeichert; nur `GET` und `HEAD` werden aus dem Cache beantwortet. | Ein wiederholtes `POST` ist nie richtig.  `HEAD` liest einen `GET`-Eintrag, schreibt aber nie einen, weil eine `HEAD`-Antwort ohne Body auskommen darf. |
| Ein Request mit `Authorization`, `Proxy-Authorization` oder `Cookie` umgeht den Cache, solange `identity` nicht gesetzt ist. | Sonst sagt nichts im Key, wessen Response es ist.  `identity` zu setzen ist das ausdrückliche Opt-in; für einen Endpunkt, der wirklich nicht vom Aufrufer abhängt, sagt `identity: () => 'public'` genau das. |
| Eine Response mit `Set-Cookie` wird nicht gespeichert. | Es gibt keinen korrekten Weg, das Cookie eines Aufrufers einem anderen zu geben. |
| `Cache-Control: no-store`, `no-cache` oder `private` auf der Response unterdrückt das Speichern. | Der Handler hat gesagt, dass die Response nicht in einen geteilten Cache gehört. |
| Eine Response mit `Vary` wird zusammen mit den Werten der genannten Request-Header gespeichert und nur an einen Request mit denselben Werten ausgeliefert; `Vary: *` wird nicht gespeichert. | Der Handler hat gesagt, dass die Response von diesen Headern abhängt. |
| Ein streamender Body wird nicht gespeichert. | Ein Stream ist einmalig lesbar. |

Dieselben Regeln gelten für den Stampede-Schutz: Ein Request, der auf
den laufenden Handler eines anderen Requests wartet, übernimmt dessen
Response nur, wenn er sie auch aus dem Cache hätte bekommen können,
und führt den Handler sonst selbst aus.  `Cache-Control` auf dem
**Request** wird bewusst ignoriert — ein Client darf den Handler nicht
am Cache vorbei erzwingen können.

## Cache-Invalidierung

`cached` **invalidiert nicht automatisch** bei Writes — die
Veraltung ist durch `ttlMs` begrenzt.

Für **stärkere Konsistenz** zwei Muster:

### Kurze TTLs

```ts
cached({ cache, ttlMs: 1_000, key });   // 1 second
```

Sub-Sekunden-TTLs begrenzen die Veraltung.  Gut für „echtzeit-nahe"
APIs.

### Manuelle Invalidierung

```ts
// After a write that affects products:42, invalidate the cache:
await cache.delete('rsp:products:42');   // 'rsp:' is the default keyPrefix
```

Der Cache ist einfach ein `Cache` — du kannst den mit Prefix
versehenen Key direkt `delete`n, wenn ein Write ihn invalidieren soll.
Mit gesetztem `identity` lautet der Key `<keyPrefix><scope>:<key>`,
der Scope URI-kodiert (`rsp:alice:users:me`).

## Geteilter Cache über Pods

```ts
import { RedisCache, RedisCacheOptions } from 'actor-ts/cache';

const redisCacheOptions = RedisCacheOptions.create().withUrl('redis://...');
const productCache = cached({
  cache: new RedisCache(redisCacheOptions),
  ttlMs: 30_000,
  key:   (req) => `products:${pathParam(req, 'id')}`,
});
```

Mit einem Redis-gestützten Cache teilen sich alle Pods denselben
Cache — nützlich für Multi-Pod-Deployments, in denen du konsistentes
Caching willst.

Für **Per-Pod-Caches** (jeder Pod hat seinen eigenen InMemoryCache)
können Pods kurzzeitig unterschiedliche gecachte Responses liefern,
bis sich die TTLs angleichen.  Oft akzeptabel; hängt von den
Konsistenzanforderungen ab.

## Verschiedene Status-Codes cachen

```ts
cached({
  cache, ttlMs: 30_000, key,
  cacheStatuses: [200, 404],   // cache both hits AND "not found"s
});
```

Cache `404`s, wenn du viele Lookups für nicht existierende IDs hast —
spart wiederholte DB-Zugriffe.  Default ist nur `[200]`, damit ein
transientes 500 nicht 30 Sekunden lang hängen bleibt.

import { Aside } from '@astrojs/starlight/components';

<Aside type="caution" title="Responses pro Aufrufer mit identity trennen">
  ```ts
  identity: (req) => jwtClaimsOf(req)?.sub ?? 'anonymous',   // ✓ verified
  identity: (req) => req.headers['x-user-id'] ?? 'anonymous', // ✗ client-chosen
  ```
  Eine Response, die davon abhängt, wer fragt, muss mit `identity`
  getrennt werden, und der Scope muss aus dem kommen, was eine
  Middleware verifiziert hat.  Mit einem rohen Header kann sich jeder
  Aufrufer den Scope eines anderen anmaßen und dessen gecachte Response
  lesen.  Requests mit Credentials umgehen den Cache, bis `identity`
  gesetzt ist — eine Response pro Aufrufer auf einen Request ohne
  Credential-Header, etwa mit einem eigenen API-Key-Header, hält aber
  nur `identity` auseinander.
</Aside>

<Aside type="note" title="Stampede-Schutz ist Per-Process">
  ```ts
  // TTL expires; 1000 concurrent requests on one pod → the handler runs once
  ```
  Bei einem Cache-Miss führt der Wrapper den Handler **einmal pro
  Prozess** aus, und die übrigen gleichzeitigen Requests für denselben
  Key warten auf dieses eine Ergebnis (eine In-Process-Single-Flight-
  Map).  Es ist **nicht** cluster-weit: mit N Pods kann der Handler bis
  zu N-mal gleichzeitig laufen.  Stale-While-Revalidate ist nicht
  eingebaut — implementiere es bei Bedarf selbst.
</Aside>

<Aside type="caution" title="In-Memory-Cache auf dein Response-Set dimensionieren">
  ```ts
  new InMemoryCache();                        // LRU-bounded: 10 000 entries
  new InMemoryCache({ maxEntries: 100_000 }); // raise it for a larger response set
  ```
  `InMemoryCache` ist standardmäßig LRU-begrenzt (10 000 Einträge), ein
  Response-Cache kann also nicht unbegrenzt wachsen — aber eine zu
  kleine Schranke evictet heiße Responses zu früh.  Dimensioniere
  `maxEntries` auf die Zahl der erwarteten eindeutigen Cache-Keys.
  Siehe [In-Memory-Cache](/de/cache/in-memory/).
</Aside>

<Aside type="caution" title="Hier entstehen die Keys — teile die Instanz nicht">
  ```ts
  const responseCache = new InMemoryCache();   // ✓ this middleware's own instance
  ```
  `key(request)` leitet sich fast immer aus etwas ab, das der Client
  kontrolliert — einem Pfadparameter, einem Mandanten-Header.  Wer das
  variiert, erzeugt pro Request einen neuen Eintrag.  Hier ist das
  harmlos: die LRU-Schranke ist genau das, was den Response-Cache am
  unbegrenzten Wachsen hindert.  Jeder dieser Einträge ist ein
  einfaches `set`, `InMemoryCache` behandelt sie also als die billigen
  Opfer und leert sie, bevor er einen Rate-Limit-Zähler oder einen
  Record anfasst, der eine doppelte Zahlung verhindert — genau das macht
  diese Flut in einer geteilten Instanz überhaupt überlebbar.  Verlass
  dich nicht darauf: die Schranke bleibt hart, die Einträge dieser
  Middleware sind der einzige Spielraum der geteilten Map, und Memcached
  sowie Redis unter `allkeys-lru` haben keine solche Politik.  Gib
  dieser Middleware eine eigene Instanz — oder
  `ext.cache('response-cache')` — statt der, die eine Garantie
  durchsetzt.  Wo eine Instanz geteilt werden muss, gib ihr eine
  `prefixQuotas`-Reservierung für den `keyPrefix` dieser Middleware; das
  begrenzt die Flut auf diesen Anteil, egal was die Map sonst hält:

  ```hocon
  actor-ts.cache.shared.in-memory {
    max-entries   = 10000
    prefix-quotas { "rsp:" = 7000, "idem:" = 2000, "rl:" = 1000 }
  }
  ```

  Siehe
  [was Eviction schützt und was nicht](/de/cache/in-memory/#was-eviction-schützt-und-was-nicht)
  und [eine Instanz nach Key-Präfix aufteilen](/de/cache/in-memory/#eine-instanz-nach-key-präfix-aufteilen).
</Aside>
