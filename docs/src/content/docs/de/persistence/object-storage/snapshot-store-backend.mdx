import { Aside } from '@astrojs/starlight/components';

`ObjectStorageSnapshotStore` ist die Snapshot-Store-
Implementierung, die
[Object Storage](/de/persistence/object-storage/overview/) als
Backing-Schicht verwendet.

```ts
import {
  ObjectStorageSnapshotStore,
  ObjectStorageSnapshotStoreOptions,
  S3ObjectStorageBackend,
  S3ObjectStorageOptions,
  PersistenceExtensionId,
} from 'actor-ts/persistence';

const s3ObjectStorageOptions = S3ObjectStorageOptions.create()
  .withRegion(region)
  .withBucket(bucket);
const objectStorageSnapshotStoreOptions = ObjectStorageSnapshotStoreOptions.create()
  .withBackend(new S3ObjectStorageBackend(s3ObjectStorageOptions))
  .withCompression({ algorithm: 'gzip' })
  .withEncryption(encryption);
const snapshotStore = new ObjectStorageSnapshotStore(objectStorageSnapshotStoreOptions);

system.extension(PersistenceExtensionId).setJournal(someJournal);
system.extension(PersistenceExtensionId).setSnapshotStore(snapshotStore);
```

Snapshots, die von jedem `PersistentActor` geschrieben werden,
gehen in den S3-Bucket; komprimiert + verschlüsselt gemäß der
Config.

## Wann verwenden

Drei Muster:

1. **Cluster-weit geteilte Snapshots** — Sharded Entities, die
   zwischen Nodes wandern, brauchen, dass jeder Node den
   Snapshot jeder Entity laden kann.  Object Storage
   funktioniert; SQLite pro Node nicht.
2. **Verschlüsselte Snapshots** — Server-Side- und/oder
   Client-Side-Verschlüsselung at rest für Compliance erforderlich.
3. **Günstiger Snapshot-Storage** — Object Storage ist pro GB
   viel günstiger als SQL-Stores für
   selten-gelesene-gelegentlich-überschriebene Daten.

Für **Single-Node**-Deployments ist
[SqliteSnapshotStore](/de/persistence/snapshot-stores/sqlite/)
schneller + einfacher.

## Konfiguration

```ts
type ObjectStorageSnapshotStoreOptionsType = {
  backend:                ObjectStorageBackend;
  prefix?:                string;   // Default ''
  keepN?:                 number;   // Default 3
  compression?:           CompressionConfig | CompressionResolver;
  encryption?:            EncryptionConfig | EncryptionResolver;
  integrity?:             IntegrityConfig | IntegrityResolver;
  allowUntaggedBodies?:   boolean;  // Default false
  requireContextBinding?: boolean;  // Default false
  maxDecompressedBytes?:  number;   // Default 512 MiB
};
```

| Feld | Zweck |
| --- | --- |
| `backend` | Filesystem- oder S3-Backend. |
| `prefix` | Object-Key-Prefix.  Nützlich, um Buckets zu teilen. |
| `keepN` | Pro persistenceId behaltene Snapshots; ältere werden beim Save entfernt.  Default 3. |
| `compression` | At-Rest-Kompression — siehe [Kompression](/de/persistence/object-storage/compression/). |
| `encryption` | At-Rest-Verschlüsselung — siehe [Verschlüsselung](/de/persistence/object-storage/encryption/). |
| `integrity` | HMAC-SHA256-Tag über jeden Snapshot-Body — signiert Writes und verlangt beim Lesen ein Tag.  Siehe [Body-Integrität](/de/persistence/object-storage/encryption/#body-integrität-hmac). |
| `allowUntaggedBodies` | Snapshots ohne Tag akzeptieren, solange `integrity` gesetzt ist — das Migrationsfenster für einen Bucket von vor der Integrität.  Default false. |
| `requireContextBinding` | Snapshots ablehnen, die nicht an den Key gebunden sind, von dem sie gelesen wurden — schließt das Einspielen auf eine andere persistenceId oder Sequenznummer.  Erst einschalten, wenn der Bucket neu geschrieben ist.  Siehe [Einen Body an seinen Key binden](/de/persistence/object-storage/encryption/#einen-body-an-seinen-key-binden).  Default false. |
| `maxDecompressedBytes` | Schutz vor Dekompressions-Bomben — Obergrenze für die Größe eines dekodierten Snapshots.  Default 512 MiB. |

## Key-Layout

```
<prefix>snapshots/<persistenceId>/<seqNr auf 20 Stellen gepolstert>.json
```

Beispiele, mit `prefix: 'acme/'`:

```
acme/snapshots/account-42/00000000000000000100.json
acme/snapshots/account-42/00000000000000000200.json
acme/snapshots/account-42/00000000000000000300.json
```

Drei Segmente, jedes mit genau einer Aufgabe.

- **`<prefix>`** gehört dir — ein Deployment, eine Umgebung, ein
  Mandant.  Er ist Teil dessen, woran ein Body gebunden wird, also
  lässt sich Staging-State nicht in die Produktion einspielen.
- **`snapshots/`** ist der Namespace, der diesem Store gehört.
  `ObjectStorageDurableStateStore` besitzt `state/` und schreibt
  `<prefix>state/<persistenceId>/state.json`.  Beide Stores
  bekommen von `registerObjectStoragePlugins` denselben Prefix, und
  der Namespace ist das, was ihre Korpora davon abhält, sich ein
  Verzeichnis zu teilen — siehe
  [Zwei Stores, ein Prefix](#zwei-stores-ein-prefix).
- **`<persistenceId>/`** ist das Verzeichnis pro Entity, das jedes
  LIST begrenzt.

Das Framework listet Keys unter
`<prefix>snapshots/<persistenceId>/`, um den neuesten Snapshot zu
finden.  Die Auflistung ist aufsteigend nach Key und trägt kein
Limit: die nullgepolsterte Sequenznummer macht den *letzten*
Eintrag zum neuesten, ein `limit: 1` lieferte also den ältesten.

Was der Store aus dieser Auflistung nimmt, ist der letzte Eintrag,
der **wie einer seiner eigenen Snapshots geformt** ist — das
Verzeichnis dieser Entity, dann exakt zwanzig Ziffern und `.json`.
Prefix-Zugehörigkeit ist kein Beleg für Eigentum: ein Bucket kann
einen zweiten Schreiber haben, und eine Marker-Datei oder eine
halb fertige Migration unter demselben Prefix wurde früher als
Snapshot gelesen, von `delete` gelöscht und auf `keepN`
angerechnet — auf Kosten eines echten Snapshots.  Ein Body, der
eine *andere* `persistenceId` nennt, wird ebenfalls nicht
zurückgegeben; der Store meldet dann keinen Snapshot, und die
Recovery spielt das Journal ab.

Für sehr große `persistenceId`-Räume ist das Listen pro pid in S3
typischerweise schnell (Per-Prefix-Durchsatz).  Vermeide es, alle
Entity-Typen unter denselben Prefix ohne Per-pid-Unterordner zu
packen — dieses Verzeichnis-Segment ist das Einzige, was
begrenzt, was ein Load aufzählen muss.

### Zwei Stores, ein Prefix

`registerObjectStoragePlugins` verdrahtet den Snapshot-Store und
den Durable-State-Store absichtlich auf ein Backend mit einem
Prefix.  Ihre Key-Namespaces sind trotzdem disjunkt:

```
acme/snapshots/account-42/00000000000000000300.json   Snapshot
acme/state/account-42/state.json                      Durable State
```

Ohne die Namespaces landeten beide in `acme/account-42/`, und
`state.json` sortiert hinter jede nullgepolsterte Sequenznummer —
eine Entity, die auf beide Arten persistiert wurde, bekam also
ihren Durable-State-Record als ihren neuesten Snapshot zurück.
Dieser Body trägt keine `sequenceNr`, die Recovery lehnte ihn ab,
und der Actor konnte nicht starten.  Dafür war keine ungültige
`persistenceId` nötig: ein Aufruf, der das Plugin verdrahtet, und
eine Entity, die beide Wege nutzt.

<Aside type="caution" title="Einen bestehenden Bucket migrieren">
  Die Namespaces sind eine **breaking** Änderung des Key-Layouts.
  Ein von einer früheren Version geschriebener Bucket enthält
  `<prefix><persistenceId>/…`, was diese Version nicht liest.

  **Snapshots brauchen keine Migration.**  Sie sind ein
  Recovery-Beschleuniger, keine Quelle der Wahrheit: findet
  `loadLatest` nichts, wird das Journal vollständig abgespielt, und
  der nächste Save schreibt unter dem neuen Key.  Lösche die alten
  Objekte, wenn du so weit bist.

  **Durable State schon** — er *ist* die Quelle der Wahrheit.
  Kopiere jedes `<prefix><persistenceId>/state.json` nach
  `<prefix>state/<persistenceId>/state.json`.  Ein Body, der weder
  mit clientseitiger Verschlüsselung noch mit einem
  Integritäts-HMAC geschrieben wurde, trägt keine Key-Bindung; eine
  serverseitige Kopie genügt.  Ein an seinen Key gebundener Body
  (#612) ist gegen den alten Key versiegelt und dekodiert am neuen
  nicht: fahre vor dem Upgrade die **alte** Version mit
  `prefix: '<prefix>state/'` allein am Durable-State-Store und
  schreibe jeden Record per `upsert` neu — das erzeugt genau die
  Keys, die diese Version liest, und bindet sie korrekt.  Danach
  upgraden und `prefix` wieder auf `<prefix>` setzen.
</Aside>

## Performance

Snapshot-Writes gehen durch das PUT von Object Storage; Reads
durch GET.  Zahlen für S3 Same-Region:

- **Save** — 20-50 ms pro Snapshot.
- **Load latest** — 1 LIST + 1 GET = 30-60 ms.

Dieses LIST ist das, was das Verzeichnis pro `persistenceId` im
Key einbringt.  Beide mitgelieferten Backends schränken es auf
`<prefix>snapshots/<persistenceId>/` ein — S3 über `Prefix` /
`MaxKeys`,
das Filesystem-Backend, indem es nur dieses Verzeichnis liest —,
sodass ein Load die Snapshots genau einer Entity kostet und flach
bleibt, während die Zahl der Entities wächst.  Das `keepN`-Pruning
setzt dasselbe LIST nach jedem Save ab; ein Backend ohne diese
Einschränkung legte das Wachstum also auch auf den Schreibpfad.

Für **Hot-Path-Snapshot-Laden** (häufige Actor-Neustarts) wickle
es mit
[CachedSnapshotStore](/de/persistence/snapshot-stores/cached-snapshot-store/)
ein:

```ts
const objectStorageSnapshotStoreOptions = ObjectStorageSnapshotStoreOptions.create().withBackend(backend);
const cachedSnapshotStoreOptions = CachedSnapshotStoreOptions.create().withCache(cache);
const cached = new CachedSnapshotStore(
  new ObjectStorageSnapshotStore(objectStorageSnapshotStoreOptions),
  cachedSnapshotStoreOptions,
);
```

Reduziert redundante S3-GETs auf Sub-Mikrosekunden-Cache-Hits.

## Snapshot-Lifecycle

```
PersistentActor.persist(event) gelingt
  ↓ snapshotPolicy() prüfen
  ↓ wenn true → Snapshot machen
backend.put('<prefix>snapshots/<pid>/<seq>.json', serialisierter State)

PersistentActor.preStart
  ↓ '<prefix>snapshots/<pid>/' auflisten — nur dieses Verzeichnis, aufsteigend
  ↓ letzter wohlgeformter Key = neueste seq
  ↓ backend.get(latest) → dekodieren → onEvent ab seq+1
```

Das Framework handhabt Snapshot-Saves + -Loads über dieses
Layout; du setzt die Policy.

## Cleanup alter Snapshots

```ts
const objectStorageSnapshotStoreOptions = ObjectStorageSnapshotStoreOptions.create()
  .withBackend(backend)
  .withKeepN(5);
new ObjectStorageSnapshotStore(objectStorageSnapshotStoreOptions);   // die 5 neuesten behalten; ältere löschen
```

Pruning ist standardmäßig aktiv: `keepN` ist per Default 3, sodass
jeder Save nur die neuesten Snapshots pro persistenceId behält und
die älteren löscht.  Erhöhe oder senke die Grenze mit `withKeepN`;
setze `keepN: 0`, um Pruning zu deaktivieren und jeden Snapshot zu
behalten.

Das Framework löscht beim Lesen nicht automatisch — es gibt ein
kleines Fenster, in dem alte Snapshots mit neuen koexistieren.

## Mischen mit dem Journal

```ts
{
  const sqliteJournalOptions = SqliteJournalOptions.create().withPath('...');
  const objectStorageSnapshotStoreOptions = ObjectStorageSnapshotStoreOptions.create().withBackend(backend);
  journal:       new SqliteJournal(sqliteJournalOptions),
  snapshotStore: new ObjectStorageSnapshotStore(objectStorageSnapshotStoreOptions),
}
```

Das Journal und der Snapshot-Store sind **unabhängig**.  Häufige
Muster:

- **SQLite-Journal + ObjectStorage-Snapshots** — lokale
  Event-Rate, geteilte Snapshots für Sharded Entities.
- **Cassandra-Journal + ObjectStorage-Snapshots** — beide über
  den Cluster geteilt.
- **ObjectStorage alles** — wenn S3 dein einziger Storage ist.
  Langsamer pro Op, aber billig.

<Aside type="caution" title="LIST-Kosten bei großen pids">
  ```ts
  // keepN: 0 deaktiviert Pruning — eine pid kann 100K Snapshots
  // ansammeln, sodass jedes loadLatest-LIST 100K Einträge zurückgibt
  ```
  `keepN` ist per Default 3, sodass Lists pro pid beschränkt bleiben;
  sie wachsen nur unbegrenzt, wenn du `keepN: 0` setzt.  Lass Pruning
  aktiv; besser noch, verwende eine engere snapshotPolicy (alle N
  Events statt jedes Event), um das Write-Volumen zu senken.
</Aside>

<Aside type="caution" title="Snapshot-Verlust ist Recovery-Zeit-Verlust">
  ```ts
  // S3-Bucket verloren (regionale Outage)
  ```
  Ohne Snapshots fällt die Recovery auf vollständigen
  Event-Replay zurück.  Größeres Journal = langsamere Recovery.
  Für missionskritische pids aktiviere S3-Cross-Region-Replikation
  auf dem Snapshots-Bucket.
</Aside>

<Aside type="caution" title="Verschlüsselte Snapshots + alte Schlüssel">
  ```ts
  // Snapshot von vor 2 Jahren, verschlüsselt unter pensioniertem Schlüssel
  ```
  Pensioniere keine Schlüssel, bis alle Snapshots auf den neuen
  Schlüssel neu verschlüsselt sind.  Siehe
  [Schlüsselrotation](/de/persistence/object-storage/key-rotation/).
</Aside>
