title: In-Memory-Journal
description: Die Referenz-Journal-Implementierung — durch plain Arrays gestützt, null Setup, von Tests und Dev verwendet. Daten leben nur so lange wie der Prozess; verwende sie **niemals** in Produktion.
---

`InMemoryJournal` speichert jedes Event im Prozess-Speicher.  Es
ist der **Default**, wenn du ein System ohne konfigurierte
Persistenz erstellst — schnell, null Setup, perfekt für Tests und
Dev.

```ts
import { ActorSystem, ActorSystemOptions, InMemoryJournal, InMemorySnapshotStore } from 'actor-ts';

// In-Memory-Journal + Snapshot-Store sind der DEFAULT — ein bloßes
// ActorSystem.create('demo') nutzt sie bereits.  Um sie explizit zu
// setzen (oder später andere Stores einzuwechseln), beim Erstellen verdrahten:
const actorSystemOptions = ActorSystemOptions.create().withPersistence({
  journal:       new InMemoryJournal(),
  snapshotStore: new InMemorySnapshotStore(),
});
const system = ActorSystem.create('demo', actorSystemOptions);

// Jetzt schreiben `PersistentActor`s in diesem System in das In-Memory-Journal.
```

Es ist außerdem die **Referenz-Semantik**, der jede andere
Journal-Implementierung entsprechen muss — Append-only, monotone
Sequenznummern, Exactly-once-Delivery an Subscriber,
Concurrency-Check auf erwarteter Sequenz.

## Was es tut

Der Journal-Vertrag:

```ts
type Journal = {
  append<E>(persistenceId: string, events: E[], expectedSeq: number, tags?: string[]): Promise<PersistentEvent<E>[]>;
  read<E>(persistenceId: string, fromSeq: number, toSeq?: number): Promise<PersistentEvent<E>[]>;
  highestSeq(persistenceId: string): Promise<number>;
  delete(persistenceId: string, toSeq: number): Promise<void>;
  persistenceIds(): Promise<string[]>;
  readonly events?: JournalEventBus;
  close?(): Promise<void>;
};
```

`InMemoryJournal` implementiert all das intern mit einer
`Map<string, PersistentEvent[]>`.  Operationen sind:

- **`append`** — Events auf das Array des Streams pushen.
  Concurrency-Check auf `expectedSeq` (wirft
  `JournalConcurrencyError`, wenn der aktuelle Head nicht passt).
- **`read`** — das Array nach Sequenznummern-Bereich slicen.
- **`highestSeq`** — die seqNr des letzten Eintrags lesen (oder 0).
- **`delete`** — das Präfix abschneiden.
- **`persistenceIds`** — über die Keys der Map iterieren.

Jedes `append` publiziert das Event außerdem in den In-Process-
`JournalEventBus` — sodass Push-basierte Queries (siehe
[Push-basierte Query](/de/persistence/push-based-query/)) in
Echtzeit ohne Polling funktionieren.

## Wann verwenden

Drei legitime Fälle:

1. **Tests** — schnell, kein IO, kein Cleanup zwischen Tests
   nötig.  Ein frisches System hochziehen, Assertions machen,
   abreißen.
2. **Entwicklung** — wenn du dich beim lokalen Iterieren nicht
   mit einer SQLite-Datei herumschlagen willst.
3. **Wegwerf-Demos** — wenn die Daten nicht überleben sollen.

Für alles, was **über Neustarts hinweg persistieren** muss,
wechsle zu [SQLite](/de/persistence/journals/sqlite/) oder
[Cassandra](/de/persistence/journals/cassandra/).

## Test-Pattern

```ts
import { describe, it, beforeEach, afterEach } from 'bun:test';
import { TestKit, Props } from 'actor-ts';

describe('OrderActor', () => {
  let tk: TestKit;

  beforeEach(() => {
    tk = TestKit.create();   // In-Memory-Journal + Snapshot-Store per Default
  });

  afterEach(async () => { await tk.shutdown(); });

  it('replays events on restart', async () => {
    const probe = tk.createTestProbe();

    // Anlegen + ein paar Commands senden
    let order = tk.system.spawnAnonymous(Props.create(() => new OrderActor('order-1')));
    order.tell({ kind: 'place', sku: 'book-1' });
    order.tell({ kind: 'place', sku: 'book-2' });
    await probe.expectMessage({ kind: 'placed', sku: 'book-2' });

    // Stoppen + neu spawnen — gleiche Persistence-ID
    await tk.system.stop(order);
    order = tk.system.spawnAnonymous(Props.create(() => new OrderActor('order-1')));
    order.tell({ kind: 'view', replyTo: probe });

    // Wiederhergestellter State sollte beide platzierten Events widerspiegeln
    await probe.expectMessage({ items: ['book-1', 'book-2'] });
  });
});
```

Ein frisches `InMemoryJournal` pro Test (über `TestKit` pro Test)
macht jeden Fall isoliert — kein State-Leakage zwischen Tests.

## Was es nicht tut

import { Aside } from '@astrojs/starlight/components';

<Aside type="caution" title="Daten sterben mit dem Prozess">
  Das Journal speichert alles in einer `Map`.  Wenn der Prozess
  beendet wird, ist die Map weg.  Das ist okay für Tests und Dev —
  aber **deploye niemals eine Produktions-App mit dem In-Memory-
  Journal**.  Neustart = totaler Datenverlust.
</Aside>

<Aside type="caution" title="Nicht über Systeme hinweg geteilt">
  ```ts
  const j = new InMemoryJournal();
  const optionsA = ActorSystemOptions.create().withPersistence({ journal: j });
  const systemA = ActorSystem.create('a', optionsA);
  const optionsB = ActorSystemOptions.create().withPersistence({ journal: j });
  const systemB = ActorSystem.create('b', optionsB);
  // ↑ gleiche Instanz, aber in einem echten Multi-Process-Setup hat jeder Prozess
  //   seinen eigenen — die In-Memory-Daten sind nicht zwischen ihnen geteilt.
  ```
  Dieselbe `InMemoryJournal`-Instanz über Systeme in einem Prozess
  zu teilen *funktioniert*, hilft aber in keinem
  Multi-Process-Deployment.  Für ein geteiltes Journal in einem
  Cluster verwende Cassandra.
</Aside>

<Aside type="caution" title="Unbegrenztes Speicherwachstum">
  Das Journal speichert jedes Event für immer (bis du
  `delete` aufrufst).  Ein lange laufender Test, der
  Tausende Events pro Sekunde emittiert, lässt den Speicher des
  Journals linear wachsen.  Für lange laufende Benchmarks entweder
  aggressiv snapshotten + nach jedem Snapshot `delete`
  aufrufen oder SQLite verwenden, das auf Disk flusht.
</Aside>

## Auf ein echtes Journal umsteigen

```ts
// Vorher (Test / Dev) — In-Memory ist der Default:
const devOptions = ActorSystemOptions.create().withPersistence({
  journal: new InMemoryJournal(),
});
const system = ActorSystem.create('app', devOptions);

// Nachher (Produktion):
import { SqliteJournal, SqliteJournalOptions } from 'actor-ts';
const sqliteJournalOptions = SqliteJournalOptions.create().withPath('/var/lib/my-app/events.db');
const prodOptions = ActorSystemOptions.create().withPersistence({
  journal: new SqliteJournal(sqliteJournalOptions),
});
const prodSystem = ActorSystem.create('app', prodOptions);
```

Keine Code-Änderungen innerhalb der Actors — das `Journal`-
Interface ist dasselbe.  Tausche einfach die Implementierung aus.

Deshalb sagen wir "verwende In-Memory für Tests und Dev" — der
Produktions-Switch ist eine Zeile, und die Test-Suite läuft
weiter gegen schnelle In-Memory-Journals.
