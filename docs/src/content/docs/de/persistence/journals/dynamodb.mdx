Das DynamoDB-Backend liefert alle drei Persistence-Komponenten gegen Amazon
DynamoDB, über [`@aws-sdk/client-dynamodb`](https://www.npmjs.com/package/@aws-sdk/client-dynamodb):

- **`DynamoDbJournal`** — das Event-Journal für `PersistentActor`s.
- **`DynamoDbSnapshotStore`** — Snapshots, um die Recovery zu begrenzen.
- **`DynamoDbDurableStateStore`** — Key-Value-Durable-State für
  `DurableStateActor`s.

Es hat die **stärkste Optimistic Concurrency** aller mitgelieferten Backends —
siehe [Concurrency-Modell](#concurrency-modell) — und ist vollständig serverless:
keine Instanz zu betreiben, standardmäßig On-Demand-Kapazität.

## Installation

`@aws-sdk/client-dynamodb` ist eine optionale Peer-Dependency:

```bash
bun add @aws-sdk/client-dynamodb
```

Es ist dieselbe SDK-Familie, die das S3-Object-Storage-Backend schon nutzt — wer
das einsetzt, kennt die Runtime-Situation also bereits. Das Framework importiert
sie lazy, erst wenn ein DynamoDB-Store zum ersten Mal genutzt wird.

## Einrichtung

Registriere Journal + Snapshot-Store an der `PersistenceExtension` und erhalte
einen einsatzbereiten Durable-State-Store. Setz die Verbindung einmal am
Composite, dann erben sie alle drei Komponenten:

```ts
import {
  ActorSystem,
  ActorSystemOptions,
} from 'actor-ts';
import {
  DynamoDbDurableStateStoreOptions,
  DynamoDbJournalOptions,
  DynamoDbSnapshotStoreOptions,
  PersistenceExtensionId,
  RegisterDynamoDbPluginsOptions,
  registerDynamoDbPlugins,
} from 'actor-ts/persistence';

const systemOptions = ActorSystemOptions.create()
  // Die DynamoDB-Plugins als aktives Journal + Snapshot-Store auswählen.
  .withConfig({
    'actor-ts': {
      persistence: {
        journal: { plugin: 'actor-ts.persistence.journal.dynamodb' },
        'snapshot-store': { plugin: 'actor-ts.persistence.snapshot-store.dynamodb' },
      },
    },
  });
const system = ActorSystem.create('my-app', systemOptions);

const ext = system.extension(PersistenceExtensionId);
const dynamoDbSnapshotStoreOptions = DynamoDbSnapshotStoreOptions.create()
  .withKeepN(3);
const registerOptions = RegisterDynamoDbPluginsOptions.create()
  .withRegion('eu-central-1')
  .withJournal(DynamoDbJournalOptions.create() /* .withEventsTable(...) */)
  .withSnapshotStore(dynamoDbSnapshotStoreOptions)
  .withDurableStateStore(DynamoDbDurableStateStoreOptions.create() /* .withTable(...) */);
const { durableStateStore } = registerDynamoDbPlugins(ext, registerOptions);
```

Credentials kommen aus der Standard-AWS-Provider-Kette (Umgebung, Shared Config,
IAM-Rolle) — daran ist nichts actor-ts-spezifisch. Mit
`withClientConfig({ credentials })` überschreibst du das.

### Lokale Entwicklung

`dynamodb-local` braucht einen Endpoint-Override, und das SDK signiert keinen
Request ohne Credentials, auch wenn der Emulator sie ignoriert:

```ts
const dynamoDbJournalOptions = DynamoDbJournalOptions.create()
  .withRegion('eu-central-1')
  .withEndpoint('http://localhost:8000')
  .withClientConfig({ credentials: { accessKeyId: 'local', secretAccessKey: 'local' } });
```

## Aus HOCON konfigurieren

Die Plugin-Id **ist** der Config-Abschnitt: Der Block, der nach der Id benannt
ist, ist der Block, den dieses Plugin liest (#872).  Die gesamte
Erreichbarkeits-Hälfte — Region, Endpoint und die Tabellennamen — kann aus der
`application.conf` kommen, `registerDynamoDbPlugins(ext)` braucht damit gar keine
Optionen mehr:

```ts
import { PersistenceExtensionId, registerDynamoDbPlugins } from 'actor-ts/persistence';

const persistence = system.extension(PersistenceExtensionId);
registerDynamoDbPlugins(persistence);
```

```hocon
actor-ts.persistence {
  journal        { plugin = "actor-ts.persistence.journal.dynamodb" }
  snapshot-store { plugin = "actor-ts.persistence.snapshot-store.dynamodb" }
  durable-state  { plugin = "actor-ts.persistence.durable-state.dynamodb" }

  journal.dynamodb        { region = "eu-central-1", events-table = "actor_ts_events" }
  snapshot-store.dynamodb { region = "eu-central-1", keep-n = 5 }
  durable-state.dynamodb  { region = "eu-central-1", table = "actor_ts_durable_state" }
}
```

`endpoint` ist das Blatt für `dynamodb-local` oder LocalStack; leer gelassen
bedeutet es den echten Dienst.  **Credentials haben gar kein Blatt** — weggelassen
liefert sie die Default-Chain des SDK (`AWS_ACCESS_KEY_ID` /
`AWS_SECRET_ACCESS_KEY`, ein Instance-Profile oder IAM Roles for Service
Accounts), also genau die Behandlung, die auch das S3-Backend des
Object-Storage-Plugins bekommt.  `clientConfig` ebenso wenig — die ganze
Optionsfläche des SDK, die code-only bleibt — und eine vorab gebaute
`operations`-Fassade oder ein `serializer` sind lebende Objekte.

Was du am Client tatsächlich einstellst, hat **typisierte Blätter** (#1490), jedes
als Kommentar in der Referenzkonfiguration, damit Weglassen die eigene Auflösung
des SDK behält — `AWS_MAX_ATTEMPTS` oder `AWS_RETRY_MODE`, dann die geteilte
Config-Datei, dann den Default des SDK — statt sie zu überstimmen:

```hocon
actor-ts.persistence.journal.dynamodb {
  region             = "eu-central-1"
  max-attempts       = 5          # attempts per request, the first included (SDK default 3)
  retry-mode         = adaptive   # standard (the SDK default) or adaptive
  request-timeout    = 10s        # one attempt's limit, after which it fails (default: none)
  connection-timeout = 2s         # opening the connection (default: none)
}
```

Jedes erreicht das SDK nur, wenn es gesetzt ist.  `retry-mode` nimmt `standard`
oder `adaptive` — die eigenen Wörter des SDK, schon kebab-case — und alles andere
wird beim Start mit dem Key und den beiden Werten abgelehnt, weil das SDK jedes
andere Wort als `standard` lesen und nichts sagen würde.  Die beiden Timeouts
werden zu `requestTimeout` und `connectionTimeout` des Request-Handlers, und
`request-timeout` setzt `throwOnRequestTimeout` daneben: Ohne das loggt der
Handler nur eine Warnung, wenn ein Request seinen Timeout überdauert, das Blatt
würde also nichts abbrechen.  Es begrenzt einen Versuch, und die Retry-Strategie
darf es erneut versuchen, ein Aufruf kann also bis zu `max-attempts` davon plus
den Backoff dazwischen dauern.  Ein aus diesen Blättern gebauter Handler ersetzt
den Default-Handler des SDK, ein Connection-Timeout, den `AWS_DEFAULTS_MODE`
liefern würde, gilt dann also nicht mehr; setze `connection-timeout` neben
`request-timeout`, wenn du dich auf einen verlässt.

Der Store prüft sie beim Bauen: Eine Anzahl von Versuchen oder ein Timeout, das
keine positive ganze Zahl ist, oder ein Timeout, das länger ist, als ein Timer
halten kann, wird mit einem `OptionsError` abgelehnt.  Ebenso ein Blatt neben
dem, was es in `clientConfig` ersetzt — `maxAttempts` oder `retryMode`, eine
`retryStrategy`, die beide gegenstandslos macht, oder ein `requestHandler` —
unter Nennung beider Seiten, statt dass eine davon stillschweigend gewinnt.

Auch das **Provisioning** der Tabellen — wie eine Tabelle angelegt wird, die der
Store beim ersten Zugriff anlegt — hat Blätter (#1490), unter allen drei
Blöcken: `billing-mode` (`"pay-per-request"`), `table-ready-timeout` (`30s`) und
`auto-create-tables` (`on`).  Die Werte des Billing-Modus sind kebab-case, wie
jeder HOCON-Wert, und der Reader bildet sie auf die Schreibweise von AWS ab:
`pay-per-request` ist `PAY_PER_REQUEST` und `provisioned` ist `PROVISIONED`.
`PAY_PER_REQUEST` in einer Config-Datei wird beim Start abgelehnt, mit dem Key
und den beiden Werten, die er annimmt.

Das Kapazitätspaar wird als **Kommentar** ausgeliefert, weil es veröffentlicht
unter dem Default `pay-per-request` für jeden Store abgelehnt würde — AWS
ignoriert Kapazität dort, und der Validator sagt das, statt einen Tippfehler
unbemerkt durchzulassen.  **Eine `provisioned`-Tabelle ohne Paar wird mit 5
Lese- und 5 Schreib-Kapazitätseinheiten angelegt**
(`DEFAULT_DYNAMODB_PROVISIONED_CAPACITY_UNITS`), aus einer Config-Datei wie aus
dem Code — nenne das Paar also, wenn du bewusst provisionierst:

```hocon
actor-ts.persistence.journal.dynamodb {
  billing-mode = provisioned
  provisioned-throughput { read-capacity-units = 25, write-capacity-units = 10 }
}
```

Setzt du eine Hälfte ohne die andere, startet der Store nicht und nennt die
fehlende Hälfte — kein Default ergänzt das Paar stillschweigend.

**`durable-state.plugin` wählt jetzt den Durable-State-Store dieses Backends
aus.**  Früher wurde er eifrig gebaut und von `registerDynamoDbPlugins`
zurückgegeben, ließ sich also nur verdrahten, indem man diese Instanz durch den
Anwendungscode reichte.  Das zurückgegebene Handle funktioniert weiterhin und
liefert dieselbe Instanz — sie wird nur bei der ersten Nutzung gebaut statt bei
der Registrierung.

## Wann du es einsetzt

- **Du bist auf AWS und willst keine Datenbank betreiben.** Keine Instanz, kein
  Connection-Pool, kein Patchen.
- **Du willst die stärkste Append-Garantie, die zu haben ist.** Der
  transaktionale Append ist atomar — das schaffen nicht einmal die relationalen
  Backends für einen Multi-Event-Batch unter Contention.
- **Dein Schreibmuster ist stoßweise.** On-Demand-Billing braucht keine
  Kapazitätsplanung.

## Konfiguration

```ts
type DynamoDbConnection = {
  region?:              string;                    // eu-central-1, …
  endpoint?:            string;                    // http(s) URL — dynamodb-local, LocalStack
  clientConfig?:        Record<string, unknown>;   // { credentials, … } — the code-only long tail
  operations?:          DynamoDbOperations;        // pre-built / shared façade
  maxAttempts?:         number;                    // attempts per request, SDK default 3  (max-attempts)
  retryMode?:           'standard' | 'adaptive';   // SDK default 'standard'               (retry-mode)
  requestTimeoutMs?:    number;                    // requestTimeout, fails the attempt    (request-timeout)
  connectionTimeoutMs?: number;                    // connectionTimeout                    (connection-timeout)
};

type DynamoDbTableProvisioning = {
  autoCreateTables?:      boolean;   // default true
  billingMode?:           'PAY_PER_REQUEST' | 'PROVISIONED';   // default on-demand
  provisionedThroughput?: { readCapacityUnits: number; writeCapacityUnits: number };
  tableReadyTimeoutMs?:   number;    // default 30_000
};

interface DynamoDbJournalOptions extends DynamoDbConnection, DynamoDbTableProvisioning {
  eventsTable?: string;   // default 'actor_ts_events'
}
interface DynamoDbSnapshotStoreOptions extends DynamoDbConnection, DynamoDbTableProvisioning {
  snapshotsTable?: string;   // default 'actor_ts_snapshots'
  keepN?:          number;   // keep newest N per pid; default 3, <=0 keeps all
}
interface DynamoDbDurableStateStoreOptions extends DynamoDbConnection, DynamoDbTableProvisioning {
  table?: string;   // default 'actor_ts_durable_state'
}
```

Die Optionen werden bei der Konstruktion des Stores validiert. Zwei Regeln
lohnen sich besonders: ein Tabellenname wird gegen DynamoDBs eigenen Zeichensatz
und die Längengrenze geprüft, und Kapazitätseinheiten werden abgelehnt, solange
`billingMode` nicht `PROVISIONED` ist — AWS ignoriert sie sonst still, was den
Fehler unsichtbar macht.  Die umgekehrte Lücke ist erlaubt und still:
`PROVISIONED` ohne `provisionedThroughput` legt jede Tabelle mit 5 Lese- und 5
Schreib-Kapazitätseinheiten an.

## Tabellen

| Tabelle | Partition Key | Sort Key | Inhalt |
| --- | --- | --- | --- |
| `actor_ts_events` | `pid` | `seq` (N) | ein Item pro Event; `seq = 0` ist die Kompaktierungs-Marke |
| `actor_ts_snapshots` | `pid` | `seq` (N) | ein Item pro Snapshot |
| `actor_ts_durable_state` | `pid` | — | ein Item pro persistenceId |

Mit `autoCreateTables` (dem Default) legt jeder Store seine Tabelle beim ersten
Zugriff an und **wartet, bis sie `ACTIVE` ist** — `CreateTable` kehrt zurück,
während die Tabelle noch `CREATING` ist, und jede Operation darauf scheitert bis
zum Umschalten. Das Warten passiert im Lazy-Init: der erste Aufrufer blockiert,
alle dahinter bekommen eine funktionierende Tabelle.

## Concurrency-Modell

- **Der Journal-Append ist eine atomare Transaktion.** Alle Events gehen in ein
  einzelnes `TransactWriteItems`, jedes `Put` mit
  `ConditionExpression: attribute_not_exists(pid)` — „nur wenn dieses
  `(pid, seq)`-Item nicht existiert". Ein konkurrierender Writer kann damit
  keinen partiellen Append gewinnen: die Transaktion ist ganz oder gar nicht, und
  ihr Abbruch wird zum `JournalConcurrencyError`. Der vorausgehende Head-Read
  ist nur eine Optimierung *für die Sicherheit des Writes*, die den häufigen
  veralteten Append zu einer billigen Query statt einer abgelehnten Transaktion
  macht — aber der **Wert**, den er zurückgibt, ist tragend, und darum ist es ein
  starker Read (nächster Punkt).
- **Jeder Read, von dem eine Recovery oder eine Sequenznummer-Entscheidung
  abhängt, ist ein starker Read.** DynamoDB liefert eventually-consistent Reads,
  solange ein Request nicht `ConsistentRead: true` setzt; das Journal setzt es beim
  Head-Read, bei der Replay-Query und bei der Query nach den zu löschenden Keys in
  `delete`, der Snapshot-Store bei `loadLatest` und `loadBefore`. Ein veralteter
  Read ist hier nicht „etwas ältere Daten": ein Head von einer nachhängenden
  Replica lässt einen intakten Stream *zurückgespult* aussehen, und eine veraltete
  Replay-Seite kürzt die Historie so, dass es weiter unten niemand merken kann —
  die Replay-Integritätsprüfungen erkennen ein Loch, eine falsche Reihenfolge und
  ein Event außerhalb des Fensters, aber nichts sagt, wo der Stream enden soll.
- **Durable-State-CAS ist ein nativer konditionaler Write** —
  `PutItem … attribute_not_exists(pid)` zum Anlegen,
  `UpdateItem … revision = :expected` zum Aktualisieren — ohne Transaktion und
  ohne Rücklesen.
- **Die Kompaktierungs-Marke steigt nur.** Sie wird mit
  `attribute_not_exists(deletedTo) OR deletedTo < :value` aktualisiert, also
  `GREATEST` als Bedingung formuliert; ein niedrigerer Wert wird abgelehnt, und
  diese Ablehnung ist das erwartete Ergebnis, kein Fehler.

<Aside type="note" title="Warum das das stärkste der Backends ist">
  Die relationalen Backends und MongoDB lesen erst den Head und schreiben dann,
  und verlassen sich auf einen Primary Key, um einen konkurrierenden Writer
  abzuweisen — das funktioniert, aber ein Fehler mitten im Batch kann trotzdem
  einen Teil des Appends hinterlassen (MongoDB dokumentiert genau diesen
  Vorbehalt). DynamoDBs transaktionaler Put schließt das aus: der Batch landet
  ganz oder gar nicht.
</Aside>

## Fallstricke

<Aside type="caution" title="Starke Reads kosten das Doppelte, und nicht nur bei der Recovery">
  Ein `ConsistentRead` verbraucht doppelt so viel Read-Kapazität wie ein
  eventually-consistent Read, und das ist **keine** Kosten pro Recovery: `read` und
  `highestSeq` rufen auch der Catch-up-Pfad der Query-Ebene, `currentEventsByTag`,
  Remember-Entities und Projection-Tooling auf — die zahlen also mit. Es ist der
  richtige Default — eine Projection, die die neuesten Events still übergeht, ist
  ein eigener Defekt, und ein veralteter Head wird dir als zweiter Writer gemeldet,
  nicht als Nachhängen — aber plane es ein. Wenn du die günstigere Variante
  brauchst: `persistenceIds` ist ohnehin der eine Read, der eventually consistent
  bleibt (eine ID, die einen Poll später auftaucht, kostet nichts), und das
  Snapshot-Pruning ebenso, weil ein veralteter Read dort nur zu wenig löschen kann.
  Eine Konsistenz-Option pro Store gibt es nicht; zu Cassandras `withConsistency`
  existiert noch kein DynamoDB-Gegenstück.
</Aside>

<Aside type="caution" title="Ein Append ist auf 100 Events begrenzt">
  DynamoDB erlaubt höchstens 100 Items in einem `TransactWriteItems`. Ein
  größerer Append wird mit einem klaren Fehler **abgelehnt** statt in Chunks
  zerlegt — Chunking würde die Atomarität brechen, auf der das
  Concurrency-Modell beruht. Persistiere in kleineren Batches; ein
  Einzel-Event-Append ist ohnehin der Normalfall.
</Aside>

<Aside type="caution" title="persistenceIds ist ein voller Table-Scan">
  DynamoDB kann Partition Keys nur per Scan aufzählen, dieser Aufruf liest also
  die gesamte Events-Tabelle und kostet entsprechend. Das Framework nutzt ihn
  nie auf einem Hot Path — er ist für Projection-Tooling — aber rufe ihn nicht
  pro Request auf.
</Aside>

<Aside type="caution" title="Noch keine indizierte Tag-Query">
  `currentEventsByTag` fällt auf den Journal-Scan zurück, genau wie bei Postgres
  und MariaDB. Ein indizierter Pfad braucht eine zweite, nach Tag geschlüsselte
  Tabelle (oder ein Slice-basiertes Modell) — eigene Designarbeit, kein
  Konfigurationsschalter. Wenn du stark auf Tag-Queries setzt, nimm MongoDB,
  SQLite / libSQL oder Cassandra.
</Aside>

<Aside type="caution" title="Reads paginieren, und das 400-KB-Item-Limit ist real">
  Eine `Query` liefert höchstens 1 MB, die Recovery paginiert also über
  `LastEvaluatedKey` — das ist für dich erledigt. Nicht erledigt: ein einzelnes
  Event, dessen JSON DynamoDBs 400-KB-Grenze pro Item überschreitet, wird vom
  Service abgelehnt. Halte Events klein, was Event-Sourcing ohnehin will.
</Aside>

<Aside type="caution" title="Per-Actor-Verschlüsselung und -Integrität schützen keine Events">
  Per-Call-`PersistenceOptions` gelten nur für die Object-Storage-Stores, wie bei
  jedem SQL-Backend, Cassandra und MongoDB.  Der DynamoDB-Snapshot-Store
  und der DynamoDB-Durable-State-Store deklarieren, dass sie keinen der
  drei Hooks honorieren, also **verweigert** ein `encryption()`- oder
  `integrity()`-Override gegen einen der beiden **den Actor beim Start**,
  und `compression()` warnt einmal
  ([#960](https://github.com/pathosDev/actor-ts/issues/960)).

  Das Journal wird nie gefragt.  `encryption()` und `integrity()` an
  einem `PersistentActor` schützen nur seine Snapshots: Jedes Journal
  speichert Events als Klartext-JSON, nichts erkennt ein an Ort und
  Stelle manipuliertes Event, und datenbankseitige Kontrollen —
  Transparent Data Encryption, ein verschlüsseltes Volume,
  Zugriffskontrolle — sind heute der einzige Schutz für Events.  Ein
  Actor, der dieses Journal mit dem Object-Storage-Snapshot-Store
  kombiniert, startet sauber und schreibt seine Events hier im Klartext.
</Aside>
