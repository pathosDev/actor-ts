Das SQL-Server-Backend liefert alle drei Persistence-Komponenten gegen eine
einzige SQL-Server-Datenbank, über den
[`mssql`](https://www.npmjs.com/package/mssql)-Treiber (intern tedious):

- **`MsSqlJournal`** — das Event-Journal für `PersistentActor`s.
- **`MsSqlSnapshotStore`** — Snapshots, um die Recovery zu begrenzen.
- **`MsSqlDurableStateStore`** — Key-Value-Durable-State für
  `DurableStateActor`s.

Wie Postgres ist es **über Cluster-Nodes geteilt** — jeder Node kann jede
persistenceId lesen und schreiben — und `mssql`/tedious ist **reines
JavaScript**, braucht also keinen nativen Build-Schritt und läuft auf allen
drei unterstützten Runtimes.

## Installation

`mssql` ist eine optionale Peer-Dependency — installiere sie neben actor-ts:

```bash
bun add mssql
```

Das Framework importiert sie lazy, erst wenn ein SQL-Server-Store zum ersten
Mal genutzt wird — bis dahin bleibt sie aus deinem Bundle heraus.

## Einrichtung

Registriere Journal + Snapshot-Store an der `PersistenceExtension` und erhalte
einen einsatzbereiten Durable-State-Store.  Übergib einen geteilten `pool`,
damit alle drei Komponenten denselben Connection-Pool nutzen:

```ts
import sql from 'mssql';
import {
  ActorSystem,
  ActorSystemOptions,
} from 'actor-ts';
import {
  MsSqlDurableStateStoreOptions,
  MsSqlJournalOptions,
  MsSqlSnapshotStoreOptions,
  PersistenceExtensionId,
  RegisterMsSqlPluginsOptions,
  registerMsSqlPlugins,
} from 'actor-ts/persistence';

const systemOptions = ActorSystemOptions.create()
  // Die SQL-Server-Plugins als aktives Journal + Snapshot-Store auswählen.
  .withConfig({
    'actor-ts': {
      persistence: {
        journal: { plugin: 'actor-ts.persistence.journal.mssql' },
        'snapshot-store': { plugin: 'actor-ts.persistence.snapshot-store.mssql' },
      },
    },
  });
const system = ActorSystem.create('my-app', systemOptions);

const ext = system.extension(PersistenceExtensionId);
const pool = await new sql.ConnectionPool({
  server: 'db.example.com',
  port: 1433,
  user: 'actor_ts',
  password: process.env.MSSQL_PASSWORD,
  database: 'app',
  options: { encrypt: true },
}).connect();

const msSqlSnapshotStoreOptions = MsSqlSnapshotStoreOptions.create()
  .withKeepN(3);
const registerOptions = RegisterMsSqlPluginsOptions.create()
  // Ein Pool für Journal + Snapshot + Durable-State (empfohlen).
  .withPool(pool)
  .withJournal(MsSqlJournalOptions.create() /* .withEventsTable(...).withTagsTable(...) */)
  .withSnapshotStore(msSqlSnapshotStoreOptions)
  .withDurableStateStore(MsSqlDurableStateStoreOptions.create() /* .withTable(...) */);
const { durableStateStore } = registerMsSqlPlugins(ext, registerOptions);
```

`registerMsSqlPlugins` registriert alle drei Stores an der Extension, die sie
über die Plugin-IDs oben auswählt, und **gibt** den Durable-State-Store
**zurück**, falls du ihn lieber von Hand verdrahtest.  Seit #872 ist das eine
Bequemlichkeit und nicht mehr der einzige Weg: `durable-state.plugin` wählt ihn
wie jedes andere Plugin aus, und das Handle wird bei der ersten Nutzung gebaut.

Ein geteilter Pool gehört dem **Caller**: kein Store beendet ihn, du schließt
ihn also selbst beim Shutdown.  Ohne ihn baut jede Komponente ihren eigenen aus
`poolConfig` / `url` und schließt ihn bei `close()`:

```ts
const poolConfig = {
  server: 'db.example.com', database: 'app',
  user: 'actor_ts', password: process.env.MSSQL_PASSWORD,
  options: { encrypt: true },
};
const msSqlJournalOptions = MsSqlJournalOptions.create()
  .withPoolConfig(poolConfig);
```

## Aus HOCON konfigurieren

Die Plugin-Id **ist** der Config-Abschnitt: Der Block, der nach der Id benannt
ist, ist der Block, den dieses Plugin liest (#872).  Alles außer den lebenden
Objekten kann aus der `application.conf` kommen, `registerMsSqlPlugins(ext)` braucht damit
gar keine Optionen mehr:

```ts
import { PersistenceExtensionId, registerMsSqlPlugins } from 'actor-ts/persistence';

const persistence = system.extension(PersistenceExtensionId);
registerMsSqlPlugins(persistence);
```

```hocon
actor-ts.persistence {
  journal        { plugin = "actor-ts.persistence.journal.mssql" }
  snapshot-store { plugin = "actor-ts.persistence.snapshot-store.mssql" }
  durable-state  { plugin = "actor-ts.persistence.durable-state.mssql" }

  journal.mssql        { url = ${?MSSQL_URL}, events-table = "events" }
  snapshot-store.mssql { url = ${?MSSQL_URL}, keep-n = 5 }
  durable-state.mssql  { url = ${?MSSQL_URL}, table = "durable_state" }
}
```

An `registerMsSqlPlugins` übergebene Optionen gewinnen weiterhin, Feld für Feld, und ein
nicht gesetztes Feld fällt auf den Block durch, statt ihn zu leeren — ein
geteilter `Pool` im Code und die Tabellennamen in HOCON sind also eine
normale Mischung.  Ein vorab gebauter `Pool` und ein `serializer` haben
**gar kein Blatt**: Das sind lebende Objekte, die eine Config-Datei nicht
ausdrücken kann.  `poolConfig` ebenso wenig — freie Treiber-Konfiguration ohne
aufzählbare Schlüsselmenge.  `tags-table` wird gelesen, wird aber als
*Kommentar* statt als Schlüssel ausgeliefert, weil sein Default aus
`events-table` abgeleitet wird und genau die Abwesenheit beide im Gleichlauf
hält.

**`durable-state.plugin` wählt jetzt den Durable-State-Store dieses Backends
aus.**  Früher wurde er eifrig gebaut und von `registerMsSqlPlugins` zurückgegeben, ließ
sich also nur verdrahten, indem man diese Instanz durch den Anwendungscode
reichte.  Das zurückgegebene Handle funktioniert weiterhin und liefert dieselbe
Instanz — sie wird nur bei der ersten Nutzung gebaut statt bei der Registrierung.

## Wann du es einsetzt

- **SQL Server ist dein System of Record.** In vielen Stacks der
  Enterprise-Default und das primäre Backend von Akka.NET — das hier ist das
  nächstliegende Gegenstück.
- **Cluster-geteilte Persistenz.** Gesharde Entities, die zwischen Nodes
  wandern, oder Cross-Node-Projections brauchen ein Journal, das jeder Node
  lesen kann.
- **Du willst ein relationales Backend ohne nativen Treiber.** tedious ist
  reines JavaScript, anders als `better-sqlite3`.

Für lokale Single-Node-Entwicklung ist
[`SqliteJournal`](/de/persistence/journals/sqlite/) einfacher (eine Datei, kein
Server).

## Konfiguration

```ts
type MsSqlConnection = {
  url?:        string;                    // Server=…;Database=… oder mssql://user:pass@host:1433/db
  poolConfig?: Record<string, unknown>;   // mssql-Config-Objekt; hat Vorrang vor url
  pool?:       MsSqlPoolLike;             // vorgebauter / geteilter Pool
};

interface MsSqlJournalOptions extends MsSqlConnection {
  eventsTable?:      string;   // Default 'events'
  tagsTable?:        string;   // Default '<eventsTable>_tags'
  autoCreateTables?: boolean;  // Default true
}
interface MsSqlSnapshotStoreOptions extends MsSqlConnection {
  snapshotsTable?:   string;   // Default 'snapshots'
  keepN?:            number;   // neueste N pro pid; Default 3, <=0 behält alle
  autoCreateTables?: boolean;
}
interface MsSqlDurableStateStoreOptions extends MsSqlConnection {
  table?:            string;   // Default 'durable_state'
  autoCreateTables?: boolean;
}
```

Die Optionen werden bei der Konstruktion des Stores validiert.  Tabellennamen
kommen aus der Config (nicht von Nutzereingaben) und werden gegen ein
Safe-Identifier-Pattern geprüft; alles andere — persistenceIds, Tags, Payloads
— geht als **benannter Bind-Parameter** (`@p1`, `@p2`, …) durch und wird nie per
String-Konkatenation zusammengesetzt.

## Schema

Mit `autoCreateTables` (dem Default) führt das Backend beim ersten Zugriff
abgesicherte `CREATE TABLE`-Statements aus.  T-SQL kennt kein `CREATE TABLE IF
NOT EXISTS`, daher ist jedes in eine `IF OBJECT_ID(…) IS NULL`-Prüfung gefasst:

```sql
CREATE TABLE events (
  persistence_id NVARCHAR(255) COLLATE Latin1_General_100_BIN2 NOT NULL,
  sequence_nr    BIGINT NOT NULL,
  payload        NVARCHAR(MAX) NOT NULL,   -- JSON
  tags           NVARCHAR(MAX) NULL,       -- CSV (zusätzlich in events_tags gespiegelt)
  timestamp      BIGINT NOT NULL,
  CONSTRAINT PK_events PRIMARY KEY (persistence_id, sequence_nr)
);
CREATE TABLE events_tags (                 -- indizierte Tag-Lookups für Projections
  persistence_id NVARCHAR(255) COLLATE Latin1_General_100_BIN2 NOT NULL,
  sequence_nr    BIGINT NOT NULL,
  tag            NVARCHAR(255) COLLATE Latin1_General_100_BIN2 NOT NULL,
  timestamp      BIGINT NOT NULL,
  CONSTRAINT PK_events_tags PRIMARY KEY NONCLUSTERED
    (tag, timestamp, persistence_id, sequence_nr)
);
CREATE TABLE events_meta (                 -- High-Water-Mark der Kompaktierung
  persistence_id NVARCHAR(255) COLLATE Latin1_General_100_BIN2 NOT NULL,
  deleted_to     BIGINT NOT NULL,
  CONSTRAINT PK_events_meta PRIMARY KEY (persistence_id)
);
CREATE TABLE snapshots (
  persistence_id NVARCHAR(255) COLLATE Latin1_General_100_BIN2 NOT NULL,
  sequence_nr    BIGINT NOT NULL,
  payload        NVARCHAR(MAX) NOT NULL,
  timestamp      BIGINT NOT NULL,
  CONSTRAINT PK_snapshots PRIMARY KEY (persistence_id, sequence_nr)
);
CREATE TABLE durable_state (
  persistence_id NVARCHAR(255) COLLATE Latin1_General_100_BIN2 NOT NULL,
  revision       BIGINT NOT NULL,
  payload        NVARCHAR(MAX) NOT NULL,
  timestamp      BIGINT NOT NULL,
  CONSTRAINT PK_durable_state PRIMARY KEY (persistence_id)
);
```

Der Primary Key der Tags-Tabelle ist bewusst **nonclustered**.  `NVARCHAR(n)`
zählt 2n Bytes zum Index-Key, `(tag, timestamp, persistence_id, sequence_nr)`
braucht damit 1036 Bytes — über dem 900-Byte-Limit für clustered Indizes, aber
innerhalb des 1700-Byte-Limits für nonclustered.  Genau deshalb ist **SQL Server
2016 oder neuer** Voraussetzung.  Die Kollation ist Metadatum, keine Breite, und
kostet in diesem Budget also nichts.

Leg die Tabellen vorab an (mit nur `INSERT/SELECT/UPDATE/DELETE`-Rechten) und
setze `autoCreateTables: false`, wenn die Datenbankrolle kein DDL ausführen
darf.

### Warum `persistence_id` und `tag` kollationiert sind

Jede `persistence_id`- und `tag`-Spalte trägt ein explizites `COLLATE
Latin1_General_100_BIN2`.  Ohne das erbt die Spalte den Datenbank-Standard —
`SQL_Latin1_General_CP1_CI_AS` auf einer Standardinstanz, und der ist
**case-insensitiv**.

Eine `persistence_id` ist nicht bloß ein Wert: sie ist der *Name eines
Event-Streams* und die Hälfte des `events`-Primary-Keys.  Unter einer faltenden
Kollation sind `Alice` und `alice` deshalb **ein** Stream hier und **zwei** auf
Postgres, SQLite, MongoDB und DynamoDB.  Ein als `Alice` gestarteter Actor liest
`alice`s Events, faltet sie in seinen eigenen State und schreibt in `alice`s
Stream — ein Cross-Entity-Read, dessen einziges Symptom eine Serie von
`JournalConcurrencyError`s ist, die wie ein Speicherfehler aussieht.  Dieselbe
Spalte ist der Schlüssel für Durable-State-Load, Revisions-CAS und Delete; dort
überschreibt und löscht eine Kollision den State einer anderen Entität.

Eine Id-Validierung kann das nicht beheben: `Alice` und `alice` sind beide
völlig legale Ids.  Was sich unterscheidet, ist der *Vergleich*, und der ist
eine Eigenschaft der Spalte.

`BIN2` vergleicht nach Unicode-Codepoint, so wie es jedes andere Backend ohnehin
tut.  Der `Latin1_General`-Teil des Namens wählt nur eine Codepage für
Nicht-Unicode-Typen; auf `NVARCHAR` ist er wirkungslos, das hier ist also ein
vollständig unicodefähiger Ordinalvergleich und keine westeuropäische
Einschränkung.  Version `100` gibt es seit SQL Server 2008 und damit weit
unterhalb der 2016er-Grenze, die der nonclustered Key der Tags-Tabelle ohnehin
setzt.

### Bestehendes Schema migrieren

Das DDL ist mit `IF OBJECT_ID(…) IS NULL` abgesichert, und `autoCreateTables`
ist standardmäßig `true` — eine **bestehende Datenbank übernimmt das also
nicht**: das Framework fasst eine vorgefundene Tabelle nie wieder an.  Neue
Deployments bekommen die Kollation stillschweigend, alte behalten den
Instanz-Standard, und beim Start sagt das nichts.

SQL Server weigert sich, eine Spalte umzukollationieren, von der ein Index oder
Constraint abhängt (Fehler 5074) — pro Tabelle heißt das also: droppen, ändern,
neu anlegen.  Führe das einmal pro Datenbank aus, während kein Knoten schreibt:

```sql
ALTER TABLE events DROP CONSTRAINT PK_events;
DROP INDEX idx_events_pid ON events;
ALTER TABLE events ALTER COLUMN persistence_id
  NVARCHAR(255) COLLATE Latin1_General_100_BIN2 NOT NULL;
ALTER TABLE events ADD CONSTRAINT PK_events
  PRIMARY KEY (persistence_id, sequence_nr);
CREATE INDEX idx_events_pid ON events (persistence_id);

ALTER TABLE events_tags DROP CONSTRAINT PK_events_tags;
DROP INDEX idx_events_tags_pid_seq ON events_tags;
ALTER TABLE events_tags ALTER COLUMN persistence_id
  NVARCHAR(255) COLLATE Latin1_General_100_BIN2 NOT NULL;
ALTER TABLE events_tags ALTER COLUMN tag
  NVARCHAR(255) COLLATE Latin1_General_100_BIN2 NOT NULL;
ALTER TABLE events_tags ADD CONSTRAINT PK_events_tags
  PRIMARY KEY NONCLUSTERED (tag, timestamp, persistence_id, sequence_nr);
CREATE INDEX idx_events_tags_pid_seq ON events_tags (persistence_id, sequence_nr);

ALTER TABLE events_meta DROP CONSTRAINT PK_events_meta;
ALTER TABLE events_meta ALTER COLUMN persistence_id
  NVARCHAR(255) COLLATE Latin1_General_100_BIN2 NOT NULL;
ALTER TABLE events_meta ADD CONSTRAINT PK_events_meta PRIMARY KEY (persistence_id);

ALTER TABLE snapshots DROP CONSTRAINT PK_snapshots;
ALTER TABLE snapshots ALTER COLUMN persistence_id
  NVARCHAR(255) COLLATE Latin1_General_100_BIN2 NOT NULL;
ALTER TABLE snapshots ADD CONSTRAINT PK_snapshots
  PRIMARY KEY (persistence_id, sequence_nr);

ALTER TABLE durable_state DROP CONSTRAINT PK_durable_state;
ALTER TABLE durable_state ALTER COLUMN persistence_id
  NVARCHAR(255) COLLATE Latin1_General_100_BIN2 NOT NULL;
ALTER TABLE durable_state ADD CONSTRAINT PK_durable_state PRIMARY KEY (persistence_id);
```

`ALTER COLUMN` ersetzt die **gesamte** Definition, `NOT NULL` muss also
wiederholt werden — lässt du es weg, wird die Spalte stillschweigend nullable.
Setze deine eigenen Tabellennamen ein, wenn du `eventsTable`, `tagsTable`,
`snapshotsTable` oder `table` überschrieben hast.

Prüfe **vor** der Migration auf Schaden, solange `GROUP BY` noch die faltende
Kollation benutzt:

```sql
SELECT MIN(persistence_id) AS sample,
       COUNT(DISTINCT persistence_id COLLATE Latin1_General_100_BIN2) AS spellings
  FROM events
 GROUP BY persistence_id
HAVING COUNT(DISTINCT persistence_id COLLATE Latin1_General_100_BIN2) > 1;
```

Jede Zeile bedeutet, dass sich zwei Ids bereits einen Stream teilen.  Die
Migration trennt sie wieder, und jeder Hälfte fehlen dann die Events der anderen
— diese Actors scheitern beim Recovery also laut mit `JournalIntegrityError`
(eine Lücke in der Sequenz), statt stillschweigend eine verschmolzene Historie
auszuliefern.  Das ist das bessere Scheitern, aber es bleibt ein Scheitern:
entscheide *vor* der Migration, was diese Streams sein sollen, nicht danach.

## Concurrency-Modell

- **Journal-Append** liest den aktuellen Head und fügt innerhalb einer
  Transaktion ein; das `expectedSeq` des Callers wird gegen diesen Head
  geprüft.  Ein konkurrierender Writer, der sich dazwischenschiebt, verletzt den
  Primary Key, und SQL-Server-Fehler **2627** (bzw. 2601 bei einem Unique-Index)
  wird als Backstop in einen `JournalConcurrencyError` übersetzt.
- **Durable-State-CAS** läuft über die `revision`-Spalte: ein Create
  (`expectedRevision === 0`) ist ein einfaches `INSERT`, eine Kollision kommt
  also als Fehler 2627 an; ein Update ist `UPDATE … WHERE revision = expected`,
  wo null betroffene Zeilen bedeuten, dass die gespeicherte Revision
  abgewichen ist.  In beiden Fällen wird die aktuelle Revision für den
  `DurableStateConcurrencyError` zurückgelesen.
- **Upserts nutzen `MERGE … WITH (HOLDLOCK)`.** Ohne diesen Hint können zwei
  konkurrierende MERGEs beide den `NOT MATCHED`-Zweig nehmen, und einer
  scheitert am Primary Key.

## Fallstricke

import { Aside } from '@astrojs/starlight/components';

<Aside type="caution" title="SQL Server 2016 oder neuer">
  Der vierspaltige Key der Tags-Tabelle überschreitet das 900-Byte-Limit für
  clustered Indizes und verlässt sich auf das 1700-Byte-Limit für
  **nonclustered**, das SQL Server 2016 eingeführt hat.  Auf einer älteren
  Instanz schlägt das `CREATE TABLE` fehl.
</Aside>

<Aside type="caution" title="persistenceIds und Tags sind auf 255 Zeichen begrenzt">
  `NVARCHAR(255)` ist genau das, was die Index-Keys innerhalb des obigen Limits
  hält.  Eine längere persistenceId oder ein längerer Tag wird vom Server
  abgelehnt, nicht still abgeschnitten.
</Aside>

<Aside type="caution" title="Eine bestehende Datenbank behält die alte Kollation">
  Das abgesicherte `CREATE TABLE` fasst eine bereits vorhandene Tabelle nie
  wieder an — eine vor dem `COLLATE Latin1_General_100_BIN2` angelegte
  Datenbank behält also den case-insensitiven Instanz-Standard, und beim Start
  sagt das nichts.  Zwei Ids, die sich nur in der Groß-/Kleinschreibung
  unterscheiden, teilen sich dann auf diesem Backend einen Event-Stream (und
  eine Durable-State-Zeile) und bleiben auf jedem anderen getrennt.  Führe die
  [Migration](#bestehendes-schema-migrieren) aus; prüfe vorher auf bereits
  verschmolzene Streams.
</Aside>

<Aside type="caution" title="TLS ist im Treiber standardmäßig an">
  `mssql` setzt `encrypt: true` als Default.  Gegen einen Server mit
  selbstsigniertem Zertifikat musst du dieses entweder installieren oder
  `options: { trustServerCertificate: true }` setzen — letzteres schaltet die
  Chain-Prüfung ab, also bitte nur in der Entwicklung.
</Aside>

<Aside type="caution" title="Kein In-Process-Event-Bus">
  SQL Server ist ein Cross-Process-Backend (wie Postgres und Cassandra) und
  veröffentlicht daher KEINEN In-Process-Journal-Event-Bus.
  `PersistenceQuery`-Live-Subscriber fallen auf Polling zurück.
</Aside>

<Aside type="caution" title="Compression- / Encryption-Optionen werden ignoriert">
  Per-Call-`PersistenceOptions` (Compression, Encryption) gelten nur für die
  Object-Storage-Stores.  Die SQL-Backends speichern JSON als Text — die
  Optionen werden hier ignoriert, genau wie bei SQLite, Postgres, MariaDB und
  Cassandra, aber nicht mehr stillschweigend: Ein `encryption()`- oder
  `integrity()`-Override gegen einen Store, der es nicht honorieren kann,
  **verweigert den Actor beim Start**, und `compression()` warnt einmal
  ([#960](https://github.com/mknorr/actor-ts/issues/960)).
</Aside>
