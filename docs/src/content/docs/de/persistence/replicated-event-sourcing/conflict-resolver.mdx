Wenn zwei Replicas derselben Entity Events gleichzeitig schreiben
(erkannt via
[Vector Clocks](/de/persistence/replicated-event-sourcing/vector-clocks/)),
muss das Framework wissen, **was die nebenläufigen Events
zusammen bedeuten**.  Standardmäßig wendet es alle an; ein
**Conflict Resolver** — eine Strategie, die du durch Überschreiben
von `resolver()` am Actor bereitstellst — wählt stattdessen eines
aus oder führt sie zusammen.

```ts
import { ReplicatedEventSourcedActor, LastWriterWinsResolver } from 'actor-ts/persistence';
import type { ConflictResolver } from 'actor-ts/persistence';

class Counter extends ReplicatedEventSourcedActor<Command, Event, State> {
  // Der Default ist null — kein Resolver; überschreiben, um nebenläufige Events abzugleichen:
  protected override resolver(): ConflictResolver<Event> {
    return new LastWriterWinsResolver<Event>();
  }
  // ...
}
```

## Der Default: kein Resolver

`resolver()` gibt `null` zurück, solange du es nicht überschreibst,
und dann wird nichts abgeglichen: Jedes Event, nebenläufig oder
nicht, läuft in der kanonischen Reihenfolge durch `onEvent` —
`(timestamp, replica, seqAtReplica)`, auf jeder Replica dieselbe
Liste.  Für ein Event, das einen Wert *ersetzt*, verhält sich das
bereits wie Last-Writer-Wins (das später gestempelte nebenläufige
Event wird zuletzt angewandt); für ein Event, das *addiert*, wirken
beide Seiten.  Überschreibe `resolver()`, wenn beides nicht ist,
was deine Domäne meint.

## Welche Events den Resolver erreichen

Die kanonische Reihenfolge entscheidet weiterhin, wo jedes Event
steht.  Der Resolver entscheidet, was eine Folge nebenläufiger
Events in dieser Reihenfolge bedeutet.  Beim Durchlaufen der
Historie in kanonischer Reihenfolge tritt ein Event der aktuellen
**Konfliktgruppe** bei, wenn es zu jedem Event darin nebenläufig
ist, und eröffnet sonst eine neue Gruppe.  Eine Gruppe aus einem
Event wird unverändert gefaltet; eine größere Gruppe wird paarweise
durch `resolve` reduziert, von links nach rechts in kanonischer
Reihenfolge, und das eine Event, das herauskommt, wird über
`onEvent` gefaltet.  Ein Event, das *nach* einem anderen geschieht,
wird dem Resolver nie zusammen mit diesem übergeben.

Die Gruppen hängen allein von der Menge der Events ab, sodass zwei
Replicas mit denselben Events denselben State falten — egal, in
welcher Reihenfolge die Events ankamen.

## Das Interface

Der Resolver versöhnt ein **nebenläufiges Paar** — er gibt genau
ein Event zurück (einen Gewinner oder eine synthetisierte
Zusammenführung der beiden):

```ts
interface ConflictResolver<E> {
  resolve(a: ConflictCandidate<E>, b: ConflictCandidate<E>): E;
}

type ConflictCandidate<E> = {
  event:     E;             // die User-Domain-Event-Payload
  timestamp: number;        // Wall-Clock der ursprünglichen Replica
  replica:   ReplicaId;     // ID der ursprünglichen Replica
  vc:        VectorClock;   // Vector Clock zum Persist-Zeitpunkt
};
```

Beachte den **einzelnen Typparameter** (das Event, *nicht* den
State).  Enthält eine Gruppe mehr als zwei Events, faltet das
Framework sie paarweise durch `resolve`, sodass die ganze Gruppe
auf ein Event reduziert wird — das dann über dein normales
`onEvent` angewandt wird.  Ein zurückgegebener Kandidat trägt
seine eigenen `timestamp`, `replica` und `vc` in den nächsten
Schritt; ein synthetisiertes Event trägt `timestamp` und `replica`
des späteren Kandidaten und die Zusammenführung beider Clocks.

## Zwei harte Verträge

`resolve` muss sein:

- **Deterministisch** — dasselbe `(a, b)`-Paar liefert auf jeder
  Replica dasselbe Ergebnis; kein `Date.now()`, kein
  `Math.random()`, keine externen Reads.
- **Kommutativ** — `resolve(a, b)` muss gleich `resolve(b, a)`
  sein.  Events kommen auf verschiedenen Replicas in
  unterschiedlicher Reihenfolge an, daher lässt ein
  nicht-kommutativer Resolver Replicas divergieren.

Entscheide den Gewinner aus den Daten der Kandidaten selbst
(`timestamp`, `replica`, Payload) — nie aus der
Ankunftsreihenfolge oder „nimm `a`".

## Eingebaute Resolver

### `LastWriterWinsResolver`

```ts
protected override resolver(): ConflictResolver<Event> {
  return new LastWriterWinsResolver<Event>();
}
```

Höherer `timestamp` gewinnt; bei Gleichstand gewinnt die höhere
(lexikografische) `replica`-ID, und ein Gleichstand in beidem —
eine Replica stempelt zwei Events in derselben Millisekunde — geht
an das Event, dessen typisierter, kanonischer Schlüssel
(`canonicalOrderKey` aus `actor-ts/util`, dieselbe Ordnung wie bei
`LWWRegister`) höher sortiert.  So hängt der
Gewinner nie von der Argumentreihenfolge ab, und jede Replica
konvergiert.
Einfach und oft „gut genug".  Vorbehalt: setzt grob vergleichbare
Wall-Clocks über Replicas voraus — derselbe Trade-off wie
`LWWRegister`.  Anders als der Default **verwirft** er das
unterlegene Event eines nebenläufigen Paars; nutze ihn also für
State, der ersetzt und nicht aufsummiert wird.

### `CustomMergeResolver`

Kapsle ein kommutatives Merge der beiden Event-Payloads — nutze
es, wenn du Domänenwissen hast, das LWW nicht erfasst (z. B.
addieren sich zwei nebenläufige Einzahlungen einfach):

```ts
import { CustomMergeResolver } from 'actor-ts/persistence';

protected override resolver(): ConflictResolver<Event> {
  return new CustomMergeResolver<Event>((a, b) => ({
    kind:   'deposited',
    amount: a.amount + b.amount,   // additives Merge
  }));
}
```

`CustomMergeResolver` sortiert die beiden Kandidaten vor dem
Aufruf deines Merge nach der Replica-ID, sodass es eine
deterministische Argumentreihenfolge erhält, selbst wenn deine
Funktion nicht perfekt symmetrisch ist — der Vertrag verlangt
aber weiterhin **Kommutativität**.

## Eigene Strategien

Für alles andere implementiere `ConflictResolver<Event>` direkt.
`resolve` gibt ein einzelnes Event zurück; der Actor wendet es
über `onEvent` an.

### Gewinner wählen (max / min)

```ts
class HighestWins implements ConflictResolver<Event> {
  resolve(a: ConflictCandidate<Event>, b: ConflictCandidate<Event>): Event {
    if (a.event.value !== b.event.value) {
      return a.event.value > b.event.value ? a.event : b.event;
    }
    return a.replica > b.replica ? a.event : b.event;   // deterministischer Tie-Break
  }
}
```

Richtig für Werte, die nicht zurückgehen dürfen: Lagerbestände,
High-Scores.  Löse exakte Gleichstände über `replica`, damit das
Ergebnis auf jeder Replica gleich ist.

### Deterministische Reihenfolge nach (timestamp, replica)

```ts
class OrderedWins implements ConflictResolver<Event> {
  resolve(a: ConflictCandidate<Event>, b: ConflictCandidate<Event>): Event {
    if (a.timestamp !== b.timestamp) return a.timestamp > b.timestamp ? a.event : b.event;
    return a.replica > b.replica ? a.event : b.event;
  }
}
```

Das ist die Reihenfolge, die `LastWriterWinsResolver` verwendet —
hier als Vorlage für dein eigenes Tie-Breaking gezeigt.  Kommutativ
ist sie nur, solange zwei Kandidaten nie `timestamp` und
`replica` zugleich teilen; der eingebaute Resolver entscheidet
diesen letzten Gleichstand zusätzlich über die Payload.

## Wann ein Merge die falsche Abstraktion ist

Manchmal **sollten** nebenläufige Events nicht mergen — sie
widersprechen sich semantisch (z. B. „Konto schließen"
nebenläufig zu „Einzahlung").  Dafür ist **Single-Writer mit
Lease** besser — siehe
[Single-Writer-Lease](/de/persistence/replicated-event-sourcing/single-writer-lease/) —
das erzwingt sequenzielle Writes, sodass keine Konflikte
entstehen.

Nutze Replicated ES, wenn nebenläufige Events **natürlich
mergen**; nutze das Lease, wenn sie gar nicht auftreten sollen.

## Performance

`resolve` läuft nur bei **Erkennung eines nebenläufigen Writes**
— begrenzt durch die Rate replica-übergreifender Events,
typischerweise selten.  Selbst ein aufwändigeres Merge ist billig
neben dem Journal-I/O.

import { Aside } from '@astrojs/starlight/components';

<Aside type="caution" title="Resolver müssen kommutativ sein">
  ```ts
  resolve(a, b) { return a.event; }   // ✗ „nimm, was als a ankam"
  ```
  `a` und `b` kommen auf verschiedenen Replicas in
  unterschiedlicher Reihenfolge an.  Entscheide aus den Daten der
  Kandidaten, sodass `resolve(a, b) === resolve(b, a)`.
</Aside>

<Aside type="caution" title="Nicht-deterministische Resolver konvergieren nicht">
  ```ts
  resolve(a, b) { return Math.random() < 0.5 ? a.event : b.event; }   // ✗
  ```
  Jede Replica wählt anders; der Cluster einigt sich nie.
  Immer rein + deterministisch.
</Aside>

<Aside type="caution" title="Ein Event zurückgeben, keinen State">
  ```ts
  resolve(a, b) { return { value: 42 }; }   // ✗ muss ein Event sein
  ```
  `resolve` gibt eines der beiden Events zurück (oder ein
  synthetisiertes Event desselben Typs).  Der Actor faltet es über
  dein bestehendes `onEvent` in den State.
</Aside>
