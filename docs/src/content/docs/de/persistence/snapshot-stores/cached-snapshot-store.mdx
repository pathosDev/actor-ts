`CachedSnapshotStore` ist ein **Decorator** — wickle jeden
`SnapshotStore` ein, um einen TTL-basierten Read-Through-Cache
für `loadLatest` hinzuzufügen, gestützt auf einen beliebigen
`Cache` (In-Memory, Redis oder Memcached).

```ts
import {
  ActorSystem,
  ActorSystemOptions,
} from 'actor-ts';
import {
  CachedSnapshotStore,
  CachedSnapshotStoreOptions,
  ObjectStorageSnapshotStore,
  ObjectStorageSnapshotStoreOptions,
} from 'actor-ts/persistence';

const objectStorageSnapshotStoreOptions = ObjectStorageSnapshotStoreOptions.create().withBackend(backend);
const underlying = new ObjectStorageSnapshotStore(
  objectStorageSnapshotStoreOptions, // S3- / Filesystem-Backend
);

const cachedSnapshotStoreOptions = CachedSnapshotStoreOptions.create()
  .withCache(cache)          // Backing-Cache (typischerweise Redis)
  .withTtlMs(60_000);
const cached = new CachedSnapshotStore(
  underlying,
  cachedSnapshotStoreOptions,        // optionale TTL
);

const actorSystemOptions = ActorSystemOptions.create().withPersistence({
  journal:       myJournal,
  snapshotStore: cached,
});
const system = ActorSystem.create('app', actorSystemOptions);
```

## Wann du ihn brauchst

Drei Muster:

1. **Langsamer zugrunde liegender Store** — Object-Storage mit
   Multi-Hop-Netzwerklatenz, verschlüsselter State mit teurer
   Entschlüsselung.  Für den verschlüsselten Fall lies zuerst
   [Sicherheit — der Cache hält Klartext](#sicherheit--der-cache-hält-klartext):
   das ist der stärkste Grund, zum Cache zu greifen, und der eine,
   der eine Entscheidung braucht.
2. **Häufige Actor-Churn** — gesharde Entities, die ständig
   passivieren / neu spawnen und jeweils denselben Snapshot neu
   lesen.
3. **Recovery-Stürme** — Full-Cluster-Restart, jeder Actor lädt
   seinen Snapshot auf einmal.  Der Cache reduziert redundante
   Loads, wenn derselbe Snapshot während des Sturms abgefragt
   wird.

Für lokale SQLite-gestützte Snapshots (Sub-Millisekunden-Reads)
fügt der Cache Overhead ohne Nutzen hinzu.  **Nutze ihn nur, wenn
der zugrunde liegende Store messbare Read-Latenz hat.**

## Konfiguration

```ts
type CachedSnapshotStoreOptionsType = {
  cache:                 Cache;    // Backing-Cache (erforderlich)
  ttlMs?:                number;   // Cache-TTL in ms, Default 5 Minuten
  keyPrefix?:            string;   // Key-Prefix, Default 'snap:'
  allowPlaintextCache?:  boolean;  // verschlüsselten State trotzdem cachen, Default false
};
```

| Feld | Was |
| --- | --- |
| `cache` | Backing-Cache (**erforderlich**) — in Produktion typischerweise Redis.  Jeder `Cache`: In-Memory, Redis oder Memcached. |
| `ttlMs` | Cache-TTL in Millisekunden.  Default: 5 Minuten. |
| `keyPrefix` | Key-Prefix (Default `'snap:'`) — verhindert Kollisionen in geteilten Caches. |
| `allowPlaintextCache` | Bestätigt, dass der Cache den Klartext von State halten darf, den der eingewickelte Store at rest verschlüsselt — und cacht trotzdem.  Default `false` — siehe unten. |

Der zugrunde liegende Store ist das **erste Argument** des
Konstruktors — `new CachedSnapshotStore(underlying, options)` —
keine Option.

## Sicherheit — der Cache hält Klartext

Gecacht wird, was `loadLatest` zurückgibt, und das ist der
**dekodierte** Domain-State: dekomprimiert und bei den
Object-Storage-Stores entschlüsselt.  Kombinierst du diesen
Decorator mit
[client-seitiger Snapshot-Verschlüsselung](/de/persistence/object-storage/encryption/),
hält das Deployment zwei Kopien des States — eine verschlüsselt im
Bucket, eine im Klartext in einem Cache, der dir gehört, den du mit
anderen Subsystemen teilst und der oft unauthentifiziert in einem
"privaten" Netz läuft.  Die zweite Kopie zu lesen braucht weder den
Bucket noch den Master-Key, und ein Redis-RDB-Dump hält sie danach
weiter lesbar.

Am Bucket selbst wird dadurch nichts schwächer; die zweite Kopie
ist die ganze Exposition.  Das macht es zu einer
Kompositions-Gefahr statt zu einem Fehler in einem der beiden
Teile — und es ist eine Komposition, die genau diese Seite
empfiehlt, weshalb sie hier ausgeschrieben steht.

Ein `loadLatest`, das `encryption` mit einem anderen Modus als
`'none'` trägt, wird deshalb **direkt aus dem eingewickelten Store
bedient, ohne Cache**, und der Decorator warnt einmal:

```text
persistence: CachedSnapshotStore caches decoded snapshot state, and this
loadLatest on 'ObjectStorageSnapshotStore' asked for encryption — …
```

`withAllowPlaintextCache(true)` ist deine Bestätigung, dass der
Cache so geschützt ist wie der Bucket, und stellt das Caching
wieder her:

```ts
const cachedSnapshotStoreOptions = CachedSnapshotStoreOptions.create()
  .withCache(cache)
  .withTtlMs(60_000)
  .withAllowPlaintextCache(true);
```

Vernünftige Antworten auf die Frage, die das Flag stellt:

- **In-Process-`InMemoryCache`** — der Klartext verlässt den Knoten
  nicht, der ohnehin entschlüsselt hat.  Setze das Flag.
- **Redis oder Memcached innerhalb derselben Vertrauensgrenze**,
  mit Authentifizierung, Transportverschlüsselung und ohne
  Persistenz auf Platte — setze das Flag und halte die Begründung
  dort fest, wo deine übrigen Key-Management-Entscheidungen leben.
- **Ein geteilter Cache, der auch HTTP-Middleware trägt**, oder
  einer, dessen Betreiber nicht die Betreiber des Buckets sind —
  setze das Flag nicht.  Gib dem verschlüsselten Store einen
  eigenen Cache oder nimm die Cold-Start-Kosten in Kauf.

Der Check sieht die **Per-Call-`PersistenceOptions`**, die der
`encryption()`-Hook deines Actors erzeugt und die jeden Read
erreichen.  Er sieht *nicht* einen Store, der bei der Konstruktion
mit Verschlüsselung konfiguriert wurde und davon pro Call nie
erfährt: `SnapshotStore` hat kein Member, das das melden würde, und
`persistenceOptionSupport` beantwortet eine andere Frage ("könnte
dieser Store verschlüsseln?", nicht "wird er es tun?").  Lebt deine
Verschlüsselung vollständig in der Store-eigenen Konfiguration, hat
dieser Decorator nichts zu warnen und die Entscheidung liegt allein
bei dir.

## Cache-Semantik

- **`loadLatest(persistenceId)`** — Read-Through mit TTL.  Cache prüfen; bei
  Treffer zurückgeben.  Bei Miss aus dem zugrunde liegenden Store laden, das
  Ergebnis mit `ttlMs` cachen, zurückgeben.
- **`save(persistenceId, seq, state)`** — Write-Through-with-Invalidate: an den
  zugrunde liegenden Store delegieren, dann den Cache-Eintrag **löschen**.  Es
  schreibt den neuen Snapshot bewusst *nicht* zurück — im Cluster können zwei
  Knoten beim Save konkurrieren, und ein lokaler Write würde einen veralteten
  Eintrag hinterlassen.  Der nächste Read füllt neu.
- **`loadBefore(persistenceId, seq)`** — **nicht gecacht** (zu viele mögliche
  `seq`-Werte, und selten genutzt — nur bei Recovery).
- **`delete(persistenceId, toSeq)`** — an den zugrunde liegenden Store
  delegieren, dann den Cache-Eintrag invalidieren.

Nach einem `save` ist der Cache-Eintrag invalidiert, sodass der
nächste `loadLatest` aus dem zugrunde liegenden Store neu holt und
den gerade gespeicherten Snapshot zurückgibt.  Die TTL ist das
Sicherheitsnetz: selbst wenn ein Knoten zwischen dem
zugrunde-liegenden Write und der Cache-Invalidierung abstürzt,
läuft der veraltete Eintrag innerhalb von `ttlMs` ab.

## Performance

Für einen langsamen zugrunde liegenden Store (etwa 50 ms pro Load)
macht der Cache nachfolgende Loads desselben Snapshots zu
Sub-Mikrosekunden-Operationen.  Ein typischer
Sharded-Entity-Workload sieht nach dem Aufwärmen 80–95 % Trefferquote.

Der Cache kann **über Knoten geteilt** werden — stütze ihn auf
Redis oder Memcached, und jeder Knoten liest aus demselben Cache,
sodass ein auf einem Knoten geladener Snapshot auf allen anderen
ein Treffer ist.  Stütze ihn stattdessen auf einen In-Memory-Cache,
behält jeder Knoten seine eigene Kopie; Misses auf einem frischen
Knoten zahlen die vollen Load-Kosten.

## Fallstricke

import { Aside } from '@astrojs/starlight/components';

<Aside type="caution" title="Externe Modifikationen">
  ```ts
  // Zugrunde liegender Store außerhalb des Caches geändert (manuelles
  // SQL-Update, Batch-Backfill) → Cache liefert veraltete Daten
  ```
  Der Cache nimmt an, **er ist der einzige Writer**.  Schreibt
  etwas anderes in den zugrunde liegenden Store, setze eine TTL
  oder invalidiere manuell.
</Aside>
