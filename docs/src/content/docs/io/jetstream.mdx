`JetStreamActor` integrates with **NATS JetStream** — the durable
streaming layer on top of core NATS.  Where [`NatsActor`](/io/nats/)
is fire-and-forget pub/sub, `JetStreamActor` gives you **persistent
streams, replay, and explicit acknowledgment** with Kafka-style
"exactly-once-with-processing" semantics via the
`acknowledgment` / `negativeAcknowledgment` / `terminate` handshake.

```ts
import { ActorSystem, Actor } from 'actor-ts';
import { JetStreamActor, JetStreamOptions } from 'actor-ts/io';
import type { ActorRef } from 'actor-ts';
import type { JetStreamMessage, JetStreamCommand } from 'actor-ts/io';

const jetStreamOptions = JetStreamOptions.create()
  .withServers(['nats://localhost:4222'])
  .withStream({ name: 'ORDERS', subjects: ['orders.>'] })
  .withConsumer({ durable: 'order-processor', ackWaitMs: 30_000 })
  .withTarget(orderProcessor);
const jetStream = system.spawn(
  () => new JetStreamActor(
    jetStreamOptions,
  ),
  'orders-stream',
);

// Publish (idempotent when messageId is set):
jetStream.tell({
  kind: 'publish',
  publish: {
    subject:   'orders.created',
    payload:   JSON.stringify(order),
    messageId: order.id,          // server dedupes within the stream's dedup window
  },
});
```

The consumer forwards every message to `target` and waits for an
explicit ack **before the ack-window (`ackWaitMs`) expires** — if none
arrives, the server redelivers:

```ts
class OrderProcessor extends Actor<JetStreamMessage> {
  constructor(private readonly jetStream: ActorRef<JetStreamCommand>) { super(); }

  async onReceive(message: JetStreamMessage): Promise<void> {
    try {
      await db.insertOrder(JSON.parse(new TextDecoder().decode(message.payload)));
      this.jetStream.tell({ kind: 'acknowledgment', ackToken: message.ackToken });
    } catch {
      // redeliver after 5 s
      this.jetStream.tell({
        kind:     'negativeAcknowledgment',
        ackToken: message.ackToken,
        delayMs:  5_000,
      });
    }
  }
}
```

## Settings

```ts
interface JetStreamOptionsType extends BrokerCommonOptionsType {
  servers?:  string[] | string;       // NATS server URLs
  token?:    string;
  user?:     string;
  password?: string;
  name?:     string;                  // client identifier
  tls?:      TlsTransportOptionsType; // cert material; also enables TLS; code-only
  stream?:   JetStreamStreamConfig;   // set when this actor owns the stream
  consumer?: JetStreamConsumerConfig; // required to start a subscription
  target?:   ActorRef<JetStreamMessage>; // receives every consumed message
  acknowledgmentTimeout?: number;     // ack-wait ceiling; default consumer.ackWaitMs ?? 30_000
}
```

The builder is the primary style; a plain object works too.  Common
broker fields — `withReconnect`, `withCircuitBreaker`,
`withOutboundBuffer` — come from the shared
[BrokerActor base](/io/broker-actor-base/).  `servers` is required.

`tls` carries the certificate **material** — a private CA to trust,
or a client certificate for mTLS — never a path to it.  NATS has no
`tls://` URL scheme, so setting it is also what asks nats.js to
negotiate TLS.  It is identical to
[`NatsOptions.withTls`](/io/nats/#tls), and like it has no config key:
a private key does not belong in `application.conf`.

### Stream config

Set `stream` when the actor should **create or update** the stream at
connect time (`create` defaults to `true`).

| Field | Meaning |
| --- | --- |
| `name` | Stream name (required). |
| `subjects` | Subjects captured by the stream, e.g. `['orders.>']` (required). |
| `retention` | `'limits'` *(default)*, `'interest'`, or `'workqueue'`. |
| `storage` | `'file'` (durable) or `'memory'`. |
| `maxMessages` / `maxBytes` | Retention caps. |
| `maxAge` | Max age in **nanoseconds** (passed through verbatim). |
| `create` | Create/update the stream at connect time.  Default `true`. |

### Consumer config

Set `consumer` to bind a durable subscription.

| Field | Meaning |
| --- | --- |
| `durable` | Durable consumer name (required — survives restarts). |
| `mode` | `'push'` *(default)* or `'pull'` (see below). |
| `deliverPolicy` | `'all'` *(default)*, `'last'`, `'new'`, `{ kind: 'byStartSeq', startSeq }`, or `{ kind: 'byStartTime', startTimeMs }`. |
| `ackPolicy` | `'explicit'` *(default — ack/nak/term required)*, `'none'`, or `'all'`. |
| `ackWaitMs` | Time before the server redelivers without an ack.  Default `30_000`. |
| `filterSubject` | Subject filter — defaults to all subjects in the stream. |
| `maxAcknowledgmentPending` | Max in-flight unacked messages.  Default `1024`. |
| `create` | Create/update the consumer at connect time.  Default `true`. |

### Both groups, from HOCON

Which stream an actor owns and which durable it binds is deployment shape, not
application logic, so both groups are readable under
`actor-ts.io.broker.jetstream` — as is the ack-wait ceiling:

```hocon
actor-ts.io.broker.jetstream {
  acknowledgment-timeout = 45s

  stream {
    name         = "BILLING"
    subjects     = ["billing.>"]
    retention    = "workqueue"
    storage      = "file"
    max-messages = 1000000
    max-bytes    = 8M
    max-age      = 3600000000000   # NANOseconds, passed through verbatim
    create       = true
  }

  consumer {
    durable                   = "billing-proc"
    mode                      = "push"
    deliver-policy            = "all"
    ack-policy                = "explicit"
    ack-wait                  = 30s
    filter-subject            = "billing.charges"
    max-acknowledgment-pending = 1024
    create                    = true
  }
}
```

`deliver-policy` also takes its two parameterised forms, as an object.  The
`kind` keeps its TypeScript spelling because it is a *value* that lands in the
union unchanged; only the leaf names around it are kebab-case:

```hocon
consumer {
  durable        = "billing-proc"
  deliver-policy { kind = "byStartSeq", start-seq = 4242 }
  # or:          { kind = "byStartTime", start-time = 1767225600000 }  # epoch ms
}
```

An unrecognised `kind` is refused at startup rather than quietly falling back
to `all`, which would replay a whole stream on a typo.

Both groups are read **whole**: `withStream({ … })` / `withConsumer({ … })` in
code replace the configured block rather than merging into it, which is the
ordinary precedence (constructor > HOCON > defaults) applied at the field each
object *is*.  `name` + `subjects` and `durable` are required, and a block
missing one is refused at start, naming the leaf.

`target` has no config key — an `ActorRef` names a live actor in this process,
which a config file cannot denote.  Neither has `tls`, which carries the
certificate material itself.

## Commands

`JetStreamActor` accepts a `JetStreamCommand` (discriminated on `kind`):

| `kind` | Fields | Purpose |
| --- | --- | --- |
| `publish` | `publish: JetStreamPublish` | Publish a message (see [idempotent publish](#idempotent-publish)). |
| `acknowledgment` | `ackToken` | Ack a delivered message — the server marks it consumed. |
| `negativeAcknowledgment` | `ackToken`, `delayMs?` | Redeliver (optionally after `delayMs`). |
| `terminate` | `ackToken`, `reason?` | Terminal failure — server drops the message permanently. |
| `inProgress` | `ackToken` | Heartbeat — extend the ack-wait window for a long handler. |
| `fetch` | `batch`, `expiresMs?` | **Pull mode only** — request up to `batch` messages. |

Every inbound `JetStreamMessage` carries `subject`, `payload`
(`Uint8Array`), `replyTo`, `streamSeq`, `consumerSeq`, `deliveries`
(delivery count — `1` on first try), `ackToken`, `timestamp`, and
`headers`.

## The ack handshake

With the default `ackPolicy: 'explicit'`, every delivered message must
be resolved with exactly one of `acknowledgment`, `negativeAcknowledgment`,
or `terminate`, keyed by `ackToken`:

- **`acknowledgment`** — processing succeeded; the server advances the consumer.
- **`negativeAcknowledgment`** — retry; the server redelivers (after `delayMs` if given).
- **`terminate`** — give up permanently; the server will not redeliver.
- **`inProgress`** — not terminal; resets the ack-wait timer so a slow handler isn't redelivered mid-flight.

`ackToken` is an opaque number the actor mints per **delivery** and hands
you on the message.  It is deliberately not `streamSeq`: a stream sequence
identifies the *message*, and JetStream reuses it verbatim on every
redelivery (only `consumerSeq` and `deliveries` move).  Two deliveries of
one message can be in flight at once — routinely so in pull mode, where
fetch batches overlap — and only `ackToken` tells them apart.  Never send
it back to the broker or persist it: it means nothing outside the actor
instance that issued it, and it does not survive a reconnect.

Set `ackPolicy: 'none'` for pure fire-and-hose delivery where no ack is
expected.

## Push vs pull consumers

- **Push** *(default)* — the server streams messages; the actor's
  internal pump fans each one to `target` and waits per-message for the
  ack handshake.  The natural fit for actor-style fan-out.
- **Pull** (`mode: 'pull'`) — the application self-paces by sending
  `{ kind: 'fetch', batch, expiresMs }`.  Each fetch delivers up to
  `batch` messages (returning early after `expiresMs`, default `5_000`);
  every message still goes through the same ack handshake.  Fits
  slow/bursty consumers better than push fan-out.

**Fetches overlap, by design.** A `fetch` command returns the mailbox turn
immediately, so a second `fetch` is served while the first batch's acks are
still outstanding — it has to be, because those acks arrive as mailbox
messages and a `fetch` that held its turn open would deadlock on them.
Pipelining fetches is therefore supported, and it is why a delivery is
addressed by `ackToken` rather than by `streamSeq`.

## Idempotent publish

`JetStreamPublish` supports JetStream's server-side dedup and
optimistic concurrency:

```ts
jetStream.tell({
  kind: 'publish',
  publish: {
    subject:         'orders.created',
    payload:         JSON.stringify(order),
    messageId:       order.id,   // sent as Nats-Msg-Id — dedupes re-publishes in the stream's window
    expectedLastSeq: lastSeq,    // server rejects the publish if the stream head moved (optimistic concurrency)
  },
});
```

import { Aside } from '@astrojs/starlight/components';

<Aside type="caution" title="A handler slower than ackWaitMs gets the message twice">
  If a handler routinely takes longer than `ackWaitMs`, the server
  redelivers **while the first delivery is still being processed** — so the
  work runs twice and two deliveries of one message are in flight at once.
  That is a correctness matter, not a tuning preference: your handler must
  be idempotent, and it must settle each delivery by that delivery's own
  `ackToken`.  To stop the overlap happening, send
  `{ kind: 'inProgress', ackToken }` to extend the window for a handler
  that is still working, or raise `ackWaitMs`.
</Aside>

<Aside type="caution" title="`fetch` is pull-mode only">
  Sending a `fetch` command to a **push**-mode consumer is a no-op
  (logged as a warning).  Use `mode: 'pull'` on the consumer config to
  drive delivery with `fetch`.
</Aside>

<Aside type="caution" title="Create-or-update only — no deletion">
  The actor only ever **creates or updates** streams and consumers at
  connect time; it never deletes them.  Destroying a stream is an
  operator concern, not a runtime one.
</Aside>

<Aside type="caution" title="KV and Object Store are separate actors">
  JetStream's Key-Value and Object-Store sub-APIs have different
  semantics, so they are separate actors —
  [`JetStreamKeyValueActor` / `JetStreamObjectStoreActor`](/io/jetstream-kv/).
  This actor is stream publish/consume only.
</Aside>
