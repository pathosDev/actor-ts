---
title: Sets (GSet, ORSet)
description: Two set CRDTs — `GSet` for add-only sets, `ORSet` for add-and-remove with "add wins" semantics. Concurrent add+remove resolves to the add observed on the same replica.
---

Two set CRDTs:

| Type | Operations | When |
| --- | --- | --- |
| **`GSet<E>`** | add only | Append-only collections — observed kinds, seen users. |
| **`ORSet<E>`** | add + remove | Membership sets that come and go. |

Both converge under concurrent writes; `ORSet`'s special trick is
resolving "concurrent add and remove of the same element" so
removes don't accidentally delete a still-wanted item.

## GSet

```ts
import { GSet } from 'actor-ts/crdt';

let s = GSet.empty<string>();
s = s.add('apple');
s = s.add('banana');
s.value();   // → ['apple', 'banana']
```

State is a plain set; merge is a union.  Cannot remove — once
added, an element stays forever.

Use for:

- **Observed event types** the system has ever seen.
- **Users that ever logged in** (a `unique-users-ever` set).
- **Tags applied** to a resource that don't get untagged.

If you need removals, `GSet` is the wrong shape; reach for
`ORSet`.

### Element identity

```ts
let s = GSet.empty<UserSession>({ identity: (u) => u.id });
s = s.add({ id: 'user-42', name: 'Alice' });
s = s.add({ id: 'user-42', name: 'Alice updated' });
s.value().length;   // → 1 (same identity)
```

By default elements are deduplicated by `JSON.stringify(element)`.
Pass an `identity: (e) => string` function for custom dedup —
useful when elements are objects with stable IDs but mutable
other fields.

## ORSet (Observed-Remove Set)

```ts
import { ORSet } from 'actor-ts/crdt';

let s = ORSet.empty<string>();
s = s.add('node-a', 'apple');
s = s.add('node-b', 'banana');
s = s.remove('apple');
s.value();   // → ['banana']
```

The trick: every `add` stamps the element with a **unique tag**;
`remove(e)` removes only the tags currently visible to the
removing replica.

This makes the "concurrent add + remove" case resolve **toward
add**:

```ts
let a0 = ORSet.empty<string>().add('a', 'apple');
let b0 = a0;                              // both see 'apple' with same tag

let a1 = a0.remove('apple');               // A removes
let b1 = b0.add('b', 'apple');             // B adds a NEW 'apple' (new tag)

a1.merge(b1).value();   // → ['apple']   — B's add survives
```

The original 'apple' had the tag B never saw, so B's fresh add
introduces a new tag.  When A and B merge, A's remove only
removed the *original* tag; B's tag remains.  Net result: 'apple'
is in the set.

This "add wins" semantics is what makes ORSet the right choice
for **shopping carts, presence sets, subscription lists** — sets
where an item briefly removed by one party shouldn't disappear if
another party concurrently re-added it.

### Tag generation

Tags are `replicaId × 96 random bits`, drawn from the platform's
cryptographic random source.  That makes them unique even within
the same millisecond, across the cluster — and, unlike the
per-replica counter they replaced, impossible to compute ahead of
being issued.

That second property is a correctness matter, not just a
hardening one.  Tombstones veto by tag on merge and are never
pruned, so a peer able to *predict* a replica's next tags could
tombstone them in advance and make that replica's next writes
disappear on the following merge — silently, and with no API to
take a tombstone back.

You don't see or manipulate tags directly; they're internal.

### Element identity (same as GSet)

```ts
const s = ORSet.empty<CartItem>({ identity: (i) => i.sku });
s.add('node-a', { sku: 'book-1', price: 10 });
s.add('node-b', { sku: 'book-1', price: 12 });
// → still one entry (same SKU), but two tags
//   — the tags are independent of the value's identity
```

The identity function determines **deduplication**; the tag
mechanics work per-add regardless.

#### Identity inside DistributedData

An identity function is a closure, so it never travels on the
wire.  A replica that materialises a key from a peer's gossip,
from a quorum reply or from its durable record therefore has to
be *told* which one to use — and the only place that knowledge
lives is the `factory` you already hand to `update`:

```ts
const emptyCart = () => ORSet.empty<CartItem>({ identity: (i) => i.sku });
dd.update('cart-42', emptyCart, (c) => c.add(dd.selfReplicaId(), item));
```

Pass the same factory on every `update` for a key, and the
replica files every value it decodes for that key under your
identity — entries a peer wrote under the default one included.
Those are re-keyed and merged into the entry they belong with,
rather than kept alongside it as duplicates.

Two limits are worth knowing (#766):

- **The first `update` for a key is what teaches it.**  A key
  that arrived by gossip, or came back from a `durableStore`
  after a restart, stays on the default identity until then — so
  a bare `dd.get('cart-42')` immediately after startup can hand
  you a set that deduplicates by `JSON.stringify`.  Issue the
  `update` first if that matters.
- **Nesting stops at one level.**  An `ORMap` recovers its own
  key identity, but the CRDTs stored *inside* it do not: neither
  the frame nor an empty template says what theirs should be.

Note also that your identity function now runs over values a
peer sent, not only over ones your process built.  A callback
that assumes its argument's shape will see data it did not
produce; one that throws turns that frame into a dropped value
rather than an accepted one.

## Picking between them

| Question | Type |
| --- | --- |
| Do you ever need to remove elements? | `ORSet` |
| Otherwise | `GSet` |

`GSet` is **smaller** (no tag bookkeeping) and **simpler**.  Use
when "remove an item" isn't part of the workflow.

`ORSet`'s extra cost is the tag tracking — for sets with high
churn (frequent add/remove cycles on the same element), the
internal state grows.  See "When ORSet isn't right" below.

## When ORSet isn't right

import { Aside } from '@astrojs/starlight/components';

<Aside type="caution" title="Very high add/remove churn">
  ```ts
  // 100 000 add+remove cycles per second on the same element
  ```
  Each `add` adds a tag; each `remove` removes the tags currently
  visible.  But tags from concurrent (or stale) adds may linger.
  Over time, the tag set can grow even when the visible set is
  small.  For high-churn workloads, periodic state refresh /
  consolidation (a "snapshot" via direct DD update with a fresh
  empty ORSet) can help.
</Aside>

<Aside type="caution" title="Removing without a stable replica ID">
  ```ts
  s.remove('apple');   // doesn't need a replica ID
  ```
  Note: only `add` takes a replica ID (for tag generation).
  `remove` is replica-agnostic — it removes whatever tags this
  replica currently sees.  This is by design.
</Aside>

<Aside type="caution" title="Don't use plain Set for shared state">
  ```ts
  // ✗ this loses information under concurrent edits
  dd.update('cart', () => new Set(), (s) => { s.add('item'); return s; });
  ```
  A plain `Set` isn't a CRDT — its merge semantics don't preserve
  concurrent updates correctly.  Wrap with `ORSet` (or `GSet`)
  so the framework's replication knows how to merge.
</Aside>
