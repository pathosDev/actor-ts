title: ManualScheduler
description: A virtual-clock `Scheduler` that fires timers only when you call `advance(ms)`. The standard tool for deterministic tests of actors that use `context.timers` or `system.scheduler`.
---

import { Aside } from '@astrojs/starlight/components';

`ManualScheduler` is a `Scheduler` implementation where **time
doesn't advance on its own**.  Schedule a 5-second timer; nothing
fires until you explicitly call `scheduler.advance(5_000)`.  The
test runs in deterministic virtual time, with no real-clock
dependencies — no flakey "sleep for long enough" patterns.

```ts
import { TestKit } from 'actor-ts/testkit';

const { kit, scheduler } = TestKit.withManualScheduler();
const probe = kit.createTestProbe();

const ref = kit.system.spawnAnonymous(() => new Heartbeat(probe));
ref.tell({ kind: 'start' });

scheduler.advance(5_000);   // virtual time jumps 5 seconds
await probe.expectMessage('tick');

await kit.shutdown();
```

`Heartbeat` schedules a tick via
`context.timers.startSingleTimer('tick', tickMessage, 5_000)`.  Real
time never elapses; the `advance(5_000)` fires the timer.

## Why it matters

```ts
// Without ManualScheduler:
ref.tell({ kind: 'start' });
await new Promise(r => setTimeout(r, 5_100));   // hope real time elapsed
await probe.expectMessage('tick');
```

That works *most* of the time.  Then CI runs slower; the test
sleeps for 5.1 s but the scheduler fires at 5.0 s vs the
`expectMessage` checking at 5.1 s — flakey.  Or your local machine is
fast; the test waits 5.1 s every time even though the timer
fires at 5.0 s — slow.

Widening the tolerance doesn't rescue it either, because timers
also fire **early**.  Platform timer quanta are coarse — Windows'
default is 15.625 ms — and an event loop that checks deadlines on
the tick boundary can consider a timer due before its nominal
delay has passed: a 30 ms `setTimeout` measured as low as 18.7 ms
on Bun/Windows, and as high as 201 ms under CPU load.  One nominal
delay, an order of magnitude of spread. No wall-clock bound is
both tight enough to mean something and loose enough to hold, and
a more precise clock doesn't help — the timer is early, not the
measurement.

`ManualScheduler` removes the dependency on real time.  Tests are
fast (no waits) and deterministic (advance fires timers in order).

## The API

```ts
class ManualScheduler extends Scheduler {
  now(): number;                                  // current virtual time (ms)
  advance(durationMs: number): void;              // jump forward, fire matured timers
  advanceToNext(): void;                          // jump to the next pending timer's fire time
  pendingCount: number;                           // non-cancelled scheduled tasks
}
```

Inherited from `Scheduler`:

```ts
scheduleOnce(delayMs, target, message, sender?): Cancellable
scheduleOnceFunction(delayMs, task): Cancellable
scheduleAtFixedRate(initialDelay, interval, target, message, sender?): Cancellable
scheduleAtFixedRateFunction(initialDelay, interval, task): Cancellable
```

Real-time `setTimeout` is **not** used.  Every schedule is a
virtual-time task that only fires via `advance`.

## Using it via TestKit

```ts
const { kit, scheduler } = TestKit.withManualScheduler('my-spec');
```

Two values:

- `kit` — a normal `TestKit` whose `system` has the manual
  scheduler wired in.
- `scheduler` — the manual scheduler.  Call `advance` on this to
  fire timers.

When the actor under test uses `context.timers.startSingleTimer`
or `system.scheduler.scheduleOnce`, the framework routes through
the system's scheduler — which here is the manual one.  Virtual
time controls *all* actor timers.

## Using it without TestKit

```ts
import { ActorSystem, ActorSystemOptions } from 'actor-ts';
import { ManualScheduler } from 'actor-ts/testkit';

const scheduler = new ManualScheduler();
const actorSystemOptions = ActorSystemOptions.create().withScheduler(scheduler);
const system = ActorSystem.create('my-spec', actorSystemOptions);

// ... test code ...

await system.terminate();
```

Same idea — pass the manual scheduler to `ActorSystem.create` via
the settings.

## Advancing time

```ts
scheduler.advance(1_000);   // jump 1 second, fire timers maturing in that window
scheduler.advanceToNext();  // jump straight to the next pending timer and fire it
scheduler.now();            // → current virtual time
```

`advance(ms)` is the common case.  Tasks scheduled to fire in the
advanced window run **in order**, sequentially, before `advance`
returns.

`advanceToNext()` fast-forwards straight to the fire time of the
next pending timer (and fires it), skipping any idle gap — handy
when you don't want to compute the exact delay by hand.  It is a
no-op when nothing is scheduled.

### Repeating timers

```ts
ref.tell({ kind: 'start-heartbeat' });   // schedules every 1s
scheduler.advance(3_500);
// → fires at virtual 1000, 2000, 3000 (three times)
```

A `scheduleAtFixedRate` task fires every interval as virtual
time crosses each multiple.  `advance(3500)` from `t=0` fires the
task three times.

### Order matters

Inside one `advance`, tasks fire in their *scheduled* order
(earliest first; ties broken by insertion order).  After firing a
task, if it schedules further tasks (e.g., a heartbeat
re-arms), those are added to the queue and fire when their
schedule time falls within the same `advance` window.

## A practical test pattern

```ts
import { describe, it, beforeEach, afterEach } from 'bun:test';
import { TestKit, type ManualScheduler } from 'actor-ts/testkit';

describe('Session expiry', () => {
  let kit: TestKit;
  let scheduler: ManualScheduler;
  let probe: TestProbe;

  beforeEach(() => {
    const setup = TestKit.withManualScheduler();
    kit = setup.kit;
    scheduler = setup.scheduler;
    probe = kit.createTestProbe();
  });

  afterEach(async () => { await kit.shutdown(); });

  it('expires after 15 minutes of inactivity', async () => {
    const session = kit.system.spawnAnonymous(() =>
      new Session(probe, 'user-42'));

    session.tell({ kind: 'activity' });   // resets the timer
    await kit.settle();                   // ← the actor has now armed it
    await kit.advance(14 * 60_000);
    await probe.expectNoMessage(0);       // not yet expired

    await kit.advance(60_000 + 1);        // crosses 15 min
    await probe.expectMessage({ kind: 'session-expired', userId: 'user-42' });
  });
});
```

The test runs in **microseconds of wall-clock time** but exercises
a 15-minute idle timeout precisely.

The `settle` on the third line is not decoration, and this sample was wrong
without it (#1025).  `tell` only queues: when `advance` ran on the next line the
actor had not yet *handled* `activity`, so the 15-minute timer it arms on
receiving one did not exist, and the clock swept past a timer nobody had set.
`settle` lets the armed turns run, so by the time time moves the timer is there.

`kit.advance(ms)` is `advance` and `settle` in that order, which is why the two
lines after it need nothing further.

## Why `advance` is not the whole story

```ts
ref.tell({ kind: 'start' });
await kit.settle();            // 'start' has been handled
await kit.advance(5_000);      // the timer fires AND its tell lands
expect(probe.messageCount).toBe(1);
```

Two stages, and virtual time only controls the first:

1. `advance` fires the timer **synchronously** — it `tell`s the actor.
2. That `tell` is delivered by the dispatcher on a **later turn of the event
   loop**, not immediately.

So `scheduler.advance(5_000)` followed by a synchronous assertion reads an empty
probe every time.  Virtual time makes *when* a timer fires deterministic; it
says nothing about when the effects of firing have landed.

`kit.settle()` is that second half: it lets every armed actor turn run, and
every turn those arm, until the `/user` tree is quiet.  It never sleeps —
nothing is being waited *for*, the work is already armed and only needs the
event loop to reach it — and it throws rather than hanging if the tree never
becomes quiet, which is what an exchange with no end looks like.

`kit.advance(ms)` does both in the right order and is what a timer-driven
assertion should be written around.

<Aside type="note" title="&quot;Just `await` something&quot; is not enough">
  This page used to say the tell is processed "on the next microtask turn,
  which runs when you `await` something".  Both halves are wrong often enough
  to matter.  The default dispatcher is not the microtask queue: it spends a
  microtask *budget* and then yields a macrotask, precisely so two actors
  volleying cannot starve timers and I/O.  So `await Promise.resolve()` may
  yield nothing at all to it.

  `probe.expectMessage(...)` does still work, because it polls on real time
  rather than on a single `await` — which also means a sample built on it is
  passing for a reason that has nothing to do with the code being demonstrated.
  Use `settle`.
</Aside>

## Pitfalls

<Aside type="caution" title="`new Date()` and `Date.now()` aren't virtualized">
  ```ts
  override onReceive(message) {
    const at = Date.now();   // ← real wall clock, NOT virtual time
    this.persist({ kind: 'observed', at });
  }
  ```
  `ManualScheduler` virtualizes the actor system's scheduler but
  **not** `Date.now()` or `new Date()`.  An actor that stamps its own
  timestamps records real wall-clock values under a test that thinks
  it controls time.

  Read the time from the system instead.  `system.clock` **is** the
  scheduler, narrowed to one method, so under a `ManualScheduler` it
  is virtual time:
  ```ts
  override onReceive(message) {
    const at = this.context.system.clock.now();   // ← virtual under a ManualScheduler
    this.persist({ kind: 'observed', at });
  }
  ```
  A component that is not an actor takes the contract instead of the
  whole system, so its dependency says what it needs and a test can
  give it a clock without also granting it the power to arm timers:
  ```ts
  import type { Clock } from 'actor-ts';

  class RetentionWindow {
    constructor(private readonly clock: Clock) {}
    expired(writtenAt: number): boolean { return this.clock.now() - writtenAt > 86_400_000; }
  }
  ```
  Pass `system.clock` in production and a `ManualScheduler` in tests —
  it implements `Clock`, so no adapter is involved.

  **`Clock` is milliseconds since the epoch, and is not promised to be
  monotonic**: the system clock moves, NTP steps included.  A duration
  that must never go backwards still belongs on `performance.now()`,
  which this contract deliberately does not cover.
</Aside>

<Aside type="caution" title="Don't mix real timers with `ManualScheduler`">
  ```ts
  setTimeout(() => probe.tell(...), 100);   // ← real timer, won't advance with scheduler
  ```
  Raw `setTimeout` runs on the real clock; the manual scheduler
  doesn't know about it.  Use the framework's scheduler API
  (`context.timers`, `system.scheduler`) for everything time-based
  in tests.
</Aside>

<Aside type="caution" title="`expectMessage` still has a real-time timeout">
  ```ts
  await probe.expectMessage('tick');   // 3s real timeout by default
  ```
  The probe's `expectMessage` waits on real time for the message to
  arrive — even though the *trigger* (the timer) is virtual.
  This is fine: `advance` fires the timer synchronously, and the
  `tell` is processed in the next microtask turn.  The 3-s
  default is plenty.
</Aside>
