`MultiNodeSpec` runs **N cluster nodes inside one test process**.
Each is a real `ActorSystem`; they communicate via an
in-process transport (no TCP).  Useful for testing cluster
behavior — sharding, singletons, gossip convergence,
failover — without Docker.

```ts
import { MultiNodeSpec, TestProbe } from 'actor-ts/testkit';

// Each role name is one node — and doubles as that node's system name.
const spec = new MultiNodeSpec({ roles: ['a', 'b', 'c'] });
await spec.start();
await spec.awaitMembers('a', 3);   // wait for the cluster to converge

// Reach any node's ActorSystem with systemFor(role):
const node2 = spec.systemFor('b');

// Spawn actors on a specific node and assert with a probe:
const probe = new TestProbe(spec.systemFor('a'));
const remote = node2.spawnAnonymous(Worker);

remote.tell({ kind: 'do', replyTo: probe });
await probe.expectMessage({ kind: 'done' });

await spec.stop();
```

## When to use it

Three primary cases:

1. **Testing cluster behavior** — sharding rebalances, singleton
   failover, gossip convergence — verifying these without
   real network setup.
2. **Reproducing distributed bugs** — easier to isolate when
   the entire cluster runs in one process.
3. **CI-friendly cluster tests** — fast (sub-second), no
   Docker, no ports.

For tests that need **true parallelism** (real OS threads —
concurrent journal writes, scheduler interleaving), use
[ParallelMultiNodeSpec](/testing/parallel-multi-node/).  For real
TCP/TLS or cross-host latency, use an external Docker-Compose
cluster.

## Configuration

```ts
type MultiNodeSpecOptionsType = {
  roles:             ReadonlyArray<string>;   // one node per role; must be unique
  seedRoles?:        ReadonlyArray<string>;   // bootstrap seeds — defaults to [roles[0]]
  addresses?:        Record<string, { host: string; port: number }>;
  failureDetector?:  ClusterOptionsType['failureDetector'];
  gossipIntervalMs?: number;                  // default 100 (vs. 1 s in production)
  awaitTimeoutMs?:   number;                  // default 10_000 — how long await* helpers wait
  logLevel?:         LogLevel;                // defaults to a quiet NoopLogger
  downing?:          (role: string) => DowningProvider | undefined;
  stableAfterMs?:    number;                  // default 100 (vs. 20 s in production)
};
```

| Field | Purpose |
| --- | --- |
| `roles` | Node list — each entry is one node, and the string doubles as its system name.  Must be unique. |
| `seedRoles` | Which roles act as bootstrap seeds.  Defaults to the first role. |
| `addresses` | Per-role host/port overrides.  Auto-allocated if omitted. |
| `failureDetector` | Failure-detector overrides — tests usually tighten these so crashes are detected quickly. |
| `gossipIntervalMs` | Gossip round interval.  Default 100 ms. |
| `awaitTimeoutMs` | Default timeout for the `await*` helpers.  Default 10 s. |
| `logLevel` | Log level — quiet by default. |
| `downing` | Per-role split-brain resolver factory. |
| `stableAfterMs` | How long the view must hold still before `downing` is consulted.  Default 100 ms — the shipped 20 s is twice `awaitTimeoutMs`, so a spec that inherited it would time out before its resolver was asked anything. |

Pass a plain object as shown, or build it fluently with
`MultiNodeSpecOptions.create().withRoles(['a', 'b', 'c'])`.

## Roles, seeds, and addresses

Each entry in `roles` is a **distinct node** — the string is that
node's identity and its `ActorSystem` name, so it must be unique
(the constructor throws on duplicates or an empty list).  By
default the **first** role is the sole bootstrap seed; override
that with `seedRoles`:

```ts
const spec = new MultiNodeSpec({
  roles:     ['seed', 'worker-1', 'worker-2'],
  seedRoles: ['seed'],
});
await spec.start();
```

Ports are auto-allocated on `127.0.0.1`; pin specific ones with
`addresses` when a test needs fixed endpoints:

```ts
const spec = new MultiNodeSpec({
  roles:     ['a', 'b'],
  addresses: { a: { host: '127.0.0.1', port: 2551 } },
});
```

## What's shared

All nodes share:

- **A shared in-process message bus** — they can talk to each
  other.
- **The same gossip protocol** — membership converges.
- **Independent actor systems** — separate dispatchers,
  schedulers, supervisor trees.

This means:

- **Real cluster semantics** — members come up, gossip converges,
  failure detector observes, sharding rebalances.
- **No serialization** — messages between "nodes" pass by
  reference (in-process).  Not a fit for testing
  serialization-dependent behavior.

## Failover testing

Two ways to take a node down: `crash(role)` yanks its transport
out abruptly (peers detect it via the failure detector), and
`leave(role)` performs a graceful cluster exit.

```ts
// Verify singleton failover:
const spec = new MultiNodeSpec({
  roles:           ['a', 'b', 'c'],
  failureDetector: { heartbeatIntervalMs: 50, unreachableAfterMs: 200, downAfterMs: 400 },
});
await spec.start();
await Promise.all([
  spec.awaitMembers('a', 3),
  spec.awaitMembers('b', 3),
  spec.awaitMembers('c', 3),
]);

// ... start the singleton on every node ...

// Identify the current host, then crash it:
const host = spec.clusterFor('a').leader().toNullable();
await spec.crash('a');

// Wait for the survivors to down 'a' and re-converge:
await spec.awaitMembers('b', 2);
await spec.awaitMemberStatus('b', 'a', 'down');

// ... assert the singleton has moved to a survivor ...

await spec.stop();
```

`crash(role)` removes the node abruptly; the others observe the
unreachable status, gossip the change, then trigger downing +
failover.  The `await*` helpers replace fragile `setTimeout`
sleeps — they poll until the condition holds (or throw after
`awaitTimeoutMs`).

## A network that works badly

`partition` and `crash` describe a network that is perfect or severed. Between
them lies every condition a cluster actually runs in: a fifth of the gossip
pushes lost, frames overtaking each other, a peer that is slow rather than
dead. `degrade(roleA, roleB, profile)` is that middle, and `restore(roleA,
roleB)` undoes it.

```ts
const spec = new MultiNodeSpec(MultiNodeSpecOptions.create()
  .withRoles(['a', 'b', 'c'])
  .withScheduler(new ManualScheduler())
  .withFaultSeed(20_231));

await spec.start();

// The cluster forms on a clean network, and the network then gets worse.
spec.degrade('a', 'b', {
  dropProbability:      0.2,   // a fifth of the frames never arrive
  duplicateProbability: 0.1,   // a tenth arrive twice
  reorderWindow:        4,     // up to four frames may overtake each other
  latencyMs:            50,    // measured on the spec's scheduler
});

await spec.advanceUntil(
  () => spec.clusterFor('a').getMembers().filter((m) => m.status === 'up').length === 3,
  { budgetMs: 60_000, description: 'the view converges despite the loss' },
);

spec.restore('a', 'b');
```

Every field is optional and defaults to "no fault", so a profile names only what
it changes. `degrade` is bidirectional like `partition`; for a one-way
degradation reach for `spec.faultsFor(role).degradeTo(address, profile)`.

### The faults are deterministic

Every decision comes from one seeded generator per node, drawn in send order —
and under a shared `ManualScheduler` that order is itself deterministic. So a
run that goes red reproduces exactly, and the spec's timeout messages name the
seed that does it:

```
MultiNodeSpec: timeout after 10000 ms — awaitMembers(a, expected=3) — current: 2
  Faults were injected on: a, b. Reproduce with withFaultSeed(20231).
```

That is not a detail. An unreproducible chaos test is a flake generator, and a
fixed seed is what makes the difference — the trade being that the suite stops
finding *new* networks on its own. Vary the seed deliberately (a loop over
`withFaultSeed`) when the question is "does this hold for many networks" rather
than "does this hold for the network that broke".

### `latencyMs` needs a scheduler

A delay taken from the wall clock would reintroduce exactly the timing
dependence [`ManualScheduler`](/testing/manual-scheduler/) exists to remove, so
it is refused rather than quietly taken: a non-zero `latencyMs` without a
scheduler throws at construction. The other three faults need no clock.

### `reorderWindow` is a depth, not a shuffle

A window of `n` holds up to `n` frames and releases them as one permuted batch,
so a frame is displaced by **fewer than `n` positions**. That bound is the
point: a shuffle could permute a frame to the end of the run and leave a test
waiting for something that is never coming. The last partial batch is released
by `restore`, by `stop`, and by the next batch filling up — continuous gossip
does the last of those on its own.

### It works on any transport

`FaultyTransport` is a decorator, so `InMemoryTransport`, `MultiNodeTransport`
and `MessageChannelTransport` all gain the same controls without any of them
growing fault logic. Outside a spec:

```ts
const link = new FaultyTransport(new InMemoryTransport(address), { dropProbability: 0.2 });
```

## Per-node TestProbe

`MultiNodeSpec` has no probe factory — construct a `TestProbe`
against whichever node's system you want to observe:

```ts
const probeA = new TestProbe(spec.systemFor('a'));   // probe on node 'a'
const probeB = new TestProbe(spec.systemFor('b'));   // probe on node 'b'
```

Each probe is **bound to one node's actor system**.  Useful
when testing routing — verify that a message ends up on the
expected node.

## Sharding tests

Start a sharding region on every node via its `Cluster` — reach
each one with `clusterFor(role)`:

```ts
const spec = new MultiNodeSpec({ roles: ['a', 'b', 'c'] });
await spec.start();
await spec.awaitMembers('a', 3);

const startShardingOptions = StartShardingOptions.create<Command>()
  .withTypeName('entity')
  .withEntityActor(Entity)
  .withExtractEntityId((message) => message.id);
const regions = spec.allRoles().map((role) =>
  spec.clusterFor(role).sharding.start(startShardingOptions)
);

// Spawn entities; verify they spread across nodes:
for (const id of ['e1', 'e2', 'e3', 'e4', 'e5']) {
  regions[0].tell({ id, kind: 'wake-up' });
}

await spec.stop();
```

The framework's coordinator distributes shards across the nodes
just like a real cluster.

## What MultiNodeSpec doesn't test

import { Aside } from '@astrojs/starlight/components';

<Aside type="caution" title="Serialization">
  ```ts
  // Messages pass by reference between nodes in MultiNodeSpec
  ```
  Serialization-dependent bugs (functions in messages,
  non-serializable types) don't surface in MultiNodeSpec —
  and ParallelMultiNodeSpec only half-closes the gap, since
  structured clone accepts payloads the wire refuses.  For
  real coverage, round-trip the message through
  `JsonSerializer` in a unit test, or run a real-cluster
  integration test.
</Aside>

<Aside type="caution" title="Real network failure modes">
  ```ts
  // Packet loss, TCP keepalive, congestion — none apply here
  ```
  In-memory transport is reliable.  For network-fault tests,
  use Toxiproxy + real Docker setups.
</Aside>

<Aside type="caution" title="No thread isolation">
  ```ts
  // One crashed node in MultiNodeSpec → crashes the test
  ```
  All "nodes" share the test process's event loop + memory.
  A genuine OOM on one node OOMs the test.  Use
  [ParallelMultiNodeSpec](/testing/parallel-multi-node/), which
  runs each node in its own worker thread, when you need that
  isolation.
</Aside>
