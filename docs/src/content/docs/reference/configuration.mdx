description: Every HOCON key the framework reads, grouped by module — defaults, overrides, environment substitution. Plus the resolution order between code, config file, and built-in reference.
---

actor-ts uses **HOCON** for configuration — a superset of JSON
common in JVM config files, with substitutions, durations and
sizes.  ([`include` directives are refused](#includes-are-not-supported)
— compose the sources in code.)  Three layers, resolved highest-first:

1. **Constructor arguments** to `ActorSystem.create(name, settings)`
   — explicit code overrides.
2. **User config** — `application.conf` at the project root, or an
   explicit path via `configFile`, or an inline `config` object in
   the settings.
3. **Reference defaults** — bundled in the framework as
   `REFERENCE_CONF` (see `src/config/reference.ts`).

Anything not specified in layers 1 or 2 falls through to the
reference default.

This page explains what each key *does*.  For the exhaustive list —
every setting the framework ships, verbatim from the bundled file — see
[The full reference.conf](/reference/reference-conf/).

## A complete `application.conf`

```hocon
actor-ts {
  system { name = "my-app" }
  logger { level = "info" }

  dispatcher {
    default    = "immediate"   # immediate | microtask | throughput
    throughput = 16
  }

  cluster {
    gossip-interval     = 1s
    seed-retry-interval = 3s
    weakly-up-after     = 0s      # 0 = opt-in only
    max-members         = 1000
    max-tombstones      = 10000
    tombstone {
      time-to-live   = 24h
      prune-interval = 5m
      min-retention  = 0s         # 0 = derive from down-after
    }
    failure-detector {
      implementation     = simple   # simple | phi
      heartbeat-interval = 500ms    # shared by both implementations
      unreachable-after  = 2s
      down-after         = 5s
      phi {
        unreachable-threshold      = 8
        down-threshold             = 12
        max-sample-size            = 200
        min-std-deviation          = 100ms
        acceptable-heartbeat-pause = 0s
      }
    }
    pub-sub {
      gossip-interval            = 1s
      max-subscribers-per-topic  = 10000
      max-topics                 = 10000
      max-remote-nodes-per-topic = 1000
      send-to-dead-letters-when-no-subscribers = on
    }
    receptionist {
      gossip-interval         = 1s
      max-subscribers-per-key = 1000
      max-subscriptions-total   = 10000
    }
  }

  distributed-data {
    gossip-interval             = 1s
    max-pending-quorum-requests = 1000    # 0 = no cap
    max-quorum-timeout          = 30s     # 0 = no ceiling
    max-gossip-bytes            = 1M      # per gossip frame; 0 = no budget
  }

  remote {
    tcp {
      host = "0.0.0.0"
      port = ${?ACTOR_TS_PORT}   # env-var substitution; falls back to default
    }
    max-frame-bytes = 16M
  }

  persistence {
    journal        { plugin = "actor-ts.persistence.journal.in-memory"        }
    snapshot-store { plugin = "actor-ts.persistence.snapshot-store.in-memory" }
  }

  sharding {
    number-of-shards           = 64
    role                       = ""       # "" = unrestricted; names a role, never grants one
    rebalance-interval         = 2s
    hand-off-timeout           = 10s
    acquire-retry-interval     = 5s       # retry a failed coordinator lease acquire
    remember-entities          = false
    passivation-idle           = 5m       # 0 disables auto-passivation
    # shard-passivation-idle              # unset: follows passivation-idle
    max-entities               = 0        # 0 = no per-node cap
    buffer-size                = 100000   # region-wide; 0 = never buffer
    register-retry-interval    = 500ms
    shard-region-query-timeout = 5s
    entity-recovery {                     # how remembered entities come back
      strategy = all                      # all | constant-rate
      constant-rate.frequency = 100ms
      constant-rate.number-of-entities = 5   # region-wide, not per shard
    }
  }
}
```

Place this at the project root.  The framework auto-loads it on
`ActorSystem.create`.

## The keys, grouped by module

### `actor-ts.system`

| Key | Default | Purpose |
| --- | --- | --- |
| `system.name` | `"default"` | System name — used in actor paths and cluster identification.  Applies when `ActorSystem.create()` is called without a name; an explicit `create('billing')` wins. |
| `system.shutdown-drain-timeout` | `2s` | How long `terminate()` lets the actors under `/user` finish queued work before the stop cascade starts.  Returns as soon as the tree is quiet, so an idle system pays a tick.  Keep it under `coordinated-shutdown.default-phase-timeout`; `0` disables draining. |

### `actor-ts.logger`

| Key | Default | Purpose |
| --- | --- | --- |
| `logger.level` | `"info"` | One of `debug` / `info` / `warn` / `error` / `off`. |

### `actor-ts.actor`

| Key | Default | Purpose |
| --- | --- | --- |
| `actor.throughput` | `16` | User messages **one** actor handles per dispatcher turn before yielding.  Override per actor with `ActorOptions.withThroughput()`. |

### `actor-ts.diagnostics`

| Key | Default | Purpose |
| --- | --- | --- |
| `diagnostics.log-dead-letters` | `10` | Dead letters logged in full before logging suspends.  `0` turns dead-letter logging off entirely.  Every letter is captured and published on the event stream either way — this gates the log line and nothing else. |
| `diagnostics.log-dead-letters-during-shutdown` | `off` | Log the burst `terminate()` produces while it drains mailboxes to dead letters.  Off because an orderly shutdown drains every queued and stashed message that way; an individual `ref.stop()` still logs, because the system is not terminating. |
| `diagnostics.log-dead-letters-suspend-duration` | `5m` | How long logging stays suspended once the count above is reached.  `0` never suspends, which is how “log every dead letter” is spelled. |

The record names the recipient path, the sender when there is one, and the
message's class — never the payload, for the same data-protection reason
`dead-letters.store` defaults to `off`.  Every key here is also settable in
code, field by field, through `ActorSystemOptions.withDiagnostics(…)`.  See
[Dead letters](/operations/dead-letters/) for the whole picture.

### `actor-ts.mailbox`

| Key | Default | Purpose |
| --- | --- | --- |
| `mailbox.default.capacity` | `0` | Bound every actor under `/user` at this many queued user messages, without touching a spawn site.  `0` means no global bound, which is the shipped behaviour — so this is not a retune, it is the switch that introduces message loss for every application actor at once. |
| `mailbox.default.overflow` | `"drop-head"` | System-wide policy for **any** bounded mailbox: the global bound above, and every actor that sets `withMailboxCapacity()` without naming a policy of its own.  `drop-head` / `drop-new` / `reject`. |

The bound reaches strict descendants of `/user` only.  The framework's own
actors live under `/system` — shard regions, the pub-sub mediator, the
reliable-delivery producer, the DevTools hub — and shedding their traffic
would break invariants the application never asked about and cannot see.  A
spawn site wins over both keys: `ActorOptions.withMailboxCapacity()` overrides
the capacity, `withMailbox()` replaces the queue outright.

Read [Mailbox sizing](/operations/tuning/mailbox-sizing/) before turning it
on.  It is the one key in this file that can lose a message in an actor whose
code says nothing about a mailbox, and the page names the two cases —
`WebsocketServerActor` and its connections — where a blanket bound is still
reachable because user code spawns them.

### `actor-ts.dispatcher`

| Key | Default | Purpose |
| --- | --- | --- |
| `dispatcher.default` | `"immediate"` | `immediate` (default) / `microtask` / `throughput`. |
| `dispatcher.throughput` | `16` | Queued actor **turns** a `ThroughputDispatcher` drains per tick, across actors — not messages, and not per actor.  See `actor.throughput` above for the per-actor batch. |

### `actor-ts.dead-letters`

| Key | Default | Purpose |
| --- | --- | --- |
| `dead-letters.store` | `"off"` | Ordered by how much is kept: `off` = publish only, keep nothing / `metrics` = count them, keep no payload / `memory` = a bounded ring / `persistent` = also write to the journal, so the queue survives a restart. |
| `dead-letters.max-entries` | `1000` | Letters held before the oldest is evicted.  Ignored by `off` and `metrics`, which hold none. |
| `dead-letters.retention` | `1h` | Age letters out after this long.  `0` disables ageing and leaves `max-entries` as the only bound. |
| `dead-letters.max-replays` | `3` | How often one letter may be replayed before it is quarantined. |
| `dead-letters.persistence-id` | `""` | Journal stream the `persistent` store writes to.  Empty derives it from the system name, so two systems sharing a journal keep separate queues. |

Every key here is also settable in code, field by field, through
`ActorSystemOptions.withDeadLetters(…)` — which wins over this block, as
explicit options always do. See [Dead
letters](/operations/dead-letters/) for what the queue holds and how to
replay from it.

### `actor-ts.cluster`

| Key | Default | Purpose |
| --- | --- | --- |
| `cluster.gossip-interval` | `1s` | How often gossip is exchanged with a random peer. |
| `cluster.seed-retry-interval` | `3s` | How often to retry seed connections during join. |
| `cluster.weakly-up-after` | `0s` | Auto-promote a `joining` member to `weakly-up` after this long.  `0` disables it — see [Weakly-up](/cluster/weakly-up/). |
| `cluster.max-members` | `1000` | Cap on live member entries gossip may introduce.  `0` disables the cap. |
| `cluster.max-tombstones` | `10000` | Cap on `removed` tombstones gossip may introduce.  `0` disables the cap. |
| `cluster.tombstone.time-to-live` | `24h` | How long a `removed` tombstone is kept before it is pruned. |
| `cluster.tombstone.prune-interval` | `5m` | How often the prune pass runs. |
| `cluster.tombstone.min-retention` | `0s` | Floor on tombstone age before pruning is allowed.  `0` derives it from `failure-detector.down-after` (6×). |
| `cluster.failure-detector.implementation` | `simple` | Which detection algorithm this node runs — `simple` (elapsed-time thresholds) or `phi` (variance-aware φ-accrual). |
| `cluster.failure-detector.heartbeat-interval` | `500ms` | How often heartbeats are sent.  Shared by both implementations — see below. |
| `cluster.failure-detector.unreachable-after` | `2s` | Suspicion threshold for `unreachable` status.  `simple` only. |
| `cluster.failure-detector.down-after` | `5s` | Suspicion threshold for forced down.  Measured from the last heartbeat, so it must exceed `unreachable-after`.  `simple` only. |
| `cluster.failure-detector.phi.unreachable-threshold` | `8` | φ value above which the peer is flagged `unreachable`.  A continuous score, so fractions are fine. |
| `cluster.failure-detector.phi.down-threshold` | `12` | φ value above which the peer is flagged `down`.  Must exceed `phi.unreachable-threshold`. |
| `cluster.failure-detector.phi.max-sample-size` | `200` | How many recent inter-arrival times are kept per peer. |
| `cluster.failure-detector.phi.min-std-deviation` | `100ms` | Floor on the sampled standard deviation, so a very steady peer is not flagged on noise. |
| `cluster.failure-detector.phi.acceptable-heartbeat-pause` | `0s` | Grace added to the last heartbeat before φ starts rising. |
| `cluster.split-brain-resolver.active-strategy` | `off` | Which downing strategy arbitrates a partition — `off`, `keep-majority`, `keep-oldest`, `keep-referee` or `static-quorum`. |
| `cluster.split-brain-resolver.keep-majority.role` | `""` | Only members carrying this role count toward the majority.  `""` counts every member. |
| `cluster.split-brain-resolver.keep-oldest.role` | `""` | Only members with this role are eligible "oldest".  `""` considers every member. |
| `cluster.split-brain-resolver.static-quorum.role` | `""` | Only members carrying this role count toward quorum.  `""` counts every member. |
| `cluster.split-brain-resolver.static-quorum.quorum-size` | *(unset)* | Reachable members required to keep running.  Required by `static-quorum`; comment-only in `reference.conf` — see below. |
| `cluster.split-brain-resolver.keep-referee.referee-address` | *(unset)* | The referee node's address; the side containing it wins.  Required by `keep-referee`; comment-only. |
| `cluster.split-brain-resolver.keep-referee.down-all-if-below-quorum` | *(unset)* | Down everyone if the referee's own side is smaller than this.  Optional; comment-only. |

These are layered under whatever `Cluster.join(system, options)` passes, so
an explicit `withGossipIntervalMs(…)` still wins.  The failure detector
merges *per threshold*: setting only `down-after` in code keeps the other
two from the file.  The `phi` block merges the same way, per field, against
`withPhiAccrual(…)`.

`heartbeat-interval` is deliberately outside `phi` and has no copy inside
it.  The cadence belongs to the cluster's heartbeat loop rather than to
either algorithm, so switching `implementation` cannot change how often this
node talks to its peers.  Everything else under `failure-detector` belongs
to exactly one implementation and is ignored by the other.

The HOCON tree and the `ClusterOptions` fields are deliberately not
isomorphic: the three tombstone knobs are grouped under `tombstone` because
that is how you tune them, while the fields stay flat
(`withTombstoneTtlMs(…)`, …).  `remote.tcp.host` → `host` already makes the
same translation.

`min-retention = 0s` means *derive the floor from the failure detector*,
not *no floor* — the same thing leaving the field unset means, so a file
that spells the default out behaves like one that omits it.

The two `max-*` caps bound the local member map.  `remote.max-frame-bytes`
bounds one gossip frame; these bound what a sequence of well-formed frames
can accumulate, which is a different quantity — see
[Cluster security](/operations/security/cluster-security/).

`split-brain-resolver.active-strategy` names a strategy rather than
describing one, which is why the object it builds needs no HOCON shape of
its own.  The provider it constructs lands in the same slot
`withDowning(…)` fills, and the same precedence applies: an explicit
`withDowning(…)` wins, an absent one falls through to the file.  See
[Downing strategies](/cluster/downing-strategies/) for what each strategy
decides.

Three of its keys ship **comment-only** in `reference.conf`, so they are
absent until you write them.  Each is required or bounded and has no legal
default: `quorum-size = 0` and `referee-address = ""` are both refused by
the strategies' own validators, so a shipped leaf could only be a value
that stops the node from starting.  Naming `static-quorum` without
`quorum-size`, or `keep-referee` without `referee-address`, is refused at
startup with the missing key in the message.

`lease-majority` is **not** selectable here.  It arbitrates through a live
`Lease` whose `owner` is this node's own address, and no key can name one —
`actor-ts.coordination` tunes leases but does not choose a backend.  Build
it in code: `withDowning(new LeaseMajority(…))`.  Writing the name into
this key is refused rather than ignored, and the message says so.

`seeds`, `roles` and the transport have no HOCON form — the first two are
per-deployment identity that belongs at the join site, and the transport is
an object a config file cannot express.

### `actor-ts.cluster.pub-sub`

| Key | Default | Purpose |
| --- | --- | --- |
| `cluster.pub-sub.gossip-interval` | `1s` | How often a mediator pushes its topic set to a random peer. |
| `cluster.pub-sub.max-subscribers-per-topic` | `10000` | Cap on local subscribers for one topic.  A `Subscribe` past it is answered with `SubscribeRejected`. |
| `cluster.pub-sub.max-topics` | `10000` | Cap on distinct topics one mediator tracks — enforced against gossiped topic claims as well as local subscribes. |
| `cluster.pub-sub.max-remote-nodes-per-topic` | `1000` | Cap on peers that may claim subscribers for one topic. |
| `cluster.pub-sub.send-to-dead-letters-when-no-subscribers` | `on` | Route a publish that reached nobody to `system.deadLetters` instead of discarding it. |

The three caps bound what one mediator can be made to hold, and publish
fan-out walks all of them — so they are a latency bound as much as a
memory one.  The gossip half is the one worth knowing about: a peer
announcing topics it claims subscribers for used to allocate an entry per
name on every receiver, with no local `Subscribe` involved.  See
[DistributedPubSub](/cluster/pubsub/).

### `actor-ts.cluster.receptionist`

| Key | Default | Purpose |
| --- | --- | --- |
| `cluster.receptionist.gossip-interval` | `1s` | How often the receptionist gossips its local registrations. |
| `cluster.receptionist.max-subscribers-per-key` | `1000` | Cap on subscribers for one service key.  A `Subscribe` past it is answered with `ReceptionistSubscribeRejected`. |
| `cluster.receptionist.max-subscriptions-total` | `10000` | Cap on key/subscriber pairs across every key on this node — one subscriber on three keys counts as three. |

Both blocks layer under whatever the extension's `start(...)` was passed,
so an explicit `withMaxTopics(…)` still wins.  Stopped subscribers are
released by death watch and do not count against either cap.

### `actor-ts.distributed-data`

| Key | Default | Purpose |
| --- | --- | --- |
| `distributed-data.gossip-interval` | `1s` | How often a replica pushes its key set to a random peer. |
| `distributed-data.max-pending-quorum-requests` | `1000` | Cap on unsettled quorum requests — `updateAsync` and `getAsync` share one budget.  A request past it is rejected outright.  `0` disables the cap. |
| `distributed-data.max-quorum-timeout` | `30s` | Ceiling on a caller's per-call `timeoutMs`; a larger value is clamped down to this one.  `0` disables the ceiling. |
| `distributed-data.max-gossip-bytes` | `1M` | Byte budget for one gossip frame's payload.  A larger store is pushed a slice per tick, resuming where the last one stopped.  `0` removes the budget. |

`max-gossip-bytes` is always **clamped down to `remote.max-frame-bytes`**, so
lowering the wire cap lowers the gossip budget with it and no setting can put
gossip back over the edge.  It matters because the two failures are not
comparable: a frame past the wire cap is rejected on its 4-byte length prefix
and the receiving transport drops the whole peer association — heartbeats,
membership gossip and every cross-node `tell` along with it — while a budget
merely spreads the same state over more ticks.  A single key whose own encoding
exceeds the budget cannot be sliced; it is skipped with a rate-limited warning
naming the key and both sizes, counted in
`distributed_data_gossip_skipped_keys_total`, and it does **not** converge.

The block is top-level rather than under `cluster.*` (where `pub-sub` and
`receptionist` live) because the module is: `DistributedData` ships from
`src/crdt/`, and the cluster is a positional argument to `start(cluster)`
rather than one of its tunables.  `durableStore` has no key here — it is a
`DurableStateStore` instance, which a config file cannot express.

Both caps bound the unsettled set itself.  Every pending quorum request holds
a promise, a timer and a target set alive until its deadline passes, so an
uncapped replicator under load accumulates all three with nothing to stop it.
Refusing past `max-pending-quorum-requests` turns what would arrive later as a
timeout storm into immediate rejections that name the knob.  See
[Quorum reads and writes](/distributed-data/quorum-reads-writes/).

`max-quorum-timeout` bounds the other axis.  A pending request holds one of
those slots for its whole deadline, so a single caller passing an hour-long
`timeoutMs` parks the budget for an hour and locks out later callers who
never came near the cap themselves.

### `actor-ts.coordination`

| Key | Default | Purpose |
| --- | --- | --- |
| `coordination.lease.ttl` | *(unset)* | Lease TTL for the whole deployment. Ships **no leaf** — a value here would supply `ttlMs` for every lease in the process and make the "`ttlMs` is required" guard unreachable. |
| `coordination.lease.renewal-interval` | *(unset)* | How often a held lease is renewed. Ships **no leaf** — unset selects the computed `max(500ms, ttl/3)`, and `0` cannot mean "derive it" because the validator rejects it. |
| `coordination.lease.kubernetes.namespace` | *(unset)* | Namespace holding the `Lease` object. Ships **no leaf** — unset means "read `namespace-path` from the Pod's ServiceAccount mount", and `""` is rejected. |
| `coordination.lease.kubernetes.namespace-path` | `"/var/run/secrets/kubernetes.io/serviceaccount/namespace"` | File the Pod's namespace is read from. |
| `coordination.lease.kubernetes.token-path` | `"/var/run/secrets/kubernetes.io/serviceaccount/token"` | File the bearer token is read from. A **path**, never the token. |
| `coordination.lease.kubernetes.ca-path` | `"/var/run/secrets/kubernetes.io/serviceaccount/ca.crt"` | File the CA cert pinning the API server's TLS is read from. |
| `coordination.lease.kubernetes.token-reload-interval` | `1m` | How long a credential read from that mount is reused before the token file's mtime is checked again. No effect on an explicit `authToken`. |
| `coordination.lease.kubernetes.operation-timeout` | `10s` | Ceiling on one API-server request. |
| `coordination.lease.kubernetes.lease-name-max-length` | `253` | Lease object names longer than this are truncated to a stable head plus a hash of the full name. `253` is the DNS-1123 subdomain bound the API server enforces. |

Nothing in the framework constructs a `Lease` for you — every `withLease(…)`
slot takes an instance — so this block layers **under** the options you pass to
`new InMemoryLease(…)` / `new KubernetesLease(…)`, in the usual order: explicit
options win, then this block, then the built-in defaults. A lease is built
before any `ActorSystem` exists, so the two constructors load the config chain
themselves, honouring `ACTOR_TS_CONFIG` and `./application.conf`.

Three keys ship **no leaf at all** and are listed above only so the names are
discoverable. Each is a field the code requires or derives, and a shipped value
would make `hasPath` true forever — which is precisely how the thing it stands
in for becomes unreachable. Set one in your own `application.conf` and it is
read normally:

```hocon
actor-ts.coordination.lease {
  ttl = 30s
  kubernetes.namespace = "actors"
}
```

:::caution[The credential keys are paths, not values]
There is deliberately **no key for `authToken`, `caCert` or `apiServerUrl`**.
Two of those are a bearer token and a private trust anchor, and a config file is
the wrong place for either: `ACTOR_TS_CONFIG` and a dropped-in
`application.conf` both feed the same loader, and the merged configuration is
readable from the DevTools config panel. The three path keys are the supported
way to move that half of the configuration out of code — indirection to a file,
never the secret itself.

They also describe the **in-cluster** source only. Pointing one of them
somewhere other than its default while also supplying an explicit
`apiServerUrl` throws `OptionsError` at construction, because that pairing is
what once sent the cluster's own ServiceAccount token to whatever host an
operator happened to name
([issue #599](https://github.com/pathosDev/actor-ts/issues/599)).
:::

`acquire-retries` and `acquire-retry-delay` are not settable here. The two
backends ship different built-in defaults — 3 attempts / 100 ms for Kubernetes,
1 / 50 ms in memory — and one leaf could not express both without silently
unifying them. Set them per lease in code.

### `actor-ts.remote`

| Key | Default | Purpose |
| --- | --- | --- |
| `remote.tcp.host` | `"0.0.0.0"` | The interface to **bind**.  A wildcard belongs here and is the default.  Used when `ClusterOptions` leaves `host` unset. |
| `remote.tcp.advertised-host` | *(unset)* | The address peers **dial** — this node's identity.  Unset, it follows `remote.tcp.host` when that is routable, then `CLUSTER_HOST` / `POD_IP` / `HOSTNAME`, then loopback.  A wildcard is refused.  Deliberately absent from `reference.conf`, because a shipped value is what "unset" would have to be distinguishable from. |
| `remote.tcp.port` | `2552` | The port to **bind**.  Used when `ClusterOptions` leaves `port` unset. |
| `remote.tcp.advertised-port` | *(unset)* | The port peers **dial**.  Unset means the same as `remote.tcp.port` — set it only where the deployment publishes the process on a different one.  Absent from `reference.conf` for the same reason as `advertised-host`. |
| `remote.max-frame-bytes` | `16M` | Per-frame wire cap.  A frame whose length-prefix exceeds it is rejected before any payload is buffered. |
| `remote.tls.enabled` | `false` | **Not honoured** — `true` buys a startup warning, not encryption.  See below. |

`host`/`port` are the **bind** pair and `advertised-host`/`advertised-port`
the **identity** pair: the first says where the listener opens, the second
says what goes into every gossip frame for peers to dial back.  They are the
same values until a deployment remaps one, which is why naming one routable
host and one port still does both jobs and nothing configured today moves.

Because the bind address is readable from config, a deployment can move it
out of code entirely:

```hocon
actor-ts.remote.tcp {
  host = "0.0.0.0"
  port = ${?ACTOR_TS_PORT}   # env-var substitution
}
```

A published container port is the case that needs all four.  The process
listens on `2552` inside the container, `docker run -p 3000:2552` puts it on
`3000` outside, and `3000` is the number that belongs in every other node's
seed list:

```hocon
actor-ts.remote.tcp {
  host            = "0.0.0.0"    # bind every interface — the container
  port            = 2552         #   does not know its published address
  advertised-host = ${?HOST_IP}  # what peers dial …
  advertised-port = 3000         #   … and on which port
}
```

Under Kubernetes only the host half moves: pod-to-pod gossip dials the
container port directly, so `advertised-host = ${?POD_IP}` on its own is the
whole configuration.

`remote.max-frame-bytes` applies to the transport the cluster builds for
itself.  If you construct a `TcpTransport` yourself and pass it via
`withTransport(…)`, set its cap there — the framework will not re-cap a
transport it did not create.

:::caution[`remote.tls.enabled` does not encrypt anything]
The key is read, but not honoured.  Setting it to `true` does **not** enable
TLS — it makes the node log a `WARN` at startup that names the key and says
the cluster wire is plaintext, so a security setting the framework ignores
shows up in your logs and not only on this page
([issue #591](https://github.com/pathosDev/actor-ts/issues/591)).  Encrypting
the transport is tracked separately as
[issue #941](https://github.com/pathosDev/actor-ts/issues/941); until that
lands, treat the cluster network as something you have to secure by other
means.

The value is type-checked, like every other key on this page.  `true`, `on`
and `yes` all ask for TLS and all produce the warning; `false`, `no` and `off`
all decline and stay silent.  Anything else — `maybe`, or a bare `1` — throws
a `ConfigError` out of `Cluster.join` and the node does not start.  A security
toggle is the wrong place to guess at what a typo meant: the forgiving reading
is "not enabled", which would leave the node on plaintext while your config
says TLS — exactly the state this warning exists to rule out.

The warning is about the transport the cluster builds for itself.  Pass your
own via `ClusterOptions.withTransport(…)` and the node stays quiet about this
key: what that transport does with TLS is yours to decide, and the framework
cannot tell from the outside whether it is encrypted.  The key is then not
read at all, so a malformed value does not stop that node either.
:::

### `actor-ts.http`

| Key | Default | Purpose |
| --- | --- | --- |
| `http.backend` | `"fastify"` | One of `fastify` / `express` / `hono`. |
| `http.shutdown-grace-period` | `0ms` | How long `unbind()` lets in-flight requests drain before connections are forced.  `0` forces immediately. |
| `http.cors` | *(see below)* | Per-route defaults for the [`cors()`](/http/middleware/cors/) directive. |
| `http.client` | *(see below)* | Outbound [`HttpClient`](/http/overview/) defaults. |
| `http.websocket` | *(see below)* | Server-side WebSocket defaults for [`websocket()`](/http/websocket/) routes. |

`http.backend` only decides what `newServerAt(...).bind()` uses when the
builder was given no backend of its own — `useBackend(new HonoBackend())`
always wins, and is still the only way to pass a backend you configured or
wrote yourself.  An unrecognised name fails the `bind()` with a
`ConfigError` rather than silently falling back to Fastify.  Express and
Hono are optional peer dependencies, imported only if you name them.

The grace period defaults to `0` — force as soon as the server closes —
because that is what `unbind()` has always done in practice.  Raise it if
you want in-flight requests to finish.

It is usually an upper bound rather than a delay: `unbind()` returns as soon
as the server has actually closed.  Where a backend's `close()` cannot
settle — Express holding a live WebSocket, for one — the window becomes a
deadline that is always reached, so a large value there is time you always
pay.  A caller that passes its own value — `binding.unbind(1_000)` —
overrides the config.

The [`cors()`](/http/middleware/cors/) route directive reads its per-field
defaults from `actor-ts.http.cors`:

| Key | Default | Purpose |
| --- | --- | --- |
| `http.cors.origins` | *(unset)* | Exact-match origin allowlist, e.g. `["https://app.example"]`. Ships **no leaf** — see below. A `"*"` entry is refused. |
| `http.cors.methods` | *(unset)* | `Access-Control-Allow-Methods`. Ships **no leaf** — unset follows the methods registered at each pattern. |
| `http.cors.allowed-headers` | *(unset)* | `Access-Control-Allow-Headers`. Ships **no leaf** — unset echoes the sanitised request headers. |
| `http.cors.exposed-headers` | `[]` | `Access-Control-Expose-Headers`. `[]` sends none. |
| `http.cors.credentials` | `false` | `Access-Control-Allow-Credentials: true`. Forbidden with `"*"` origins. |
| `http.cors.max-age` | *(unset)* | Preflight cache lifetime in **seconds**, a bare integer. Ships **no leaf** — unset sends no `Access-Control-Max-Age` at all. |

The usual order applies per field: what `cors(options, routes)` names in code
wins, then this block, then the built-in default. So a deployment can move the
allowlist out of code entirely and keep `withCredentials()` where it is.

Two of the option arms are **code-only and have no key here**. The `"*"`
wildcard is one: `withAnyOrigin()` is documented as the explicit opt-in, and a
config file that could write `origins = ["*"]` would widen every `cors()` route
in the process to any origin with one line — so a `"*"` in this list is refused
with a `ConfigError` naming the key. The other is `withOriginPredicate(...)`,
which is a function and has no HOCON spelling at all.

Four leaves ship **no value** and are listed above only so the names are
discoverable — a published literal would be worse than no key. `methods` and
`allowed-headers` have defaults computed per pattern and per request, which a
fleet-wide list would override; `max-age` unset means the header is not sent;
and a shipped `origins` would satisfy the required-origins check for every
route in the process, turning a `cors()` that names no allowlist anywhere from
a loud error into a silent deny-all. Set any of them in your own
`application.conf` and it is read normally:

```hocon
actor-ts.http.cors {
  origins = ["https://app.example", "https://admin.example"]
  max-age = 600          # seconds — not a duration string
  exposed-headers = ["x-request-id"]
}
```

Values are validated on the merged result, so a bad one throws `OptionsError`
naming the field rather than reaching a browser as a header it will reject.

Because `cors()` is a route *directive* rather than a middleware, this block is
resolved when the route tree is **compiled** — inside `bind()`, the first
moment the tree and the `ActorSystem` are both in scope. That is also where a
`cors()` with no `origins` in code and none in config now fails, rather than at
the `cors(...)` call itself.

The system's shared `HttpClient` — and any `newClient(...)` that leaves a
field unset — reads its bounds from `actor-ts.http.client`:

| Key | Default | Purpose |
| --- | --- | --- |
| `http.client.max-response-bytes` | `8M` | Largest response body buffered before the request is aborted. |
| `http.client.default-timeout` | `30s` | Deadline for a call that names no `timeoutMs` of its own. |
| `http.client.redirect` | `"follow"` | What to do with a 3xx carrying a `Location` — `follow` / `error` / `manual`. |
| `http.client.max-redirects` | `5` | Hops a followed chain may take before the call is refused.  `0` refuses the first. |

These are a floor, not a policy: an integration passes its own bounds to
`newClient(...)`, and a single call overrides them with `maxResponseBytes` /
`timeoutMs` / `redirect` / `maxRedirects`.  What the block buys is the ability
to move the fleet-wide numbers without a code change — an endpoint that turns
out to need 60 s, or a deployment on a link where 8 MiB is the wrong ceiling,
used to force every caller off the shared client.

Every leaf is the kebab-case of its `HttpClientOptions` field with any unit
suffix dropped — the value carries the unit, so `default-timeout = 30s`.  The
camelCase spellings this block used before are **rejected at startup** with a
`ConfigError` naming both, rather than ignored: `max-response-bytes` is a
ceiling a deployment lowers deliberately, and quietly restoring the built-in
default would be the one failure mode a rename must not have.

Values are validated on read, on the merged settings, so a bad one throws
`OptionsError` naming the field rather than failing later inside a request.
`max-response-bytes` and `default-timeout` must both be positive here — unlike
a *request's* `timeoutMs`, where `0` is the documented way to opt one call out
of any deadline.  A `0` in this block would disarm every call that named no
deadline of its own, which is the state the defaults exist to prevent.

Server-side WebSocket routes (`websocket(path, actorRef)`) read their
defaults from `actor-ts.http.websocket`:

| Key | Default | Purpose |
| --- | --- | --- |
| `http.websocket.max-frame-bytes` | `1M` | Largest inbound frame accepted (bytes). |
| `http.websocket.on-oversize-frame` | `"close"` | What to do when a frame exceeds the limit — `close` / `drop`. |
| `http.websocket.on-invalid-message` | `"close"` | What to do when a message fails to decode — `close` / `drop` / `hook`. |
| `http.websocket.max-buffered-bytes` | `4M` | Outbound backpressure threshold (bytes). |
| `http.websocket.on-backpressure` | `"drop"` | What to do when the buffer is exceeded — `drop` / `close`. |
| `http.websocket.max-connections` | *(unlimited)* | Max concurrent connections per route; a new upgrade beyond it is closed with 1013. |
| `http.websocket.max-pre-attach-frames` | `256` | Inbound frames held while the connection actor starts. |
| `http.websocket.max-pre-attach-bytes` | `4M` | Bytes held while the connection actor starts; past either cap the socket is closed with 1013. |
| `http.websocket.accept-timeout` | `10s` | How long an admitted upgrade waits for its connection actor before the socket is closed and its `max-connections` slot released. |

The same leaf rule and the same startup rejection apply here: kebab-case, unit
suffix dropped, and a retired camelCase spelling is a `ConfigError` rather than
a cap that silently reverted to the default.

### `actor-ts.serialization`

| Key | Default | Purpose |
| --- | --- | --- |
| `serialization.read-constraints.max-nesting-depth` | `256` | Container levels a decoder will descend before refusing the payload.  Never raised past the encoder's own ceiling. |
| `serialization.read-constraints.max-document-bytes` | `0` | Ceiling on one document handed to `JsonSerializer` / `CborSerializer`, checked before it is parsed.  `0` = no ceiling of our own. |
| `serialization.read-constraints.max-string-length` | `20M` | Ceiling on one CBOR byte string, text string or map key, checked against the length prefix before the bytes are allocated.  `0` removes it. |

These bound what this node **reads**, never what it writes.  A peer that
completes the handshake, or any client whose body reaches a serializer, chooses
the bytes; these decide how much work this process will do on them before
giving up.  Lowering one therefore makes this node stricter than its own
encoder — it does not change the wire format.

`max-nesting-depth` is the one that matters, because until it existed there was
nothing at all on the JSON side: `JSON.parse` is iterative in every runtime
actor-ts supports and accepts a million levels without complaint, so the
recursion that overflows is the framework's own tagged-tree walker, reached
straight off the cluster wire.  It may be lowered freely and **cannot be
raised** past `256`: that number is also the encoder's hard cap, and a node that
read deeper than it writes would accept a payload it is unable to produce.
Raising it is an `OptionsError` at startup.

`max-document-bytes` ships as `0` because every path the framework owns is
already bounded — `remote.max-frame-bytes` on the cluster wire, the server's
body cap over HTTP.  Set it where a serializer is reached some other way (a
broker payload, a queue message) and nothing upstream has an opinion.

`max-string-length` binds on **CBOR only**, and its default sits deliberately
above `remote.max-frame-bytes`, so on the cluster wire the frame cap is the
effective ceiling and this one never fires.  The asymmetry is the point: a CBOR
item announces its length, so refusing it costs nothing and prevents the
allocation, while by the time the JSON walker sees a string `JSON.parse` has
already materialised it.

Two edges are deliberately outside this block.  The persistence `PayloadCodec`
decodes bytes the framework itself wrote, so a tightened ceiling there would
turn recoverable history into unreadable history.  And the HTTP body edge
builds its serializers with no `ActorSystem` handle to read config through —
that seam is issue #967.

### `actor-ts.management`

| Key | Default | Purpose |
| --- | --- | --- |
| `management.enable-leave-endpoint` | `false` | Serve `POST /cluster/leave` ([HTTP endpoints](/observability/management/http-endpoints/)). |
| `management.enable-down-endpoint` | `false` | Serve `POST /cluster/down` — operator-initiated force-down of a peer. |
| `management.enable-metrics-endpoint` | `false` | Serve `GET /metrics` in Prometheus text format. |
| `management.auth-protect-health` | `false` | Extend the `auth` middleware over `/health` and `/ready` as well as `/cluster/*`. |
| `management.liveness-path` | `"health"` | Single path segment the liveness probe answers on. |
| `management.readiness-path` | `"ready"` | Single path segment the readiness probe answers on. |
| `management.health-checks.check-timeout` | `1s` | Deadline for **one** health check; past it that check reports `status: false` and its siblings still report normally. |

These are the settings `managementRoutes(system, cluster, options)` layers
under its explicit options — the usual three layers, so a value set in code
wins, a file fills what the code left unset, and the built-in defaults are the
floor.  The port and host are not here: they belong to
`system.http(port, { host })`, not to the route tree.

**`auth` and `ipAllowlist` have no key, and cannot get one.**  Both are
`Middleware` functions, which HOCON has no way to express, so this block
decides *which* endpoints exist and *where* the probes answer — never *who*
may reach them.  A config file therefore cannot loosen the management server's
access control, which is why the two mutating endpoints are safe to expose as
config at all.

The two probe paths are **single segments**, and a value containing `/` is
refused with an `OptionsError` when the routes are built.  That rule is not
cosmetic: `path(segment, …)` strips surrounding slashes only, so
`readiness-path = "k8s/ready"` would be stored as one segment holding a slash,
match no URL, and take the endpoint out of existence with nothing logged.  A
startup error is the visible version of the same outcome.

`check-timeout` bounds a single check rather than the whole probe.  A probe
aggregates every registered check into one response, so without it the slowest
check *is* the response time and a check that never settles is a probe that
never answers — which Kubernetes reads as a failure carrying no clue as to
which dependency hung.  Past the deadline the registry answers for that check
with `{ name: 'unknown', status: false, detail: … }`; the name is `unknown`
because the name lives inside the result the check never returned.

The `object-storage` block configures **both** stores
`registerObjectStoragePlugins(ext)` returns: the snapshot store and the
durable-state store share one backend, so it is declared once rather than
twice.  With the block filled in, the call needs no options at all —
`await registerObjectStoragePlugins(ext)`.  Explicit
`ObjectStoragePluginOptions` still win, field by field, and a field left unset
in code falls through to the block instead of shadowing it.  Values are
validated once, on the merged settings, so `backend = s3` without a bucket
throws an `OptionsError` naming `backend.bucket` at registration rather than
failing at the first snapshot.

**No key material has a path in that block, and that is structural rather than
a convention.**  There is no leaf for S3 credentials, for a client-side master
key or for an integrity key, so a config file cannot express one.  Omitting S3
credentials falls through to the SDK's default chain — `AWS_ACCESS_KEY_ID` /
`AWS_SECRET_ACCESS_KEY`, an EC2 instance profile, or IAM Roles for Service
Accounts.  `encryption.mode = client-aes256-gcm` is **refused** with an
`OptionsError` rather than quietly ignored, because a deployment that asked for
client-side encryption and silently got plaintext is the worse outcome;
configure that mode in code with `ObjectStoragePluginOptions.withEncryption(…)`.
`kms-key-id` is fine — an ARN is a name, and the key itself never leaves KMS.

**`durable-state.plugin` is the third axis**, and it is new.  Durable state used
to be the one persistence contract with no registry: every `registerXxxPlugins`
helper built its store eagerly and handed it back, so a `DurableStateActor` had
to be given that instance in code.  It is now selected exactly like the journal
and the snapshot store, and `DurableStateOptions.store` is optional — an actor
that names no store uses whichever this key selects.

**SQLite is registered with `registerSqlitePlugins(ext)`**, and needs no options
at all when the three blocks above are filled in:

```ts
const ext = system.extension(PersistenceExtensionId);
registerSqlitePlugins(ext);          // path, tables, retention … from HOCON
```

Precedence is the usual three layers — explicit `RegisterSqlitePluginsOptions`
outrank the block, the block outranks the built-in defaults, per field, and a
field left unset in code falls through instead of shadowing.  A `path` given in
code is shared by all three stores as a *default*, so a leaf that names its own
keeps it; a pre-opened `database` is an override, because sharing one handle is
the more specific instruction.  There is no leaf for a `driver`, a `database` or
a `serializer` — those are live objects, and a config file cannot express one.

The plugin keys point to *another* config section that holds
that plugin's settings.  `actor-ts.persistence.journal.sqlite` above is the
worked example: it is both the id the journal is registered under and the block
that journal reads.  See each journal page in
[Persistence](/persistence/overview/) for the per-plugin keys.

and the nesting; the reader drops them rather than handing them on.  That
is also why `host` and `port` are comments rather than leaves: `url` is
mutually exclusive with them, and a shipped `host = "localhost"` would be

for its own key space is what the [one cache per
consumer](/cache/in-memory/#one-cache-per-consumer) advice needs.

| `sharding.remember-entities` | `false` | Persist the set of active entity IDs. |
| `sharding.passivation-idle` | `5m` | Auto-passivate an entity after this idle window.  `0` = disabled.  An entity that keeps state in memory and does not rebuild it in `preStart` loses that state — see [passivation](/cluster/sharding/overview/#passivation). |
| `sharding.shard-passivation-idle` | *(unset)* | Auto-passivate a shard after it has stood empty this long.  Unset it follows `passivation-idle`; `0` keeps empty shards resident.  Deliberately absent from `reference.conf`, because a shipped value is what "unset" would have to be distinguishable from. |
| `sharding.max-entities` | `0` | Per-node entity cap; the least-recently-used entity is passivated on overflow.  `0` = no cap. |
| `sharding.buffer-size` | `100000` | How many messages one region may hold **across all its shards** while their homes are unknown or handing off.  Past the cap the *newest* message is dropped to dead letters with its sender, so what is already queued keeps the order the caller sent it in.  **Mind the polarity against `max-entities` above**: here `0` means *never buffer — dead-letter immediately*, not "no cap". |
| `sharding.register-retry-interval` | `500ms` | How often a region re-sends an unacknowledged registration to the coordinator.  Everything routed for the type buffers until the coordinator answers, so this is also how long a lost `Register` stalls it. |
| `sharding.shard-region-query-timeout` | `5s` | Default wait for `sharding.shards()` and `sharding.shardRefFor()`.  An explicit `timeoutMs` argument still wins over it.  Unrelated to how long the region keeps a correlation for a cross-node `ask`, which is minutes on purpose. |
| `sharding.entity-recovery.strategy` | `all` | How remembered entities come back after a region is handed a shard.  `all` starts every one at once — today's behaviour, and the reason the default did not move.  `constant-rate` paces them, see [pacing a remembered-entity restore](#pacing-a-remembered-entity-restore) below. |
| `sharding.entity-recovery.constant-rate.frequency` | `100ms` | Gap between two paced recovery batches.  Ignored under `strategy = all`. |
| `sharding.entity-recovery.constant-rate.number-of-entities` | `5` | Entities one paced batch starts.  **A region-wide budget, not a per-shard one** — the queue is fed by every shard the node owns, so this is entity starts per window *on this node*.  Ignored under `strategy = all`. |

These apply to **every** sharded type started on the node.  They are read
once per `sharding.start(...)` and layered under whatever that call passes
explicitly, so the usual order holds per field:

```ts
// actor-ts.sharding.passivation-idle = 2 minutes

const shardingOptions = StartShardingOptions.create<CartCommand>()
  .withTypeName('cart')
  .withEntityActor(CartEntity)
  .withExtractEntityId((command) => command.entityId)
  .withNumShards(256);

cluster.sharding.start(shardingOptions);
// numShards 256 (explicit), passivationIdleMs 120_000 (config file)
```

#### A role names, it does not grant

`sharding.role` says **which** role hosts a type.  It does **not** give the
node that role.  A node's own roles are per-node identity rather than tuning,
so `ClusterOptions.roles` has no config leaf at all and stays in code:

```ts
// On every node that should host the shards:
const clusterOptions = ClusterOptions.create()
  .withHost('10.0.0.7')
  .withPort(2551)
  .withRoles(['backend']);
```

```hocon
# In the config file every node shares:
actor-ts.sharding.role = "backend"
```

Set only the first half and nothing changes; set only the second and **no
shard is ever allocated** — the coordinator finds no candidate member, every
message for the type accumulates in the region's routing buffer, and the only
sign of it is one warning naming the role and the number of regions it
excluded.  A `role` that no member carries is the same silent failure a typo
in `withRole` produces, except that from a shared config file it applies to
every sharded type on every node at once.

That asymmetry is also why the key exists: *which* role hosts a type is
uniform across a deployment, and *which* roles a node carries is not.

A configured role reaches [sharded daemon
processes](/cluster/sharding/sharded-daemon-process/) too, because they are
started through the same `sharding.start(...)`.  That is intended — a
deployment that places its entities on `backend` nodes usually means its
daemons as well — and `ShardedDaemonProcessOptions.withRole(...)` still wins
over it per process.

`proxy` deliberately has no leaf.  It is per-node topology, not a
deployment-wide fact: a second `start` disagreeing about it throws, and a
`proxy = on` everyone shared would leave nothing hosting anything.

#### Pacing a remembered-entity restore

Under [`remember-entities`](/cluster/sharding/remember-entities/) a region that
is handed a shard is shipped that shard's whole registry and, by default,
spawns every entity in it at once — for every shard it is given.  A node
restart or a rebalance therefore opens one journal replay per remembered
entity, all in the same tick.  `constant-rate` spreads those starts:

```hocon
actor-ts.sharding.entity-recovery {
  strategy = constant-rate
  constant-rate.frequency = 100ms
  constant-rate.number-of-entities = 5
}
```

Two things about that budget are worth stating plainly, because both are easy
to read the other way:

- **It is region-wide.**  Five entities per 100 ms is five *on this node*, no
  matter how many shards the node holds.  Read per shard the same numbers
  would mean 5 × the shard count, which on a 64-shard cluster is not a bound
  at all — the same conflation `max-entities` is kept region-wide to avoid.
- **It paces starts, not replays.**  A replay is asynchronous, so one that
  outlasts the window still overlaps the next batch.  What this key smooths is
  the arrival rate; how many recoveries may be *in flight* is a persistence
  concern and is not settable here.

Nothing is shed: the backlog drains until every remembered entity is back, and
a message routed to an entity still in the queue creates it immediately — only
the recovery burst waits.  The default stays `all` because pacing changes when
an entity comes back, and how fast a journal can take the replays is a fact
about that journal rather than about sharding.

#### Bounding rebalance churn

The default [allocation
strategy](/cluster/sharding/allocation-strategy/) places a shard by
`shardId % candidates.length`, so a node joining changes the answer for most
shards at once.  At the shipped `number-of-shards = 64` that is 32 shards on a
1 → 2 node join, **42 on a 2 → 3 join** and 46 on a 3 → 4 — each one a shard
stopped, every entity under it stopped, then re-allocated, re-created and, if
it persists, replayed.  Nothing announces it either: the coordinator does not
react to a `MemberUp`, so the whole burst arrives on the next periodic tick.

The two limits bound how many of those may be **in flight at once**:

```hocon
actor-ts.sharding {
  rebalance-absolute-limit = 0     # 0 = no absolute ceiling
  rebalance-relative-limit = 0.1   # fraction of number-of-shards
}
```

Three things about that bound are worth stating plainly:

- **It counts shards in flight, not shards per tick.**  A tick fires every
  `rebalance-interval` while a hand-off may stand for a whole
  `hand-off-timeout`, so a per-tick six would admit roughly thirty at once.
  What the coordinator budgets each tick is the ceiling *minus what is already
  moving*.
- **Only voluntary moves are capped.**  A region that dies leaves its shards
  with no owner at all; those are re-homed immediately, ceiling or not.
  Throttling that path would leave shards unreachable rather than merely slow
  to settle.
- **Nothing is dropped, and no node is drained first.**  What the budget leaves
  behind is proposed again on the next tick until the map is balanced, and the
  shards that go first are picked round-robin across their current owners — a
  ceiling that empties one node before touching the next is worse than no
  ceiling.

Set `rebalance-relative-limit = 0` (with the absolute limit already `0`) to
restore the unbounded behaviour.

A per-type setting therefore belongs in the builder; the config file is for
the node-wide baseline you want to move between staging and production
without a rebuild.  The polymorphic options — the entity actor, the extractors,
the allocation strategy, a lease, the stores — have no HOCON form and stay
in code.

### `actor-ts.coordinated-shutdown`

| Key | Default | Purpose |
| --- | --- | --- |
| `coordinated-shutdown.default-phase-timeout` | `5s` | Default per-phase timeout.  A phase that overruns it is abandoned so the next one still runs. |
| `coordinated-shutdown.terminate-actor-system` | `true` | Whether the built-in terminator task calls `system.terminate()` in the final phase. |
| `coordinated-shutdown.exit-process` | `false` | Whether to call `process.exit(exit-code)` once the pipeline completes. |
| `coordinated-shutdown.exit-code` | `0` | Status that exit carries.  `0`–`255`; anything else is a `ConfigError` at startup. |
| `coordinated-shutdown.auto-register-tasks` | `true` | Whether framework components register their own teardown — the HTTP unbind, broker closes, the cluster leave, the DevTools detach. |
| `coordinated-shutdown.run-by-process-signals` | `true` | Whether `runUntilTerminated()` and the cluster bootstrap arm SIGTERM/SIGINT when the caller named no signals. |
| `coordinated-shutdown.phases.<name>.timeout` | — | Per-phase budget, overriding `default-phase-timeout` for that phase alone. |
| `coordinated-shutdown.phases.<name>.recover` | — | `false` makes a failing task in that phase halt the pipeline instead of being logged and stepped over. |
| `coordinated-shutdown.phases.<name>.depends-on` | — | Phases that must run first.  Added to a canonical phase's existing edge; required when the name declares a new phase. |

Setting `terminate-actor-system = false` removes only the built-in
terminator — user tasks registered in `ActorSystemTerminate` still run.  Use
it when a host process owns the system's lifetime and a signal handler must
not kill it.

The `phases` block is the config front-end to the phase DAG, and it ships no
values of its own — its children are named after *your* phases, so there is
nothing to publish a default for:

```hocon
actor-ts.coordinated-shutdown.phases {
  service-requests-done { timeout = 30s }        # retime one canonical phase
  flush-metrics {                                # …and add one of your own
    timeout    = 3s
    recover    = false
    depends-on = ["before-actor-system-terminate"]
  }
  actor-system-terminate { depends-on = ["flush-metrics"] }
}
```

A child naming one of the twelve canonical phases **merges** into it: fields
it leaves out keep what the phase was seeded with.  Any other name **declares**
a phase, and there `depends-on` is required — a phase with no edges sorts into
the first ready batch and would run before `before-service-unbind`, which is
never what adding a phase meant.  `depends-on` on a canonical phase is *added*
to the edge it already has rather than replacing it, so a config file cannot
re-parent `cluster-leave` ahead of `service-unbind`; the topological sort
catches cycles, not a pipeline quietly running in the wrong order.  Declaration
order in the file does not matter — two phases may name each other and are
registered dependency-first.  An unresolvable name, a cycle, or an unknown
setting under a phase is a `ConfigError` at startup, not at shutdown.

`run-by-process-signals` switches the *default*, not the capability.  Naming
signals explicitly — `runUntilTerminated(['SIGTERM'])`, or `shutdownOnSignals`
in the bootstrap options — still installs them, because explicit options
outrank config.  Turning it off is for a host process that owns SIGTERM
itself: `runUntilTerminated()` still waits and still holds the event loop open,
it simply arms nothing.

`exit-process` is for the opposite case: a lingering handle (an open socket,
a pooled connection a driver never released) keeps the process alive after
the pipeline is done, and from the outside that is indistinguishable from a
hang.  Off by default, because forcing an exit hides exactly the leaks you
would rather find.  `exit-code` is the status it hands over — `0`, because a
pipeline that ran to the end is the success case; set it where a supervisor
should tell a planned drain apart from a crash.

is deliberately no `enabled` key: reading one would mean importing the
DevTools subsystem, embedded UI bundle and all, into every system that never
opens it.

**A configured host faces the same rule a code-set one does.**  Options are
validated once, on the merged settings, so `devtools.host = "0.0.0.0"` throws
an `OptionsError` naming `host` exactly as `.withHost('0.0.0.0')` in code
does.  `auth` and `ipAllowlist` are middleware and have no HOCON form, which
is what makes `allow-remote` the only answer a file can give to that rule.

Seven fields have no key.  `auth`, `ipAllowlist`, `backend`, `cluster` and

`uiDevelopmentRoot` is a panel-development escape hatch whose own
documentation says never to set it in an application.  The last two are a
decision rather than an impossibility: `allow-ungated-mount` states a fact
about the code that binds `mount()`'s routes rather than about a deployment,
and `allow-message-sending` is the one DevTools capability that *writes* into
the running system from a browser.  Both stay beside the call they qualify.

A `panels` object passed in code overrides the configured switches **one
switch at a time**, not wholesale: `.withPanels({ timeTravel: false })` on top
of a file that says `panels { send = false }` leaves `send` off.  That is the
usual precedence applied one level deeper — otherwise naming one panel in code
would switch every panel an operator disabled back on.

The four duration keys drop the `Ms` suffix their options-object fields carry
(`ready-timeout` sets `readyTimeoutMs`) and take a HOCON duration literal, the
same way `logger.close-timeout` feeds `closeTimeoutMs`.  `restart-random-factor`
is a plain fraction, not a duration.

and `onWorkerPermanentlyDown` are live objects a config file cannot express,
and `bootstrap` names a module the runtime will *execute* — `ACTOR_TS_CONFIG`
and a dropped-in `application.conf` are a wider surface than the call site, so
it stays a code-only field.

Validation runs on the merged settings, so every one of these is rejected with
an `OptionsError` when it comes from a file exactly as it would from code: an
empty `system-name` or `hostname`, a `base-port` outside `[1, 65535]`, a
`restart-random-factor` outside `[0, 1]`, a negative backoff or window, a
`max-restarts` below `-1`, and a `restart-max-backoff` under
`restart-min-backoff`.

These fill in `WorkerCluster.spawn(options)` for fields it leaves unset.
`spawn` is a static with no `ActorSystem` in scope, so it loads the config
chain itself — the same one `ActorSystem.create` uses, honouring
`ACTOR_TS_CONFIG` and `./application.conf`.  An unknown `restart-policy` is
rejected with an `OptionsError` instead of silently meaning "never".

## HOCON-specific syntax

### Durations

```hocon
gossip-interval = 1s        # 1000 ms
unreachable-after = 2.5s    # 2500 ms
down-after = 5000ms         # explicit ms
gc-cadence = 10m            # minutes
ttl = 24h                   # hours
```

Recognized units: `ns`, `us`, `ms`, `s`, `m`, `h`, `d`.

### Sizes

```hocon
max-frame-bytes = 16M       # 16 777 216 bytes
buffer = 64K
heap = 2G
```

Recognized units: `B`, `K`, `M`, `G`, `T` — binary (1024) by
default.

### Environment substitution

```hocon
port = ${?ACTOR_TS_PORT}              # use env if set, else fall through
log-level = ${?LOG_LEVEL}             # same
api-key = ${API_KEY}                  # required — error if env is unset
fallback-port = ${?ENV_PORT}
fallback-port = ${fallback-port:-2552}  # default-if-empty syntax
```

Use `${?ENV}` for optional, `${ENV}` for required.

### Includes are not supported

```hocon
include "shared-cluster.conf"   # error: `include` is not supported
```

A config source cannot name another file or URL to pull in.  That is a
decision, not a gap: resolving an include would let whoever writes the
config choose which paths the process reads, relative to a root the
parser has no way to know.  Merging in code leaves that choice with the
caller.

```ts
import { Config } from 'actor-ts';

const shared = Config.parseFile('shared-cluster.conf');
const application = Config.parseFile('application.conf');
const config = shared.merge(application);
```

`merge` layers its argument on top, so the local file wins — the same
order the `include` above was reaching for.  Pasting the shared content
into one file works too.

The parser says all of this when it meets an `include`, quoting the line
and the target, so a config ported from Akka or Pekko fails with an
answer rather than a puzzle.

### Reserved keys

Three keys are refused anywhere in a config source — as a key, as any segment
of a path expression, and inside a substitution:

```hocon
__proto__.anything = 1   # error: refused
constructor.x      = 1   # error: refused
prototype          = 1   # error: refused
value              = ${__proto__}   # error: refused
```

A key path is expanded onto a plain object, and assigning `__proto__` writes
through to the object prototype rather than creating a normal key — so allowing
it would let a config file change the behaviour of every object in the process.
The parser rejects these with the usual line and column instead.

The check is exact-match, so keys that merely resemble them are fine:
`_proto_`, `constructorName` and `prototypes` all work normally.

#### Reads see own keys only

Refusing three names guards the write side.  The read side is guarded the
other way round — positively — because `Object.prototype` has a dozen more
members and a list could never keep up with them:

```hocon
name = ${toString}    # error: unresolved substitution — not a native function
port = ${?valueOf}    # optional: falls through to the environment, then away
```

Every lookup — a substitution, `hasPath`, and each typed getter — reads
**own** keys only, in the config tree and in the environment alike.  A name
that happens to match an inherited member therefore misses instead of
resolving to whatever lives on the prototype, and `hasPath('toString')` is
`false` on any config that does not declare a `toString` key itself.
Declaring one is still allowed and still works: an own key shadows the
inherited member, so `toString = "mine"` reads back as `"mine"`.

## Reading config in code

```ts
const actorSystemOptions = ActorSystemOptions.create().withConfig({
    'actor-ts.cluster.gossip-interval': '500ms',
  });
const system = ActorSystem.create(
  'my-app',
  actorSystemOptions,
);

// Inside an actor / extension:
const config = system.config;
const interval = config.getDuration('actor-ts.cluster.gossip-interval');
//      → 500 (in ms)
```

The `Config` interface has typed getters: `getString`, `getNumber`,
`getBoolean`, `getDuration`, `getBytes`, `getStringList`, etc.
Missing keys throw unless you check first with `hasPath`.

## Loading order

```
1. REFERENCE_CONF                           ← bundled defaults
2. application.conf (CWD)                   ← project root, auto-loaded
3. file path from `configFile` setting      ← explicit override
4. ENV var ACTOR_TS_CONFIG                  ← path or inline HOCON
5. constructor `config: { ... }`            ← code-level override
6. constructor field overrides              ← explicit fields beat config
   (logLevel, dispatcher, scheduler, …)
```

Each layer overlays on top of the previous.  Layer 6 (constructor
fields) always wins for the fields it covers; everything else
flows through the HOCON merge.

### Where the built-in default lives

Layer 1 is `reference.conf`, but not every setting has a key there — and
even those that do need a value in code for the case where nothing is
configured.  That value has a fixed home, so you can always find what a
setting falls back to:

- **Options defaults** sit next to the field they back, in the matching
  `XOptions.ts`.  `DEFAULT_MAX_ENTRIES` is in `InMemoryCacheOptions.ts`,
  `DEFAULT_NUM_SHARDS` in `ShardingOptions.ts`.
- **Everything else** — caps, bounds and timeouts with no option behind
  them — is in a `Constants.ts`: `src/<subsystem>/Constants.ts` for one
  subsystem, `src/util/Constants.ts` for values several share.

So a `reference.conf` leaf and its code-level fallback are always exactly
two files, and the second one is named after the first.

</Aside>

## Validation

Option values are **validated once, at consume time, on the merged
settings** — after the three layers above are resolved.  Because it runs
on the merged result, the same rules apply no matter how a value
arrived: the fluent builder, a plain settings object, or a HOCON key.
Cross-field rules (e.g. "`downThreshold` must exceed
`unreachableThreshold`") see the final values.

An invalid value throws an **`OptionsError`** (exported from the package
root), naming the offending field and what it expected:

```text
MqttOptions: protocolVersion must be one of 4, 5 (got 6)
```

- For **broker actors** (MQTT, Kafka, WebSocket client, …) the error is
  raised when the actor starts (`preStart`), after the required-field
  check — so a *missing* required setting still surfaces as
  `BrokerOptionsError`, and only *present-but-invalid* values become
  `OptionsError`.
- For **non-broker consumers** (caches, leases, sharding, …) the error is
  raised from the constructor.

`OptionsError` is distinct from `ConfigError` (malformed HOCON — wrong
type, missing path) and `BrokerOptionsError` (a required broker setting
absent from every layer).  Unset optional fields never trigger it; they
fall through to their defaults.

<Aside type="note" title="A rejected URL is reported with its credentials masked">
  ```text
  MqttOptions: brokerUrl must use protocol mqtt, mqtts (got "amqp://***@rabbit:5672/vhost")
  ```
  Every rule that rejects a URL — the `url` check helper, and the
  connection-URL rules of the Mongo, libSQL, D1 and DynamoDB stores —
  replaces the userinfo with `***` in **both** the message and
  `OptionsError.value`.  A rejected broker URL is logged at ERROR when it
  fails an actor's `preStart`, and a password that has reached a log
  aggregator has to be rotated, not deleted.

  Nothing else about the value is touched — no normalisation, no trailing
  slash, no lowercased host — so you still recognise what you typed, and a
  value that is not a URL at all (`":memory:"`, `"file:local.db"`) comes
  back verbatim.  The same masking is available to your own code as
  [`redactUrlCredentials`](/reference/utility-helpers/).
</Aside>

```ts
import { CircuitBreaker, CircuitBreakerOptions, OptionsError } from 'actor-ts';

// Non-broker consumers validate in their constructor, so the error is
// thrown synchronously and a plain try/catch works:
try {
  const options = CircuitBreakerOptions.create()
    .withMaxFailures(0);             // invalid — must be a positive integer
  new CircuitBreaker(options);       // validates in the constructor
} catch (e) {
  if (e instanceof OptionsError) {
    console.error(`bad option ${e.field}: ${e.message}`);
  }
}
// For a broker actor the OptionsError is thrown later in preStart and
// re-wrapped as ActorInitializationError, so it surfaces via supervision
// (not the spawning call's try/catch).
```
